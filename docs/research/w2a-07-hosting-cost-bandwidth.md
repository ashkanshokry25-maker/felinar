## Summary

1. **The web-seed host and the site host are different jobs, and most of the "custom domain / wildcard TLS" worry belongs to the second one.** In shell and hub mode the web seed URL (`ws=`) is never shown to the visitor: it can be a provider's own hostname (`<bucket>.s3.<region>.amazonaws.com`, `f001.backblazeb2.com/file/<bucket>`, `<space>.<region>.cdn.digitaloceanspaces.com`, `*.b-cdn.net`, `link.storjshare.io`), so it needs **no custom domain and no wildcard certificate**; it needs CORS, Range, identity bytes and a price that survives a traffic spike. In drop-in mode the web seed is the site's own origin read **same-origin by the service worker** (ARCHITECTURE section 3.4.7), so neither CORS nor Range nor compression applies at all; what matters there is the host's egress price (F4, F21). Custom domains and wildcards matter only for the shell host and for hub mode (table in F19). `[DC]`

2. **Only a quarter of the hosts I probed (6 of 24) work as a cross-origin web seed with the stock WebTorrent request, and the reason is the request, not Range.** WebTorrent 3.0.21 sends `Cache-Control: no-store` and `user-agent` with every piece request; neither is CORS-safelisted, so every web-seed fetch is preflighted and the preflight must allow those headers. In a real browser (Chromium 156; 28 test URLs on 24 distinct hosts) **6 hosts** passed with the stock request (Storj linksharing, 3 of 4 Blossom servers, unpkg, one S3 bucket with explicit CORS); **13 hosts** pass with the exact slice if the two extra headers are dropped (GitHub Pages, Vercel static, DigitalOcean Spaces with a GET rule, the Pinata and Filebase IPFS gateways, 4everland and GitHub raw join the list). Removing two headers from one fetch call more than doubles the set of usable hosts and deletes about F (the number of files) preflights per cold visit. `[DC]` (F2, F3, R1)

3. **SUPERSEDES w1-10 F12 and Summary item 4: the "Range is applied to the compressed bytes" hazard does not exist for browser web-seed requests.** The Fetch Standard says that when a request carries `Range` the user agent appends `Accept-Encoding: identity`; I measured exactly that in Chromium 156 and WebKit 27.2 (server-side log), and GitHub Pages then returned identity bytes with a correct `Content-Range` (`bytes 1000-3411/12226`, whereas the curl probe with `Accept-Encoding: gzip, br` had returned `0-99/3412`, the gzip size). The remaining Range failures are server bugs: **jsDelivr returns slices of the brotli representation even for `Accept-Encoding: identity` and labels them identity (wrong bytes with HTTP 206)**, **Cloudflare Pages documents that it "returns 200 responses for HTTP range requests"** (page updated 2026-10-10), and **the Primal Blossom server ignores Range and returns 200 with the whole 184,292-byte blob**. WebTorrent accepts any 2xx and hashes whatever bytes arrive, so all three fail as piece-hash mismatches, not as errors. `[DC]` (F1)

4. **Request count, not egress, decides the bill on per-request-priced hosts, and the layout decides the request count.** One web-seed GET is issued per (piece x file) overlap, so a cold visit costs P + F - 1 range GETs (plus F preflights with stock headers). For an 8 MB, 200-file site (P = 31) that is **431 requests per cold visit and 38.8 M requests per month at 10,000 visits/day**, against **33 requests (3.0 M per month)** for the same bytes as one archive file. CloudFront pay-as-you-go goes from $28.79 to $0.00; Netlify credits from $148 to $100; Pinata from $798 to $81; R2, B2, Bunny, DigitalOcean and Storj do not care (flat or no per-request price). A single-file (or few-file) torrent layout is the cheapest compatibility and cost lever in this report. (F5, F20, R6)

5. **Zero-egress or flat-egress stores win by one to two orders of magnitude once peers do not help.** Monthly web-seed cost, 8 MB / 200 files / 10,000 visits/day / 720 GB / 38.8 M requests, stock headers, no P2P savings (Model): Cloudflare R2 behind a custom domain and cache $0.00 (worst case, every request reaching R2: $10.36); Backblaze B2 behind Cloudflare $0.00; DigitalOcean Spaces $5.00; Storj $5.04; Bunny Standard $7.20 (Volume $3.60); B2 direct $7.20; CloudFront pay-as-you-go $28.79; S3 direct $71.32; Vercel Pro with a $100 Flat Rate CDN tier $120; Netlify Pro with top-up credits $147.72; Pinata $797.80. The same site at 25 MB and 100,000 visits/day (22.5 TB per month): R2 $5.99 to $92.30, Bunny Volume $112.50, DigitalOcean $204, CloudFront $2,026, S3 $2,062, Netlify $3,355, Pinata $7,528. (F20)

6. **How many bytes will peers carry on a small site? Almost none, and the v0.2 design choices are the reason (Model).** With the web seed started at once (race), peers only after the consent click (about 4 s) plus tracker and ICE setup (about 2 s), a visitor on a 20 Mbit/s link has a 5 MB site complete in 2.4 s, before any peer byte can arrive. Simulated share of first-visit payload bytes from peers, race policy, 60 s mean dwell: **5 MB site: 0.0 % at 100, 1,000, 10,000 and 30,000 visits/day and 0.1 % at 100,000; 25 MB: 0.0 / 1.0 / 7.1 / 18.3 % at 100 / 1,000 / 10,000 / 100,000 visits/day; 100 MB: 0.0 / 1.8 / 13.8 / 41.4 %.** Slow links change the picture (a 5 MB site on a 2 Mbit/s link: 26 % at 10,000 visits/day), and so does a peer-first policy (a 5 MB site at 10,000 visits/day: 27.8 % when the web seed waits 8 s, at the price of a 9.3 s instead of 2.4 s first-visit download). The consent gate puts a hard ceiling on the share of visitors who can use peers (60 % under my assumption). **Rule of thumb for the docs: for payloads under about 20 MB, or sites under about 10,000 visits/day, the web seed is the CDN; P2P buys resilience, large payloads, background copies and chain gossip, not a smaller hosting bill.** Public evidence of high offload comes from regimes far from a small site: Maygh's simulation of Etsy's image traffic (205.6 M requests in a week from 5.7 M IPs) cut the 95th-percentile bandwidth by 75 % (2013, OLD), and Microsoft IT reports "more than 76 percent" of Windows update content from peers inside one AD domain (undated). (F22-F25)

7. **Drop-in mode can multiply origin egress instead of reducing it (design-critical, arithmetic from ARCHITECTURE v0.2).** The first page view is served by the host; at idle on an unmetered network the engine then completes a copy of the whole torrent through `/_mw/ws/`. Host bytes per new device go from B_visit (what the visitor would have loaded) to about B_visit + (S_site - B_visit) x (1 - peer share) when the copy is completed from the host. For a 20 MB site where a typical visit loads 1.5 MB that is **13.3x** with no peer help and still 7.2x with 50 % peer help. Unless the host is zero-egress, copy completion needs a byte budget, and background completion should be peer-first with a delayed host fallback (Model: that policy moves a 5 MB site at 10,000 visits/day from 0 % to 27.8 % of payload bytes from peers, 27.2 % of host bytes saved, without touching first paint). `[DC]` (F21, R4, R5)

8. **Provider-specific facts that change recommendations** (each is a finding below): Cloudflare **Pages is not usable as a cross-origin web seed** (Range answered with 200) though it is free and unlimited as a shell host; **R2 needs the zone on Cloudflare (partial/CNAME setup is Business and Enterprise only), `r2.dev` is rate-limited and "for development"**, and Cloudflare's terms require a Developer Platform product (R2, Pages, Workers) to serve "video and other large files" through the CDN; **Backblaze B2 free egress is "3x average monthly storage"**, which is almost nothing for a small site, so B2 only makes sense behind a partner CDN (Cloudflare, Fastly, bunny.net, CacheFly and others get unlimited free egress), and B2's friendly URLs are **HTTP/1.1 only**; **S3 REST endpoints are HTTP/1.1 only**, deny CORS until configured, and need CloudFront for a custom domain; **Netlify's Free plan is 300 credits (15 GB of bandwidth) with a hard limit that pauses every project on the account**; **Vercel Hobby is non-commercial with 100 GB and 1 M requests**; **GitHub Pages** answers OPTIONS with 405 (stock headers fail) and has a 100 GB soft limit; **Storacha is gone** (every storacha.network, docs and gateway URL now redirects to Fil One, whose FAQ says "Public buckets are not currently supported"); **ipfs.io and dweb.link answer 429 or a challenge** and `cloudflare-ipfs.com` no longer resolves; **Storj linksharing passes the stock preflight out of the box** (Allow-Headers `*`) but charges $7/TB egress; **Blossom** is a good fit for single-file archives (BUD-01 mandates `Access-Control-Allow-Origin: *` and preflight `Allow-Headers: Authorization, *`, which passes the stock request) but Range is only a SHOULD and one major server ignores it. (F6-F17, F26)

9. **HTTP/2 and HTTP/3 (negotiated or advertised on 2026-10-17):** HTTP/2 everywhere except B2's `f001.backblazeb2.com` friendly URLs, S3 REST endpoints and one Blossom operator's blob host (HTTP/1.1 only). `alt-svc: h3` seen on Cloudflare-fronted hosts (Cloudflare docs: HTTP/3 on all plans), CloudFront (documented setting `http2and3`), jsDelivr, unpkg, hzrd149's Blossom server and ipfs.io; **not seen** on GitHub Pages, Netlify, Vercel, Bunny's own site, B2, Storj, Pinata or Filebase (absence of the header in one HEAD request is not proof of no support, but nothing in their docs says otherwise). For a web seed with 4 parallel requests per host HTTP/1.1 is not a handicap; it matters for the shell host. (F19)

10. **Wildcard and custom-domain TLS, host by host** (F19): CloudFront (ACM wildcard in us-east-1, w1-10), Vercel (wildcard domains with Vercel DNS or NS delegation of `_acme-challenge`), Cloudflare Workers routes (`*.hub.example/*`, Universal SSL covers first-level subdomains on a full setup), Bunny (automatic wildcard Let's Encrypt certificate **only when the DNS zone is on Bunny DNS**, otherwise upload your own), DigitalOcean (Let's Encrypt wildcard only if DNS is on DigitalOcean; one custom subdomain per CDN endpoint), Netlify (automatic wildcard certificate with Netlify DNS for subdomains of a Netlify-DNS domain; a wildcard domain alias for one site is not documented, so unverified) work; **Cloudflare Pages, GitHub Pages and Storj linksharing (one CNAME plus TXT records per hostname, HTTPS only with a paid Pro account) do not**.

11. **Biggest levers (details in Recommendations):** drop `Cache-Control`/`user-agent` from the web-seed fetch (R1, P0, S) and ship a seed doctor with the measured failure vectors (R2, P0, S); publish the tiered host list with prices (R3, P0, S); document the drop-in egress multiplier now (R4, P0, S), then budget copy completion and make background completion peer-first (R5, P1, M); offer a single-file archive layout for shell-mode web seeds (R6, P1, M); default the docs' hosting recipe to R2, or B2 behind Cloudflare or Bunny, after a real-bucket check (R7, P1, S) with a request-aware cost estimator in `publish.mjs` (R8, P1, S); verify Firefox and Safari on real devices (R10, P1, S); state the honest P2P expectation in README and DEPLOY (R13, P2, S).

## Findings

Each finding has: the claim, a confidence, a design-critical flag where a wrong answer would change the architecture or a compatibility promise, the evidence, the sources and their dates. Findings F1-F5 are about what any web-seed host must do; F6-F17 go provider by provider (price, limits, HTTPS and wildcard, CORS, Range, cache headers, HTTP versions); F18-F19 are the two comparison matrices; F20-F21 are cost; F22-F25 are the P2P savings; F26 is policy risk.

### A. What a web-seed host must do for WebTorrent 3.0.21 in a browser

**F1. SUPERSEDES w1-10 F12 / Summary 4: a browser `fetch()` with a `Range` header carries `Accept-Encoding: identity`, so "Range applied to the compressed bytes" does not happen for web-seed requests; what remains are servers that mishandle `identity` or ignore Range.** Confidence: **High**. Design-critical: **yes** (it removes a compatibility rule that would have excluded GitHub Pages and every Fastly or Cloudflare compressed path, and it shows which hosts really are unsafe).
- Spec. Fetch Standard, main branch, "HTTP-network-or-cache fetch": "If httpRequest's header list contains `Range`, then append (`Accept-Encoding`, `identity`) to httpRequest's header list", with the note "This avoids a failure when handling content codings with a part of an encoded response. Additionally, many servers mistakenly ignore `Range` headers if a non-identity encoding is accepted." [S59]
- Measured (loopback server that logs the headers it receives; script `exp-accept-encoding-local.mjs`): **Chromium 156.0.8078.4**: no Range sends `Accept-Encoding: gzip, deflate, br, zstd`; `Range: bytes=0-3` sends `identity`, also for WebTorrent's exact header set (cache no-store, Cache-Control, user-agent, range). **WebKit 27.2**: no Range sends `gzip, deflate`; Range sends `identity`. Firefox: not tested (Playwright's Firefox Nightly will not start here). [S66]
- Measured against a real host with CDP wire headers (`exp-accept-encoding-on-range.mjs`): `pages.github.com/css/pages.css` (12,226 B identity, 3,412 B gzip). Without Range: `AE: gzip, deflate, br, zstd`, `200`, `content-encoding: gzip`, 3,412 B. With `Range: bytes=1000-4999`: `AE: identity`, `206`, `content-range: bytes 1000-3411/12226`, no Content-Encoding, 2,412 B (the tail of the file). The w1-10 probe used curl with `Accept-Encoding: gzip, br` and got `206 gzip bytes 0-99/3412`; that is what a non-browser client sees, not a browser. Same pattern on raw.githubusercontent.com (`1000-2687/8613`) and unpkg (`1000-4999/222929`). [S66]
- What is still broken, in the browser (all rows in F3): **jsDelivr** answers `Accept-Encoding: identity` + `Range: bytes=1000-4999` with `206 content-range: bytes 1000-4999/66074` and no `Content-Encoding`. 66,074 is the brotli size of `webtorrent.min.js` (identity 222,929). So the slice is cut from the brotli stream and labelled identity; Chromium receives 4,000 bytes that are not bytes 1000-4999 of the file (verified: neither the identity nor the gzip/br curl slice equals the identity slice). **Cloudflare Pages** documents 200 for every Range request (F8). **Primal's Blossom server** returns 200 and the whole blob (F17). **cdnjs** (Cloudflare, dynamic) returned 200 for Range even with `identity`.
- Consequence for the seed doctor: the useful assertions are "status 206", "`Content-Range` total equals the torrent's file length", "no `Content-Encoding`", and "SHA-256 of two spot-checked pieces matches the torrent". "Host compresses" is no longer a disqualifier. A small file requested in full survives most of these bugs, which hides them in small tests.
- Sources: [S59] fetch.bs; [S66] measurements 2026-10-17; [S60] `webconn.js` (takes any 2xx body as piece bytes). Source dates: spec read 2026-10-17 (main branch); measurements 2026-10-17.

**F2. WebTorrent 3.0.21's own request headers, not Range, are what trigger a CORS preflight, and most default host configurations fail that preflight.** Confidence: **High**. Design-critical: **yes**. (Confirms w1-10 F8/F9 with new live data; extends it to 24 hosts.)
- Code (read 2026-10-17, `node_modules/webtorrent/lib/webconn.js`): `fetch(url, { cache: 'no-store', method: 'GET', headers: { 'Cache-Control': 'no-store', 'user-agent': 'WebTorrent/3.0.21 (https://webtorrent.io)', range: 'bytes=a-b' }, signal: AbortSignal.timeout(60000) })`; `if (!res.ok) throw`; `new Uint8Array(await res.arrayBuffer())`. No check of 206, `Content-Range`, `Content-Length` or `Content-Encoding`. [S60]
- Spec/lab: `Range: bytes=N-M` is CORS-safelisted; `Cache-Control` and `user-agent` are not, so the preflight carries `Access-Control-Request-Headers: cache-control[,user-agent]` (project lab `w1-11-opaque-frame-lab`, Chromium 156: `cache-control`; WebKit 27.2: `cache-control,user-agent`). [S60][S59]
- Live result (F3): stock request passes on 6 of 24 hosts; with only `Range` it passes on 13. The difference is exactly the hosts whose preflight does not allow `cache-control`: GitHub Pages (OPTIONS answered **405** by Varnish for every header combination), Vercel static (OPTIONS 204 with `Allow-Methods` but no `Allow-Headers`), DigitalOcean Spaces (OPTIONS 403 XML error, the bucket's rule has no allowed headers), Pinata and Filebase IPFS gateways (`Allow-Headers: Content-Type, Range, User-Agent, X-Requested-With`, no `Cache-Control`), 4everland, raw.githubusercontent.com (OPTIONS 403).
- What passes stock: `Access-Control-Allow-Headers: *` (Storj linksharing, unpkg), `Authorization, *` (Blossom, as BUD-01 requires), an S3 bucket whose owner configured CORS (NOAA's public bucket echoes the requested headers). For a request without credentials `*` matches every header name except `Authorization` (Fetch Standard), and the matrix confirms it.
- Cost of the preflight: one extra OPTIONS per distinct file URL per cold visit (the preflight cache is keyed by URL, default 5 s, and browsers cap `Access-Control-Max-Age`; R2's page says "Browsers may limit this to 2 hours or less, even if the maximum value (86400) is specified" [S2]). For F files that is +F requests (F5).
- Fix options: (a) drop the two headers by overriding `WebConn.prototype.httpRequest` or patching the bundle (w1-10 R-list has the exact patch site); the `cache: 'no-store'` init option is independent of the preflight decision (w1-10 F9), (b) give every host the correct CORS rule (S3/R2/B2/DO/Bunny all need explicit configuration), (c) use a single-file layout so there is only one URL to preflight.
- Sources: [S60][S59][S66]. Source dates: code and measurements 2026-10-17.

**F4. In drop-in mode the web seed is the existing origin read by the service worker, same-origin; CORS, Range and compression do not apply, only the provider's egress price does.** Confidence: **High** (design text) / **Medium** (not yet built). Design-critical: **yes** for how the provider table is used.
- ARCHITECTURE v0.2 section 3.4.7: the engine adds the web seed `https://<host>/_mw/ws/`; the SW answers `GET /_mw/ws/<name>/<path>` with `Range` by fetching `/<path>` same-origin with `cache: 'force-cache'` and returning the 206 slice; "No CORS is involved". Section 3.4.8: the origin remains the crawler and no-JS fallback. [S61]
- Consequences: (1) every provider that can host a static site can be the drop-in web seed, including Cloudflare Pages (its Range=200 bug is irrelevant because the SW slices); (2) the SW fetches whole files, so a "web seed Range request" costs a whole-file GET (cache hits are free); (3) the bill is the host's normal egress, multiplied by the copy-completion effect in F21; (4) a site with a restrictive CSP needs `connect-src` only for trackers and DoH.

**F5. Request count is P + F - 1 range GETs per cold visit (+ F preflights with stock headers), so the file layout, not the bytes, drives the bill on per-request-priced hosts.** Confidence: **High** (code read) / **Medium** (arithmetic).
- Code: for a web seed WebTorrent requests the whole remaining piece in one HTTP request (`piece.reserveRemaining()`, `chunkLengthRemaining`, torrent.js lines ~1941-1955), at most `maxWebConns = 4` at once (torrent.js line 145); `WebConn.httpRequest` issues one `fetch` per file that overlaps the piece's byte range. Summed over a contiguous layout that is P + F - 1 requests (each file adds one extra request at every piece boundary it crosses). Piece size in this project: 256 KiB (ARCHITECTURE section 10). Plus one GET for the `.torrent` (`xs=`). [S60][S61]
- Examples (256 KiB pieces): 2 MB / 40 files: P = 8, 47 range GETs, 87 with preflights; **8 MB / 200 files: P = 31, 230 range GETs, 430 with preflights**; 60 MB / 300 files: P = 230, 529 range GETs, 829 with preflights; the same 8 MB as one file: **31 range GETs, no preflight after the first**. The cost model (F20) multiplies these by 90,000 cold visits per month.
- Host-side effects of many small requests: rate limits (GitHub Pages 429; R2 `r2.dev` "hundreds of requests/second" then 429 [S4]; DigitalOcean 800 operations/s per new bucket and ">400 read requests per second, we recommend using the Spaces CDN" [S37]; Bunny Storage 500 RPS on the S3 API and 100 concurrent HTTP connections per IP per server [S35]).

### B. Providers: 2026 price, limits, HTTPS and wildcard, CORS, Range, cache headers, HTTP versions

For every provider the same fields: price and free tier; HTTPS custom domain and wildcard; CORS; Range; cache-header control; HTTP/2 and HTTP/3; limits and terms; verdict for a web seed and for a shell host. Prices are list prices read on 2026-10-17.

**F6. AWS S3 + CloudFront.** Confidence: **High** (price list files and pricing pages), **Medium** (behaviour not tested end to end: I have no AWS account).
- CloudFront pay-as-you-go, US/Mexico/Canada, per GB out: first 10 TB **$0.085**, next 40 TB $0.080, next 100 TB $0.060, next 350 TB $0.040, next 524 TB $0.030, next 4 PB $0.025, over 5 PB $0.020. Requests: **$0.0100 per 10,000 HTTPS** ($1.00 per million), $0.0075 per 10,000 HTTP. Origin fetches from S3 or any AWS origin: free. Invalidations: first 1,000 paths a month free, then $0.005 each. [S22][S20]
- **Always-free tier on pay-as-you-go: 1 TB data transfer out, 10,000,000 HTTP/HTTPS requests, 2,000,000 CloudFront Function invocations and 2,000,000 KeyValueStore reads per month**, 10 distribution tenants, free SSL certificates, "no limitations, all features available". [S20] (Matches w1-10 F6.)
- **Flat-rate plans (new, no overage charges):** Free $0/month (1 M requests, 100 GB), Pro $15 (10 M, 50 TB), Business $200 (125 M, 50 TB), Premium $1,000 (500 M configurable up to 6 B, 50 TB configurable up to 600 TB). Allowances are soft per the AWS plan documentation (w1-10 F6); custom response-header policies are Business-tier. [S21][P1]
- **New-account free tier changed:** a new AWS account gets a Free plan with "$100 in credits immediately" plus "up to $100 more" for exploring services, "up to $200 over 6 months", and "The account closes on its own 6 months after you open it or when your credits run out"; "30+ AWS services are always free within monthly usage limits on both the Free and Paid plans". So the CloudFront always-free allowance survives, but a production site needs the Paid plan. [S25]
- S3 Standard, us-east-1: **$0.023/GB-month** (first 50 TB), GET and other **$0.0004 per 1,000** ($0.004 per 10,000), PUT/COPY/POST/LIST $0.005 per 1,000. Transfer out to the internet (S3 direct, no CloudFront): first 100 GB a month free (aggregated across services), then **$0.09/GB** first 10 TB, $0.085 next 40 TB, $0.07 next 100 TB, $0.05 above 150 TB. [S22]
- HTTPS, domains, wildcard: S3 website endpoints are HTTP only; use the REST endpoint (HTTPS) directly for a web seed, or CloudFront for a custom domain. ACM wildcard certificates (us-east-1) work with CloudFront at one label depth; a wildcard alternate name counts as one of 100 per distribution (w1-10 F3). [P1]
- CORS: none by default; S3 answers preflight 403 until a CORS rule exists; the rule must list every requested header (`AllowedHeaders: ["*"]` for the stock request). Detail and ready JSON: w1-10 F11 and Appendix CFG-1. [P1]
- Range: CloudFront serves ranges from cache; if the origin supports Range it caches the returned range; if not it "returns the entire object" and then serves ranges from the cached whole; ranges must be ascending and non-overlapping or CloudFront returns 200 with the full object; `Transfer-Encoding: chunked` from the origin also yields the full object; no caching above 50 GB. [S23] S3 itself supports Range (measured: the NOAA bucket answered 206 with a correct `Content-Range`).
- Cache headers: object `Cache-Control` metadata set at upload (S3), cache policies and response-headers policies on CloudFront; managed policy IDs in w1-10 F5. [P1]
- HTTP versions: CloudFront "Supported HTTP versions" setting (HTTP/1.1, HTTP/2, HTTP/2 and 3, HTTP/3), HTTP/3 needs TLS 1.3 and SNI [S24]; measured: `a0.awsstatic.com` (CloudFront) HTTP/2 with `alt-svc: h3`. **S3 REST endpoints negotiate HTTP/1.1 only** (measured on `noaa-goes16.s3.amazonaws.com`).
- Verdict: **web seed**: S3 direct is fine for a hobby site (HTTPS, Range, CORS on request) but egress costs $0.09/GB; CloudFront in front is free up to 1 TB and 10 M requests and then request-priced, so it is cheap only with few requests (F5, F20). **Shell host**: S3 + CloudFront + ACM is the only AWS shape that gives HTTPS, headers, SPA fallback and wildcard; it is the strongest wildcard option.

**F7. Cloudflare R2.** Confidence: **High** (docs read), **Medium** (Range and caching through a public custom domain are documented in pieces, not exercised).
- Price (page "Last updated Oct 1, 2026"): Standard **$0.015/GB-month**, Class A (writes, lists) **$4.50 per million**, Class B (reads: GetObject, HeadObject) **$0.36 per million**; free each month: **10 GB-month, 1 M Class A, 10 M Class B** (Standard only). Infrequent Access: $0.01/GB-month, $0.01/GB retrieval, A $9.00/M, B $0.90/M, 30-day minimum. "There are no charges for egress bandwidth for any storage class." Footnote: egress is free "including via the Workers API, S3 API, and r2.dev domains"; "If you connect other metered services to an R2 bucket, you may be charged by those services" (R2 behind CloudFront pays CloudFront). Billing example on the page: 10 M reads a day is **$104.40 a month**, all of it Class B. [S1]
- Limits (updated Jun 8, 2026): unlimited storage and objects, 1,000,000 buckets, object size 5 TiB (4.995 TiB), single-part upload 5 GiB (4.995), **1 write per second per object key**, bucket management 50/s, **100 custom domains per bucket**. **`r2.dev` is "rate-limited and should only be used for development"**: "hundreds of requests/second" then 429, bandwidth may be throttled. [S4][S3]
- HTTPS and domains: "The domain being used must have been added as a zone in the same account as the R2 bucket"; for a domain not on Cloudflare "you need to set it up using a partial (CNAME) setup", which is **available only on Business and Enterprise** [S16]. So on the Free or Pro plan the zone's nameservers must be at Cloudflare. Practical answer for a web seed: use a separate hostname on any zone you control at Cloudflare (the web seed URL is not user-visible). Universal SSL covers the root and first-level subdomains on a full setup (docs updated Aug 14, 2026) [S14]. Minimum TLS version and ciphers are configurable per custom domain [S3].
- Caching: "To use features like WAF custom rules, caching, access controls, or Bot Management, you must configure your bucket behind a custom domain"; by default only certain file extensions are cached ("To cache all files in your bucket, you must set a Cache Everything page rule"); Smart Tiered Cache is available. [S3][S19] I did not find a sentence saying that cache hits are not billed as R2 operations; I assume they are not (Model uses 90 % hit as the base and 0 % as the worst case).
- CORS (updated Sep 23, 2026): JSON rules with `AllowedOrigins` (`*` or at most one `*` wildcard per pattern, "can span periods", no port wildcards), `AllowedMethods`, `AllowedHeaders` ("Cross-origin requests that include custom headers ... should specify these headers"), `ExposeHeaders`, `MaxAgeSeconds`; CORS headers are only returned when the request has an `Origin`; propagation "up to 30 seconds"; "If you set a CORS policy on a bucket that is already serving traffic using a custom domain, any existing cached assets will not reflect the CORS response headers until they are refreshed in cache. Use Cache Purge". Whether `"*"` is accepted in `AllowedHeaders` is not stated, so list `Range, Cache-Control, User-Agent` explicitly (or ship the patched request and list only `Range`). [S2]
- Range: the S3 API compatibility table marks `GetObject` `Range` as implemented [S5]; Cloudflare's cache documentation (updated Sep 14, 2026) says it serves ranges from complete or partial cached files, aligns origin range fetches to 1 MiB, and **"If Cloudflare must decompress a complete encoded response, it ignores Range" (returns 200 with the whole uncompressed body)** [S13]. The only live Cloudflare-edge Range failures I measured (cdnjs, a docs site) are not R2, but they show what the failure looks like. Mitigation to test: store web-seed objects as `application/octet-stream` with `Cache-Control: public, max-age=31536000, immutable, no-transform` so the edge neither compresses nor decompresses them.
- Cache headers: `Cache-Control` object metadata plus Cache Rules (Edge TTL) on the custom domain. HTTP/3: all plans [S15].
- Terms: Cloudflare's CDN terms (updated Sep 28, 2026) say non-Enterprise customers "must use" paid services "(e.g., the Developer Platform, Images, and Stream)" to serve "video and other large files via the CDN"; R2, Pages and Workers are the Developer Platform. R2 is the sanctioned route. [S17][S18]
- Verdict: **best default web seed** on price (zero egress, 0.36 USD per million reads) provided the hostname sits on a Cloudflare zone and Range-through-cache is verified with the seed doctor. Not a shell host (no SPA fallback logic; use Workers static assets or Pages for the shell).

**F8. Cloudflare Pages and Workers static assets.** Confidence: **High** (docs), **Medium** (the live Range probe was on a site whose deploy product is not stated).
- Bandwidth policy: the product page says "All plans come with unlimited sites, seats, requests, and bandwidth" [S12]; the docs say "On both free and paid plans, requests to static assets are free and unlimited" (Pages, updated Sep 8, 2026) [S7] and for Workers static assets "Requests to static assets are free and unlimited ... There is no additional cost for storing Assets" (updated Apr 23, 2026) [S10]. Functions invocations are billed as Workers requests (Free plan: 100,000 a day, resetting at midnight UTC).
- Limits: Pages Free 500 builds a month, **20,000 files** (100,000 on paid with `PAGES_WRANGLER_MAJOR_VERSION=4`), **25 MiB per file**, 100 custom domains per project, 100 projects per account, `_headers` 100 rules and 2,000 characters per header [S6]; Workers static assets 20,000 files Free / 100,000 Paid, 25 MiB per file (Workers limits, updated Oct 12, 2026) [S6b].
- **Range: "Pages currently returns 200 responses for HTTP range requests; however, the team is working on adding spec-compliant 206 partial responses."** (Pages "Serving Pages", updated Oct 10, 2026) [S8]. Measured on `developers.cloudflare.com`: Range on small static assets returns 200 with the whole file (F3). For Workers static assets I found no Range statement: **unverified**. Consequence: Pages is **unusable as a cross-origin web seed** (WebTorrent would hash the whole file as one piece) but fine as a shell host and as a drop-in origin (F4).
- Headers: Pages always adds `Access-Control-Allow-Origin: *`, `Etag`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`; `Cache-Control: public, max-age=0, must-revalidate` only when the request has no `Range` or `Authorization`; "Cache-Control: no-transform" when it served an encoded asset; "Pages will also serve Gzip and Brotli responses whenever possible"; `_headers` overrides. [S8] OPTIONS on the measured Cloudflare static site: 405 (stock headers would fail).
- Domains: "It is currently not possible to add a custom domain with a wildcard, for example, *.domain.com" (Pages known issues, updated Oct 15, 2026) [S9]. Workers **routes** (not Custom Domains) do support `*.hub.example/*` (w1-10 F18). Pages apex domains need the zone on Cloudflare.
- Verdict: **shell host and drop-in origin: yes, free**. **Web seed: no** (Range). Do not put web-seed objects in a Pages project.

**F9. Backblaze B2.** Confidence: **High** (pricing and CORS pages), **Medium** (the Cloudflare/Bunny paths were not exercised).
- Price: **$6.95 per TB per 30 days**, first 10 GB free; **free egress up to 3x your average monthly stored data, then $0.01/GB**; "unlimited free egress when downloading to or through partner content delivery networks and compute services, including Fastly, Cloudflare, bunny.net, CacheFly, CoreWeave, Equinix Metal, Vultr, and phoenixNAP"; Class A, B and C calls free for pay-as-you-go; Class D $0.004 per 10,000 (first 2,500 a day free); B2 Overdrive from $15/TB/month with unlimited free egress; 1 to 5 year commitments available. [S27]
- **The 3x rule is useless for a small site**: a 24 MB site stored in three versions earns about 0.2 GB of free egress a month, so direct B2 behaves like $0.01/GB flat (720 GB is $7.20). Free egress needs a partner CDN in front. (F20)
- HTTPS and domains: friendly URL `https://f00X.backblazeb2.com/file/<bucket>/<key>` and S3 URL `https://<bucket>.s3.<region>.backblazeb2.com/<key>`; **custom domain needs a CDN**: the Cloudflare guide (updated Jun 26, 2026) uses a proxied CNAME to the bucket origin and "no download fees from Backblaze"; Bunny documents a pull zone with the B2 S3 URL as origin [S29][S35b]. Public buckets require a verified email and payment history on file [S29].
- CORS (doc updated Jul 17, 2025): up to **100 rules per bucket, each under 1,000 bytes**; "By default, the Backblaze B2 servers will deny preflight requests"; a preflight matches when the origin matches, the operation is allowed and "every value in the Access-Control-Request-Headers is in the rule's allowedHeaders"; origins may contain one `*`. Measured on a bucket without rules: GET without ACAO, OPTIONS 401. [S28]
- Range: the native API supports a single range (`bytes=0-99`) with 206 and `Content-Range`; "Only byte-range requests with a single range of bytes are supported"; a range enclosing the whole file returns 200 without `Content-Range` (the S3-compatible API returns 206) [S30]. Measured: `bytes=0-99` gave 206 with `content-range: bytes 0-99/277989`.
- HTTP: **`f001.backblazeb2.com` negotiated HTTP/1.1** (measured); HSTS `max-age=63072000`.
- Verdict: **good cheap origin behind Cloudflare or Bunny** (storage-only pricing); poor direct web seed (billed egress). Needs CORS rules with `allowedHeaders: ["*"]` or the patched request. Cloudflare terms caveat in F26.

**F10. Bunny (Storage + CDN).** Confidence: **High** (pricing pages and docs), **Medium** (CORS and OPTIONS behaviour not verified; HTTP/3 unverified).
- CDN price (pricing page): **Standard Network (119 PoPs): Europe and North America $0.01/GB, Asia and Oceania $0.03, South America $0.045, Middle East and Africa $0.06. Volume Network (10 PoPs): $0.005/GB for the first 500 TB, $0.004 for 500 TB to 1 PB, $0.002 for 1 to 2 PB.** "$1 Monthly Minimum", "No Request Fees", overcharge protection (monthly bandwidth limits), 14-day free trial. [S31]
- Storage price: Standard (HDD) **$0.01/GB-month for one region**, $0.02 for two, $0.025 for three, +$0.005 for each additional region up to nine; Edge (SSD) $0.02/GB per region up to 15; $1 monthly minimum; "FREE traffic to Bunny CDN", no API fees, free API egress. [S32]
- HTTPS and wildcard: free auto-renewing Let's Encrypt certificate for a custom hostname (the CNAME must point at the pull zone; with Cloudflare the orange cloud must be off), or upload your own; **"When your domain is hosted on a Bunny DNS zone, Bunny automatically issues and renews a free Let's Encrypt wildcard certificate"**, otherwise upload a wildcard certificate yourself; limits: 10 hostnames per pull zone, 500 pull zones, 50 edge rules per zone. [S34][S35]
- Range: "BunnyCDN fully supports range requests for both cached and uncached content. By default ... for any request involving cached content. Ensure that you activate 'Optimize for large object delivery' in your pullzone's caching settings to enable this for uncached content." [S33] Measured on bunny.net's own zone: with `Accept-Encoding: identity` (what a browser sends on Range) both a JPEG and a compressible SVG return a correct 206 with `Content-Range`; with `Accept-Encoding: gzip, br` the SVG returns 200 with the whole brotli body. Bunny compresses gzip, Brotli and Zstandard for listed MIME types and for `.css .js .json .xml .svg .html` regardless of type. [S35]
- CORS: no CORS by default (measured: GET without ACAO, OPTIONS **403**). Docs show two mechanisms: Pull Zone > **Headers** lists file extensions that get CORS headers (examples: `woff2`, `woff`, `html`, `json`) and Edge Rules offer a **Set Response Header** action. Whether the edge answers a preflight with 2xx once CORS is on is **not documented in what I read: unverified**. [S35]
- Cache headers: Edge Rules (custom cache time per extension), Smart Cache, Perma-Cache, Vary cache; storage "Rewrite 404 to 200 status code" and a custom 404 path exist for SPA fallback. [S35]
- HTTP: HTTP/2 on bunny.net (measured); no HTTP/3 page in the docs index and no `alt-svc` header seen: **unverified**. Storage limits: 100 concurrent HTTP connections per IP per server, 250 per zone per server, S3 API 500 requests/s per zone, path length 6,000 characters. [S35]
- Verdict: **strong web seed and shell host for small money** ($0.01/GB, no request fees, $1 minimum, one bill) once CORS is switched on and the preflight is tested; the cheapest option that needs no Cloudflare zone. Wildcard is easy only with Bunny DNS.

**F11. DigitalOcean Spaces.** Confidence: **High** (pricing page verified 13 Jul 2026, limits verified 3 Sep 2026).
- Price: **$5.00 a month** subscription "includes 250 GiB of storage" and "**1,024 GiB of outbound data transfer** ... shared between all buckets"; extra storage $0.02/GiB-month, extra transfer **$0.01/GiB**; inbound free; "The Spaces Content Delivery Network (CDN) is included at no additional cost" and "The transfer allowance included with your base subscription covers both CDN and origin bandwidth"; Cold Storage $0.007/GiB-month + $0.01/GiB retrieval (no CDN, no website hosting). [S36]
- Limits: 100 buckets and 200 access keys per account; **new buckets: 800 total operations per second**; older buckets 1,500 requests per IP per second, 500 total operations per second; "For more than 400 read requests per second, we recommend using the Spaces CDN"; PUT up to 5 GB, multipart up to 5 TB; 100 million unversioned objects per bucket; **"You cannot use multiple CDNs from different vendors with a single Spaces bucket"**; presigned URLs are not cached by the CDN. [S37]
- Domains and TLS: the CDN endpoint `<space>.<region>.cdn.digitaloceanspaces.com` works without a custom domain; a custom subdomain needs a certificate: **Let's Encrypt integration if the domain's DNS is on DigitalOcean (the form offers "secure all subdomains (wildcard)", a new subdomain or an existing one), otherwise bring your own certificate**; "You cannot secure a CDN subdomain using a custom wildcard SSL certificate already in use elsewhere in your account", "Wildcard SSL certificates do not match bucket names containing periods", "You cannot use Cloudflare Origin CA certificates for custom subdomains". One custom subdomain per CDN endpoint (the docs describe a single subdomain). Default edge cache TTL 1 hour, configurable. [S38][S37]
- CORS: per-bucket rules in the control panel (origin with one wildcard in the host, methods GET/PUT/DELETE/POST/HEAD, allowed headers, max age; "We recommend setting this value to 5 seconds") and an XML file for `ExposeHeader`. Measured on a product-docs bucket: GET has ACAO `*` with `Allow-Methods: GET` and `Max-Age: 0`, OPTIONS with the stock headers returns **403** (no allowed headers in the rule). So the rule must list the headers or the client must send only `Range`. [S39]
- Range and protocols: measured 206 with `Content-Range` and HTTP/2 on both the origin (`*.digitaloceanspaces.com`) and the CDN endpoint; the CDN endpoint answered with `server: cloudflare` (the Spaces CDN is served by Cloudflare's network) and no `alt-svc`. [S66]
- Verdict: **simplest flat-price web seed** ($5 for 1 TiB egress and 250 GiB, CDN included); needs the CORS rule; wildcard and Let's Encrypt only with DigitalOcean DNS.

**F12. GitHub Pages.** Confidence: **High** (docs source read in two forms, probes today).
- Limits ([S40], GitHub docs source on `main`): published sites "may be no larger than 1 GB" (source repositories 1 GB recommended); "a _soft_ bandwidth limit of 100 GB per month"; "a _soft_ limit of 10 builds per hour" (not for a custom Actions workflow); deployments time out after 10 minutes; "rate limits may apply ... an appropriate response with an HTTP status code of `429`"; "not intended for or allowed to be used as a free web-hosting service to run your online business, e-commerce site, or any other website that is primarily directed at either facilitating commercial transactions or providing commercial software as a service (SaaS)"; on overuse GitHub "may not be able to serve your site" or suggests a CDN, releases or another host.

[S66][P1]
- Domains: apex A/AAAA/ALIAS or subdomain CNAME, Let's Encrypt certificate; no wildcard custom domain (w1-10 F15). Project sites (`user.github.io/repo/`) break root-absolute loader URLs (w1-10 F16).
- Verdict: **shell host for non-commercial small sites; web seed only with the patched request and under 100 GB a month**. Cannot set any header, so no CSP/HSTS from the host (w1-10 F26).

- Verdict: **do not use as a web seed** (credits at 20 per GB, request credits, pause-everything failure mode); acceptable shell host for a small site on a paid plan.

**F16. IPFS: public gateways and pinning services (Pinata, Filebase, Storacha).** Confidence: **High** for what is dead or alive on 2026-10-17 (probes plus w1-07), **Medium** for plan details.
- Public gateways: from my probes `ipfs.io` and `dweb.link` return **429** to a GET of a well-known CID (and 5xx to OPTIONS); w1-07 F8 documents the retirement (gatewaychanges.ipfs.io: the gateway "steps aside a little each hour ... until it retires for good on September 21 (UTC)"; IPFS Foundation post of 2026-08-25: rate limiting "has begun on ipfs.io and dweb.link for hotlinked and backend traffic"); `cloudflare-ipfs.com` no longer resolves; `w3s.link` refuses connections; `trustless-gateway.link` answers 522. In Chromium all of these are blocked. [S66][P2]
- **Storacha is gone**: `storacha.network`, `docs.storacha.network` and `/pricing` answer 301 to `fil.one`; `web3.storage` and `storacha.link` redirect through `storacha.network` to the same place. Fil One is an S3-compatible store at **$5.99 per TB-month**, "1 TB free for 30 days", "$0 egress (subject to reasonable use)", no API fees, and its FAQ says "**Public buckets are not currently supported**. To share individual files, you can generate a presigned URL ... How do I migrate from Storacha". So there is no public HTTP object URL and no IPFS gateway. **F21. Drop-in mode: copy completion can turn a lazy site into an eager one, multiplying origin egress.** Confidence: **High** for the design text, **Model** for the multiplier. Design-critical: **yes**.
- Design text: ARCHITECTURE v0.2 section 3.4.7: the web seed `https://<host>/_mw/ws/` is added "only on unmetered networks at idle, to complete the copy for seeding and offline use, within `maxSiteBytes`" (128 MiB desktop, 48 MiB mobile Wi-Fi, 24 MiB otherwise); the SW fetches whole files with `cache: 'force-cache'`, so HTTP-cache hits cost the host nothing; DESIGN-REVIEW section 3.4.7 adds that completion "costs about one extra download of the non-HTML files per new device". [S61]
- Arithmetic: let B_visit be the bytes a visitor would have loaded anyway (the pages and assets of the 1 to 3 pages they read), S_site the torrent size, p the peer share of the completion. Host bytes per new device go from B_visit to **B_visit + (S_site - B_visit) x (1 - p)**, a multiplier of **M = (S_site (1 - p) + p B_visit) / B_visit**. For S_site = 20 MB and B_visit = 1.5 MB: **M = 13.3 at p = 0, 7.2 at p = 0.5, 2.2 at p = 0.9**. For S_site = 5 MB and B_visit = 1 MB: 5.0 at p = 0. A photo-heavy site with S_site = 100 MB (capped at 128 MiB) and B_visit = 2 MB: 50 at p = 0. The cap `maxSiteBytes` bounds the damage per device but not the bill.
- Why this matters for cost: a drop-in migration is sold as "one script tag, nothing else changes"; on a per-GB host it silently raises the egress bill by the multiplier for every eligible first-time desktop visitor, and the peer share p is small for small sites (F23). On a zero-egress host (R2, B2 behind Cloudflare, Pages) the multiplier is free; on S3 direct ($0.09/GB), CloudFront or Vercel it is real money.
- Mitigations (R4, R5): a host-copy byte budget (default a small multiple of B_visit, or a fixed few MB) with the rest coming from peers only; peer-first background completion with a delayed host fallback (Model, F24); `publish.mjs --dropin` printing M and the expected monthly egress for the site's S_site and a visits/day input; Save-Data and metered-network rules already in the design stay.

### E. How many bytes will peers really carry? (honest numbers for small sites)

**F22. Public evidence of high P2P offload comes only from regimes with thousands of simultaneous clients; I found no published byte-offload measurement for a small static site (unknown/unverified).** Confidence: **High** for what the sources say, **Low** for any extrapolation. Design-critical: **yes** (it sets the README's honesty line).
- Availability arithmetic already in the project (review/distributed-systems.md section 2): expected concurrent visitors E[N] = visits per day x dwell seconds / 86,400, and with Poisson arrivals P(you are alone) = e^(-E[N]): 100 visits a day with 60 s dwell gives E[N] = 0.07 (alone 93 % of the time); 1,000 a day gives 0.7 (alone 50 %); 10,000 a day with 120 s dwell gives 14 (alone about 0 %). [P4] On top of that only visitors who consented, are on desktop (uploads default off on mobile, ARCHITECTURE section 8), have a finished copy, announced, and can complete an ICE handshake count as seeders. With my base assumptions (60 % consent, 55 % desktop, 75 % pair success; vendor estimates put 10 to 25 % of consumer pairs behind NATs that need TURN, which stock WebTorrent does not have [P3]) the usable seeder count is about 0.25 x E[N].
- **Maygh** (Zhang, Zhou, Mislove, Sundaram, EuroSys 2013, **OLD**): abstract "if Maygh was deployed to Etsy, it would reduce network bandwidth due to static content by 75% and require only a single coordinating server". The simulation: 7 days of Etsy image logs, **205,586,135 requests to 56,084 unique objects from 5,720,737 IPs, 2.77 TB (395 GB a day)** over the busiest 18 hours a day; clients assumed online for a random 10 to 30 seconds after each request ("likely to be conservative"); upload ratio 1 and 10 MB per client; result "the median bandwidth used drops from 50.3 Mb/s to 11.7 Mb/s (a 77% drop)" and "the 95th-percentile bandwidth ... shows a similar decrease of 75%"; a plug-in system on 10 % of users saved 6.9 % (median). That is about 29 M requests a day (hundreds per second): E[N] in the thousands. [S62]
- **Windows Delivery Optimization** (Microsoft docs, undated): at Microsoft IT, peer caching limited to one Active Directory domain with content cached 24 hours: "More than 76 percent of content came from peer devices versus the Internet." Managed always-on devices wanting the same update on one LAN. [S63]
- **P2P Media Loader** (the library PeerTube kept after dropping WebTorrent): no numeric offload in the README; sizing text "For smaller setups (1,000-2,000 simultaneous viewers), public trackers alone can handle peer connections". [S64] PeerTube's own history (w1-07 F21): WebTorrent player removed in 6.0.0, "the P2P aspect of WebTorrent is not really used". [P2]
- Reading: every high number is a large, simultaneous, same-object audience. The project's own prior conclusion stands (w1-07 F21 lesson: "A small site's peer density will be near zero most of the time, so the web seed is the product and peers are an optimisation").

**F24. Policy levers that move the number (Model): a peer-first background lane is where the savings are.** Confidence: **Model**. Design-critical: **no** (a tuning choice) but **P1** for the cost story.
- Peer-first (web seed starts after Td seconds, then fills whatever peers have not delivered): 5 MB at 10,000 visits a day: Td 3 s gives 2.8 % (mean first-visit completion 4.9 s); **Td 8 s gives 27.8 % (9.3 s)**; Td 15 s gives 45.1 % (13.8 s). At 100,000 visits a day: 6.6 %, 44.7 %, 58.2 %. 25 MB at 10,000 visits a day: 11.7 %, 21.0 %, 32.7 % (completion 11.8 s, 15.9 s, 21.6 s versus 9.7 s under the race policy).
- Upper bound for this design (everyone consents, everyone on desktop, every pair connects, 300 s dwell, Td 8 s): 5 MB gives 24.4 % at 100 visits a day, **95.2 % at 1,000**, 99.6 % at 10,000; 25 MB gives 13.0 %, 76.9 %, 99.8 %. Real values sit between this and the base table.
- Break-even payload for peers to carry at least a quarter of first-visit bytes under the race policy, in the best traffic case (100,000 visits a day, 120 s dwell, everyone consents on desktop, 20 Mbit/s): 5 MB 0.1 %, 10 MB 3.1 %, **20 MB 23.0 %**, 40 MB 53.1 %, 80 MB 72.5 %, 120 MB 79.0 %.
- Therefore: keep the race policy for the **render-critical lane** (first paint must not wait for peers) and use **peer-first with a delayed web-seed fallback for the background lane** (copy completion, seeding copy, prefetch of other pages). That lane has no latency cost, and it is exactly the extra egress that drop-in mode adds (F21).

**F25. Rule of thumb: when is the web seed effectively the CDN?** Confidence: **Model** with literature context. Design-critical: **yes** for README and DEPLOY wording.
- Under the v0.2 race policy and consent gate the web seed carries more than 99 % of first-visit bytes when the payload is 5 MB or less at any traffic level on a 20 Mbit/s or faster link (about 97 % at 10 MB even in the most favourable traffic case); more than 90 % for any payload up to 100 MB below roughly 3,000 visits a day; and more than 75 % for 25 MB below 100,000 visits a day. Peers carry a quarter of the bytes only for payloads of about 40 MB and up at tens of thousands of visits a day, or on slow links (at most 8 Mbit/s), or in a spike, or in a background lane.
- What P2P still buys on a small site: (1) resilience while the host or its web seed is down (peers hold the verified copy), (2) the chain's gossip and replication (a different job from byte offload), (3) faster completion of large payloads at higher concurrency (25 MB at 100,000 visits a day: 8.6 s instead of 10.4 s), (4) a cushion in a traffic spike, (5) a mirror that outlives the host. It does not shrink the hosting bill of a small site, and plans must budget web-seed capacity and money for **100 % of cold-visit bytes**.

## Gotchas

1. **curl without an `Origin` header shows no CORS headers on R2 and S3**; test with `-H 'Origin: https://example.org'` and also test the OPTIONS preflight. (F7)
2. **After changing an R2 CORS policy on a hostname that is already cached, purge the cache**, or old responses keep their old headers; propagation takes up to 30 s. (F7)
3. **The preflight cache is per URL, default 5 s, and browsers cap `Access-Control-Max-Age` (R2: "2 hours or less")**; with F files a cold visit pays F preflights unless R1 or the archive layout is used. (F2, F5)
4. **S3's recipe `AllowedHeaders: ["Range"]` fails the stock request**; use `["*"]`. DigitalOcean's default rule and Vercel's static OPTIONS also lack `cache-control`. (F2, F3, w1-10 F11)
5. **WebTorrent treats any 2xx as piece data**: a 200 with the whole file (Pages, Primal) or a 206 with the wrong bytes (jsDelivr) causes hash failures and endless 10 s retries, not an error. (F1)
6. **B2's "3x free egress" is computed on your stored bytes**; a 24 MB site earns about 0.2 GB. Free egress needs a partner CDN, and B2's `f00X` hostnames are HTTP/1.1 only. B2's native API returns 200 (not 206) when the range covers the whole file. (F9)
7. **Cloudflare partial (CNAME) setup is Business or Enterprise only**; R2 custom domains need the zone in the same account, so a site whose DNS lives elsewhere needs a separate seed domain. `r2.dev` is rate-limited and for development. (F7)
8. **Cloudflare Pages "returns 200 responses for HTTP range requests"** and cannot take a wildcard custom domain; Workers **routes** can. (F8)
9. **Bunny**: with Cloudflare in front of a Bunny hostname the proxy must be off for Let's Encrypt; uncached Range needs "Optimize for large object delivery"; CORS is a per-extension Headers setting or an Edge Rule; the edge compresses listed MIME types (Range with a compressed `Accept-Encoding` returns 200 whole). (F10)
10. **DigitalOcean**: the CDN is the Cloudflare network but you cannot also front a Space with another CDN; presigned URLs are never cached; a wildcard certificate does not match bucket names that contain periods; Cloudflare Origin CA certificates are rejected. (F11)
11. **GitHub Pages**: fixed 10-minute cache, no headers, OPTIONS 405, 1 GB, 100 GB soft, no commercial use. (F12)
12. **Netlify Free pauses every project in the account** when credits run out; Vercel Hobby makes you wait 30 days and forbids commercial use; the AWS Free plan closes the account after 6 months. (F6, F13, F14)
13. **Blossom**: a redirect target must also send `Access-Control-Allow-Origin: *` (satellite.earth redirects); `.ext` is optional; no directories (single-file torrents only); Range is a SHOULD. (F17)
14. **IPFS path gateways allow `Range` but not `Cache-Control` in preflight**; Pinata serves HTML only through a dedicated gateway with a custom domain. (F16)
15. **Chromium learns HTTP/3 from `alt-svc` and uses it from the second connection**, so a single-request probe reports h2 even on an h3 host. (F3, F19)
16. **`Accept-Encoding: identity` on Range requests can split a CDN's cache** into an identity variant and compressed variants for compressible types (CloudFront keys on normalised Accept-Encoding); keep web-seed objects non-compressible (`application/octet-stream`) to avoid double storage in cache and to dodge edge-compression bugs. (Inference from w1-10 F5 and F1; Medium.)
17. **In drop-in mode a Range request becomes a whole-file GET** because the SW fetches `/<path>` and slices; on large media the first Range costs the file once (then the HTTP cache serves it). (F4)
18. **Cost-model blind spots**: DoH, trackers, STUN are third-party and not billed to the publisher; Route 53, WAF, CloudWatch and domain fees are excluded; Pinata and Netlify request prices dominate fan-out layouts; a 24-hour spike can exceed a month's allowance on credit-based hosts. (F20)
19. **Prices and plans moved in the last 12 months** (AWS Free plan credits since July 2025, CloudFront flat-rate plans, Netlify credits since 2025-09-04, Vercel Flat Rate CDN, Storj tier change, Storacha to Fil One); every number here carries "list price on 2026-10-17" and should be re-read before a publication.

## Open questions

1. **Range through an R2 custom domain with a Cache Everything rule**: does a browser (`Accept-Encoding: identity`) get 206 with correct `Content-Range` for `application/octet-stream` + `no-transform` objects, and does a compressible type ever return 200? Needs a real R2 bucket. (F7, R7)
2. **Are Cloudflare cache hits billed as R2 Class B operations?** The docs I read do not say; the cost model assumes no.
3. **Firefox and Safari**: do they send `Accept-Encoding: identity` on Range fetches (Fetch Standard says yes; verified Chromium and WebKit locally only), and does Safari accept `Access-Control-Allow-Headers: *` for `cache-control`? Firefox would not launch here. (R10)
4. **Cloudflare Workers static assets and Range**: no statement found; the one live Cloudflare static site probed returned 200 for small assets. (F8)
5. **Bunny**: once CORS is enabled does the edge answer OPTIONS 2xx; is HTTP/3 available and on by default? (F10)

7. **Netlify**: can one site claim a wildcard domain alias (`*.hub.example`) and on which plan; what do legacy plans (before 2025-09-04) allow? (F13)

10. **Real P2P offload on a live small site**: the consent rate, dwell time, desktop share and pair-success values in the model are assumptions; no public data exists. (F22, F23, R15)

## Appendix D - Ready-to-use snippets

Patched web-seed request (R1), for `webtorrent@3.0.21` `lib/webconn.js`:

```js
const res = await fetch(url, {
  cache: 'no-store',            // still bypasses the HTTP cache; the browser adds Cache-Control/Pragma itself AFTER the CORS decision
  method: 'GET',
  headers: { range: `bytes=${start}-${end}` },   // the only author-set header; safelisted
  signal: AbortSignal.timeout(SOCKET_TIMEOUT)
})
```

Seed doctor assertions per file (R2): `OPTIONS` with `ACRH: cache-control,range,user-agent` -> classify PASS-stock if 2xx and the response allows all three; else try `ACRH: range` (or no preflight needed) -> PASS-needs-patched-client. `GET` with `Range: bytes=a-b` and `Accept-Encoding: identity`: status 206; `Content-Range` is `bytes a-b/<file length>`; no `Content-Encoding`; body length b-a+1; SHA-256 of a piece-aligned range equals the torrent piece hash; no redirect, or the redirect target also sends ACAO. Fixtures: GitHub Pages (405), Cloudflare Pages (200), Primal (200 whole), jsDelivr (206 wrong bytes).

R2 recipe (R7): zone on Cloudflare (Free plan is enough), bucket custom domain `seed.<your-domain>`, Cache Rule "Cache Everything" with a long Edge TTL for that hostname, upload with `Content-Type: application/octet-stream` and `Cache-Control: public, max-age=31536000, immutable, no-transform`, CORS policy:

```json
[{"AllowedOrigins":["*"],"AllowedMethods":["GET","HEAD"],"AllowedHeaders":["Range","Cache-Control","User-Agent"],"ExposeHeaders":["Content-Range","Content-Length","Accept-Ranges","ETag"],"MaxAgeSeconds":86400}]
```

After changing CORS on a hostname that already served traffic, purge its cache. Then run the seed doctor and the browser matrix script against the new `ws=` URL.

Cost estimator input (R8): `tools/prices.json` with, per provider, `{ asOf, storage_gb_month, egress_tiers, free_egress_gb, request_per_million, free_requests, minimum_month, notes }`; the formulas are in `cost_model.py`.
