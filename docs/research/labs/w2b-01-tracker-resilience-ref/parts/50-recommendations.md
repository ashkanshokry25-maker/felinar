## Concrete recommendations for magnet-web

Effort: S = under a day, M = 1-3 days, L = more. Priority: P0 = blocks "production-ready", P1 = needed for a credible launch, P2 = soon after, P3 = optional. Module names refer to `docs/ARCHITECTURE.md`/`INTERFACES.md`. "Evidence" points to the finding above.

| # | Priority | Effort | What to build / change | Why (evidence) |
|---|---|---|---|---|
| R1 | **P0** | S | Replace the placeholder `CONFIG.trackers` in `src/loader/config.js` (it still lists `tracker.btorrent.xyz`, which resolves to 127.0.0.1, and `tracker.files.fm:7073/announce`, which answers 403 to any origin but files.fm) with: own neutral-host tracker(s) first, then `wss://tracker.webtorrent.dev`, `wss://tracker.openwebtorrent.com`, `wss://tracker.novage.com.ua`, optionally `wss://open.ftorrent.com`. Same list in the magnet `tr=` and in code; no `ws://`, no non-443 ports. | F1 (100% of the counted soak samples for these four; dead/locked entries unchanged), first-wave F1-F3 |
| R2 | **P0** | S | Make `ws=` **and** `xs=` mandatory in production pointers (`tools/publish.mjs`, `src/common/pointer.js` `magnetFromRecord`, `docs/DEPLOY.md`): `xs` = `https://.../<name>.torrent`, `ws` = the web-seed base; CORS on both (`Access-Control-Allow-Origin`, `Allow-Headers: range, cache-control`, `Expose-Headers: Content-Range, Content-Length, Accept-Ranges`). Treat "all trackers failed" as a status ("Peers unavailable - loading from the web seed"), never as `E_NO_PEERS`; add the C/D/E scenarios of `e2e/degrade.mjs` to the e2e suite. | F10: with `xs`+`ws` the page loaded in 18-85 ms (loopback) under dead, black-hole, mute and absent trackers in Chromium and WebKit; without `xs` nothing loads |
| R3 | **P0** | S-M | Do **not** ship `tools/tracker.mjs` as the stock `bittorrent-tracker` CLI. Use the hardened wrapper (`w2b-01-tracker-resilience-ref/tracker/tracker.mjs`, 16 tests, also green on Ubuntu 24.04) or at minimum: `uncaughtException` supervision, `ws.maxPayload`, message validation, `OPEN=1`/allow-list. Report the `offers:[null]` crash upstream (webtorrent/bittorrent-tracker; PeerTube's `@peertube/bittorrent-tracker-server` is identical). | F3: one message from any client exits the stock process; no ping, 100 MiB frames, unbounded swarms/backlog, `/stats` blocks the loop |
| R4 | **P0** | M | Tracker connection shim in `src/loader/torrent.js` (new `tracker-shim.js`): per-tracker-instance `_startReconnectTimer` override (500 ms + U(0, min(60 s, 1 s x 2^retries))), keepalive cadence cap (`setInterval` <= 55 s with `numwant: 0`), and a `kick()` on `visibilitychange`, `pageshow`, `online` (resets retries, reopens sockets now). | R5 | **P1** | S-M | Announce policy: count-aware probe-then-offer (`numwant` 0 on the first announce; 3 only while `connected WebRTC peers < min(2, others reported by the tracker)`), at most 4-5 trackers. | F7: 0 vs 45 `RTCPeerConnection`s per 30 s (scaled) alone, 0 vs 54 connected, -95% tracker bytes, +16 ms to first wire; Trystero 0.25.4/0.26.0 precedent |
| R6 | **P1** | M | Run at least one own tracker on a **neutral hostname** (`rtc.<domain>`), in `tr=` first: Node wrapper behind Caddy on Oracle Always Free A1 or a $4-7 VPS (reference deployment), optionally a second one on Cloudflare (Durable Object prototype, per-swarm URL with an HMAC capability token) for a different failure domain. Use `ALLOW_FILE` (site `btih` + chain-room id) in production, `OPEN=1` only for demos. Add `--tls` to the dev `tracker.mjs` for phones (review M8). | F2: HaGeZi Anti-Piracy blocks all four public trackers by hostname and BlockListProject "torrent" two of them; F5/F6/reference deployment tested; security review M6 (open tracker) |
| R7 | **P1** | S | Daily CI job that re-checks every hostname in `config.js` against browser and DNS lists (`probes/filterlist-check/`, `monitoring/tracker-health.yml` job `hostnames`); fail on any hit. Never use `tracker`, `torrent`, `peer`, `bt` or free dynamic-DNS suffixes (`duckdns.org` is blocked as a third-party WebSocket by EasyPrivacy). | F2; review m8 closed |
