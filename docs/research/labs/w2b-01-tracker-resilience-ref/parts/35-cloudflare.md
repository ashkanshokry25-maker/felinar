### F6. A WebTorrent tracker on Cloudflare Workers + Durable Objects: it works (prototype passes with real WebTorrent clients), costs about the $5 plan minimum, and has three design constraints `[DESIGN-CRITICAL for the "no server we run" option]`

**Claim.** A Durable Object (DO) per swarm using the WebSocket Hibernation API is a working WebTorrent-protocol tracker. I built a ~110-line prototype (`w2b-01-tracker-resilience-ref/cf-do/`) and ran it in `workerd` 2026-10-12 via `wrangler dev --local` 4.151.1:
- 8/8 black-box checks pass (announce reply with `interval: 120`; offer relayed to a random other peer; answer relayed back; `offers:[null]` rejected without a crash; `peer_id` changing on a connection rejected; wrong swarm rejected; bad path -> HTTP 400; clean close handshake).
- **Hibernation-safe:** with 25 s of silence the object was evicted and its constructor re-ran on the next message ("Swarm constructed" logged twice) and the offer was still relayed in 22 ms, because all peer state lives in per-socket attachments (`serializeAttachment`, 16,384-byte limit) rather than in memory.
- **Real clients:** two headless Chromium pages running the project's `webtorrent.min.js` 3.0.21: page A filled itself from the HTTP web seed, page B had *no* web seed and *no* `xs=`, only `tr=ws://127.0.0.1:8787/<btih>`; B announced at 140 ms, got a WebRTC wire at 151 ms, metadata at 153 ms and completed the 473,645-byte torrent from A at 184 ms (`do-e2e.mjs`). So the stock client speaks to it without modification.
Not tested: Cloudflare's production edge (latency, real hibernation timing, deploy-time disconnects), billing, abuse at scale.

**Existing implementations (as of 2026-10-17):** only one public repo implements the WebTorrent WS announce/offer/answer messages on DOs: `manalejandro/cf-feditorrent` (MIT, 0 stars, 10 commits; the tracker is a component of an ActivityPub torrent-sharing app; uses `acceptWebSocket` + `serializeAttachment`; authorises info hashes through a KV lookup; no rate limiting, no peer caps, answers accepted from unannounced senders, a malformed bencode failure string, offers silently dropped when the swarm is small). The earlier note (F17: "none implements...") was wrong on that point; it is a toy, not a drop-in. `yanshiqwq/cf-http-tracker` (HTTP announce only) and `99percentpeople/weblink-ws-worker` (generic room signalling) were seen in search hits only and not read. GitHub topic `webtorrent-tracker` has no repositories.

**Design constraints.**
1. **One socket = one Durable Object.** The stock client multiplexes all torrents of one tracker URL over one socket, so the swarm must be in the URL: `wss://<worker>/<40-hex btih>`. The loader controls `tr=`, so that is free, and it isolates each site's swarm and bounds blast radius. The URL is also a natural place for a *capability token* (`?k=<HMAC(secret, btih)>`, produced by `publish.mjs`) so strangers cannot create unlimited DOs on our bill (each new room = billed requests); verify it in the Worker before `idFromName`.
2. **Deploys disconnect every WebSocket** (Cloudflare docs: code deploys and restarts terminate sockets); the loader's reconnect logic (R4) must therefore be fast and jittered, not the stock 10 s + U(0, 5 min).
3. **In-memory state resets on hibernation**: keep peer state in attachments (done) and treat `getWebSockets()` (O(n) per announce) as the peer table; fine for swarms of hundreds, re-think above ~1,000 peers per swarm.

**Pricing (Cloudflare docs, Durable Objects page "Last updated Sep 30, 2026"; Workers page "Last updated Oct 2, 2026").**

| Item | Free plan | Workers Paid ($5/month minimum) |
|---|---|---|
| DO requests | 100,000 / day (SQLite-backed DOs only) | 1 M / month included, then $0.15 / M |
| DO duration | 13,000 GB-s / day | 400,000 GB-s / month included, then $12.50 / M GB-s |
| Workers requests (the Worker that routes the upgrade) | 100,000 / day, 10 ms CPU per invocation | 10 M / month included, then $0.30 / M; 30 M CPU-ms included, then $0.02 / M CPU-ms |
| WebSocket billing | connection = 1 request; **incoming messages billed 20:1** (100 messages = 5 requests); outgoing messages free; incoming protocol pings free; auto-responses (`setWebSocketAutoResponse`) add no duration | same |
| Hibernation | objects that are eligible to hibernate are **not billed for duration**, even before eviction; `setTimeout`/`setInterval`, alarms and outgoing WebSockets prevent hibernation | same |
| Limits | soft limit 1,000 requests/s per object, 32 MiB max received message, 128 MB memory billed per active object, no documented cap on sockets per object ("thousands") | same |

**Cost estimate (mine, low-to-medium confidence).** Per visit: 1 Workers request + 1 DO request for the upgrade, about 4 incoming tracker messages (a `started` announce, one `update` at 120 s, a couple of answers) = 0.2 billed DO requests, about 12 ms of CPU in total. So **1 M visits/month = about 1.2 M DO requests (0.2 M over the 1 M included = $0.03), 1 M Workers requests (inside the 10 M included), roughly 12 M CPU-ms (inside the 30 M included), duration well inside the 400 k GB-s => the $5 minimum is the whole bill**; 10 M visits/month is about $8.5 (DO requests 12 M: $1.65; Workers requests at the 10 M included; CPU 120 M ms: $1.8; plus the $5 minimum). The Free plan's 100 k DO requests/day carry about 77 k visits/day on paper; a Cloudflare Community post (found 2026-10-14, user report only) says Free-plan enforcement cut off near 64 k billed requests, i.e. enforcement may not match the documented 20:1 (**unverified**). The bill is linear in visits (≈ $0.72 per million beyond the allowances), so above roughly 10 M visits/month a flat $4-7 VPS or Oracle's free tier is cheaper; below that Cloudflare is as cheap as any VPS and nothing is operated.

**Verdict.** Best "no server to patch" option and the only one whose cost scales to zero when nobody visits; the cost of that is a Cloudflare account/lock-in, per-swarm URLs, deploy-time disconnects and a code base we must own (the prototype is a starting point, not production code). It is still a third-party operator that sees IP, swarm id and SDP.
**Confidence:** high for the prototype results (re-runnable) and for the pricing facts (official pages); low-medium for the cost estimate and for production behaviour.
