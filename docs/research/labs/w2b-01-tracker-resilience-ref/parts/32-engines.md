### F3. Self-hosting engines: capacity is not the constraint for our workload; the stock Node server is crashable and unbounded, and a ~400-line wrapper fixes that `[DESIGN-CRITICAL]`

**Claim 1 - the stock `bittorrent-tracker` 11.2.3 WebSocket server can be crashed by one unauthenticated message.** Reproduced on 2026-10-17 (`tracker/test/stock-crash-demo.mjs`): a client that sends `{"action":"announce", ..., "offers":[null]}` into a swarm that already contains one other peer makes `server.js:528` (`params.offers[i].offer`) throw `TypeError: Cannot read properties of null (reading 'offer')` inside a `process.nextTick` callback; there is no `try/catch` on that path, so the Node process exits with code 1; reproduced against the documented command itself, `bittorrent-tracker --ws --port N` (`tracker/test/stock-cli-crash-demo.mjs`: exit code 1, `server.js:528`), because the bundled CLI has no `uncaughtException` handler. The attacker needs only two of its own connections (one decoy peer) and any 20-character swarm id. I found no open upstream issue for it (the 15 open issues include #525 "Server does not validate that offer_id is 20 bytes", #164 "Tracker server should prune old torrents and swarm" open since 2016, #288 `MaxListenersExceededWarning`; closed issues not searched), so it is probably unreported: report it upstream (effort S, R15). **PeerTube's tracker package `@peertube/bittorrent-tracker-server` 11.1.2 has byte-identical `server.js`, `parse-websocket.js` and `swarm.js`**, so every PeerTube instance's `/tracker/socket` has the same defect for known video hashes.

**Claim 2 - other stock-server defects, all verified in code or by test:** no WebSocket ping/pong anywhere in `server.js`/`lib/server/*` (half-open sockets and ghost peers live until TCP gives up or the 20-minute LRU TTL); `ws` `maxPayload` left at its 100 MiB default (a 20 MiB message was accepted and RSS jumped to 215 MiB); one socket can create unlimited swarms and `server.torrents` entries are never deleted (grep: no `delete this.torrents`); `scrape` without `info_hash` returns every swarm and a scrape with a huge `info_hash` array is unbounded work; the library removes only the **first** `peer_id` seen on a socket when it closes, so a client that announces different peer ids on one socket leaves ghost peers for 20 minutes (`tracker/test/stock-ghost-demo.mjs`: 5 swarms with 5 peer ids on one socket, after the close 4 ghost peers remain and all 5 swarms stay in `server.torrents`); `socket.send` has no backpressure check (a slow reader makes the server buffer without limit: RSS reached 955 MiB with 4,000 sockets when my load generator could not keep up); `/stats` and `/stats.json` (on by default in the CLI) iterate **every peer synchronously** on each request (cost measured below). Fix list = the validation, quotas, ping/pong, GC and backlog cut in `tracker/tracker.mjs`; all 16 black-box tests pass (`node --test tracker/test/run.mjs`).

**What capacity means for magnet-web.** Concurrent tracker sockets ≈ visits/day × mean dwell (s) / 86,400 (the loader keeps a socket for as long as a tab is open): 10,000 visits/day at 120 s ≈ 14 sockets; 1 M visits/day ≈ 1,400. Tracker egress per connected client ≈ (offers relayed to it + answers returned) / interval. Measured offer size in a real Chromium announce is **0.69-0.74 KB** (host candidates only; add STUN candidates and expect up to roughly 1 KB, unverified), an answer about 0.5 KB. In a swarm of at least 6 peers with the stock 5 offers and every offer answered that is ≈ (5 × 0.7 + 5 × 0.5) KB / 120 s ≈ **50 B/s per socket (≈ 130 GB per month per 1,000 permanently connected clients)**; in a 2-peer swarm only one offer per announce has a recipient (measured: 7.8 KB received by a page in 3 cycles); with the count-aware policy of F7 it is a few hundred bytes per cycle, i.e. about 1 B/s. Novage plans for ≈ 38 B/s per peer ("about 100k peers inside 10 TB/month"). So a single-core Node wrapper on a 512 MB VM is more than enough for any plausible small-site workload; engine choice should be driven by **crash-safety, operations and bandwidth**, not by peers-per-core.
