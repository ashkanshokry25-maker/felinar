## 1. Summary

1. **Install friction is the first filter; HTTPS gateways are the second; then the gateway is the weak point.** Every system that asked visitors to install something stayed niche: Maelstrom (a custom Chromium fork), ZeroNet (a Python client on 127.0.0.1:43110), Beaker (an Electron browser), Pear (a runtime), Swarm Bee, Peergos (JVM server), Freenet (local node). Brave shipped native `ipfs://` in 2021 and removed it on 2024-08-22 because "less than 0.1% of users made use of this feature". The systems that reached real traffic did it through plain HTTPS gateways: IPFS public gateways served "over 614 million requests and 45TB of data to 10 million users daily" (Shipyard, 2025-07-23), but only 9.4% of requests came from browsers loading pages and 67.4% from backend scripts using the gateway as a free CDN. Then the sponsor stopped paying. ★
2. **The strongest precedent for magnet-web arrived in 2026, and so did its strongest warning.** IPFS stopped having `ipfs.io` and `dweb.link` fetch content for visitors and now hands the browser a Service Worker that fetches and verifies blocks locally (redirect started 2026-05-11, announced 2026-08-25, HTTP gateway scheduled to retire 2026-09-21). That is our architecture: static bootstrap + Service Worker + verification in the browser + one origin per site. In the same month Protocol Labs did not renew Shipyard's funding; Shipyard stopped on 2026-09-30 and the Service Worker gateway, Helia and Kubo lost their dedicated maintainers (the SW gateway still shipped v3.5.0 on 2026-10-06 and v3.5.1 on 2026-10-15 under new maintainers). The pattern works technically and is fragile organisationally. ★
3. **Why they stalled, by how many independent cases show it.** (a) **Availability is a business, not a protocol, problem** (ZeroNet "as long as at least one seeder exists", PeerWeb "Sites available while browser tab is open", Beaker "variable uptime"; paid persistence kept dying: Skynet Labs 2022-08, Cloudflare's gateway 2024-05, Scaleway pinning 2024-11-27, NFT.Storage Ltd 2025-04-16, Fleek Hosting 2026-01-31, Shipyard 2026-09-30; Arweave charges about US$81.68 per GiB one time; Swarm stamps expire; Pear needs "blind peers" that are always-on servers). (b) **No user problem solved / no stickiness** (Beaker, Maelstrom). (c) **Slow first paint and discovery** (Beaker, PeerWeb demos stuck on "Connecting to peers"). (d) **Abuse and legal exposure** (ZeroNet; Fleek and Skynet were the top two services in Web3 credential-phishing URLs in 2022; Shipyard-run gateways were 84% of Netcraft's IPFS-fronted phishing in 2026). (e) **Maintainer or funding loss** (ZeroNet's creator went silent after 2019; Maelstrom "investor problems"; Beaker solo; Skynet; Shipyard; Fleek). (f) **Security incidents on a shared origin** (six ZeroNet sandbox/wrapper/XSS fixes 2016-2019). (g) **Updates and dynamic content** (Maelstrom: "biggest limitation is dynamic content"; a new hash per version). ★
4. **What survived is HTTP-first with peers as an accelerator.** PeerTube removed its WebTorrent player in 6.0.0 ("the P2P aspect of WebTorrent is not really used") and kept WebRTC P2P under HLS; P2P Media Loader says public trackers alone handle "1,000-2,000 simultaneous viewers". When Shipyard moved 15+ IPFS project sites off Fleek (2026-01-06) it kept a plain static host in the loop (GitHub Pages) and added CID/CAR creation in CI, pinning and DNSLink. This supports the web seed (`ws=`, `xs=`) as mandatory, not optional.
5. **Mutable pointer over immutable content is universal, and every system has a different weak link in the pointer.** IPNS needs a publisher key online; DNSLink and ArNS rely on resolver honesty (ar.io: "content integrity does not by itself prove that the gateway resolved the ArNS name correctly or freshly"); eth.limo caches 5 minutes; Swarm feeds need immutable stamp batches; Maelstrom had no update path. magnet-web's signed pointer with `seq`/`exp` is at least as strong as any of them (my judgement, not a source claim).
6. **One origin per site (subdomain + wildcard TLS + Public Suffix List) is the settled answer to isolation.** IPFS removed path-gateway support in SW gateway v3 and warns "NEVER use path-only gateways for loading dapps with sensitive information"; ar.io redirects every transaction to a base32 sandbox subdomain; eth.limo and nsite hosts do the same; all of `*.inbrowser.link`, `*.dweb.link`, `*.eth.limo` are on the PSL. ZeroNet's shared-origin wrapper + iframe sandbox produced six security fixes. New detail for us: a SHA-256 (BitTorrent v2) infohash is 64 hex characters and does not fit one 63-octet DNS label; base32 (52 chars) does. ★
7. **Takedown at the edge does not reach installed Service Workers.** The SW gateway's own Bad Bits doc says: "Service workers already installed answer navigations locally, so the edge only sees a visitor's first request to a host." Any hub that serves arbitrary btih needs an in-SW revocation check and the kill switch already planned in DESIGN-REVIEW 20. ★
8. **Databases:** only ZeroNet (per-site SQLite rebuilt from signed JSON, per-user quotas) and Freenet (contract state) shipped one. Beaker's two "crawling indexer" API designs were never released, and Beaker's post-mortem says scaling a user's view past roughly 100k users "is pretty much out the window" when each device builds its own indexes. magnet-web's capped signed log is in the ZeroNet/Freenet family; the cap in the plan (50,000 blocks) is consistent with this evidence.
9. **Identity providers become centralisation and spam points** (ZeroID: the conservancy README still lists "centralized elements like zeroid"). Per-site local keys, as planned, avoid this.
10. **Reusable pieces exist** (section 5): the SW gateway's subdomain flow, kill switch and sharded denylist; DNSLink parsing rules; NIP-5A's order-independent aggregate hash; ZeroNet's `user_contents` quota and ReDoS-safe regex limits; Bugout's wire-extension gossip with signed packets; ar.io's `ario-deploy` / Shipyard's `ipfs-deploy-action` + `dnslink-action` one-command deploy shape.
11. **Top actions** (section 6): ship a pinner and make the web seed non-optional in `publish` (P0); race web seed and peers from t=0 with a first-paint budget (P0); probe every default third-party endpoint daily (P1); one origin per untrusted site with a label-length test for v2 hashes and a PSL checklist (P1); SW-resident revocation (P1); a one-command migration path with a CI action and DNS automation (P1).

## 3. Findings

### 3.1 ZeroNet

#### F1. ZeroNet: design, and how it ended up with one tired fork `[DESIGN-CRITICAL]`
**Claim.**
- *Design.* A site is identified by a Bitcoin-style address. Every site has a `content.json` listing each file with `sha512` and `size`, signed with the site key (or, for multisig, several signers); peers verify the signature before accepting an update. Discovery uses BitTorrent trackers. A built-in SQL database is rebuilt from the signed JSON files (the README says "built-in SQL server with P2P data synchronization"; Wikipedia says SQLite). Default site size limit 10 MB (Wikipedia). User-generated content lives in per-user directories governed by `user_contents` rules in `content.json`: regex-matched `permission_rules` with `files_allowed` and `max_size`, per-user bans and quotas, `cert_signers` (identity providers such as ZeroID), and `archived` / `archived_before` timestamps that delete older user directories. Regexes in these rules are limited against ReDoS (at most 255 characters, at most 9 repetition operators, a `.` before every `*`, `+`, `{`).
- *Mutability.* Same address, newer signed `content.json` (`modified`), real-time update push.
- *Local software.* Required: `zeronet.py` serves the UI at `http://127.0.0.1:43110/{address}`; the conservancy README states "The client doesn't work directly from a browser" and lists browser-direct access as a priority for the "mid-future". It also lists "no private sites, no DHT, no I2P, no reliable spam protection, no data transparency, no on-disk encryption" and "centralized elements like zeroid remain".
- *Status.* GitHub releases v0.7.0 and v0.7.1 are both dated 2019-09-06 (the changelog dates them 2019-06-12 and 2019-07-01; Wikipedia says 4 September 2019 for the last stable release). The default branch's last commit is 2021-01-25. Issue #2749 "Where did the ZeroNet creator go?" (2021-04-28) shows the community noticing the creator was silent. Forks: ZeroNetX (last release v0.8.5, 2023-02-11; pushed 2025-09-12), zeronet-conservancy (releases v0.7.9 2023-07-23 and v0.7.10 2023-07-27; pushed 2026-02-22; one maintainer; README: "Development is sparse and slow" and "0net is in deeper crisis than ever before and this fork seems to be the last one standing"). Wikipedia says EpixNet took over development in September 2025; I found no second source.
- *Why it stalled.* Creator disengagement and no governance; a public dispute between forks (issue #2823, which contains unverified allegations that I do not repeat); local-install friction; the security record (F2); spam and identity centralisation; legal exposure (F3).

**Confidence.** High for design and release facts (raw changelog, GitHub release data, README). Medium for the stall reasons: the "creator lost interest" reading rests on issue #2749 and a personal blog; no maintainer statement exists. Low for EpixNet (single Wikipedia sentence; the Medium page returned HTTP 403).
**Sources.** https://zeronet.io/docs/site_development/content_json/ (fetch summary); https://github.com/zeronet-conservancy/zeronet-conservancy (README, fetch summary); https://raw.githubusercontent.com/zeronet-conservancy/zeronet-conservancy/master/CHANGELOG.md; https://github.com/HelloZeroNet/ZeroNet (README, fetch summary); https://github.com/HelloZeroNet/ZeroNet/issues/2749 and /2823 (read through the GitHub API); https://en.wikipedia.org/wiki/ZeroNet; GitHub API repo/tag/release metadata queried 2026-10-17.
**Source date.** Docs page undated (circa 2016-2019); changelog entries 2016-2023; README and API data 2026-10-17; Wikipedia 2026.

#### F2. ZeroNet's security record: six fixes in three years, all from the shared-origin wrapper design `[DESIGN-CRITICAL]`
**Claim.** The ZeroNet changelog documents:

| Release (changelog date) | Issue |
|---|---|
| 0.4.1 (2016-09-05) | "Fix for important security problem, which is allowed anyone to publish new content without valid certificate from ID provider" (sic) |
| 0.5.2 (2017-02-09) | "Sandbox escape security fix" |
| 0.5.6 (2017-06-15) | XSS via DNS rebinding: the web interface "did not validate the request's Host parameter" |
| 0.6.3 (2018-06-26) | "Important security issue: Iframe sandbox escape" |
| 0.6.4 (2018-10-20) | "The Vacation" sandbox escape: invalid file-type detection (by extension) let a malicious site escape the iframe sandbox; affected everything before Rev3616 |
| 0.7.1 (2019-07-01) | Wrapper HTML injection: template variables rendered incorrectly, so "the opened site was able to gain WebSocket connection with unrestricted ADMIN/NOSANDBOX access, change configuration values and possible RCE on client's machine" (before rev4188; back-ported to the Python 2 line) |

Also: issue #331 (2016-03-07) "any site may call certAdd for any domain" was closed on 2016-04-09 with a confirmation dialog, not a domain check; issue #2244 (2019-10-25) Tor Browser 9.0 removed the proxy exception ZeroNet needed for localhost; conservancy 0.7.10 (2023-07-26) fixed a ReDoS in the file editor and a leak of local 0net sites to clearnet sites.
All of these follow from one design: many untrusted sites share one origin (the local UI), rendered by a wrapper page in an `iframe sandbox`, with a privileged WebSocket API next to them.
**Lesson for magnet-web.** DNS rebinding does not apply (no local server). The wrapper + iframe + privileged channel pattern does: it is our hub mode. This is independent confirmation of DESIGN-REVIEW 6 ("one origin per untrusted site"). Also: ZeroNet's `certAdd` finding is the same class as our bridge: a site must not be able to act on identity state it does not own.
**Confidence.** High (changelog text read raw; issues read).
**Sources.** https://raw.githubusercontent.com/zeronet-conservancy/zeronet-conservancy/master/CHANGELOG.md (the file embeds the original ZeroNet changelog); https://github.com/HelloZeroNet/ZeroNet/issues/331 (fetch summary) and /2244 (fetch summary).
**Source date.** Entries 2016-2023; retrieved 2026-10-17.

#### F3. ZeroNet: abuse, legal exposure and identity
**Claim.** (a) Check Point (2016-04-12) reported ZeroNet "already used for shady purposes, hosting sites which violate copyrights and sell botnets", sites stay online "as long as at least one seeder exists", and a proof-of-concept ransomware payment gateway. (b) After Cloudflare dropped 8chan (August 2019) an "emergency bunker" copy of 8chan appeared on ZeroNet; DarkOwl (updates dated 2019-08-07) reports "thousands of posts" in 48 hours and says an 8chan admin tweeted that the team had not created it. (c) A personal blog (undated, after September 2019) claims that visitors "host ALL content of that site", that illegal-content spam on that site meant users unknowingly hosted it, that posting needed a certificate and most sites whitelisted only ZeroID. I found no news or primary source for the illegal-content claim: **low confidence, do not rely on it**. The conservancy README independently lists "centralized elements like zeroid".
**Lesson.** Bound what a visitor stores to the owner-signed file list plus a capped, moderated log, and say so in the consent text. A model where every visitor replicates everything a site's users post turns every visitor into a host of legal risk.
**Confidence.** High for (a) and (b); low for (c).
**Sources.** https://blog.checkpoint.com/research/new-technologies-pose-new-threats/ (fetch summary); https://www.darkowl.com/blog/8chan-finds-new-home-on-dark-web (fetch summary); https://xianc78.codeberg.page/articles/zeronet.html (fetch summary); conservancy README as in F1.
**Source date.** 2016-04-12; 2019-08-07; blog undated.

### 3.2 Project Maelstrom

#### F4. Maelstrom: a vendor browser, static sites, and silence
**Claim.** BitTorrent Inc. released Maelstrom as an alpha in December 2014 and a public beta in April 2015. It was a closed-source Chromium fork with libtorrent. Sites were torrents addressed as `bittorrent://<infohash>` (and `magnet://`); a Python developer tool snapshotted a folder into a torrent. Updating a site meant a new torrent with a new hash; the author of the ctrl.blog retrospective found no evidence of use of the update/signing extensions (BEP 35, 39, 44). A BitTorrent product manager called "dynamic content" the biggest limitation. New clients needed a central server to bootstrap. Bram Cohen attributed the end to "investor problems". The company stopped mentioning the project after 2015; the website stayed up until October 2016. The UCD forensic paper (page 5) reports that the option to keep running background apps after Maelstrom is closed "is enabled by default", which leaves `chrome.native.torrent.exe` "sharing cached website torrent data from the user's system without any visible indicator"; defaults were a 5 GB cache, an upload ratio equal to download, no rate or transfer limits, and anonymous crash reports on; idle traffic was about 800 B/s each way (attributed to DHT updates and pings) with about 50 concurrent connections; the browser contacted `router.bittorrent.com`, `tracker.openbittorrent.com` and `bench.utorrent.com` (anonymous usage statistics with a unique id).
**Lesson.** A vendor browser cannot become the default; static-only plus new-hash-per-version is a dead end for anything dynamic; and hidden background seeding is a privacy and consent failure (our ARCH 8 consent line and visible upload switch address this).
**Confidence.** High for the technical facts (paper read in full text); medium for the stall reasons (one retrospective quoting Bram Cohen and a product manager; no BitTorrent Inc. statement exists).
**Sources.** https://markscanlon.co/papers/ProjectMaelstrom.pdf (Farina, Kechadi, Scanlon, JDFSL vol. 10 no. 4, 2015; read with pdftotext); https://www.ctrl.blog/entry/bittorrent-maelstrom/ (fetch summary).
**Source date.** 2015 (paper); ctrl.blog undated.

### 3.3 Beaker, Dat/Hypercore and Pear

#### F5. Beaker's post-mortem is the best first-hand account of why browser P2P websites stall `[DESIGN-CRITICAL]`
**Claim.** Paul Frazee archived Beaker on 2022-12-27 with a long post-mortem. Verbatim points from the notice:
- Product: "actual usage stalled. We would produce updates that improved the polish and usability of the browser, and there'd be a small bump, but no stickiness." Beaker "didn't solve a problem for people". "Beaker's MVP was a tool for making static websites ... by 2016, that was a pretty dubious value prop to people, and that's ignoring the bad time-to-first-paint and variable uptime." "Ironically, the only demographic that Beaker actually helped was teachers on a LAN."
- Adoption: "The dat/hyper sites weren't accessible in most browsers; there was no mobile browser; there was no way to safely sync state between multiple devices; the APIs weren't useful enough."
- Technology: "Without some logically centralized repository of data or router of messages, you struggle with discovery and delivery. Users don't stay consistently online and connections will randomly fail, so you struggle with availability and performance. Initial connections and thus time-to-first-paints are slow, which is very bad news for web browsing. Debugging is quite hard. Managing resource usage on the device is hard. Scaling a user's view of the network past (say) 100k users is pretty much out the window because you're not sharing indexes; rather, you're having each device build the indexes locally."
- Two "crawling indexer" API designs (JSON/Markdown published by sites, queried locally) were never released. "By 2021 Beaker was pretty dead."
- His next step: Bluesky uses "p2p structures (IPLD) on a federated network, giving us some of the key advantages of p2p like account portability while retaining the performance and reliability advantages of servers".
- A Hacker News reply thread added: "it's not about the protocol, it's about the interface" (kyledrake) and that IPFS, SSB and Dat "developed their own protocols rather than piggybacking on HTTP", which forced daemons, special browsers or gateways (boramalper).
**Lesson.** magnet-web already sidesteps Beaker's first three blockers (works in ordinary browsers including mobile, no install, HTTP web seed as the logically centralised fallback). It does not sidestep "no stickiness": a migrated existing site must be indistinguishable or better for its visitors, which is why the drop-in mode and a first-paint budget matter more than the P2P layer.
**Confidence.** High (full text of the notice read raw); medium for the HN comments (fetch summary).
**Sources.** https://raw.githubusercontent.com/beakerbrowser/beaker/master/archive-notice.md; https://github.com/beakerbrowser/beaker (archived banner); https://news.ycombinator.com/item?id=34154896 (fetch summary).
**Source date.** 2022-12-27.

#### F6. Pear / Hypercore: the ecosystem's answer to "nobody is online" is an always-on, content-blind server
**Claim.** Pear is "an installable peer-to-peer runtime, development, and deployment platform" (`curl https://install.pears.com/pear.sh | sh`) for desktop, mobile and terminal apps, not browser pages. Its docs say: "A peer-to-peer core is only available while a peer that has it is online. Blind peering closes that gap: a blind peer is an always-on server that replicates and seeds your Hypercore or Autobase without holding the read capability - it stores and forwards encrypted blocks it cannot decrypt" (`pear blind-peer start` since Pear 3.4.0; `pear seed <link> --blind-peer <key>`). File 06 records that Hypercore/Hyperswarm in a browser exist only through an experimental relay marked "Do not use it in production".

#### F16. ENS + eth.limo + DNSLink: a gateway you must trust, and the TXT rules to copy
**Claim.** eth.limo is a free, open-source gateway: wildcard DNS `*.eth.limo`; for each request it takes the ENS name from the hostname, reads the resolver's `contenthash` from Ethereum (including CCIP-read, ERC-3668), fetches from IPFS/IPNS, Arweave/ArNS, Swarm or TON Sites, and serves over HTTPS "with security headers and per-site origin isolation applied". #### F20. Bugout, P2PT and Trystero: the same wire-extension gossip, and the tracker-reliability record
**Claim.** `chr15m/bugout` (MIT) builds "browser-to-browser networking built on WebTorrent": an identifier or server public key becomes a dummy torrent (seeded `Blob` named after the identifier) whose swarm is found through WebSocket trackers (defaults `wss://hub.bugout.link`, `wss://tracker.openwebtorrent.com`, `wss://tracker.btorrent.xyz`); messages travel as a **WebTorrent wire extension** (the same BEP 10 mechanism as our `mw_chain`), are signed with `tweetnacl` (`nacl.sign.detached`), carry a timestamp that must be within a timeout window, and the first copy of each message is forwarded to all connected wires (flood gossip). README: "This is a functional prototype. It's pre-alpha quality software"; running under Node needs `wrtc`, "not that stable"; headless Chrome or Firefox "seems to work better". Last push 2024-05-08; 12 open issues (GitHub count). Issue titles show the failure modes: #42 "hub.bugout.link performance" (41 comments), #43 "Getting error connecting to tracker" (34 comments), #46 browser "takes minutes, or several page refreshes before connecting", #49 Safari 14.1.1 "makes no peer connections", #64 "Bugout does not work anymore" (2022-11), #68 build broken with WebTorrent 2.x (2023-07), #70/#72 crashes (2024). `subins2000/p2pt` (MIT, last push 2025-09-08) uses WebSocket trackers as general-purpose WebRTC signalling. `dmotz/trystero` (MIT, last push 2026-10-05) supports Nostr (default), MQTT, BitTorrent trackers, Supabase, Firebase, IPFS and a self-hosted WebSocket relay; its author ranks them: "By default Trystero uses the Nostr network which is highly decentralized with hundreds of active relays ... The other decentralized strategies are recommended in the order of MQTT, BitTorrent, and IPFS, based on robustness", and warns "Browsers can only handle a limited amount of WebRTC connections at a time".
**Lesson.** Our gossip design is the Bugout design plus a DAG and moderation, so Bugout's source is directly comparable (signed packets, timestamp window, flood-forward). Its issue list is independent evidence for 02's recommendation of a second, non-tracker discovery plane, and the dead default `btorrent.xyz` tracker appears in Bugout's defaults too.

#### F21. What survived in production: HTTP-first with peers as an accelerator `[DESIGN-CRITICAL]`
**Claim.** PeerTube, the largest deployment of WebTorrent in browsers, removed its WebTorrent player in 6.0.0: issue #5465 "Remove WebTorrent support in client in V6" (opened 2022-12-15, closed 2023-07-10) cites "many limitations of the library", "a bigger bundle size for a bad user experience" (slow start, hacky resolution changes) and "the P2P aspect of WebTorrent is not really used" because most videos use HLS. #### F22. Nostr "nsites" (NIP-5A): signed manifest, hash-addressed blobs, subdomain hosts
**Claim.** NIP-5A (status `draft` `optional`) defines static sites on Nostr: a manifest event (kind 15128 root site, replaceable; kind 35128 named site, addressable with a `d` tag of 1-13 characters; kind 5128 immutable "manifest snapshot") whose `path` tags map absolute paths to sha256 hashes; blobs live on Blossom servers (hints in `server` tags or the author's kind 10063 list). The **aggregate hash** is order-independent: collect all `path` tags as lines `<sha256> <path>\n`, sort lexicographically, concatenate, sha256, lowercase hex; two manifests are equivalent iff the aggregate hashes match. **Copying** a site into another author's namespace uses `a` (parent) and `A` (origin lineage) tags. Host servers should use one DNS label per site to avoid multi-level wildcard certificates: `<npub>.host`, `v<50-char base36 snapshot id>.host`, `<50-char base36 pubkey><dTag>.host` (DNS labels are limited to 63 characters, which is why `d` is at most 13). Hosts SHOULD verify each blob's sha256. The reference host (`hzrd149/nsite-gateway`, Deno + Hono) is a server-side gateway with `MAX_FILE_SIZE` 128 MB and a 3,600 s cache TTL. I found no client-side verifying (Service Worker) implementation.
**Lesson.** Useful details to borrow: the order-independent aggregate hash for a file manifest, snapshots as a named immutable version, copy lineage for mirrors, and the single-label hostname rule. The trust model (server gateway) is the one IPFS just abandoned.
**Confidence.** High for the spec text (raw); the NIP is a draft and may change.
**Sources.** https://raw.githubusercontent.com/nostr-protocol/nips/master/5A.md ; https://raw.githubusercontent.com/hzrd149/nsite-gateway/master/README.md
**Source date.** Retrieved 2026-10-17.

## 4. Lessons: what to copy and what to avoid

**Copy**
1. One origin per untrusted site, a single DNS label, wildcard TLS and a PSL entry for hub operators (F23). Confirms DESIGN-REVIEW 6.
2. A documented unregister URL plus an out-of-band kill switch (`?ipfs-sw-unregister=true`; DESIGN-REVIEW 20) and an in-SW revocation check, because edge enforcement cannot reach installed workers (F11).
3. The Bad Bits edge design for hub operators: a 4-byte-prefix sorted index (about 2 MB for 511k entries) in front of sharded lookups, fail-open with loud telemetry, a deploy gate that refuses to ship with an empty list (F11).
4. DNSLink's record rules: dedicated `_name` subdomain, ignore bad records, deterministic sort, CNAME delegation, about 60 s TTL, sandboxed zone for CI (F16).
5. One-command deploy shaped like `ario-deploy` and `ipfs-deploy-action` + `dnslink-action` (F12, F14).
6. Wayfinder's vocabulary for verification levels and its explicit fail-open / fail-closed policy (F14).
7. NIP-5A's order-independent aggregate hash, named snapshots and copy lineage (F22).
8. ZeroNet's `user_contents` model: per-user quotas, regex-limited path rules, ReDoS caps, `archived_before` pruning (F1).
9. A pinner: Pear's "blind peer" idea applied to public signed data (F6).
10. Origin-first, peers-as-accelerator delivery (F21).

**Avoid**
1. Hidden background seeding (Maelstrom) and unbounded "visitors host everything" (ZeroNet). Visible indicator, off switch, bounded set.
2. Path-based hubs on one origin, and HTML sanitisers as a substitute for origin isolation (ZeroNet, PeerWeb).
3. A global identity issuer (ZeroID). Keep per-site keys.
4. A single free sponsored endpoint for any role (IPFS delegated routing and bootstrap nodes, `hub.bugout.link`, `tracker.btorrent.xyz`).
5. "Uncensorable", "cannot be taken offline", "impossible to shut down" copy (ZeroNet README: "Impossible to shut down"; the Maelstrom forensic paper's abstract: "cannot be taken offline"). Say what is true: available while the web seed or a pinner is up.
6. Native-protocol UX investment (Brave) and bloated MVP scope (Beaker's own lesson: "Also, don't bloat your MVP", "mission needs PMF").
7. A local-server wrapper architecture (ZeroNet) and any privileged channel reachable from an untrusted site.

## 7. Gotchas

- **Everything about IPFS in this file is moving.** Shipyard ended 2026-09-30, Protocol Labs said it would decide the future of `ipfs.io`, `dweb.link` and `delegated-ipfs.dev`, and new maintainers took the SW gateway in October. Re-check before quoting any "current" IPFS fact in public documentation.
- **Vendor numbers are claims.** "Performance is now on par with traditional gateways" (IPFS Foundation, 2026-08-25), "99.99% guaranteed uptime" (Fleek case study), "over 75 million monthly active users" (Shipyard footer) were not independently measured here. The traffic split (F9) is a three-day sample.
- **Forum and Hacker News posts are untrusted data.** I used them only for context or flagged them low. The IPFS forum thread 20324 contains speculation (for example about funding) that I did not use; the ZeroNet issue 2823 contains unverified allegations about named individuals that I did not repeat.
- **Date conflicts are real.** ZeroNet 0.7.1 is 2019-07-01 in the changelog, 2019-09-06 as a GitHub release and 4 September 2019 on Wikipedia. I give the changelog date for code changes and the GitHub date for releases.
- **The `curl` view of ipfs.io is not a browser view.** The Cloudflare challenge on `ipfs.io/ipfs/<cid>` blocks my client; I cannot say what a browser navigation does today, only that the official page says the HTTP gateway retired on 2026-09-21.
- **A SHA-256 infohash does not fit a DNS label as hex** (64 > 63). Anything that puts a BitTorrent v2 or hybrid hash in a hostname must use base32 or base36.
- **A PSL listing is slow and checked.** The guidelines require two years of remaining registration and favour a `_psl` TXT record; submissions take time to reach browsers.
- **The SW gateway needs a wildcard certificate and edge logic**, and its own docs warn that path-only deployments give no isolation. Do not copy its simplest demo configuration into a hub.
- **A Service Worker outlives its operator.** If a hub disappears, installed workers keep serving cached sites (good for offline, bad for takedown). The kill switch must be reachable without the hub (host-served worker URL that never changes).
- **ArNS-style name resolution without signatures trusts the resolver.** Our DoH path is only as good as the pointer signature plus `seq`/`exp`; keep those mandatory in hub mode.
- **Arweave's price is dynamic.** US$81.68/GiB is the 2026-10-17 snapshot from Turbo's rates endpoint, not a guarantee.
- **Documentation URLs rot.** The ZeroNet `content.json` docs page is from the 2016-2019 era; the Skynet Labs site returned 403; `peercloud.io` has no A record; several Medium pages returned 403. I used raw GitHub files wherever possible.
- **No code in this repository was changed, and no browser or phone testing was done for this file.**

## 8. Open questions

1. Who operates `ipfs.io`, `dweb.link`, `delegated-ipfs.dev` and the bootstrap nodes after 2026-09-30, and does `inbrowser.link` have a funded long-term operator? Netcraft says Protocol Labs made no commitment.
2. How much faster than a web-seed-only load is a peer-assisted load for a small site with few visitors? No published data exists for WebTorrent sites; a pilot with three real sites and the R2 telemetry would answer it.
3. Does an apex-hosted Service Worker bundle get re-downloaded for every PSL-listed subdomain (HTTP cache partitioning)? My inference says yes; test with a two-subdomain page and the network log.
4. What first-paint budget is realistic on an LTE phone? The Beaker notice and the HN reports say "slow"; nobody quantifies it.
5. Is there demand for a DNSLink-compatible alias (`dnslink=/btih/<hex>` or similar) so that existing DNSLink tooling can publish our pointer? The spec allows any namespace; untested with the tools.
6. What happened to ZeroNet's network size, and is EpixNet real? Wikipedia mentions it once; I could not read the Medium piece or find a repository.
7. How does `freenet.org/try` work technically (a hosted peer? a gateway?), and what does it do about served-code trust beyond "export to your own peer"?
8. Does any client-side verifying nsite implementation exist? I found only the server-side gateway.
9. Which BitTorrent namespace, if any, would multiformats accept for ENS-style pointers? The multicodec table has none today.
10. What legal basis do hub operators use for `451` takedowns, and what do browsers' Safe Browsing programmes do with PSL-listed hub subdomains? Not researched.
