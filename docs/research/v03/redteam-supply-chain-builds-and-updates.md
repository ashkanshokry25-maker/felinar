# Red team: supply chain, builds and updates

- **Date:** 2026-10-20. **Scope:** magnet-web 0.2.1 plus the v0.3 proposals (IDENTITY-AUTH-DESIGN, REALTIME-AND-FILES-DESIGN, and the cross-site sign-in addendum). Read-only review; nothing else was changed. Nothing was run or built (no Node on this shell's PATH), so every behaviour below is read from files, and anything that needs a run is marked 'needs measurement'.
- **Labels:** works today / works against the proposal / blocked by / needs measurement.
- **Why this class matters more in v0.3:** today the loader holds a throwaway guest key. In v0.3 the loader origin holds a root that derives every site key, the sealed-record keys and the chat keys, and the cross-site addendum makes that root the sign-in for other people's servers. Whoever controls the bytes of the loader controls all of it. The design says so for host compromise (IDENTITY 6.5) but never for the build and release path that produces those bytes.

## What already stops things (credit where due)

| Control | Where | Stops |
|---|---|---|
| Install scripts off, one allow-listed | `.npmrc:4`, `package.json` allowScripts | a planted `postinstall` in this repo's CI and dev installs |
| Stock and patched webtorrent pinned by sha256; every patch must match exactly once | `build.lock.json`, `build.mjs` `applyVendorPatches`, `checkLock` | silent change of the vendored file in `node_modules`; a moved patch point |
| Actions pinned to full SHAs, `permissions: {}` at workflow level, `persist-credentials: false`, no secrets, release job runs no repo code | `release.yml:23,37-46,133-162` | tag-moving attacks on third-party actions; token theft from build steps |
| SRI on boot.js and loader.js; worker embeds sha384 of precached JS and CSS and refuses a mismatched install | `build.mjs` `applySri`, `integrityMap`; `sw.js:6-20` | a CDN or edge that corrupts a single file after the SW is installed |
| Tag must equal package.json version; CHANGELOG heading required | `release.yml:52-63` | accidental tag |
| Pointer `seq` floor | DEPLOY.md Rollback | rollback of site content (not of the loader) |

## Attacks

### SC-1. Forged or swapped release: unsigned `SHA256SUMS` next to the zip, replaceable by design (works today; works against the proposal) - blocker

- **Preconditions:** write access to the release (a stolen maintainer session or token, a compromised lead-maintainer account; GOVERNANCE.md:26 has one lead maintainer holding repository settings, and the first release has one maintainer, GOVERNANCE.md:34) or the ability to push a `v*` tag.
- **Actions:** (1) Re-run the release workflow or call the API: `release.yml:155-157` does `gh release upload --clobber` on an existing release, so files of a published release are replaceable with no new tag and no review. (2) Upload a trojaned `magnet-web-0.2.1-dist.zip` and a matching `SHA256SUMS`; both live in the same release, so the sums have the same trust root as the zip (SECURITY-MODEL.md:162 admits this: "catches a damaged download but not a forged one"). (3) Alternatively force-push the tag to a malicious commit; the job only checks that the tag name matches `package.json` (`release.yml:57`), and nothing requires an environment with reviewers.
- **Gain:** the zip is what owners copy onto their own hosts (ROADMAP.md:114: "owners copy `dist/` onto their own hosts"). A trojaned `loader.js`/`mw.js` sees the root, the phrase typed into the restore card, the unwrapped site keys, PRF output and chat plaintext, on every site that deploys it, and the SW then pins the trojan (SC-6).
- **Harm and scale:** every visitor of every site that deployed the release; persistent, because a stolen root cannot be rotated (SC-5). One compromise, N sites.
- **Verifier today:** can rebuild from the tag and compare `dist/build.json` hashes. Almost no owner will; the zip is the documented install path (DEPLOY.md).
- **Cheapest defences:** (a) GitHub immutable releases and a tag ruleset (no force-push, no delete, restricted creation); remove `--clobber` and fail if the release exists; (b) put the release job in an environment with a required reviewer who is not the pusher; (c) `actions/attest-build-provenance` in the release job (needs `id-token: write` and `attestations: write` there only) and document `gh attestation verify`; (d) a maintainer-signed (minisign or sigstore) `SHA256SUMS` whose public key is pinned in the README, SECURITY.md and a second place the repo owner does not control (a DNS TXT or a separate account). Cost to honest users: one extra command at install; none at runtime. Cost to the project: a second maintainer or a hardware-key ceremony. Until (a)-(d) exist, the v0.3 sign-in must not be called safe to use on a site the visitor does not already trust.

### SC-2. Malicious update of a dependency or of the vendored bundle that the patch gate cannot see (works against the proposal; some parts needs measurement) - blocker

- **Preconditions:** the attacker publishes a hostile `webtorrent` 3.0.x (maintainer takeover, as in past npm incidents) whose `dist/webtorrent.min.js` still contains the five patch strings and `_onMessageLength(`.
- **Actions:** Dependabot opens a weekly PR (`.github/dependabot.yml`, no cooldown). `npm ci` plus build fails the lock check, and the failure message itself tells the maintainer what to do: "read its changelog and diff the bundle, then run: node build.mjs --update-lock" (`build.mjs` `checkLock`). The bundle is a 222,929 byte minified single line (`build.lock.json`); a diff of it is not reviewable by one maintainer (GOVERNANCE.md:49: "One maintainer, after discussion"). `--update-lock` re-pins whatever is there.
- **Why the gates do not stop it:** the gates prove "same bytes as last time", not "bytes that correspond to source". The file is a prebuilt artifact the upstream maintainers uploaded; it is not built from the repo's lockfile. Whether webtorrent publishes with npm provenance is not checked anywhere: needs measurement.
- **Why it is worse in v0.3:** the bundle runs in the same realm as the loader code that unwraps the root (IDENTITY 3.3: root unwrapped "only in loader code" is a function boundary, not a realm boundary). Hostile bundle code can wrap `crypto.subtle.importKey/sign/deriveBits`, `navigator.credentials.get` and `JSON.stringify`, and read plaintext chat before encryption and plaintext file bytes. In drop-in mode the realm is the host page.
- **Also:** new runtime packages in the loader. Today `src/` imports no bare npm module (checked by grep); the design adds `@noble/curves` and `hash-wasm` (IDENTITY 1 bullet 2, 3.3), and `hash-wasm` embeds a wasm blob. esbuild bundles them into `_mw/loader.js` and `_mw/mw.js`; `build.lock.json` pins only the webtorrent file, so these are covered by `package-lock.json` integrity alone, which proves "the registry tarball I locked", not "the source I reviewed". Opaque wasm cannot be reviewed from the bundle.
- **Cheapest defences:** (a) `cooldown` in dependabot (for example 14 days) and an npm minimum release age on installs; (b) extend `build.lock.json` to every package bundled into `_mw/*.js` (sha256 of each resolved tarball plus a reviewed-by note), failing the build on any bare import not in the lock; (c) prefer no wasm: vendor noble source and use WebCrypto Argon2-free KDF choices, or build hash-wasm from source in CI with the toolchain pinned; (d) two-person rule for any change to `build.lock.json` (CODEOWNERS plus required review); (e) the roadmap's own bundle built from source (ROADMAP.md:104) moved ahead of v0.3 identity, because the identity trust boundary depends on it; (f) isolate webtorrent in a Worker or sandboxed frame that only ever sees ciphertext and has no access to the unlocked keys (Safari support for WebRTC in workers: needs measurement). Cost: (a)-(d) a few days' delay on dependency fixes (a security fix can bypass by an explicit override); (e)-(f) real engineering and, for (f), a performance and compatibility cost.

### SC-3. The npm tarball installs without the lockfile and without `ignore-scripts` (works today) - major

- **Evidence:** `package.json` `files` lists `bin/`, `src/`, `tools/`, `build.mjs`, `build.lock.json`, `test/e2e/browser-args.mjs`. `.npmrc` and `package-lock.json` are not in it, and there is no `npm-shrinkwrap.json`. The release ships `magnet-web-<v>.tgz` and tells people to `npm install -g ./magnet-web-<v>.tgz` (`release.yml:88`).
- **Actions:** the owner's install resolves `bittorrent-tracker ^11.2.3`, `create-torrent ^6.1.3`, `parse-torrent ^11.0.24`, `webtorrent ^3.0.21` (and their transitive tree) fresh from the registry, with the owner's own npm settings, so install scripts of any new transitive version run. A hostile version published an hour earlier is taken.
- **Gain and harm:** code execution on the machine that holds the owner key (`keygen`, `--key owner.jwk`, `ledger-admin`) and, in v0.3, moderator and recover keys. That is the site's authority root, and the owner key never leaves that machine only if that machine is clean.
- **Cheapest defence:** ship `npm-shrinkwrap.json` in the package, set `ignore-scripts` guidance in the install command (`npm install -g --ignore-scripts ./x.tgz`), and make the tools run without the heavy dependencies where possible (publish needs `create-torrent`; the keygen does not). Cost: none for honest users beyond a longer command.

### SC-4. The new server-side verification library and the npm name (works against the proposal) - blocker

- **Preconditions:** the proposal publishes a small Node and browser `verifyLogin` library that servers run (task addendum; IDENTITY 4.1 describes it as pure). Today nothing is published to npm (`release.yml` header: "Nothing here publishes to npm"; `package.json` `private: true`).
- **Actions:** (1) Name squatting: register `magnet-web-verify`, `mw-verify`, `@magnet-web/verify`, `magnet-web-auth` and one-character variants before the project does; distribute a copy that returns true when the signature matches any key in the proof or skips the `aud` check. (2) Account takeover of the real publisher after launch. (3) Adding publish to CI means a publishing credential or trusted-publishing `id-token: write`, which breaks the invariant that the release job "runs no repository code" (`release.yml:9-11`) if the job that publishes is the job that builds.
- **Gain:** authentication bypass on every server that adopted it, without touching any visitor's device, and silent: servers believe they verify. Phishing-grade harm for the bearer-style proofs (IDENTITY 4.1 'bearer').
- **Cheapest defences:** reserve the names and the scope now; zero runtime dependencies and under about 300 lines so a server can vendor the single file instead of installing; publish only through npm trusted publishing with provenance from a protected environment, in a separate job from the build; publish test vectors and a conformance suite so a server can test its copy (a copy that accepts the negative vectors fails); print the file's sha256 in the spec; no `postinstall`. The format itself should include a version and a fixed `t` so an attacker cannot make the library accept a proof of another type. Cost: the project owns an npm org and a second publishing path.

### SC-5. A captured root is permanent: the phrase typed into any loader copy (works against the proposal) - blocker

- **Preconditions:** any loader copy the attacker controls. Owners deploy their own copy of `dist/` on their own origin and anyone can fork and host a modified one (SC-1 is one route; a lookalike site serving a patched but honest-looking loader is another). The visitor cannot tell which build runs: `dist/build.json` is on the same host, and no check ties it to anything outside the host (SECURITY-MODEL.md:46: the host "is the trust root").
- **Actions:** the design makes the 12-word phrase "entered only in loader UI" (IDENTITY 3.5). Restore, "use on another device" and "use the same identity here" all end in a phrase or hand-off typed into a loader the person has no reason to distrust. The root then derives every siteSeed (3.1) and `recoverKey`.
- **Gain:** all current and future site keys of that person, all sealed records the person ever wrote, the ability to `rotate` (D-10) the victim away from every site using `recoverKey`, and to read chat history. The per-site derived keys that give unlinkability do nothing here: the root is above them.
- **Today's mitigations do not apply:** D-10 `rotate` rotates a site key, not the root; there is no root revocation. Without D-10 it is "a new identity" (IDENTITY 9, compromised site key).
- **Cheapest defences:** (a) never need the phrase on a site: make the passkey and the QR hand-off the cross-device routes and show a blunt warning on the phrase field; (b) a loader self-check card: show the build id, its sha256 manifest hash and a link to the release attestation; the card the visitor enters a phrase into compares the running build against a manifest signed by the project key, delivered over the swarm or a second origin the host does not control (cost: an extra fetch, and a build that is not on the list shows a warning, which will annoy owners who patched their copy; that is the point); (c) a dedicated identity origin run by the project for phrase entry only, the design's own 'fix that works' (IDENTITY 6.5, R5 F7 fix 4), which becomes necessary rather than optional once identity is a sign-in for other people's sites; (d) root rotation as a first-class op, with a notice at every site the person has a key for. State this in the user-facing text: the phrase is safe only on a loader whose build you have verified.

### SC-6. The Service Worker pins the attacker's loader and the kill switch does not remove stolen secrets (works today as a persistence property; works against the proposal)

- **Actions:** a hostile `mw-sw.js` is served once (compromised host, CDN edge, or SC-1 deploy). The browser registers it with `updateViaCache: 'none'` (`boot.js:566`, `swreg.js:357`), so it persists and is served first on every later visit until the host serves a different `/mw-sw.js` and the browser next checks it. The embedded hashes (`sw.js:6-20`) are the attacker's own hashes: the SW is its own integrity root.
- **Trust of first load:** the drop-in tag has no SRI and cannot get one (`tools/publish.mjs:95`: `<script data-cfasync="false" type="module" src="/_mw/mw.js" async>`; hosts that rewrite bytes would break a hash, DEPLOY.md:187), so the first visit, which is where sign-in cards appear first, runs unverified bytes. SRI on `boot.js` and `loader.js` helps only against the edge, and the host also serves `index.html`.
- **Kill switch:** it unregisters and clears `mw-*` caches but leaves IndexedDB alone (`kill-switch.js:5-8`, DEPLOY.md:596). That is right for recovering saved sites and wrong after a compromise: the wrapped root, the derived signing keys and the vault stay in the origin, exposed to whatever page loads next, and anything the hostile code already exfiltrated is not recalled. The documented alternative `Clear-Site-Data: "storage"` deletes "visitors' posting identities" for good (DEPLOY.md:592-594), which in v0.3 means the local root, the vault and unsynced records, recoverable only from the phrase or file.
- **Attacker use of the kill switch as an update channel:** anyone who controls `/mw-sw.js` for ten minutes can push the kill switch to make every returning visitor reload (annoyance), or push `Clear-Site-Data` headers to destroy every visitor's local identity (denial of service against people who never made a backup; the design backs up only after "the first thing worth keeping", IDENTITY 3.5). Both need host control, which is already the stated trust root, so this is a harm-amplifier, not a new entry.
- **Downgrade:** there is no minimum loader version. DEPLOY.md's rollback advice ("deploy the previous loader build and purge the CDN") is also an attacker's tool: a stale edge or a host owner can serve a 0.2.1 loader against v0.3 data (wrapped roots, sealed records). The pointer `seq` floor covers site content only. Whether an old loader mishandles `mw-id` stores is not tested: needs measurement.
- **Cheapest defences:** (a) after a compromise runbook step: a second 'purge' worker mode that deletes the origin's identity store only on the owner's explicit request (separate file, so a mistaken deploy cannot wipe) and keep it out of the default kill switch; (b) a persisted `maxSeenBuildFloor` in IndexedDB plus a signed `minLoader` field in the pointer, so a newer loader refuses to be replaced by an older one; (c) prompt a backup before the first sealed write so `Clear-Site-Data` is survivable. Cost: a field in the pointer and one more state item to test.

### SC-7. Drop-in widget as a third-party script (works against the proposal) - major

- **Cases:** (i) The widget is copied from `dist/` to the site's own `/_mw/mw.js` today, which is the right shape. The cross-site addendum invites (ii) a shared-CDN tag (`<script src="https://cdn.jsdelivr.net/npm/...">` or a project domain), floating on a version range, or (iii) a loader-owned sign-in card for server-backed sites whose own scripts and tag managers share the origin.
- **Actions:** for (ii) a compromise of the CDN package or the version range pushes code into every adopting site's origin at once, with the owner never deploying anything; the site owner's SRI would pin one version but owners rarely add SRI and the existing tag has none. For (iii) any other script on that page (analytics, ads, a package in the host's own bundle) is in the widget's realm; the panel's closed shadow root is not a security boundary (IDENTITY 6.5 says so in words). On a server-backed site that is the site's whole front-end dependency tree.
- **Gain and scale:** (ii) unbounded across sites with one change; (iii) per-site, but the person's root is the same root, so one poorly kept site can be the thief for all (SC-5).
- **Cheapest defences:** ban the shared-CDN form in docs and tooling (the publish tool already copies the runtime to the site's own origin); require `integrity` on the documented tag when the host does not rewrite bytes; for server-backed sites, run sign-in in a framed identity origin (SC-5c), so the host page sees only a signed proof; the proof format should carry the build id of the signer so a server can refuse proofs from unknown builds. Cost: one extra frame and a postMessage hop; build-id allow-lists need server owners to update them (a staleness cost).

### SC-8. Reproducibility: what a verifier can and cannot check (needs measurement; partly works today)

- **Good:** `build.json` carries no timestamp and lists hashes; `build.lock.json` pins inputs; the release job sets file times to the commit time and sorts the file list (`release.yml:110-114`); CI proves reproducible *example publishing* by double-packing (`ci.yml`, job `pack`).
- **Gaps:** (1) No CI job builds `dist/` twice, on different runners or operating systems, and compares; the claim "builds are reproducible" in `build.mjs` is untested across platforms (esbuild is a per-platform native binary; the output is expected identical but unmeasured). (2) The zip is the signed unit (`SHA256SUMS`), and zip bytes depend on the `zip` tool version on `ubuntu-latest`, which is unpinned; a verifier on macOS who rebuilds gets the same files but a different zip hash, so "compare the release files with a build of that tag" (SECURITY-MODEL.md:163-164) will report a false mismatch and teach people to ignore the check. The unit to verify is `dist/build.json` and per-file hashes. (3) `npx playwright install` and `ubuntu-latest` mean the test step is not hermetic, which only matters if tests gate release; they do. (4) Node is pinned to `24` by `.nvmrc` (major only), and the Node patch level can change esbuild's JS-side behaviour; unmeasured.
- **Attack this allows:** a trojan injected at build time (a hostile esbuild or a dependency of the build) produces a different `dist` than a clean rebuild would; nobody rebuilds, and if they do the zip hash disagrees even for a clean build, so the signal is lost. 
- **Cheapest defences:** a CI job that builds on two OS runners and diffs `dist/` file hashes; publish the per-file hash list (`build.json`) as the thing signed and attested; pin the runner image and the `zip` version or ship a tar with a fixed mtime and sorted entries, and document a one-command verifier (`node tools/verify-release.mjs <zip>` that rebuilds and compares per file). Cost: some CI minutes.

### SC-9. CI/CD surface (mostly blocked; two gaps)

- **Blocked by:** SHA-pinned actions, no secrets, `permissions: {}` and per-job read, `persist-credentials: false`, no `pull_request_target`, forks run `ci` with read-only tokens (`ci.yml` triggers `push` to main and `pull_request`).
- **Gap A (works today, limited):** `pages-demo.yml` deploys on every push to `main` with `pages: write` and an OIDC token; whoever can push to `main` (one maintainer, no stated branch protection in the repo files; PUBLISH-CHECKLIST.md:574 leaves it to the plan) deploys code to the project's public demo origin, which is where first-time users will try the identity feature. Demo-origin compromise is a sign-in phishing platform with the project's name. Defence: branch ruleset requiring review, deployments environment with reviewer, and keep the demo's identity store separate from any 'real' deployment origin (it is, by origin).
- **Gap B (needs measurement):** Dependabot groups `esbuild`, `playwright` and `http-server` in one weekly group; a single merge updates the build tool that produces every shipped byte. Review burden is real; with `cooldown` and a required second reviewer it is acceptable. `esbuild@0.28.2` is the one dependency whose install script is allowed to run in CI (`allowScripts`), so a hostile esbuild patch release runs code in the build job before any gate: CI has no secrets and read-only token, so the harm is a poisoned `dist/` (SC-1, SC-8), not credential theft.

### SC-10. Spec and library drift on the sign-in format (works against the proposal) - minor

- The addendum's format is "SIWE-shaped". Two or more implementations (browser loader, Node library, a community port) that disagree on canonicalisation, `domain` versus `aud`, or clock tolerance create exploitable differences: a proof valid for site A accepted at site B because a port skipped `aud`. `canonical(c)` is not specified byte for byte in the design (IDENTITY 4.1). Defence: a normative canonical form (for example RFC 8785 JCS), an `aud` check that is mandatory in the library API (no default), and the shared negative vectors of SC-4. Cost: a stricter spec.

## Residual exposure that cannot be removed (state it in user text)

1. The party that controls the bytes of the loader on an origin can take the person's keys on that origin. A project-signed manifest and attestations let a careful person detect a wrong build; they do not help a person who does not look.
2. Without a project-run identity origin, the phrase is only as safe as the loader copy it is typed into.
3. A stolen root has no revocation in the proposal.

## Ordered fix list (cost to honest users in brackets)

1. Immutable releases, tag ruleset, no `--clobber`, reviewer environment, provenance attestation, signed per-file hash list (one command at install).
2. Dependabot cooldown, second reviewer on `build.lock.json`, lock every bundled package, no wasm blob (days of delay on updates).
3. Ship `npm-shrinkwrap.json` and `--ignore-scripts` install guidance (none).
4. Reserve npm and PyPI names, publish the verify library with provenance, zero dependencies, vendorable single file, conformance vectors (none).
5. Loader self-check card and signed build manifest; identity origin before the cross-site sign-in ships; root revocation op (one frame, one extra fetch).
6. Loader version floor in the pointer and IndexedDB; keep `Clear-Site-Data` out of default runbooks; backup nudge before first sealed write (a pointer field).
7. Cross-OS rebuild job and a `verify-release` tool (CI minutes).
