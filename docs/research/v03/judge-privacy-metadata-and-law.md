# Judge: privacy, metadata and law lens on the v0.3 identity and realtime proposals

- **Date:** 2026-10-20. **Judged:** [IDENTITY-AUTH-DESIGN.md](IDENTITY-AUTH-DESIGN.md) (cited as ID) and [REALTIME-AND-FILES-DESIGN.md](REALTIME-AND-FILES-DESIGN.md) (cited as RT), against the goals in [DIFFERENTIATORS-AND-WHY.md](DIFFERENTIATORS-AND-WHY.md) and [PRIVACY-UPGRADES.md](PRIVACY-UPGRADES.md) (cited as PU), the owner's addition of 2026-10-20 about 08:25 ET (one root identity usable on every magnet-web site, on existing sites through the drop-in widget and on server-backed sites through a published challenge format and a verification library), and the current spec ([PRIVACY.md](../../PRIVACY.md), [SECURITY-MODEL.md](../../SECURITY-MODEL.md), `src/chain/block.js`, `src/chain/state.js`).
- **Lens:** what peers, trackers, STUN, DoH, relays and the host learn; linkability across sites and devices; what the ledger keeps forever; erasure and controller roles under GDPR, UK GDPR, Quebec Law 25 and PIPEDA; age and digital-ID law; seeders' and the owner's exposure for shared files; consent texts; sentences that overstate privacy. Not legal advice; every legal point below is for counsel.
- **Method:** every guarantee in both proposals was attacked. Only problems with a concrete failure scenario are reported. Numbers come from the proposals or the code they cite; no new measurement was made.
- **Wording:** "no backend", "site ledger". This file adds no figure that lacks a source.

## 1. Verdict in one paragraph

Both proposals are unusually honest about IP exposure, same-origin code and per-site erasure, and most of their residual tables are right. They fail this lens in three places that block shipping. First, the recovery root is unwrapped inside the loader of whatever site the visitor is on, and that loader is served by the site's own host (SECURITY-MODEL: "the host is the trust root"), so one hostile or compromised site obtains the visitor's identity, sealed records and recorded direct messages on every other site. Second, the owner's 08:25 requirement (one root, any site, server-backed verification, an explicit "use the same identity here") is not designed at all, and the obvious ways to build it break the one privacy property the design rests on: key derivation is keyed by a ledger id that the page itself declares, so any origin can ask for another site's key. Third, a cross-site sign-in drawn inside the site's own page has no trusted UI, so the restore flow trains people to type their 12 words into whatever page draws the card. Below those, ten major gaps: chat keys derived from the phrase (deleting or rotating a key does not protect old messages), signed and therefore provable private messages, holder and tracker metadata that reveal who talks to whom, permanent public membership and chat-key lists, the erasure and international-transfer gap, a false "nothing is sent anywhere" card, seeding defaults that put visitors' IP addresses next to content they did not create, defaults that are not the most private, cross-site tracking by the shared default trackers and STUN servers, and a list of user-facing sentences that overstate privacy.

## 3. Blockers

### B1. The recovery root is unwrapped in code served by each site's host (ID 3.3, 3.5, 6.5, 9; owner's 08:25 requirement)

- **Problem.** ID 3.3 stores the root in IndexedDB `mw-id` "(loader origin)" and unwraps it "only in loader code"; `K_rec`, `K_vault` and `K_name` are derived from the unwrapped root on demand. On a per-domain or drop-in site the loader is served by that site's host, which SECURITY-MODEL names the trust root ("serve any code to anyone ... nothing technical"). The root is not per site: it derives every site's signing key, chat key and record key (ID 3.1). The restore paths (phrase, file, "link everything" QR in ID 3.5 step 3) put the whole root into whichever origin the visitor is on.
- **Failure scenario.** A visitor uses their identity on a support forum and on a hobby site run by someone else. The hobby site's host is compromised (or its owner is hostile) and ships a loader that posts the unwrapped root to itself at the next unlock. The attacker now derives the visitor's keys for the support forum's ledger id (public), signs posts there as the visitor, decrypts every sealed record the visitor ever synced to any ledger (all public ciphertext), and, with chat keys also derived from the root (M1), decrypts every direct message anyone recorded. ID 9 lists "Malicious owner ... can exfiltrate after unlock" and 6.4 says hostile code "can read" this site's record; both understate it: the loss is every site, past and future.
- **Why blocker.** It is a security hole, and the summary bullet "Sites cannot match a visitor by key" and the PU sentence "Nothing in magnet-web ties your identities on two sites together unless you choose to link them" mislead while it stands.
- **Fix.** (1) A site origin never holds the root, only its own `siteSeed` (wrapped by a passkey for that RP ID, by a passphrase, or for the session). (2) The root lives only in an identity agent that no site controls: a browser extension, an installed app, or a single identity origin opened as a top-level window (not an iframe, see B2), which derives `siteSeed` for the origin the browser reports and hands only that seed over. (3) Phrase and file restore happen only in that agent; on a site origin, "I already have one" means passkey, QR of one `siteSeed`, or a hand-off from the agent. (4) Remove the "link everything" QR option from site origins. (5) Until the agent exists, say on the sign-in card: "Your 12 words open every site. Enter them only in <agent>, never on a site." and do not ship phrase entry on site origins.

### B2. The cross-site identity the owner asked for is not designed, and the obvious builds break unlinkability (ID 2 non-goals, 3.1, 4.1; owner's 08:25 requirement)

- **Problem.** ID 2 lists "cross-site identity by default" as a non-goal and specifies no published challenge format for server-backed sites, no Node verification library, no drop-in flow for sites that are not magnet-web sites, and no "use the same identity here" choice. Three properties of the current design make the naive builds unsafe:
  1. **Derivation is keyed by a self-declared ledger id.** `siteSeed = HKDF(root, info = "seed|" + ledgerId)` and ID 3.1 chooses "per ledger id, not per origin" so mirrors share a key. A ledger id is public, and anyone can mirror a public ledger. Whatever code tells the deriver "this is ledger X" gets the visitor's key for X.
  2. **A shared identity origin in an iframe meets storage partitioning.** Current Chromium, WebKit and Firefox partition third-party storage by top-level site (browser vendor documentation; not re-checked in this pass), so an `id.` origin framed on site A and on site B sees two empty stores, unless the design moves to a top-level window, an extension, or the Storage Access API with a prompt per site.
  3. **A single identity origin is itself the tracker.** If one origin derives keys for every site, its host sees every sign-in on every site with IP and time: the identity-provider failure PU F9 says magnet-web removes.
- **Failure scenario.** A server-backed site M integrates the published widget and tells it `ledger = <ID of site V>` (or for a server-backed V, `origin = https://v.example`). If the deriver trusts that input, M receives the visitor's V public key (cross-site linkage, defeating R3 F21) and a signature by it; with B1 unfixed, M can sign as the visitor on V. Separately, a naive "use the same identity here" that writes an `mw.link` item (ID 3.7 uses that pattern for migration) publishes a permanent, unredactable cross-site link in a public ledger (control-op and entry fields never redact, `block.js` lines 8 to 16).
- **Why blocker.** The owner made this a requirement; shipping v0.3 as written either omits it or invites one of the unsafe builds, and the phrase "one root identity per person, usable on any site, sites cannot link you" would mislead.
- **Fix (spec to add as ID section 4.4 and a new `src/identity/verify-node.js`).**
  1. **Bind derivation to what the browser verifies, like a WebAuthn RP ID.** The agent derives from the requesting origin it observes (`event.origin` or the extension's sender URL), never from a page-supplied string. For magnet-web mirrors, derive from the ledger id only when the origin appears in an owner-signed origin list in that ledger's pointer (the same idea as Related Origin Requests, ID 3.4). Server-backed sites: derive from the registrable domain plus an optional site-published label in `/.well-known/mw-id`.
  2. **Challenge format for servers:** `{ v, t: 'mw-login', domain, aud (origin), ledger? , pub, nonce (from the server, at least 16 bytes), iat, exp, statement, scope }`, signed under the existing `"mw-login-v1\n"` prefix. The library rejects a `domain` that is not the server's own, a nonce it did not issue or has seen, and an `exp - iat` above the server's limit; it never trusts `pub` without the signature. Vectors in `test/vectors/login.json` for Node and two browser engines.
  3. **"Use the same identity here"** = the agent signs with the other site's existing key for this origin, after a card naming both sites and saying "Both sites will be able to tell this is you. This cannot be undone once this site has seen it." Nothing is written to any ledger unless the person separately asks for a public link, which gets its own card ("public and permanent").
  4. **The agent's own host must learn nothing:** the agent ships as an extension or an installable static bundle with a pinned hash; if it is a hosted origin, the docs name its operator as a recipient of IP and the list of sites in the register (section 5).
  5. Add rows to ID 9: "relying party supplies another site's label", "agent host as tracker", "same-identity link replayed by a third site".

### B3. A sign-in card drawn inside the site's page is not a trusted UI, so the restore flow is a phishing flow (ID 3.5, 4.3, 9 row 1, 11 drop-in widget)

- **Problem.** ID 9 mitigates phrase phishing with "phrase only in loader UI". In drop-in mode the panel is a closed shadow root inside the site's own realm (ID 11; SECURITY-MODEL row "Site code taking the visitor's identity"), and in shell mode the loader is the host's code. For the 08:25 requirement on existing and server-backed sites, the "loader-owned card" is drawn by code that the site serves. A site can draw an identical card. The cross-site design makes typing the phrase the normal path on every new site ("I already have one": phrase, ID 4.3).
- **Failure scenario.** A visitor signs in seamlessly on three sites, then meets a fourth site with a pixel-identical "Sign in with your magnet-web identity: I already have one, enter your 12 words" card. They have done this before on legitimate sites (each new origin had no stored root), so they type the words. The fourth site now holds every identity (B1). The "No one will ever ask you for these words" line is contradicted by the product's own flow on every new site.
- **Fix.** Same as B1: never accept the phrase or the backup file on a site origin. On a new site the only routes are passkey (if a seed was already wrapped for that RP ID), the agent, or a QR showing a single `siteSeed`. Card copy: "magnet-web never asks for your 12 words on a website. If a site asks, it is not us." Test: E-10, the drop-in panel and the shell expose no phrase field on any origin except the agent.

## 4. Major findings

### M1. Chat keys are derived from the phrase, so deletion and rotation protect nothing (ID 3.1 `chatKey`; RT 5.2, 5.3 "honest limits", 5.7, Principle 3)

- **Problem.** `chatKey = HKDF(siteSeed, "chat|" + e)`. RT 5.2 says "old private halves stay on the device to read old held mail until the visitor deletes them" and RT 5.3 says anyone "who later obtains the recipient's chat private key" can read kept envelopes. Every epoch's private key is a pure function of the 12 words and a counter, so deleting it or rotating does not remove it, and there are no forward-secrecy-like properties even at 90-day granularity. RT Principle 3 calls everything conversational "ephemeral in the swarm".
- **Failure scenario.** A lane recorder keeps every ENV frame for a year. The visitor later loses their phrase to phishing (B3) or a seized paper backup. Every direct message ever sent to them on every site, at every epoch, decrypts.
- **Fix.** Make chat keys random per epoch, wrapped under `K_vault` and included in the encrypted backup, so deleting an epoch key really retires it (the phrase-only restore loses old held mail, which is the right trade). State: "Messages are not stored by the site, but anyone connected can record the encrypted copies. Until you delete a chat key, those copies can be read by whoever gets your key or, for the current design, your 12 words." Drop "ephemeral" from RT Principle 3 and replace it with "not stored in the site ledger".

### M2. Private messages, room messages and peer login proofs are signed, so they are provable to third parties (RT 5.3 `sig`, 5.5 ROOM, 4.2 CHAL/RESP; ID 4.1 challenge-response)

- **Problem.** Every DM carries an ECDSA signature over ledger id, recipient key, id, time and body hash; signKey is public in the ledger. Binding the recipient's `ek` stops re-addressing, not disclosure: the recipient (or anyone who later gets their key, M1) can show plaintext plus signature to anyone, who can verify the sender wrote it. ROOM frames are signed plaintext relayed four hops. Peer login proofs (`chan: [idA, idB]`, time) are transferable evidence that a key was online with a given peer at a given time. This is the opposite of what people expect from "end-to-end encrypted chat" and matters for leaks, coercion and court discovery.
- **Failure scenario.** In a dispute, a recipient hands a regulator or an opposing party a year of DMs with valid signatures; the sender cannot deny any of them. A recorder on a public room keeps signed messages and later attributes them to the key and, through V1, to an IP address.
- **Fix.** For DMs, authenticate with a key both parties could have computed (a MAC under the static-static ECDH secret of sender chat key and recipient `ek`, which is already in `K_pair`), not a signature; keep the signature only for the chat-key record. For peer authentication, use a MAC-based challenge under the same pairwise secret. For rooms, keep signatures (impersonation matters there) but label rooms "public and signed: anyone can record and prove what you wrote". Add to RT 9.2: "Messages in public rooms are signed. A recording proves you wrote them."

### M3. Holders, WANT-TAGS, ACKs and the flood reveal who talks to whom (RT 5.3 tags, 5.7 holders, 9.1 holder and contact rows)

- **Problem.** RT 5.7: "Holders learn tag, size and arrival time, never sender or recipient." Three counter-examples, each from the design itself:
  1. The stranger inbox tag `SHA-256("mw-inbox-v1|" + ek + "|" + day)` is computable by anyone for every member (the `ek` is public in `mw.ck`). RT 5.7 has recipients send "their own inbox tag" in WANT-TAGS. A holder that receives that WANT-TAGS from a neighbour learns that this IP is the member with that chat key.
  2. A holder that is a direct neighbour of both the depositing peer and the fetching peer sees the same pair tag deposited by IP A and requested by IP B: an IP-to-IP edge for the day. RT 16 Q2 already expects few members online together, which makes the holder a neighbour of both.
  3. In a swarm of a few peers, the first peer to emit a frame is the sender, and the peer that emits a sealed ACK soon after is the recipient.
- **Failure scenario.** A holder on a small site logs WANT-TAGS and deposit IPs for a week and builds a contact graph of IP addresses with chat keys attached for everyone who uses message requests.
- **Fix.** (1) Never send the public inbox tag in WANT-TAGS; fetch stranger mail by a short tag prefix (k-anonymity buckets) or by "everything you hold" when the holder is small. (2) Recipients fetch pair-tag mail by prefix too. (3) Delay and batch ACKs by a random interval and send them as normal ENV frames. (4) Rewrite RT 5.7 and 9.1: "Holders see the encrypted message's size and time, and may see the addresses of the people who leave and collect it. On a small site that can show who writes to whom." (5) Add a unit test that WANT-TAGS never contains a tag computable from public data.

### M4. Trackers learn private group membership and private file pairings (RT 4.1, 5.4, 6.1 F2, 9.1 tracker row)

- **Problem.** RT 4.1 rejects per-pair swarms because they show "the tracker who talks to whom", then the group lane (`sha1("mw-grp1|" || groupSecret)`) and every private file torrent (F2, default on when chat is on) announce new infohashes to the same trackers. RT 9.1 calls this "IP and an opaque id for groups". An opaque id shared by exactly the members' IPs is a membership list. A private file's infohash announced by the sender's and recipient's IPs is a pairing. On rekey (RT 5.4) the remaining members move to a new id at once, which shows the tracker that someone was removed and, by difference, who.
- **Failure scenario.** A public tracker operator (PRIVACY.md lists four by default) clusters IPs by group id and sees a 6-member group shrink to 5 the moment one IP stops announcing; it also sees two IPs announce the same never-listed infohash within a minute: one shared a file with the other.
- **Fix.** Never announce group ids or private infohashes to trackers. Find group members and private-file seeders over the existing chat-lane wires (a WANT-PIECES frame to neighbours, or the direct channel), at the cost of availability. If tracker rendezvous is kept as an option, say in the share card: "The connection servers can see which addresses join this group or fetch this file."

### M5. The ledger keeps public membership, bans and chat activity forever (ID 5 `allow`, D-9, `_roles/`; RT 3, 5.2 `mw.ck`; `block.js` lines 8 to 16)

- **Problem.** `allow` and `ban` are control ops whose whole content sits in the signed entry and "can never be redacted" (`block.js` header). On an `allow` site the allow list is a public, permanent list of member keys; bans are a permanent public accusation attached to a key; `_roles/` advisory entries leave the key name forever (PRIVACY.md: "keys and list names are never deleted"). Every `mw.ck` rotation adds a permanent, timestamped "this key uses chat on this site" entry, so 90-day rotation is a liveness beacon. On a site for a health condition, a religion or a union, membership is an inference about special-category data (GDPR Art. 9).
- **Failure scenario.** A member of a support-group site asks for erasure. The owner tombstones their posts, but their key stays in the allow list, in the ban list if they were ever banned, and in four years of chat-key rotations, in every copy, linkable to their IP by any peer who logged it.
- **Fix (freeze-window items, same window as D-9 and D-10).** (1) Replace the public allow list with owner-signed membership credentials carried in the writer's block (the ledger checks the owner signature, no list is published), or with a salted commitment list. (2) Make bans expire or let the owner issue a superseding checkpoint that drops them. (3) Move the chat-key record off the ledger: members serve a signed chat-key record over the chat lane, with only an optional ledger copy for offline first contact, and no rotation history. (4) State today in PRIVACY.md: "On a members-only site, the list of members' keys is public and permanent."

### M6. Erasure and international transfers have no path (ID 6.3, 10; RT 3; PU 4.3; GDPR Art. 17, 25 and Chapter V; UK GDPR; Law 25 ss. 17, 28, 28.1)

- **Problem.** Erasure in both proposals is tombstone, which keeps `{ e, h, s }`: author key, time, list name or key, and the salted value hash (`block.js` `redact()`), and only for copies that sync. No mechanism, ever, lets an honest copy drop a stub, so Art. 25 (data protection by design) has nothing to point to. Separately, every peer anywhere in the world receives IP addresses, keys, posts, sealed records and chat-key records: a transfer outside the EEA, the UK and Quebec with no safeguard. R6 F3 notes Quebec s. 17; neither proposal mentions GDPR Chapter V or the UK equivalent. PIPEDA has no statutory erasure right, but Principle 4.5 (retain only as long as necessary) is breached by design for stubs.
- **Failure scenario.** An EU visitor's erasure request: the owner can tombstone records and posts but must answer that the author key, list names and times stay in every copy forever, and that copies were sent to peers in any country. A supervisory authority asks for the Art. 25 measure; there is none.
- **Fix.** (1) Add an owner-signed checkpoint op (freeze window): a signed state root after which honest copies may prune every block before it, stubs included, so erasure converges for honest copies. (2) Offer per-site shreddable record keys (PU PR-2) as the default for EU, UK and Quebec audiences (`aud=`), because tombstone alone is not erasure. (3) In the DPIA and Quebec PIA templates, add a transfers section stating that peers can be anywhere and listing what reaches them; for `aud` EEA, UK or Quebec, default records and chat to off. (4) User copy never says "delete my private data"; say "Hide my private record from copies that sync. Who wrote it and when stays in every copy."

### M7. The sign-in card says "Nothing is sent anywhere" (ID 4.3) and the passkey provider is missing from every register

- **Problem.** Creating a discoverable passkey (ID 3.4) stores a credential with the RP ID and a user name in the platform or third-party password manager, and synced providers copy it to their cloud. The provider then holds the list of sites where the person has a magnet-web identity. For server-backed sites (B2) the proof is sent to the server. The card text is false for both.
- **Failure scenario.** A visitor with passkey sync on creates identities on several sites. Their password manager's account lists each site by RP ID; a breach or subpoena of that account shows the list. The visitor was told nothing was sent.
- **Fix.** Card copy: "This creates a key for this site on this device. If you protect it with a passkey, your passkey provider (for example your phone's password manager) stores a passkey for this site." Use an opaque `user.name` and `user.displayName` (for example "magnet-web identity"), never a display name. Add the passkey provider and any server-backed relying party to the recipients register (section 5).

### M8. Seeding defaults put visitors' IP addresses next to content they did not create (RT 6.5, 6.1 F2, 8)

- **Problem.** RT 6.5: "Desktop fetchers re-seed while the tab is open and policy allows", and "Seed only files the visitor uploaded or chose to open". Opening equals distributing. Private-file recipients seed ciphertext to anyone with the infohash. For the visitor this is exposure under copyright making-available rules (Canada's notice-and-notice regime forwards rights holders' notices to the subscriber; German courts have held individual seeders liable; background, not re-checked) and, for illegal content, distribution offences that do not depend on intent to share. For the owner, enabling public uploads plausibly brings hosting duties: DSA Art. 6 and 16 notice and action where the DSA applies, UK OSA user-to-user duties (RT 8 already says so), and Canada's Act respecting the mandatory reporting of Internet child pornography by persons who provide an Internet service (background, not re-checked), which RT 8 does not mention.
- **Failure scenario.** A visitor opens a public file that turns out to infringe or to be illegal; for as long as the tab is open their browser uploads it to anyone in the swarm, monitors log the IP (PU F16), and the visitor saw only a one-time notice.
- **Fix.** Download-only by default for every file; "Share this file with others" is a per-file opt-in with the IP sentence. The owner can publish a block list of infohashes and plaintext SHA-256 values that honest loaders refuse to fetch or seed. RT 8 adds the Canadian reporting statute and the owner's notice contact. Never reseed a private file's ciphertext beyond the named recipients' own fetches.

### M9. Several defaults are not the most private, against Law 25 s. 9.1 and the UK children's codes (RT 5.3 message requests, 6.1 F2 default, ID 7 `remember`)

- **Problem.** Message requests from strangers are on unless "a member can turn message requests off" (RT 5.3); the private file lane is "on for signed-in members when chat is on" (RT 6.1); `mw.auth.signIn({ remember })` lets site code choose whether a locked identity is shown to the site (ID 4.2, 7). Quebec Law 25 s. 9.1 requires the highest level of confidentiality by default (PRIVACY.md "Impact assessments"). R6 F10 cites the Ofcom and ICO joint statement of 2026-03-25: without highly effective age assurance a service must assume children are present; Ofcom's illegal-harms approach expects children not to receive messages from strangers by default (background, not re-checked).
- **Failure scenario.** A general-audience site turns chat on; a child on it receives first-contact messages from any member who pays the 20-bit stamp (RT 5.6), and files can be offered to them, all by default.
- **Fix.** Message requests off by default; the private file lane is its own opt-in; `remember` is a visitor choice in the loader card, default off, never a site parameter. Rewrite RT 8 "Defaults for children's sites" as "on every site, unless the owner adds an age method".

### M10. The shared default trackers, STUN and DoH are a cross-site tracker (RT 9.1; PU F1, F6; PRIVACY.md register)

- **Problem.** PU F6 says "the IP address is the common thread across swarms", but neither proposal names the actors who see that thread for every site at once: the four default WebSocket trackers, the two default STUN operators and the default DoH resolvers (PRIVACY.md register). v0.3 adds the chat lane, group lanes and file torrents to what those same operators see. That is the third-party cross-site tracking PU F1 says magnet-web avoids, done by connection servers instead of scripts.
- **Failure scenario.** One tracker operator sees an IP announce the ledger rendezvous of a political site, then a health forum's chat lane, then a private group id, each with timestamps, and builds a cross-site profile without any key.
- **Fix.** Default to the owner's own tracker and STUN for signed pointers that name them (PU P2 "no big-provider defaults" becomes P1 when chat ships), require `tr=` for chat and files rather than falling back to the public four, and add to the first-run and chat cards: "These connection servers are shared by many sites and can see which of them you open." Add a row to ID 9: "Linkability across sites by connection servers: IP and timing; mitigation: per-site servers."

## 5. Minor findings

- **m1. The record list name is not opaque (ID 6.2).** `l = "mw.r." + 16 characters` and a fixed value of about 1,450 bytes identify every record item at a glance, so the HMAC buys nothing. Fix: use a neutral prefix shared with other lists, or accept the shared `mw.records` list (ID's own alternative) and drop the claim that the name hides purpose.
- **m2. Private file sizes are not padded (RT 6.3, 9.1).** Ciphertext length is plaintext plus 16 bytes per 64 KiB, so anyone with the infohash can match a private file against a known file by size. Fix: pad to size buckets before encryption, and say "the rough size of a private file is visible".
- **m3. Presence beats reveal contact count (RT 5.1).** If a member sends one blinded PRES per contact every 30 s, neighbours count contacts. Fix: one PRES frame carrying a fixed number of blinded ids, padded with random ones.
- **m4. The QR hand-off shows the ledger id (ID 3.5 step 1).** Anyone who photographs the screen learns which site is being linked. Fix: put `H(ledgerId)` in the QR and let device A confirm the site by name.
- **m5. Harvest now, decrypt later.** Chat envelopes and private-file keys are P-256 ECDH, and recorders can keep them; PU F11 cites NIST IR 8547 (draft, secondary). Records use symmetric keys and are not affected. Fix: say so in RT 9.2 and keep PU P3 (post-quantum key agreement) before long-lived history is offered.
- **m6. The owner's TURN relay can log who connects to whom (RT 9.4).** RT states the relay sees both IPs; it does not tell the owner to turn peer-address logging off or to state retention. Fix: the compose file ships with minimal logging, and the notice template gains a TURN row with retention.
- **m7. External age methods reintroduce an identity vendor (RT 8, PU F10).** The "external age method" is a third party that learns who uses which site, the breach class PU F10 cites. Fix: accept only a yes or no attestation verified locally (PU's reserved slot), and name the vendor as a recipient. Owners outside the UK and EU should also check national minimum-age laws for social features (for example Australia's Online Safety Amendment (Social Media Minimum Age) Act 2024; background, not re-checked).
- **m8. The 7-day bearer proof (ID 4.1, 7).** `ttlMs <= 7 d` for a bearer token readable by same-origin code is long for a token that cannot be revoked. Fix: cap bearer proofs at the session and the 12 h default; reserve longer `exp` for challenge-response.

## 6. What this means for magnet-web

- **Today (0.2.1, true of the code):** one random extractable key per ledger per origin, so a hostile site gets only its own key; everything in the ledger public; IP visible to peers, trackers and STUN after consent; no root, no chat, no files.
- **v0.3 as proposed:** better key hygiene and good residual tables, but one shared root unwrapped in each site's host-served code (B1), no safe cross-site design (B2), a phishing-shaped restore flow (B3), and the metadata gaps in M1 to M12.
- **v0.3 after the fixes:** sites cannot recognise a person by key unless they choose; the phrase never touches a site; chat keys can be retired; private messages are deniable; trackers do not see private groups or files; membership lists are not public; erasure converges for honest copies after a checkpoint; consent cards and PRIVACY.md name every recipient.
- **Cannot, with any fix:** hide IP addresses from peers, trackers, STUN or a relay; stop shared connection servers from seeing which sites an address opens, unless each site runs its own; erase copies on devices that never sync; stop recipients keeping what they receive; verify anyone's age.
