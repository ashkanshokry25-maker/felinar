# Judge: user experience and adoption (v0.3 identity, auth, chat and files)

- **Status:** judgment, 2026-10-20. Reviews [IDENTITY-AUTH-DESIGN.md](IDENTITY-AUTH-DESIGN.md) (cited as ID-x.y) and [REALTIME-AND-FILES-DESIGN.md](REALTIME-AND-FILES-DESIGN.md) (cited as RT-x.y) against the owner's goals, including the requirement added 2026-10-20 about 08:25 ET (one root identity usable on every magnet-web site, on any existing site through the drop-in widget, and on server-backed sites through a published challenge format and a Node and browser verification library; per-site keys by default with a visible "use the same identity here" choice; one tap in a loader-owned card), and against the demo `examples/social` (personal sites in hub mode: profiles, walls with media, follows, a merged follow feed, groups, direct messages and rooms, files, a directory).
- **Lens:** the visitor who has never heard of keys, the phone, the site owner's setup, and whether the example sites can be built without guessing.
- **Method:** read both proposals in full, DIFFERENTIATORS-AND-WHY, PRIVACY-UPGRADES, R3, R4, R7, R8, and ARCHITECTURE sections 3.2, 6.1, 8 and 9. No browser was launched and nothing was run. Every number below is either quoted from a named file and line, or is arithmetic on such numbers and says so.
- **Wording:** "no backend", "site ledger". Straight quotes. No em dashes.
- **Severity:** blocker = cannot ship as written; major = user-visible gap or wrong claim; minor = hygiene.

## 1. Verdict in eight lines

1. Neither proposal implements the 08:25 requirement. ID-2 lists "cross-site identity by default" as a non-goal and stores the root per origin (ID-3.3), so the second magnet-web site a person visits asks for the 12 words, a file or a second device. That is the opposite of "one tap, nothing to type".
2. Because the root lives per origin, restoring it on each new site means typing the master phrase into that site's own code, which the proposal itself says can read anything while unlocked (ID-6.5). One hostile site owner collects roots that open every site. This is a blocker, not a residual.
3. The server-backed path (c) is impossible as written: the loader refuses nonces from site code (ID-4.1), and a server's nonce can only arrive through site code; `verifyLogin` needs ledger state and `location.origin`, which a server does not have; there is no `statement` field and no library specification.
4. First sign-in on a phone is 6 to 9 interactions with 2 or 3 biometric prompts in the best case (section 2), against a goal of one tap and one prompt (R7 6.1 goal 2).
5. Phones cannot share files by default: uploads are choke-locked on every phone class until "Share on this network", and locked again the moment the tab hides (ARCHITECTURE section 8, table row "uploads" and "hidden tab"). iOS is always `mobileUnknown`. A phone-to-phone private photo therefore has no seeder, and no screen tells the sender.
6. `examples/social` is not specified anywhere. Both proposals specify only `examples/peer-guestbook`. Of 24 mechanisms a social site needs (section 5), 4 are covered, 7 partly, 13 not at all, and three are architecturally blocked: a person cannot post to their own personal site from a browser (the owner key never enters a browser, ID-2), a merged follow feed needs whole-ledger copies that exceed the phone storage budget after about 16 follows, and per-site unlinkable keys make "follow", "block" and "same person" unanswerable across sites by default.
7. Recovery has three traps: the iOS reminder fires after Safari may already have deleted the identity; a session-only identity can lose its private vault before any backup card has been shown; a mistyped phrase that passes the checksum silently restores a different, empty identity.
8. The wording rules are respected in both proposals (grep for the forbidden terms and for curly quotes and em dashes found nothing). One sign-in string makes a false claim (finding M2).

## 3. Findings

### Blockers

**B1. The 08:25 cross-site requirement is not designed, and the storage model rules it out.** (ID-2 non-goals, ID-3.3, ID-3.5, ID-13)
- *Failure:* Ana signs in on `blog.example` (shell mode, own origin). She opens `club.example`. Its loader has its own IndexedDB `mw-id` and no root. Her only routes are typing 12 words, picking a file and typing a passphrase, or a second device. On a hub, each personal site is `<32 base32 chars>.hub.example` (ARCHITECTURE 3.2), its own origin, so every profile she wants to comment on repeats this.
- *Fix:* make the separate identity origin (ID-6.5, today P3) the P0 core. One statically hosted origin (for example `id.<project domain>`) holds the root and runs the phrase, passkey and consent cards; sites receive only derived per-site public keys and signatures by `postMessage`. Open it as a first-party popup (`window.open` on the sign-in tap), not a third-party iframe: browsers partition third-party iframe storage by top-level site, so an embedded identity frame gets a different IndexedDB on each site and recreates the problem (state the partitioning behaviour per browser in the compatibility matrix after a lab run; it is not measured in the repo). One passkey for that origin's RP ID then works on every site. State the new trust: whoever controls that origin's code controls every visitor's root, so it needs pinned, reproducible builds, a published hash, and an "operate your own identity origin" option.

**B2. The phrase is entered into code the site owner controls, on every new site.** (ID-3.5, ID-4.3 "I already have one", ID-6.5, ID-9 first row)
- *Failure:* the threat table says "phrase only in loader UI; loader never asks unprompted". But the loader on `evil.example` is shipped by evil's owner, and "I already have one" is the normal path on every new site (B1). The owner's loader card looks identical to the honest one (there is no browser chrome to tell them apart), records the 12 words, and derives Ana's keys for every ledger id it likes. ID-6.5 already concedes same-origin code can read everything while unlocked; the phrase is worse because it is the root of all sites, not one.
- *Fix:* the phrase is typed only on the identity origin of B1, whose address shows in the popup's address bar. The card text says "Type your recovery words only on <identity origin>. A site that asks for them on its own page is trying to steal them." Rewrite the ID-9 row: residual = "a visitor who types the words into any site's page loses every identity", and train the habit at the backup moment.

**B3. Sign-in for server-backed sites (requirement c) cannot work as written.** (ID-4.1, ID-7 `mw.auth.verify`, ID-12)
- *Failure:* a server issues a nonce; the only way it reaches the loader is through site code; ID-4.1 says the loader never accepts "a challenge whose nonce came from site code". If relaxed, the challenge has no `statement`, no `uri`, no `version` string the server can pin, and `verifyLogin` checks `c.aud === location.origin` and "its role in the current state", which a Node server has neither of. There is no package name, no API, no nonce-store contract, no clock-skew rule for servers, no error list. A server developer cannot build it.
- *Fix:* publish `mw-login-v1` as a standalone spec: fields `domain`, `uri`, `ledger` or `origin`, `pub`, `nonce` (server-issued allowed in challenge-response kind, at least 16 bytes), `iat`, `exp`, `statement` (plain text, shown verbatim in the card), `version`, `chain` absent. The safety comes from the loader or identity origin filling `domain` and `uri` from the real top-level location, never from site input, which is SIWE's rule (R3 F16). Ship `@magnet-web/verify` with `verifyLogin(proof, { domain, uri, nonceStore, now, maxSkewMs, roleOf? })` where `roleOf` is optional, and a one-time-use nonce store interface. Add vectors and an E2E test against a loopback Node server.

**B4. The drop-in widget on "any existing site" would put a cross-site root in that site's page realm.** (ID-6.5 "in drop-in mode the page is the loader's realm", ID-11 drop-in paragraph)
- *Failure:* an existing news site with an ad tag adds the drop-in. If the drop-in ever holds the shared root (needed for requirement b without B1), the ad script can read it and sign as the visitor on every site. Even with today's per-origin root, the closed shadow root only blocks honest code; R3 F18 records that a non-extractable key can be used and structured-cloned by same-origin code.
- *Fix:* the drop-in never holds a root or a phrase. It opens the identity-origin popup of B1 and receives a per-site signature. State in the drop-in docs: "Scripts on this page can act as you on this site while you are signed in; they cannot reach your other sites."

**B5. In `examples/social`, a person cannot post to their own personal site from a browser.** (ID-2 non-goals "owner login from a browser (the owner key never enters a browser)"; ARCHITECTURE 6.2 and 6.8)
- *Failure:* Ana's personal site's ledger owner is the offline publish key. Her browser key is a visitor key. With `writers: 'owner'` she cannot write her own wall; with `'open'` anyone can; with `'allow'` someone runs a CLI command to add her browser key, and only the owner signs `allow` (ID-5 D-9). Creating the personal site at all needs `keygen` and `publish` (R7 2.1: 8 steps, 9 flags). No person who has never heard of keys gets a profile.
- *Fix:* decide, as a new D-n, how a personal site comes into being in the browser: either (a) the hub creates the site from a template and the person's identity-origin root derives the site's owner key (this reverses ID-2 for personal sites and needs its own threat row: a browser-held owner key can be phished or used by same-origin code), or (b) the publish key stays offline, but the site is published with the person's derived key as a moderator, and the hub runs the publish as a service, which is a backend and must be called one. Without this decision the demo cannot be built.

**B6. A merged follow feed and "global in reach" do not fit whole-ledger copies on a phone.** (ARCHITECTURE 6.1 `maxChainBytes` 8 MiB default, 64 MiB ceiling, line 504 and 506; storage budget 128 MiB on mobile, line 821; rendezvous wires 3/5 per swarm and maxConns 4 to 8, section 8 table)
- *Failure (arithmetic):* each followed person is a separate site ledger at a separate origin. The viewer's origin cannot read another origin's IndexedDB, so it must join each ledger swarm and copy each ledger whole (the ledger is copied and verified by every visitor; no partial sync exists). 128 MiB / 8 MiB = 16 full-size followed ledgers; at the 64 MiB ceiling, 2. Following 200 people means 200 swarms against a phone's 4 to 8 content connections and 3 to 5 wires per swarm. A single hub-wide directory ledger at the 64 MiB ceiling, at an assumed 300 bytes per entry, holds about 223,000 entries (arithmetic, assumption labelled), and every visitor downloads all of it.
- *Fix:* specify the feed mechanism before building: per-identity outbox ledgers with a size budget per person (for example a rolling window), a "recent entries" sparse fetch from the `cs=` snapshot over HTTPS, a cap on followed sites per device class with the numbers above in the UI ("Your phone can follow about 16 full sites; older posts load from the host"), and drop every "global" claim from the demo copy until a lab measures it.

### Majors

**M1. One tap is not one tap.** (ID-3.4, ID-4.3) Section 2 counts 6 to 9 interactions and 2 or 3 biometric prompts on first sign-in. "Protect with this device's screen lock" is an extra opt-in instead of the default; the separate `get()` after `create()` adds a prompt, and the self-test may add another. *Failure:* a first-time visitor sees Face ID twice for one "Sign in" and abandons. *Fix:* make the passkey the default in one card ("Sign in with Face ID" or the platform's name), request PRF with `eval` at `create()` and use the result when the platform returns it, call `get()` only when it does not, reuse the PRF output in memory for the self-test, and add a "Tap to finish" button if the second call needs a fresh user activation (verify on G-ID-1). Count the "what others can see" card into the sign-in card as one screen.

**M2. "Nothing is sent anywhere" is false when the passkey syncs.** (ID-4.3 card text; R7 6.2 draft "Nothing is sent to a server") *Failure:* on iPhone the passkey is saved to iCloud Keychain, on Android to Google Password Manager (R3 F3 lists both as PRF providers). A visitor told "nothing is sent" later sees the site's passkey on her other devices. *Fix:* "Your passkey may be saved by your password manager (for example iCloud Keychain or Google Password Manager). Your identity itself stays on this device."

**M3. Passkey sprawl on hubs.** (ID-3.4 "Per-origin scope"; ARCHITECTURE 3.2 "list the hub suffix on the Public Suffix List") *Failure:* with the hub suffix on the PSL, `hub.example` cannot be an RP ID for `<label>.hub.example`, so every personal site gets its own passkey; following and commenting on 50 sites leaves 50 entries named by 32-character labels in the visitor's password manager. Related Origin Requests are capped at 5 registrable-domain labels in Chrome (ID-3.4). *Fix:* B1 (one RP ID on the identity origin). Until then, state the sprawl in the card and set passkey `user.name` and `displayName` to something readable (finding m2).

**M4. Cross-device by passkey sync is not in v0.3, and QR hand-off is per site.** (ID-3.4 "cross-device unwrap waits for the two-device lab", ID-3.5 step 6) *Failure:* the requirement names passkey sync as a cross-device route; the design gives phrase or QR only. QR defaults to one `siteSeed`, so a new phone for 10 sites is 50 actions (section 2). A desktop without a camera needs about 167 typed characters. *Fix:* QR hand-off of the root to the identity origin (B1) by default, with the SAS check; one ceremony per device, not per site. Keep the per-site seed as the "link only this site" option. Run G-ID-3 before v0.3 ships and say in the card which route this device used.

**M5. The iOS backup reminder fires after the deletion it warns about.** (ID-3.5 "iOS: again after 7 days without a visit"; WebKit ITP 7 days, R3 F19) *Failure:* if Safari deleted script-writable storage after 7 days of use without interaction, the loader has no record that a reminder is due and no identity to back up. *Fix:* on iOS outside Home Screen mode, show the recovery-kit card at every visit until a kit is saved, and on the first visit offer "Add to Home Screen keeps your identity" (Home Screen apps are exempt, R3 F19). Copy: "Safari can delete this site's data, including your identity, after 7 days of Safari use without visiting it. Save a recovery kit now."

**M6. Session-only identities can lose private data before any backup card.** (ID-3.3 `session` wrap; ID-3.5 card timing "after the first ledger write, first chat message or first upload") *Failure:* a visitor on a device without PRF who declines a passphrase gets `session`. She saves private notes with `mw.me.set` (stored `local`, not a ledger write, so no backup card) and closes the tab. Next visit the signing key still works from IndexedDB, but `K_vault` needs the root, which is gone, and she was never shown the phrase: the notes are undecryptable forever. iOS is the likely case (ID-8 "reported failures" for CryptoKey in IndexedDB, then "derive per session"). *Fix:* never create a `session` root without either showing the phrase first or saying "This identity disappears when you close this tab"; treat the first `mw.me.set` and the first "keep history" toggle as backup-card triggers.

**M7. "Sign out" does not say what it locks, and returning sign-in has no specified user check.** (ID-3.3 stores `sign` as a usable non-extractable CryptoKey; ID-4.2 lock; R3 F18) *Failure:* after "Sign out", `keys:<ledgerId>` still signs for any same-origin script, and the proposal does not say whether "Sign in" again requires the passkey, the passphrase, or nothing for the signing key. A person who picks up an unlocked laptop may be one tap from posting as the owner of the browser. *Fix:* specify: sign-in after lock requires user verification (passkey `get()` or passphrase) whenever the root kind is `prf` or `pass`; wrap the stored signing key under a key derived at unlock, or state on the Sign out button's help that "signing out hides your account in this site's pages; someone using this browser can sign in again without your face or PIN" where that is the case.

**M8. A mistyped phrase can silently restore someone else.** (ID-3.5 phrase route; ID-12.2 E-3) *Failure:* 12 BIP-39 words carry a 4-bit checksum (BIP-39 encoding of 128 bits), so about 1 in 16 wrong words still passes. The visitor lands in an empty, new identity, posts, and her real one is orphaned. *Fix:* after restore, show "This is the identity that last posted as <name>, <short id>, on <date>" when the site's ledger knows the derived key, and "No posts found for these words on this site. Check the words or continue as new" when it does not. Add an E2E test.

**M9. No revocation, no "sign out everywhere", no key-change warning.** (ID-5 D-10 optional; ID-9 "Compromised site key"; RT-5.2) *Failure:* Ana loses her phone unlocked, or a thief knows its PIN. Without D-10 her keys stay valid on every site; with D-10 she must rotate per site. Her contacts get no warning when her signing key changes after a restore with a new identity, so a new key claiming her name is accepted as "Ana". *Fix:* make D-10 a P0 decision, add "Replace my keys on all sites" in the identity origin, and add a contact key-change notice: "Ana's key changed. If you did not expect this, check with Ana another way." State that magnet-web has no equivalent of a server-side session revoke.

**M10. The private record cannot hold a contact list or follows.** (ID-6.2: plaintext padded to exactly 1,024 bytes; fields include `contacts` and `files`) *Failure (arithmetic):* a P-256 public key is 65 bytes raw, 87 base64url characters, about 92 with the `p256:` tag; with a short nickname and JSON overhead about 110 bytes per contact, so about 8 contacts fill the record with nothing else. A file key reference (40-hex infohash, 43-character key, prefix, name) is about 150 bytes. A restored second device therefore loses all but a handful of contacts, follows and received files. *Fix:* split the record into a fixed-size index plus padded chunk records (each counted against the ledger budget, finding M21), or keep contacts in the encrypted backup file and the QR hand-off only, and say so: "Contacts move to a new device with the hand-off or the recovery file, not with the words."

**M11. Phones cannot share files by default and nothing tells the sender.** (RT-6.1 F2 "on for signed-in members when chat is on"; RT-6.5; RT-7 "Seeding files: after opt in"; ARCHITECTURE section 8 uploads row and hidden-tab row) *Failure:* Ana on an iPhone (always `mobileUnknown`) sends Bo a photo privately. Uploads are choke-locked, so Bo's fetch finds no seeder: `E_FILE_UNAVAILABLE`. If she turned sharing on, the upload locks again when she switches apps to tell Bo. *Fix:* at "Share a file" on a phone, a card: "To send this, your phone must share it with Bo while this page stays open and on screen. [Share this file now] [Cancel]", scoped to that one infohash, not the whole site; a sender-side state "Waiting for Bo to download (keep this page open)"; the recipient's string "Ana's phone is not sharing this file right now. Ask Ana to open the conversation."

**M12. Offline messages on a phone-heavy audience mostly end as "not delivered", with no retry.** (RT-5.7 holders desktop-only by default; RT-2 principle 5; RT-5.3 "no ACK to strangers") *Failure:* in a social demo used on phones, holders are rare, so most DMs to an offline friend are "not delivered"; the spec does not say whether the sender's page retries. A first message to a stranger never gets an ACK, so its state has no defined end. *Fix:* sender-side outbox that retries while the page is open, with "Will send when Bo is online while this page is open"; a defined state for strangers: "Sent to the network. You will not know if it arrived until they reply."

**M13. Joining an `allow` site needs a moderator online and a CLI command.** (ID-5 "Membership requests", D-9) *Failure:* the visitor must enable chat to send a join request, a moderator must be online at the same time, and approval writes `allow`, which today only the owner signs from `tools/`. No screen covers "request sent", "no moderator online", "approved", "declined". *Fix:* decide D-9 (recommendation a) before any public ledger; add the four screens; hold join requests in holders like envelopes.

**M14. The owner's setup for auth, records, chat and files has no steps.** (ID-5 `_mw.chat` owner key; ID-6.1 `records: 'sealed'`; RT-6.1 "owner turns on" F1; RT-9.4 D-C8) *Failure:* `records` is not a field of `Policy` (ARCHITECTURE line 503), so it is either a format change during the freeze or an undeclared key; `_mw.chat` must be written by the owner key, which never enters a browser, by a command that does not exist; there is no `publish` flag list. A builder must guess. *Fix:* a table of owner settings with storage location, CLI flag (for example `--chat members --files private --records sealed`), default, and the command count, and add them to the `init` wizard of R7 5.2.

**M15. `examples/social` has no specification.** (ID-11 and RT-11 cover only `examples/peer-guestbook`) *Failure:* builders of the demo must invent profiles, walls, feed, follows, groups, directory and their failure states. *Fix:* a section-by-section spec with the mechanism table of section 5 below, each row naming the SDK calls, ledger lists and schemas, sizes, phone behaviour and strings.

**M16. Per-site unlinkability defeats follows, blocks and reports across sites, and the "same identity here" choice is missing.** (ID-1 bullet 1; ID-3.6 link statements; ID-9 "Linkability across sites") *Failure:* Bo harasses Ana on her site; she blocks his key. He comments on her friend's site under an unrelated key; her block does not follow him. Followers on Ana's site are keys unrelated to their own sites, so "who follows me" cannot link to their profiles. There is no card for "Use the same identity here", no statement of what it reveals, and no indicator of which mode a site is in. *Fix:* in the identity origin, a per-site choice shown in the sign-in card: "Private to this site (default)" or "Same as on <site>: this site and <site> will know you are the same person". For hubs used as social networks, make the hub scope an explicit owner choice with the cost stated. Blocks stay per key; say so: "Blocking hides this key on this site only."

**M17. Names are self-asserted, and profile addresses are 32 random characters.** (ARCHITECTURE line 506 `maxName: 48`; ARCHITECTURE 3.2 label = 32 base32 characters) *Failure:* two visitors both named "Ana" in DMs; a copycat takes a friend's name. Profiles live at addresses no person can read or remember. *Fix:* always show the short id beside the name in chat and on walls; add contact verification by comparing a short code in person or by QR, modelled on safety-number comparison (source needed before naming Signal, m1); allow a site to show its own domain as the handle; a "This is a new contact, not someone you know" label on first message.

**M18. Photos are uploaded with their location metadata.** (RT-6.2 to RT-6.4; nothing strips metadata) *Failure:* Ana posts a phone photo to her public wall; its EXIF GPS block reveals her home to the whole swarm, permanently (copies cannot be erased, RT-6.7). *Fix:* re-encode images on the device before seeding (decode with `createImageBitmap`, draw, export) for public and private lanes, with a visible "location and camera details removed" note and an explicit "send original" option for private shares only.

**M19. A directory contradicts the ROADMAP.** (ROADMAP line 142 "A directory of sites on a hub: Only after counsel has looked at it."; line 127 hubs "no directory") *Failure:* the social demo ships the feature the roadmap held back pending counsel, with DSA and UK OSA duties (RT-8). *Fix:* keep the directory out of the demo or mark it "pending counsel" and opt-in per person, with a report button and statements of reasons.

**M20. Wall media disappears when the phone closes, and a site holds about 10 large files.** (RT-1 bullet 6 "A file lasts only while someone keeps it"; RT-7 public file 25 MiB, 256 MiB per site; the pin node is `tools/pin.mjs`) *Failure:* most people will not run a headless pin node, so a phone-only person's wall media is unavailable whenever their page is closed and no follower happens to be seeding. 256 MiB / 25 MiB = 10 maximum-size files per personal site (arithmetic). *Fix:* the hub or the person's static host keeps public media as a web seed (a host, stated as such); each media tile shows "Not available right now: nobody is sharing it"; state the per-site cap in the upload screen.

**M21. Sealed records and chat-key records fill an open site's ledger fast.** (ID-6.2 value about 1,450 bytes; ID-9 "Ledger bloat"; RT-5.2 175 to 260 bytes per rotation) *Failure (arithmetic, values only, headers excluded, so an upper bound):* 8,388,608 / 1,450 is about 5,785 records; at the 64 MiB ceiling about 46,282. Each update leaves a tombstoned stub `{e, h, s}` (ARCHITECTURE line 510) forever, and each 90-day chat-key rotation adds another entry. A site with a few thousand active members reaches the default cap from records alone. "Reach the 8 MiB default sooner" understates it. *Fix:* state these numbers in ID-9 and the owner docs, make sealed records opt-in per site with a member cap, and add a ledger-budget meter to the owner tools.

**M22. User-facing strings are missing for most error codes and states.** (ID-7, RT-10) *Failure:* the visitor sees `E_NO_CHAT_KEY` or a blank. *Fix:* add strings, English and French (ID-12.4 A5 owns `strings.js`), at least for: `E_NO_CHAT_KEY` ("Bo has not turned on messages on this site"), `E_FILE_UNAVAILABLE`, `E_FILE_TOMBSTONED` ("Removed by the site's moderators"), `E_DECRYPT`, `E_HOST_ONLY` ("You chose host only, so chat is off. [Change]"), `E_STAMP` with a progress line, `E_UNSUPPORTED` naming the browser, `E_HOST_ONLY_IDENTITY`, passkey cancelled versus passkey unavailable versus PRF unavailable after create, wrong passphrase, camera denied during QR, storage evicted ("This browser deleted your identity for this site. Restore it from your recovery kit"), identity restored but no posts found (M8), "held by N peers", and "nobody online to hold it".
