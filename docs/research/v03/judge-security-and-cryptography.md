# Judge: security and cryptography lens (v0.3 identity, auth, chat, files)

- **Status:** review, 2026-10-20. Judges [IDENTITY-AUTH-DESIGN.md](IDENTITY-AUTH-DESIGN.md) (cited as ID) and [REALTIME-AND-FILES-DESIGN.md](REALTIME-AND-FILES-DESIGN.md) (cited as RT) against the owner's goals, including the 2026-10-20 08:25 ET addition (one root identity usable on every magnet-web site, on any existing site through the drop-in widget, and on server-backed sites through a published challenge format and a verification library; per-site keys by default; a visible "use the same identity here" choice; passkey-like one-tap UX).
- **Checked against code:** `src/chain/block.js` (ops, unknown-op rule, values outside the hash), `src/chain/state.js` (bans remove every payload of the author; `_` names privileged; put last-writer-wins), `src/chain/wire-ext.js` (remote peer id is self-declared and "nothing checks" it, lines 13 to 19), `docs/SECURITY-MODEL.md` (shell CSP `script-src 'self'`; same-origin code reads IndexedDB), `docs/ARCHITECTURE.md` (identity keyed by ledger id on every origin, line 147).
- **Severity:** blocker = cannot ship as written; major = user-visible gap or wrong claim; minor = hygiene. Nothing here was run; every scenario is a reading of the design text and the code.
- **Wording:** "no backend", "site ledger". No measured numbers appear below; bit counts are arithmetic.

## Verdict

Neither proposal can ship as written. The owner's 08:25 requirement (cross-site sign-in) is not designed at all: ID lists "cross-site identity by default" as a non-goal, has no server format, no verification library and no "same identity here" flow. Under the design as written, using one root on many sites means importing the root into every site's origin, where any one hostile or compromised site gets the master secret. That single fact defeats the per-site unlinkability claim, the phishing claims and the "only you can decrypt" claims at once. Five blockers, fourteen majors, seven minors.

## Blockers

### B1. The cross-site sign-in requirement is missing (ID 2, 4.1, 13)
- **Problem:** ID 2 makes cross-site identity a non-goal. There is no challenge for server-backed sites (the format requires `ledger` and a ledger role; a server has neither), no `statement` field (the requirement lists it), no `uri`/`version`/`not-before`/`request-id` equivalents, no Node verification library, no rule for how a per-site key is derived for a site that has no ledger id, and no design for "use the same identity here": what key is shown, how the choice is recorded, how it is revoked, and what the second site learns.
- **Failure scenario:** a server-backed site integrates the drop-in widget, calls `mw.auth.prove()`, and receives a proof whose `ledger` is undefined and whose `scope` check depends on ledger state the server cannot read. It either rejects every proof or skips the checks and accepts any signature by any key.
- **Fix:** add a section "Sign-in for any site" with: (1) message `mw-signin-v1` with `domain` (browser-stamped origin, see B2), `audience` (ledger id or origin), `statement` (human text shown verbatim in the card), `nonce` (verifier-issued, required), `iat`, `exp` (at most 5 minutes after `iat` for server use), `nbf`, `requestId`, `keyMode` (`pairwise` or `linked`), `pub`; (2) a published canonical encoding and test vectors; (3) `@magnet-web/verify` for Node and browsers whose `verify()` refuses a missing nonce, requires an exact `domain`, checks a single-use nonce store supplied by the caller, and returns the key, never a role (roles are the caller's business); (4) pairwise derivation for non-ledger sites from the registrable origin; (5) "use the same identity here" = a signed link statement between the two pairwise keys, created only in the identity card, listed in a "linked sites" page, revocable for the future by publishing nothing further and rotating the pairwise key, with the card text "the sites you link can tell they are the same person, forever; unlinking stops future use, not what they already know".

### B2. The root ends up on every site's origin, where any one site can take it (ID 3.3, 3.4, 3.5, 6.5; DIFFERENTIATORS 108, 161; PRIVACY-UPGRADES 35, 61)
- **Problem:** the root lives in IndexedDB `mw-id` of the loader origin, which is the site's origin in per-domain and drop-in modes. To use one root on site B the visitor must restore it there (phrase, file or "link everything" QR). Loader code that unwraps it runs in the site's realm (drop-in) or is same-origin with the site frame (shell; SECURITY-MODEL line 73). Per-site HKDF only separates sites that behave honestly.
- **Failure scenario:** the visitor restores their phrase on `forum-b.example` to sign in there. The forum owner (or an XSS, or a compromised analytics tag) hooks `crypto.subtle.importKey` or the loader's HKDF before the loader runs, captures the root, then computes `siteSeed` for every ledger id it can see in public swarms. It can now post as the visitor on every site, decrypt their sealed records and every captured chat envelope (chat keys derive from the root, M5), and link all their site keys, which falsifies "two sites cannot match you by key". In drop-in mode the restore card is a closed shadow root in the page realm: a `keydown` listener on `document` still sees every key (keyboard events are composed and retargeted, not hidden), and a page that hooks `Element.prototype.attachShadow` first gets an open root. "No one will ever ask you for these words" is contradicted by the design's own need to ask on every new origin.
- **Fix:** make the identity origin (ID 6.5, "design note only") the v0.3 design, not P3, because cross-site use requires it: one static origin per identity provider (self-hostable, files content-addressed and SRI-pinned) opened as a first-party popup (not an iframe: browsers partition third-party storage, so a framed identity origin would get a different store per top-level site; verify with a lab row) that holds the root, wraps it with a passkey PRF for its own RP ID, derives the pairwise key from `event.origin` as reported by the browser to `postMessage`, never from anything the site sends, renders the statement itself, and returns only a signature and a public key. Until that ships: never import the root on a site origin; restore and QR hand-off carry only that site's `siteSeed`; the phrase is entered only on the identity origin or a local, offline page. Reword DIFFERENTIATORS line 108 and 161 and PRIVACY-UPGRADES line 35 to "two honest sites cannot match you by key; a site you restored your phrase on can compute all of them".

### B3. Keys are scoped to a ledger id that any origin can claim (ID 3.1 "per ledger id, not per origin")
- **Problem:** blocks sign `e.site` only; nothing binds a ledger to an origin. ARCHITECTURE line 147 keys identity by ledger id on every origin. A look-alike origin that loads ledger L in its drop-in config derives and uses the L key.
- **Failure scenario:** `examp1e.org` serves a copy of example.org with the genuine drop-in configured for ledger L and a "your session expired, restore your identity" card. The visitor restores (B2 makes this the normal flow on a new origin). The look-alike now signs ledger entries on L as the visitor; honest peers accept them because the block is valid for L. Login proofs are origin-bound, ledger writes are not.
- **Fix:** an owner-signed origin list in the ledger (`_mw.origins`, owner or moderator `put`, advisory today, enforced by the loader): the loader uses ledger L's key only on an origin listed for L, otherwise derives a separate key for that origin and shows "this address is not one of this site's addresses". Mirrors join the list explicitly. Add the case to the threat model.

### B4. The QR hand-off releases the secret before the person confirms the code, and the code has no commitment (ID 3.5 steps 2 to 5)
- **Problem:** step 3 puts `ct = AES-GCM(K, siteSeed or root)` in A's reply before step 4's SAS comparison, so the comparison can only reveal a theft after it happened. The SAS hashes both public keys with no commitment, so on the optional network path a man in the middle who sees `eA` before choosing its key toward B can search 2^20 candidates for a matching 20-bit code (arithmetic). The `ledgerId` inside B's QR is chosen by whoever made the QR.
- **Failure scenario:** a phishing page says "scan to verify your account" and shows `mwlink:1:<attacker eB>:<target ledger>`. The visitor's unlocked phone (A) scans it under "Link a device", and the reply goes back over the wire path to the attacker's ephemeral key. The attacker's page shows the same SAS because it can compute it, so the visitor confirms. The attacker receives the `siteSeed` for a ledger of their choice, or the root if the visitor picked "link everything". Device-link phishing of this shape against a messenger has been publicly reported (Google Threat Intelligence Group on Signal linked devices, February 2025; not re-fetched for this review).
- **Fix:** commit first (B sends `H(eB)`, A sends `eA`, B reveals `eB`; SAS over the transcript), confirm on A before A emits any ciphertext, require both QR scans in person for any transfer (drop the network path for the root and make it opt-in, with a warning, for one site), name the site and the device on A's card ("Give <site> to the device in front of you?"), and refuse a hand-off whose ledger is not the one A currently shows. Use 7 decimal digits or say "20 bits shown as up to 7 digits" (m1).

### B5. The section 3 lint turns a value's shape into block validity, so one bad write can stall every v0.3 client (RT 3)
- **Problem:** values travel outside the hash and are dropped on tombstone (`block.js` lines 8 to 16), yet RT 3 has peers "drop them as `shape`". v0.2.1 clients accept and relay such blocks; later blocks by other authors name them in `prev` (up to 8 parents).
- **Failure scenario:** a visitor appends a malformed `mw.ck` value on an open site. v0.2.1 peers accept it and other visitors' later blocks reference it as a parent. v0.3 peers reject it, so every descendant has a missing parent and cannot be validated; v0.3 clients stop converging on that ledger. A stub without `v` cannot be linted at all, so the rule is also inconsistent between peers that saw the value and peers that did not.
- **Fix:** treat a schema miss as "redact the value, keep the block" (the same path tombstones use: store `{e,h,s}`, never relay `v`), never as invalid. Keep validity rules in `block.js` to what is inside `e`. List the `mw.*` schemas, including the record lists `mw.r.*` (ID 6.2), which the lint as written would reject.

## Majors

### M1. "Signed out" leaves usable keys on disk (ID 3.3, 4.2)
- **Problem:** `keys:<ledgerId>` stores the sign and chat CryptoKeys non-extractable but usable. Locking forgets only the root and symmetric keys.
- **Failure scenario:** the visitor signs out on a shared laptop. Any script on that origin (the site's own, an injected tag, a later visitor with the console open) calls `crypto.subtle.sign` with the stored key to post as them, and `deriveBits` with the chat key to open their held mail. "Sign out locks the key" is false.
- **Fix:** do not persist usable private keys: store them wrapped (or re-derive per unlock), so signed-out means no usable key exists until a passkey tap or passphrase. If speed requires persistence, rename the state "paused" and say "this browser can still sign as you until you remove it from this device".

### M2. "Non-extractable" does not stop copying the key, so DIFFERENTIATORS line 161 is wrong (ID 3.1, 3.3)
- **Problem:** scalars are computed in JS (`@noble/curves`, mod reduction) and passed as a JWK `d` to `importKey`; the root is a byte array in loader memory while unlocked and in `session` mode.
- **Failure scenario:** same-origin code replaces `SubtleCrypto.prototype.importKey` before the loader runs and records every JWK `d`. It has copied the key, not just used it.
- **Fix:** reword to "while you are signed in on a site, code on that site can copy your keys for that site, and your recovery root if you entered it there". Do derivation in a dedicated Worker loaded from a fixed URL (narrows, does not close, since same-origin code can register a Service Worker in drop-in mode); B2's identity origin is the real fix.

### M3. Bearer proofs are long-lived, readable and unrevocable; the nonce rule contradicts itself (ID 4.1, 4.2, 7)
- **Problem:** default `exp` is 12 hours, maximum 7 days; a copy sits in `sessionStorage`; `expectNonce` is optional in `verifyLogin`; logout does not invalidate a proof. ID 4.1 says a challenge "whose nonce came from site code" is never accepted, yet `mw.auth.prove({ nonce })` takes the nonce from site code, and a server-backed site can only work that way.
- **Failure scenario:** an XSS reads the proof from `sessionStorage` and replays it to the site's own code (or to a server that copied the browser verifier without a nonce) for up to 7 days after the visitor signed out.
- **Fix:** challenge-response only for anything that leaves the tab, with a verifier-issued single-use nonce, `exp` at most 5 minutes, and the server minting its own session after one check (that is the server's backend, not ours). Bearer proofs at most 15 minutes, never stored, never accepted outside the tab. Replace the "nonce from site code" rule with "the nonce may come from anywhere; the domain may not" (B2). Add a local revocation epoch so in-tab verifiers refuse proofs issued before the last sign-out.

### M4. Peer challenge binding uses self-declared peer ids, so a relay attack works (ID 4.1 `chan`, RT 4.2 CHAL/RESP)
- **Problem:** `chan: [idA, idB]` binds wire session ids; `wire-ext.js` lines 13 to 19 say the remote peer id is self-declared and nothing checks it.
- **Failure scenario:** Eve connects to Alice claiming Bob's id and to Bob claiming Alice's id. Bob's challenge is forwarded to Alice, Alice signs `chan: [Alice, Bob]`, Eve forwards it, and Bob's check passes. Bob now treats Eve's wire as Alice (where to send a direct-channel offer, whose WANT-TAGS to answer).
- **Fix:** say plainly that a peer login proves key possession, not the transport. Bind every later frame on that wire to the proven chat key (seal to it, as SIG frames already do) so a relay gains nothing, and keep DTLS binding as the open question.

### M5. Chat keys for every epoch, and the recover key, derive from the root (ID 3.1; RT 5.2, 5.3)
- **Problem:** `chatKey` is HKDF of `siteSeed` and the epoch counter; `recoverKey` is HKDF of the root. Rotating every 90 days and deleting old private halves gives nothing against phrase theft, and a phrase thief can sign `rotate` too (if D-10 ships).
- **Failure scenario:** a holder peer or a recording visitor keeps envelopes for months. The phrase leaks once (a photo of the printed kit). The thief derives every past epoch's chat key on every site and reads all kept mail, then rotates each site key with `recoverKey` before the owner of the phrase does, locking them out. RT 9.2's "if someone later gets your chat key" understates it: "if someone ever gets your 12 words, they can read every message anyone kept, on every site".
- **Fix:** make chat keys random per epoch, stored wrapped in the vault and backup file, so deleting an epoch's key actually protects that epoch (accepting that a phrase-only restore cannot read old mail, and saying so). For `rotate`, require a key not derivable from the phrase (a separately printed recovery card) or a waiting period in which the current key can cancel; state who wins a race.

### M6. Every message is a transferable proof of authorship; the proposal never says so (RT 5.3, 5.4, 5.5)
- **Problem:** the inner ECDSA signature names the recipient key and the body hash. The recipient can show any third party a message the sender cannot deny. The goal is "every residual exposure stated".
- **Failure scenario:** after a falling-out, a recipient publishes a DM with its signature; anyone can verify that the sender's site key wrote it to them. In a group, any member can do the same.
- **Fix:** state "messages are signed, so anyone you message can prove to others that you wrote it" in RT 9.2 and the chat card. Offer deniable authentication for DMs (a MAC under a static-static ECDH key between sender and recipient chat keys, which the recipient could also have computed) as the default, keeping signatures for public rooms.

### M7. Small groups: no context in signatures, history open to newcomers, forks on concurrent removal (RT 5.4)
- **Problem:** the inner signature is specified for DMs; group messages say only "the sender's signature inside", with no `groupId` or `epoch` in the signed text. Adding a member hands over the current secret. Two admins removing different members at the same time each create epoch + 1, and nothing orders them.
- **Failure scenario:** (a) a member replays a sender's signed message from group G1 into group G2 or into a later epoch after someone left; it verifies. (b) A new member receives the current secret and asks holders (7-day hold, RT 5.7) for the epoch's envelopes, reading what was said before they joined. (c) Two admins remove two people concurrently; members split into two secrets and two swarms, and each half thinks the other left.
- **Fix:** sign `"mw-grp-msg-v1\n" + ledgerId + groupId + epoch + id + t + SHA-256(body)`; rekey on add as well as remove; order epoch changes with a rule (lowest hash of the signed rekey wins, losers re-propose) and show "group changed by two admins at once". Admin lists must be signed by the creator or an existing admin and checked on every rekey.

### M8. The stranger stamp is not bound to the message (RT 5.6)
- **Problem:** the stamp covers recipient key, day and nonce only. The design does not say whether it sits inside or outside the encryption, so relays may not be able to check it.
- **Failure scenario:** a spammer computes one 20-bit stamp per target per day and attaches it to unlimited messages; or posts it so many senders reuse it. If the stamp is inside the ciphertext, relays forward every unstamped frame and only the recipient pays the decrypt cost.
- **Fix:** bind the stamp to `epk` and the ciphertext hash, put it outside the encryption so relays check it before relaying, and keep a per-recipient seen-set of stamps.

### M9. WANT-TAGS links an IP to a chat key with presence off (RT 5.3, 5.7, 9.2)
- **Problem:** a recipient sends its own stranger inbox tag in WANT-TAGS, and anyone can compute that tag from the public `mw.ck` record. Pair tags sent the same way let a holder link two people's IPs.
- **Failure scenario:** a malicious visitor on the chat lane computes today's inbox tag for every member's chat key, waits for WANT-TAGS, and learns which IP is which member, though nobody turned presence on. "Nobody sees you as online unless you turn presence on" (RT 9.2, PRIVACY-UPGRADES 177) is false.
- **Fix:** request by short tag prefixes shared by many members (fetch more, reveal less). No option fully hides this for stranger mail, because a stranger must be able to compute the tag from public data; so send WANT-TAGS only to holders the visitor chose, and state "asking for your messages shows the people you ask that this IP holds your chat key".

### M10. Private file sharing exposes who shares with whom to trackers, and the exact size (RT 6.3, 6.5, 9.1)
- **Problem:** a private file is a fresh infohash that only the sender and recipients announce. Its ciphertext length equals the plaintext length plus 16 bytes per 64 KiB record.
- **Failure scenario:** the tracker sees a new infohash with exactly two IPs within minutes: sender and recipient, a pairing the chat lane design worked to hide (RT 4.3). The exact length matches a known leaked document. Neither appears in the 9.1 tracker or file rows.
- **Fix:** add both to 9.1; pad private files to size buckets; offer F3 direct send or chat-lane relay for small files so no infohash is announced; delay or batch the recipient's announce.

### M11. Argon2id through WebAssembly is blocked by the shell CSP (ID 3.3, 3.5; SECURITY-MODEL line 75)
- **Problem:** `hash-wasm` compiles WebAssembly; the shell CSP is `script-src 'self'` without `'wasm-unsafe-eval'`, and drop-in hosts set their own CSP. CSP enforcement on WebAssembly compilation is my understanding of current engines, not verified in the lab.
- **Failure scenario:** `wrap:pass` and the encrypted backup file fail on every shell-mode site and on drop-in sites with a strict CSP; the visitor is pushed to session-only or to the phrase, the riskiest route.
- **Fix:** add a lab row; add `'wasm-unsafe-eval'` to the shell CSP (and to the drop-in CSP that `publish --dropin` prints), or ship a pure-JS Argon2id fallback with its own timing row; never silently fall back to a weaker KDF.

### M12. Passkeys: the provider becomes a new recipient, and the PRF wrap protects the root, not one site (ID 3.4)
- **Problem:** ID creates a discoverable passkey per origin but does not specify `user.id`, `user.name` or `displayName`. The PRF output wraps the root, so a passkey tap on any one site unwraps the secret for all sites.
- **Failure scenario:** the loader reuses a root-derived `user.id` or a stable name; the passkey provider's synced list shows every site the person uses under one identity. Separately, a malicious site triggers one legitimate-looking passkey prompt on its own origin and gets the root (B2).
- **Fix:** random `user.id` per site, generic name ("magnet-web key"), state "your passkey provider can see which sites you made passkeys for"; wrap only that site's `siteSeed` on a site origin; wrap the root only on the identity origin (B2).

### M13. Replay windows are not tied to timestamps; room messages carry no site context (RT 4.2, 5.3, 5.5)
- **Problem:** receivers keep a seen-set of `id` "for the retention window" but `t` is not checked against that window. ROOM frames sign `{ room, id, t, text, author }` with no ledger id.
- **Failure scenario:** a holder re-delivers an 8-day-old envelope after the seen-set expired; it shows as new. A recorded Lobby message is replayed later into another room on the same site, or into another site's room under the same key if the visitor linked identities (B1).
- **Fix:** refuse `t` outside the seen-set window plus a stated skew; sign ROOM frames with `"mw-room-v1\n" + ledgerId + room + id + t`.

### M14. "Sites cannot match a visitor by key" and "only you can decrypt" need their conditions in the same sentence (ID 1, 6.4; DIFFERENTIATORS 108 to 109; PRIVACY-UPGRADES 35, 170, 228)
- **Problem:** both claims fail on any site where the root was entered (B2), any origin that claims the ledger (B3), and any device signed out but not removed (M1). The texts state the same-origin limit for the current site only.
- **Failure scenario:** a visitor reads "two sites cannot match you by key", restores their phrase on a new site, and that site links and reads everything.
- **Fix:** rewrite as conditions the visitor can act on: "Only sites you never typed your recovery words into stay unable to match you by key."

## Minors

- **m1. SAS digits (ID 3.5):** 20 bits run to 1,048,575, which is seven decimal digits, not six. Take 20 bits mod 10^6 and state the bias, or show seven digits.
- **m2. Verification library encodings:** WebCrypto signs P1363 `r||s`; Node's `crypto.verify` defaults to DER unless `dsaEncoding: 'ieee-p1363'`. ECDSA signatures are malleable (`s` and `n - s`), so never use the signature as a dedupe or replay key; dedupe on the nonce. Put both in the library and its vectors.
- **m3. Clock skew (ID 4.1):** the 2-minute grace applies to `iat` only; a phone with a wrong clock fails `exp` or `future` with no hint. Apply a stated skew on both ends and return the verifier's time in the error.
- **m4. Record IV and capacity (ID 6.2):** say the IV is 12 random bytes per seal and never a counter (two restored devices would repeat a counter). 1,024 bytes holds a handful of contacts and file keys (a 32-byte key plus a 40-hex infohash is about 100 characters encoded); specify the overflow behaviour (second record, or keep `contacts` and `files` vault-only). Changing `signKey` index changes `authorPub` in the AAD; say records are re-sealed on rotation.
- **m5. Advisory roles (ID 5, D-8):** `_roles/` is a `put`, last writer wins among moderators, and any moderator can label anyone "owner". Say in the SDK docs that site code must never gate a security decision on `_roles/`.
- **m6. Private files on by default (RT 6.1):** F2 "on for signed-in members when chat is on" contradicts RT principle 1 (uploads opt in). Make it a separate opt-in.
- **m7. Bans remove more than posts (`state.js` lines 32 to 34):** a ban drops every payload of the author, so the banned person's `mw.ck` record and sealed record disappear from honest copies and they become unreachable by DM. State it in ID 6.3 and RT 8; `unban` (D-10) would not bring back values already dropped by peers.

## Claims that hold

- Domain-separated prefixes for block, login, chat-key and message signatures (ID 3.2) prevent cross-purpose replay among those uses.
- The record AAD binds ledger, author and version (ID 6.2); with `append` rather than `put` (U-7 to confirm), another author cannot substitute a record.
- File STREAM encryption (RT 6.3) with a random per-file key, counter nonces and a final-record flag is sound for the stated sizes; plaintext pieces never reach the swarm for F2.
- The serving rule for uploads (RT 6.6) is the right control.
- The honest statements already present (no forward secrecy, no server session, same-origin code can act while unlocked, no per-site shredding while the phrase exists) are correct, though M5 and M14 show they understate the reach.

## What this means for the build

Wave 0 must add owner decisions for B1 (format and library), B2 (identity origin in v0.3, with the popup and storage-partitioning lab row), B3 (origin list), B4 (protocol rewrite) and B5 (redact, not reject) before agent A1 starts, because each changes `derive.js`, `login.js`, `link.js` or `block.js`. M1, M5 and M12 change what is stored and wrapped, so they also belong before A1 and A3.
