# w1-08 - Mobile browser constraints (iOS Safari, Android Chrome, Samsung Internet, Firefox Android)

- Research date: 2026-10-17. "Current" means as of that date.
- Project: magnet-web (static loader + WebTorrent/WebRTC + Service Worker rendering + replicated signed chain). This file answers topic 08 of wave 1: what mobile browsers allow, what breaks, and what policy and minimum-browser matrix follow.
- Method: primary sources read directly (WebKit/Chromium/Gecko source files, WebKit bugs and release notes, Apple/Android/MDN/Chrome docs, MDN browser-compat-data JSON, caniuse usage data, TC39 repos), plus experiments run on this Mac against the project's vendored `webtorrent@3.0.21` bundle in Chromium 156 (V8) and in Playwright's **WebKit 27.2 build (JavaScriptCore, macOS)**. Scripts and raw results are in `docs/research/labs/w1-08-mobile-lab/` (run with `node`, needs the repo's `node_modules`). **Not tested on any phone**: no iOS or Android device was used, WebKit ran on macOS (same engine and storage code as Safari, different platform layer), and Firefox 157 was downloaded but would not start here (`Could not find profile folder`, even when launched directly with an existing profile directory), so SpiderMonkey was never run. Every iOS/Android *behaviour* below therefore comes from source code, vendor docs or developer reports, and says so.
- Confidence: **high** = primary source read directly, or two independent sources agree, or reproduced here. **medium** = one good source, partial conflict, or code reading without a device test. **low** = anecdote or my own inference (labelled "inference").
- Design-critical = if the claim is wrong, the architecture or a compatibility promise changes.
- Age flag: [OLD: year] marks non-normative sources older than 2024.
- Reference versions (MDN browser-compat-data `browsers/*.json`, read 2026-10-17): Chrome 155 (released 2026-10-06; 4-week cadence up to 152 on 08-25, then every 2 weeks: 153 = 09-08, 154 = 09-22, 155 = 10-06), Firefox 158 (2026-10-13), Safari and iOS 27 (2026-09-14, WebKit 625.1.29), Samsung Internet 30.0 (2026-05-11, Blink 143), Playwright Chromium 156.0.8078.4 (used for the experiments).

## Summary

1. **Hard blocker, reproduced.** The vendored WebTorrent bundle calls `Uint8Array.prototype.toHex/toBase64` and `Uint8Array.fromHex` (via `uint8-util@2.3.2`, unguarded). These are ES2026 (TC39 Stage 4 in July 2025, not ES2025) and shipped in **Chrome/Edge/Android Chrome/WebView 140, Firefox 133, Safari/iOS 18.2, Samsung Internet 30**. With the six methods deleted, `new WebTorrent()` itself throws `TypeError: e.toBase64 is not a function` (so the failure comes at construction, earlier than the first `client.add()`). caniuse usage (2026-10-13) puts about **8.5 % of global web traffic** on engines without them (iOS Safari < 18.2 alone is 1.10 %, i.e. 7.5 % of iOS Safari users; Chrome desktop < 140 is 4.05 %). A **2,448-byte polyfill** (1.2 KB gzip) written for this study passes 78/78 official test262 cases for the four methods it implements on both V8 and JavaScriptCore (WebKit 27.2), and with it the same bundle seeds an identical infohash in both engines and completes a real 3 MiB WebRTC transfer in Chromium. Install it in `boot.js` (P0).
2. **A phone only helps the swarm while the page is visible.** Apple's own docs give an app 5 s after entering the background before suspension; Apple DTS says that once suspended "all low-level networking stops"; WebKit gives a web process a 20 s prepare-to-suspend window and keeps nothing alive for a data-channel-only page. On Android, cached processes may receive "limited or no execution time" since Android 13. Chrome's exemptions for pages with an open data channel only apply to hidden tabs inside a running Chrome. Firefox Android delays timers in inactive tabs by 15 minutes and may unload them. The ARCHITECTURE section 8 "seed when hidden" and "gossip when hidden" rows cannot be honoured on mobile.
3. **A dead tracker socket takes minutes to heal.** `bittorrent-tracker` reconnects after `10 s x 2^retries + random(0..5 min)` and ignores `announce()` while reconnecting, so `TorrentManager.resume()` calling `tracker.update()` does nothing for minutes after a phone returns from the background. Measured with the bundled code: eight clients re-announced after 56, 73, 80, 152, 171, 226, 265 and 300 s (median 171 s). Rebuild the torrent instead of resuming it.
4. **iOS will never tell the page anything about the network, battery or memory.** WebKit's tracking-prevention page lists the Network Information API, Battery Status API and Device Memory API as features it will not implement; a request for "power-saving detection" was closed on 2026-07-07. Android Chromium offers `navigator.connection` (Chrome 61, Android 38, Samsung 8.0), `getBattery` and `deviceMemory`; Firefox Android removed `navigator.connection` in 99. So "unknown network" is the normal iPhone case and must default to download-only, which matches what Windows Delivery Optimization (a large production P2P system) does by default: no upload on cellular, on battery or in standby, plus a monthly upload cap.
5. **Memory is fine at the planned caps but not at 128 MiB on small devices.** WebKit engineers: iPhone WebContent processes have a "soft" limit of about 1.5 GB (lower on low-RAM models); the tab is killed with no catchable exception. Measured here (desktop Chromium proxy, vendored bundle, in-memory chunk store): a 128 MiB site raised the tab from 94 MB to 296 MB at rest and **peaked at 434 MB while building the Blob (about 2.7x the site size)**; 24 and 48 MiB sites sat at 160-225 MB. 48 MiB mobile and 24 MiB cellular caps are safe; 128 MiB belongs on desktop or `deviceMemory >= 4`.
6. **On iOS Safari tabs the whole local database is a cache, not a store.** ITP deletes IndexedDB, Cache API, LocalStorage, SessionStorage, Service Worker registrations, media keys and OPFS after days of Safari use without user interaction (published rule: 7 days; WebKit trunk since 2024-02-09 uses a 30-operating-day window unless the site was reached through unfiltered link decoration from a classified tracker; the shipping version was not determined, so plan for 7). Exempt: Home Screen web apps, app-bound/managed domains, domains with recent Web Push use. **`navigator.storage.persist()` resolves false in an ordinary Safari tab** (WebKit grants it only to exempt domains; confirmed on WebKit 27.2 in both ephemeral and persistent contexts); it helps on Chromium (silent heuristics) and Firefox (a prompt). The identity key, TOFU pin, chain and cache all live in that purgeable store.
7. **Service Workers by container.** iOS Safari and Home Screen apps: yes (11.3+). Other iOS browsers: yes if they hold the default-browser entitlement (WebKit `WKWebView.mm` gate). Generic WKWebView in-app browsers (Instagram, Facebook, Gmail, ...): no. Lockdown Mode: no (see 03/04). EU (iOS 17.4+) and Japan (iOS 26.2+, MSCA) allow non-WebKit engines by entitlement, but per Open Web Advocacy (2026-05-15, 2026-06-18) no browser vendor has shipped one; treat every iPhone browser as WebKit and feature-detect.
8. **bfcache and WebRTC differ per engine.** Chrome and Firefox refuse to bfcache a page with an open RTCPeerConnection; Safari does cache it but suspends and closes its sockets (restored peers are dead). The existing `pageshow`-persisted reload in `app.js` is the right answer for Safari.
9. **Minimum-browser matrix** (with the two polyfills): refuse below iOS/Safari 14.5, Chromium 80, Firefox 78, Samsung 13; promise and test iOS/Safari 16.4+, Chromium/Edge 110+, Firefox 115 ESR+, Samsung Internet 21+ (Blink 110). Native base64/hex needs 18.2 / 140 / 133 / Samsung 30.
10. **Corrections to earlier work.** (a) The review's B1 is right but understated: it fails in the constructor, and the proposal is ES2026. (b) The review's claim that `BigInt64Array` is used by the bundle was not found (0 matches in the 3.0.21 minified bundle), and neither the bundle nor `src/` uses `structuredClone` or `.at()`, so the hard floor is lower than the review's 15.4/110/115 (those remain sensible *support* floors). (c) `FileSystemFileHandle.createWritable` is Safari **26**, so Safari 15.2-25.x take the `fsa-chunk-store` polyfill path. (d) `persist()` cannot be earned in a Safari tab, contrary to the review's M1 advice.
11. **New from running WebKit 27.2 (macOS):** in an **ephemeral (private-browsing-style) session OPFS throws `UnknownError` and IndexedDB refuses every Blob/File value** (`Error preparing Blob/File data to be stored in object store`; ArrayBuffers are fine), so WebTorrent's default store and the loader's Blob-in-IndexedDB persistence both fail in a Safari private tab (R-05, R-21). A non-extractable **P-256 and Ed25519 CryptoKey survive an IndexedDB round trip, X25519 does not** (WebKit bug 312279 still reproduces). `connection`, `deviceMemory` and `getBattery` are `undefined` in WebKit 27.2.
12. **What I could not verify**: any real-device timing (iOS teardown seconds, Android screen-lock behaviour), the ITP window in shipping Safari, `persist()` in a Home Screen app, SpiderMonkey/Firefox behaviour, Samsung Internet's own storage/tracking features (its developer docs are stale), and whether any alternative-engine browser has shipped since June 2026.

### B. ES2026 base64/hex and the other polyfillable APIs

**F-03. Uint8Array base64/hex support.** `Uint8Array.prototype.toHex/toBase64/setFromHex/setFromBase64` and `Uint8Array.fromHex/fromBase64`: Chrome, Edge, Chrome Android, WebView **140**; Firefox and Firefox Android **133**; Safari and iOS **18.2**; Samsung Internet **30.0** (first Blink >= 140); Node 25.0.0; Deno 2.5.0. The proposal reached Stage 4 at the July 2025 TC39 meeting with "Expected Publication Year 2026", i.e. **ES2026, not ES2025**.
- Confidence: high. Design-critical: **yes** (compatibility promise).
- Evidence: BCD `javascript/builtins/Uint8Array.json` (all six entries identical; mirror resolved with the Samsung release table); `tc39/proposals/finished-proposals.md` row "Uint8Array to/from Base64", notes link `2025-07/july-28.md#uint8array-base64hex-for-stage-4`, year 2026; proposal README: "currently at stage 4 ... This repo is archived."
- Sources: BCD above ; https://raw.githubusercontent.com/tc39/proposals/main/finished-proposals.md ; https://raw.githubusercontent.com/tc39/proposal-arraybuffer-base64/main/README.md.

**F-04. The vendored WebTorrent cannot even be constructed without them.** `uint8-util@2.3.2` (`src/browser.ts`) defines `arr2hex = data => data.toHex()`, `hex2arr` -> `Uint8Array.fromHex(str)` for strings longer than 64 chars, `arr2base = bytes => bytes.toBase64()` with no feature guard, and `dist/webtorrent.min.js` contains `toHex` x1, `fromHex` x1, `toBase64` x1. Experiment: headless Chromium 156 with the six natives deleted -> `new WebTorrent(...)` throws `TypeError: e.toBase64 is not a function` at `webtorrent.min.js:1:76027` called from `new Wn` (the WebTorrent constructor, 1:212477); WebKit 27.2 with the natives deleted fails at the same call site (`y` at 1:76035 from `Wn` at 1:212478). Nothing in the current `boot.js` feature list predicts this, and `MIN_BROWSERS` there claims Safari 14+ / Chrome 80+.
- Confidence: high (source + reproduced). Design-critical: **yes**. Affects every iPhone on iOS <= 18.1 (1.10 % of global traffic by F-02), Chrome/Edge < 140, Firefox < 133, Samsung Internet <= 29, and in-app WebViews that have not updated: about 8.5 % of global traffic in total (sum of the caniuse rows above, excluding Android Chrome/Firefox tails).
- Evidence: `node_modules/uint8-util/src/browser.ts`; grep counts on `node_modules/webtorrent/dist/webtorrent.min.js`; `docs/research/labs/w1-08-mobile-lab/out/results-webtorrent-b64.txt` (variant B).
- Sources: local vendored files (webtorrent 3.0.21, uint8-util 2.3.2) ; lab results.

**F-05. A correct polyfill costs 2.4 KB and passes the official tests.** My polyfill (`labs/w1-08-mobile-lab/u8-polyfill.js`, full source in Appendix C) implements `toHex`, `toBase64({alphabet, omitPadding})`, `fromHex`, `fromBase64(str, {alphabet, lastChunkHandling})` with all three `lastChunkHandling` modes, ASCII-whitespace skipping, brand and detached-buffer checks, spec property descriptors and `length`/`name`, in ES2017 syntax. It omits `setFromHex/setFromBase64` (nothing in the stack calls them). Size: 3,680 B source, **2,448 B minified (esbuild 0.28.2, target es2017), 1,193 B gzip-9**; the proposal's own reference polyfill is 9,427 B source / 5,036 B minified. Results: test262 (`test/built-ins/Uint8Array/{fromBase64,fromHex,prototype/toBase64,prototype/toHex}`, 39 files x sloppy+strict = **78/78**) in a Node vm realm and in Chromium 156 with natives deleted; native Chromium 156 also scores 78/78, so the runner is faithful. End to end: with the six natives deleted plus the polyfill, `client.seed()` of a 600,000-byte file yields infohash `0d728bec15bd1f0ea2beabc959a1d2bd84e07f97`, identical to native Chromium and to Node `create-torrent`+`parse-torrent`, and two clients move 3 MiB over WebRTC through a local tracker in 162 ms with a matching SHA-256 (native: 157 ms; Chromium only, see F-32 for why WebKit could not be used for the transfer).
- Confidence: high for V8 (Chromium 156) and for JavaScriptCore (WebKit 27.2: native 78/78, natives deleted + polyfill 78/78, bundle seed gives the same infohash `0d728bec...`); **medium for older Safari/iOS builds and for Firefox** (SpiderMonkey not run; "WebKit 27.2 with natives deleted" is not "iOS 17"; the polyfill only uses `btoa`/`atob`, typed arrays and regexes).
- Design-critical: yes (it is the fix for F-04).
- Evidence: `out/results-t262-node.txt`, `out/results-t262-browser.txt`, `out/results-t262-webkit.txt`, `out/results-webtorrent-b64.txt`, `out/results-webtorrent-b64-webkit.txt`; 70 test262 files fetched from `raw.githubusercontent.com/tc39/test262/main/test/built-ins/Uint8Array/` (the 31 setFrom* files fail by design).
- Sources: https://raw.githubusercontent.com/tc39/test262/main/test/built-ins/Uint8Array/ (files listed in `t262-files.txt`) ; https://raw.githubusercontent.com/tc39/proposal-arraybuffer-base64/main/playground/polyfill-core.mjs (reference, read 2026-10-17).

### C. Backgrounding, screen lock and lifecycle

**F-07. iOS: a hidden page loses the network within seconds; nothing keeps a data-channel page alive.** Apple's UIKit docs: after the app moves to the background "that method has five seconds to perform any tasks and return. Shortly after that method returns, the system puts your app into the suspended state"; background tasks extend this for a "finite amount of time". Apple DTS (forum thread 799259, Sep 2025, native-app context): "everything works like it does in the foreground as long as your app is running. Once your app gets suspended, however, all low-level networking stops"; with the screen locked "the device might eventually get around to turning off Wi-Fi". WebKit (`ProcessThrottler.cpp`): `processSuspensionTimeout { 20_s }` (prepare-to-suspend message plus a 20 s timer), `removeAllAssertionsTimeout { 4_min }`, `processAssertionCacheLifetime { 1_s }`; the background-keeping activities I found in `WebPageProxy.cpp` are a page that is "likely to show notifications" and a title-change trick that is **disabled on iPhone** (`deviceClassIsSmallScreen`); media capture and audio have their own paths (not read), and there is no activity for RTCDataChannel. Net: a data-channel page dies somewhere between about 5 s and 20 s after hiding (inference; not measured on a device), and a screen lock hides the page.
- Confidence: high that it dies; **low** on the exact seconds. Design-critical: **yes**.
- Evidence: the three sources above plus WebKit `LibWebRTCSocket` (F-11).
- Sources: https://developer.apple.com/tutorials/data/documentation/uikit/extending-your-app-s-background-execution-time.json ; https://developer.apple.com/forums/thread/799259 (read through WebFetch, Sep 2025; independently quoted in research 03) ; `WK:Source/WebKit/UIProcess/ProcessThrottler.cpp` ; `WK:Source/WebKit/UIProcess/WebPageProxy.cpp` (lines ~10660-10670, ~16944-16953).

**F-08. Android: the same rule applies to the browser app; Chrome's data-channel exemptions are for hidden tabs inside a running Chrome.** Android docs: "Since cached processes can be killed by the system at any time, apps should cease all work while in the cached state ... Starting in Android 13, an app process may receive limited or no execution time until it enters one of the above active lifecycle states." Chrome: timers in hidden pages are only "Throttled" (once per second) when WebRTC is active and are never "Intensively throttled" (once per minute, Chrome 88) while WebRTC is active; the Page Lifecycle doc says hidden pages using WebRTC "won't be discarded unless under extreme resource constraints"; Chromium's freezing policy lists `CannotFreezeReason::kWebRTC`, `kHoldingWebLock`, `kHoldingBlockingIndexedDBLock`. Whether that desktop policy also runs on Android Chrome is **not established**. Doze (03) can suspend network access when the device is idle with the screen off.
- Confidence: high for the documented rules; low for what Chrome Android actually does to an open data channel on screen lock (no measurement exists). Design-critical: **yes**.
- Sources: https://developer.android.com/guide/components/activities/process-lifecycle (read via WebFetch) ; https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout ; https://developer.chrome.com/docs/web-platform/page-lifecycle-api ; `chromium.googlesource.com/chromium/src/+/refs/heads/main/components/performance_manager/freezing/freezing_policy.cc?format=TEXT` ; research 03 F-19, F-34.

**F-09. Firefox Android: 15-minute timers and tab unloading.** MDN `setTimeout`: "Firefox for Android has a minimum timeout of 15 minutes for inactive tabs and may unload them entirely"; Firefox desktop 1 s. A timer-based heartbeat or "pause after N seconds hidden" never fires there.
- Confidence: high (MDN, current text). Design-critical: yes (timer logic must use timestamps).
- Sources: https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout .

**F-10. Lifecycle events: only `visibilitychange` and `pagehide`/`pageshow` are portable; `freeze`/`resume` are Chromium-only.** `Document` `freeze`/`resume` events and `document.wasDiscarded`: Chrome/Edge 68, Samsung Internet 10.0, WebView 68; **no Firefox, no Safari/iOS** (BCD). `visibilitychange`: Chrome 62, Firefox 56, Safari/iOS 14.1. `pageshow`/`pagehide` + `PageTransitionEvent.persisted`: Chrome 3/4, Firefox 6/11, Safari 5/4 (iOS). Chrome's Page Lifecycle doc and MDN both say the transition to `hidden` is "the last event that's reliably observable ... especially on mobile" because `beforeunload`, `pagehide` and `unload` are not fired when the user swipes the app away. The doc also tells apps to close WebRTC, IndexedDB, BroadcastChannel, WebSocket and Web Lock holders on `freeze`. The doc text says `wasDiscarded` is desktop-only (Android "being tracked"), while BCD mirrors 68 to Android: treat Android support as unverified.
- Confidence: high. Design-critical: yes (do state work on `visibilitychange`, not `pagehide`).
- Sources: `BCD: api/Document.json, api/Window.json, api/PageTransitionEvent.json` ; https://developer.chrome.com/docs/web-platform/page-lifecycle-api ; https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event .

**F-11. bfcache and open WebRTC connections.** Chrome and Firefox treat a page with an open RTCPeerConnection as ineligible (WPT `back-forward-cache-with-open-webrtc-connection` expects `not restored`, reasons `rtc`, `mediastream`; Chromium tracks `kWebRTC` "WebRTC live connection" and `kWebRTCSticky`). WebKit does the opposite: on page-cache entry `RTCPeerConnection::suspend(BackForwardCache)` suspends the socket factory and `LibWebRTCSocket::suspend()` sets `m_isSuspended` and calls `signalClose(-1)`, drops incoming packets and silently swallows outgoing ones; WebKit engineer youennf (2024-01-23): "We are shutting down the TCP/UDP connections", and (2026-04-09): "There is no spec stating whether RTCPeerConnection should prevent entering page cache or not. Safari is supporting it, Chrome and Firefox are not." After a Safari restore (`pageshow.persisted === true`) the peers are dead. For WebSockets, web.dev (updated 2026-10-16): "Chrome (as of 149) and Safari do not block on open WebSockets but other browsers do"; WebKit closes the socket and queues a `close` event (bug 301702, resolved INVALID 2025-11-27, intentional per bug 143505). The vendored bundle registers no `unload`/`beforeunload` handler (0 matches) and one `pagehide` handler (inside `fsa-chunk-store`). DataChannel-specific WebKit fixes that matter for dead-peer detection on older iOS: 26.4 "RTCDataChannel close events did not fire when RTCPeerConnection was closed" and 27.0 "RTCDataChannel did not check the SCTP buffered amount synchronously", so on iOS <= 26.3 a closed or dead connection may not report `close` and the loader must rely on its own per-wire inactivity timeouts (research 01 F31). Message-size and back-pressure limits per engine are in research 03 (its F-25 and F-26).
- Confidence: high for the code paths; medium for exact Safari restore behaviour (not device-tested). Design-critical: medium. The current `app.js` `pageshow` handler (`if (e.persisted && S.destroyed) location.reload()`) is correct.
- Sources: https://lists.w3.org/Archives/Public/public-webrtc-logs/2026Apr/0022.html ; https://lists.w3.org/Archives/Public/public-webrtc-logs/2024Jan/0203.html ; https://raw.githubusercontent.com/web-platform-tests/wpt/master/webrtc/back-forward-cache-with-open-webrtc-connection.https.window.js ; `WK:Source/WebCore/Modules/mediastream/RTCPeerConnection.cpp`, `WK:Source/WebKit/WebProcess/Network/webrtc/LibWebRTCSocket.cpp`, `LibWebRTCMediaEndpoint.cpp` ; https://web.dev/articles/bfcache ; https://bugs.webkit.org/show_bug.cgi?id=301702 ; `chromium.googlesource.com/.../third_party/blink/common/scheduler/web_scheduler_tracked_feature.cc?format=TEXT` .

**F-12. After a drop, the tracker client waits `10 s x 2^retries + random(0..5 min)` and ignores announces meanwhile.** `bittorrent-tracker` `websocket-tracker.js`: `RECONNECT_MINIMUM = 10 s`, `RECONNECT_MAXIMUM = 60 min`, `RECONNECT_VARIANCE = 5 min`; `_startReconnectTimer` waits `floor(random * 5 min) + min(2^retries * 10 s, 60 min)`, sets `reconnecting = true`, and `announce()`/`scrape()` return immediately while `reconnecting`; `retries` resets only on a successful open. `TorrentManager.resume()` calls `tracker.update()`, which is therefore a no-op until the reconnect timer fires. Measured here with the bundled code (8 browser clients in Chromium 156, server-side `terminate()` of every tracker socket at 21:40:31Z): the first re-announce arrived after **55.9, 73.0, 80.1, 152.3, 171.1, 225.9, 265.3 and 299.9 s (median 171 s, maximum 300 s)**, matching `10 s + U(0, 300 s)`; with `Math.random` pinned to 0 all four clients of the smoke test re-announced after 10.1 s, which validates the harness. The server emits no event for announces without an `event` field, so the harness parses the raw WebSocket messages.
- Confidence: high (code read; measurement above). Design-critical: **yes** for the mobile resume path.

**F-13. Continuous WebRTC is a battery and radio cost; the one large production P2P system avoids it by default.** RFC 7675: consent expires after 30 s and STUN consent checks default to every 5 s (randomised 0.8-1.2x, never below 4 s) per connection. Android's networking guide (updated 2026-10-16): for a typical radio "every data transfer session will cause the radio to draw energy for at least 18 seconds" (transfer + 5 s tail + 12 s low state) and "an app which makes a one second data transfer, three times a minute, will keep the wireless radio perpetually active". So any open peer connection pins a cellular radio awake (inference: the guide's example is 3G, but "the general principles and resulting best practices are applicable for all wireless radio implementations"). Microsoft's Delivery Optimization (Windows' built-in P2P content delivery): its peering port is inactive when the device "is on low battery", "in Connected Standby", "using a cellular network" or on a disallowed VPN (FAQ updated 2026-10-01); "By default, devices won't upload while on battery" (reference updated 2026-05-21); default monthly upload cap 20 GB.
- Confidence: high for the quoted rules; medium for the inference. Design-critical: yes (policy defaults).

**F-14. iOS exposes no network, battery, power-mode or memory signal, and WebKit says it will not.** The WebKit tracking-prevention page lists, among "features we have decided to not yet implement due to fingerprinting, security, and other concerns, and where we do not yet see a path to resolving those concerns": **Device Memory API, Network Information API, Battery Status API**, User Idle Detection and others. Low Power Mode only shows up indirectly: WebKit then aligns timers of a *visible* page to 30 ms (vs 0 s) and hidden pages are aligned to 1 s (`DOMTimer.h`). `prefers-reduced-data` is Chromium behind a flag and nowhere else.
- Confidence: high. Design-critical: **yes** (an iPhone on LTE with Low Data Mode is indistinguishable from a desktop on Wi-Fi).

### D. Memory

**F-16. iOS: a soft limit of about 1.5 GB per tab on iPhone, no JavaScript exception, undocumented by Apple.** WebKit engineer Simon Fraser (bug 277848, 2024-08-09): "WebContent processes on iPhone are subject to a 'soft' limit of around 1.5GB; if they use more than this amount of memory, they are subject to getting killed by 'jetsam'. ... these processes are allowed to go above this limit and will not be killed if memory demands from other processes are low ... design your web content to not exceed the 1.5GB limit. It will be somewhat lower on iPhone models with less RAM." (The reporter saw ~3 GB right after a reboot and 1.5 GB after 2-3 days.) Ben Nham (bug 268816, 2024-03-13): "On iPhones, for most devices, the limit is 1.5GB ... On iPad, the WebContent process has a higher memory limit ... For an 8GB device, the limit will be in the 4GB+ range"; typed arrays and Wasm memory live in a separate "Gigacage" of 2 GB on iOS (later enlarged by 277124@main); Alexey Proskuryakov: "I do not think that this is documented by Apple." Jeff Johnson (2026-01-22, iOS 26.2): a page filling a JS array crashed at the "100 MB" setting on an iPhone SE 3rd gen and "200 MB" on an iPad 8th gen, and "there's no JavaScript exception to catch" (his test pushes size x 2^20 array elements, about 8 bytes each, so the real figure is roughly 0.8-1.6 GB: inference).
- Confidence: high for the 1.5 GB soft limit (two WebKit engineers); medium for low-RAM models (stated qualitatively only). Design-critical: **yes** (caps).
- Sources: https://bugs.webkit.org/show_bug.cgi?id=277848 ; https://bugs.webkit.org/show_bug.cgi?id=268816 ; https://lapcatsoftware.com/articles/2026/1/7.html .

**F-17. Measured footprint of the download path (desktop Chromium proxy).** Vendored WebTorrent, custom abstract-chunk-store holding piece buffers, `storeCacheSlots: 0`, then `file.blob()` and an IndexedDB `put(Blob)`; tab renderer RSS via `ps`, after `gc()`; two runs. Baseline 94-95 MB. **128 MiB site** (128 KiB pieces): 296 MB when all pieces are held (+201 MB = 1.6x the site), **434-435 MB at the `file.blob()` peak (+340 MB = 2.7x)**, 297 MB after the IDB write, still 296 MB after `client.destroy()` (RSS is not returned to the OS). **48 MiB**: 188-224 MB at rest, 188-282 MB peak. **24 MiB**: 161-180 MB, no visible spike. Default OPFS store (`fsa-chunk-store`) at 128 MiB: 194-213 MB at rest, 367-375 MB peak, 229-238 MB after the write. Run-to-run variance: 36 MB at rest and up to 94 MB at the peak for the 48 MiB case, under 2 MB for the 128 MiB case. Rule of thumb for planning: **peak tab memory ~ 95 MB + 2.7 x site size** with an in-memory store (~2.2x with OPFS), so 128 MiB ~ 440 MB (29 % of an iPhone's 1.5 GB), 48 MiB ~ 225 MB, 24 MiB ~ 160 MB. The whole Chromium process tree (browser, GPU, both renderers) grew by about 0.41 GB between baseline and the Blob peak at 128 MiB.
- Confidence: medium (one engine, one machine, RSS not PSS; phones differ; Safari's Blob and allocator behaviour not measured). Design-critical: yes.
- Evidence: `labs/w1-08-mobile-lab/mem-exp.mjs`, `out/results-memory.txt`, `out/mem-results-*.json`.
- Sources: lab results ; vendored `webtorrent.min.js` 3.0.21.

**F-18. Android: no published per-tab limit; one low-end data point; Chromium has a coarse RAM hint.** No Android or Chrome document gives a per-tab memory limit; renderer processes are killed by the low-memory killer in importance order. A WebTorrent user reported Android Chrome 95 on a Moto G8 crashing while seeding a 170 MB file (70 MB worked) with WebTorrent 1.5.6 [OLD: 2021, anecdote, no memory figures]. `navigator.deviceMemory` gives a power-of-two RAM class on Chrome (63), Edge, Samsung Internet (8.0) and WebView; not Firefox, and WebKit has declined it (F-14).

### E. Storage, eviction and persistence

**F-19. Quota rules.** iOS/iPadOS 17 and Safari 17: per-origin quota up to **60 % of total disk for "browser apps" (apps that can be the default browser, so Safari, Chrome iOS, Firefox iOS, ...) and 15 % for other WebKit apps (WKWebView)**; a Home Screen web app gets the browser-app quota; cross-origin frames get 10 % of the main frame's quota; overall limits 80 % / 20 %; `QuotaExceededError` on overflow; `estimate()` values "might change based on factors like existing usage and site visit frequency" (fingerprinting mitigation). Chromium (Chrome, Edge, Android Chrome): origin up to 60 % of disk in both modes, browser up to 80 %; in incognito about 5 % of disk; with Chrome's "Clear cookies and site data when you close all windows" the quota drops to about 300 MB. Firefox: best-effort origin limit is the smaller of 10 % of disk and a 10 GiB group limit; persistent origins up to 50 % (cap 8 TiB). So quota is not the mobile constraint; eviction is (F-20).
- Confidence: high (WebKit blog + MDN agree; web.dev 2024-09-23 for Chrome). Design-critical: no.
- Sources: https://webkit.org/blog/14403/updates-to-storage-policy/ (2023-08-10) ; https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria ; https://web.dev/articles/storage-for-the-web (updated 2024-09-23).

**F-20. Safari ITP deletes script-writable storage of unvisited sites; the clock and the exact window need care.**
- Published rule: ITP "deletes all cookies created in JavaScript and all other script-writeable storage after 7 days of no user interaction with the website" - IndexedDB, LocalStorage, media keys, SessionStorage, "Service Worker registrations and cache". The 2020 post specifies "seven days of Safari use": the counter advances only on days the browser is used, and Home Screen web apps "have their own counter".
- Source code (WebKit main): the data types ITP monitors and removes are Cookies, **DOMCache, IndexedDBDatabases, LocalStorage, MediaKeys, SessionStorage, ServiceWorkerRegistrations and FileSystem (OPFS)**. The windows are `operatingDatesWindowShort = 7` and `operatingDatesWindowLong = 30` operating days. Since commit 4506123001 (2024-02-09, bug 265598) the removal window for an ordinary domain is **Long (30)**; it is Short (7) only for a domain reached by a cross-site navigation with link decoration from a classified tracker while link-decoration filtering is off. The commit message still describes the old rule as "7 operational-days" and calls filtering "currently disabled by default". Which Safari release first shipped this was **not determined**; both WebKit documents still say 7. Plan with 7, expect up to 30.
- Exempt (`domainsExemptFromWebsiteDataDeletion` plus Web Push): app-bound domains, managed domains, sites persisted through an embedder SPI (added 2024-07-22), **the Home Screen web app's own domain**, and domains with Web Push interaction inside the Long window.
- Status 2025-2026: the Safari 26.0-26.6 and 27.0 release notes (searched for ITP, storage, tracking and persistence changes) announce no change to ITP storage deletion; 26.0 added that known fingerprinting scripts may not "set long-lived script-written storage such as cookies or LocalStorage".
- Applies to every WebKit browser on iOS that keeps tracking prevention enabled (inference from the shared `WebsiteDataStore` code; `defaultTrackingPreventionEnabled()` depends on the host app).
- Confidence: high for the rule and data types; medium for the 7-vs-30 detail (trunk code, not a shipped-binary test). Design-critical: **yes** (identity key, TOFU pin, chain DB and site cache are all in this store).
- Sources: https://webkit.org/tracking-prevention/ ; https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/ (2020-03-24) ; `WK:Source/WebKit/NetworkProcess/Classifier/{ResourceLoadStatisticsStore.cpp,WebResourceLoadStatisticsStore.cpp}` ; commit https://github.com/WebKit/WebKit/commit/45061230013728ec9c4900b01b12af26dc592b4b (message + diff, read through the GitHub API) ; https://webkit.org/blog/17333/webkit-features-in-safari-26-0/ and the 26.1-26.6 and 27.0 posts.

**F-21. `navigator.storage.persist()` per browser.** Support: Chrome 55, Firefox 57, Safari/iOS 15.2, Samsung 6.0; `estimate()`: Chrome 61, Firefox 57, Safari 17. **Safari**: `NetworkStorageManager::persist` only returns true when the origin's registrable domain is in the exempt set from F-20 (`persistOrigin`), and only for top-level origins; so it resolves **false in an ordinary Safari tab** and true in a Home Screen web app. Confirmed empirically on WebKit 27.2 (macOS): `persisted()` and `persist()` returned `false` in both an ephemeral and a persistent context (Chromium 156 headless also `false`); the Home Screen path was not testable. The 2023 WebKit post says the same in prose: "WebKit currently grants a request based on heuristics like whether the website is opened as a Home Screen Web App." **Chromium** (Chrome, Edge, Android Chrome; Samsung assumed): silent decision from "site engagement, installed or bookmarked, notification permission" (web.dev, [OLD: 2020]); MDN (current): "Safari and most Chromium-based browsers ... automatically approve or deny the request based on the user's history of interaction with the site and do not show any prompts". **Firefox**: a permission prompt, so call it only after a user gesture. Persistent origins are skipped by LRU eviction under storage pressure.
- Confidence: medium-high (source reading + MDN). Design-critical: yes (review M1's "call persist() and the identity survives" does not hold for Safari tabs).
- Sources: `BCD: api/StorageManager.json` ; `WK:Source/WebKit/NetworkProcess/storage/NetworkStorageManager.cpp` (lines ~882-950), `WK:Source/WebKit/NetworkProcess/NetworkProcess.cpp` (~845) ; https://webkit.org/blog/14403/updates-to-storage-policy/ ; https://web.dev/articles/persistent-storage [OLD: 2020] ; the MDN quotas page above.

**F-22. Eviction in general, and what a Home Screen / installed app buys.** Eviction is per origin and all-or-nothing; triggers are storage pressure (LRU over non-persistent origins), exceeding the browser-wide quota, and, only in Safari, inactivity (F-20). Chrome "very rarely" evicts. **iOS Home Screen web apps** (iOS 26.0: "every site can be a web app on iOS and iPadOS", "zero requirements for 'installability'", the user can opt out when adding): exempt from ITP, `persist()` succeeds, full browser-app quota, own storage container ("Storage shared with Browser: no"; login cookies are copied at install since iOS 17.2), installable from other browsers since 16.4 if they opt in, no install prompt or banner, Web Push only for installed apps, no Background Sync/Fetch. They still get suspended like any app. **Android Chrome** installed PWAs raise engagement, which feeds the `persist()` heuristic; they are foreground-only too.
- Confidence: high. Design-critical: yes (the one durable-storage path on iOS).
- Sources: https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria ; https://webkit.org/blog/17333/webkit-features-in-safari-26-0/ ; https://firt.dev/notes/pwa-ios/ (read 2026-10-17) ; https://webkit.org/tracking-prevention/ ("Home Screen Web Application Domain Exempt From ITP").

**F-23. Safari IndexedDB has had connection and transaction defects fixed as recently as 27.0.** 26.4: "IndexedDB databases might have mismatched metadata version and database name encoding format"; **26.5: "IndexedDB connections could become permanently broken until the page was reloaded"**; **27.0: "IndexedDB transactions could be blocked for an extended period before starting when another page's transaction was suspended in the background"**, "IndexedDB could incorrectly return a version 0 database after an abort during the initial onupgradeneeded", "connections in workers recover after a network process crash". A hidden iOS page holding an open transaction can therefore stall the Service Worker or a second tab on iOS <= 26.
- Confidence: high that the defects existed (release notes). Design-critical: medium.
- Sources: https://webkit.org/blog/17862/webkit-features-for-safari-26-4/ ; https://webkit.org/blog/17938/webkit-features-for-safari-26-5/ ; https://webkit.org/blog/18325/webkit-features-for-safari-27-0/ .

**F-24. WebCrypto and key persistence on mobile.** Ed25519 (`generateKey/sign/verify`): Chrome/Android Chrome/Edge/WebView **137**, Firefox **129**, Safari/iOS **17.0**, Samsung **30.0**. The project's ECDSA P-256 + SHA-256 works everywhere (`SubtleCrypto` Chrome 37, Firefox 34, Safari/iOS 11, Samsung 3.0), which is why keeping P-256 is right until iOS 16 and Samsung <= 29 are out of scope. WebKit bug 312279 (NEW, filed 2026-04-14, Safari 26.4): a **non-extractable X25519 CryptoKey** stored in IndexedDB comes back as `null` on the next read. Reproduced here on WebKit 27.2 in both ephemeral and persistent contexts: a non-extractable **ECDSA P-256 key and an Ed25519 key round-trip through IndexedDB and still sign** (64-byte signatures), AES-GCM works, **X25519 reads back `null`** (Chromium 156 round-trips all four). The chain's identity (non-extractable P-256 in IndexedDB) is therefore sound on current WebKit; older iOS builds (16-18) still need a device test.
- Confidence: high for the support table (BCD); medium for the WebKit bug's reach. Design-critical: yes for identity storage (also see F-20).
- Sources: `BCD: api/SubtleCrypto.json` ; https://bugs.webkit.org/show_bug.cgi?id=312279 .

Consequences observed with the vendored bundle: WebTorrent's default `fsa-chunk-store` fails in the ephemeral session (an unhandled `UnknownError` rejection from its import-time `getDirectory().then(...)`, and the failed OPFS call at first use), and works with an explicit in-memory store; with that store WebKit seeds the same infohash as Chromium and Node. Two clients in one headless WebKit page did not connect over WebRTC within 30 s even natively (inference: `.local` mDNS host candidates, as in research 01/03), so no WebKit transfer was tested.
- Confidence: high for what was observed (reproducible with the lab scripts); medium for transfer to iOS Safari Private Browsing (same engine and storage code; the iOS platform layer and Safari's own private-mode policy were not tested). Design-critical: **yes**: the loader's persistence unit is a Blob in IndexedDB, so a Safari private tab turns `persistSite` into an error and forces the degraded path; and WebTorrent's default store throws.
- Sources: `labs/w1-08-mobile-lab/out/results-storage-probe.txt`, `out/results-webtorrent-b64-webkit.txt`, `out/results-t262-webkit.txt` ; https://webkit.org/tracking-prevention/ (ephemeral session wording) ; Playwright build https://cdn.playwright.dev/dbazure/download/playwright/builds/webkit/2370/webkit-mac-26-arm64.zip .

## Concrete recommendations for magnet-web

Effort: S = under a day, M = 1-3 days, L = more. Priority: P0 = blocks any mobile claim, P1 = before launch, P2 = soon after, P3 = nice to have. File names refer to the current tree (`src/loader/boot.js`, `policy.js`, `app.js`, `torrent.js`, `config.js`; `tools/build.mjs` does not exist yet).

**R-01 (P0, S). Install the base64/hex and `AbortSignal.timeout` polyfills in `boot.js` before anything imports WebTorrent, and fix `MIN_BROWSERS`.** Put `u8-polyfill.js` and `abort-polyfill.js` (Appendix C) into `src/loader/polyfills.js`, import it first from `boot.js` (the build bundles `boot.js` as an ES2017 IIFE), then run a self-test and treat a failure like a missing feature: `new Uint8Array([1,2,254,255])` must give `toHex() === '0102feff'`, `toBase64() === 'AQL+/w=='`, `toBase64({alphabet:'base64url', omitPadding:true}) === 'AQL-_w'`, `Uint8Array.fromHex('0102FEFF')[3] === 255`, `Uint8Array.fromBase64('AQL-_w', {alphabet:'base64url'})[2] === 254`, and `typeof AbortSignal.timeout === 'function'`. Replace the `MIN_BROWSERS` string with the matrix below. Add `test/unit/polyfills.test.mjs` that runs `selftest.mjs`'s vectors, and keep the test262 runner (`labs/w1-08-mobile-lab/run-t262.mjs`) as an optional CI job. Add a `build.mjs` gate: `esbuild node_modules/webtorrent/dist/webtorrent.min.js --target=safari14.5,chrome80,firefox78 --log-level=warning` must stay silent, so a future vendored bundle that needs newer syntax fails the build (APIs are not detected by esbuild; keep the F-06 grep list in the same script). Why: F-03 to F-06; without it about 8.5 % of web traffic gets `TypeError: e.toBase64 is not a function` from `new WebTorrent()`.

**R-02 (P0, S). Default to download-only on every mobile network that is not verified unmetered, and make sharing an explicit toggle.** Extend `detectEnvironment`/`classifyEnvironment` as in "Mobile policy v1": drop `mozConnection`/`webkitConnection` (dead), record whether `connection.type` is a known string, treat `cellular|bluetooth|other|mixed|none` and `saveData` as metered, treat missing `connection` (iOS, Firefox Android, most WebViews) as `mobileUnknown`. Upload stays 0 (implemented by the existing choke-lock, which keeps chain gossip frames flowing) until the visitor turns on "Share this site with other visitors while this page is open" (stored per origin in `PREF_KEYS.upload`). Why: F-14, F-15, F-13, F-31. This supersedes review M3.

**R-03 (P0, M). Rebuild instead of resume.** In `installLifecycle` (`app.js` ~797-820): on `visibilitychange` to hidden record `hiddenAt = Date.now()` and lock uploads immediately (`hiddenPauseMs: 0` for all mobile classes; the OS gives no grace); on visible, if `Date.now() - hiddenAt > 10_000` (iOS suspends within 5-20 s), or on `online`, or on `pageshow` with `persisted`: call a new `TorrentManager.rebuild()` that `destroy()`s the client and runs `seedFromCache()` again (a fresh `tracker.Client`, fresh peer connections, `retries = 0`) and re-attaches the chain node to the new wires; otherwise `resume()`. Never call `tracker.update()` as the recovery step (no-op while `reconnecting`, F-12). Replace `setTimeout`-based pausing by timestamp comparison (timers do not run while suspended, F-09, F-07). Keep the `pagehide` best-effort teardown and the `pageshow` reload (F-11). Why: F-07 to F-12.

**R-04 (P0, S). Say what mobile can and cannot do, in the UI.** Status line under the peer count on mobile: "Sharing only while this tab is open and the screen is on." Do not claim offline availability on iOS: "Saved on this device until Safari clears it" plus the Home Screen hint (R-08). Why: F-07, F-08, F-20.

**R-05 (P1, M). Memory-bounded download path.** Never use WebTorrent's default store on mobile: pass an explicit store (a 25-line in-memory abstract-chunk-store, or an IndexedDB-backed one from the lab in `labs/01-webtorrent-lab/www/e8.html`) and build each file's Blob on its own `file.on('done')` instead of one `blob()` for the whole site, to avoid the 2.7x peak (F-17). Caps: keep 48 MiB for mobile and 24 MiB for metered; allow 64 MiB when `navigator.deviceMemory >= 4`; keep 128 MiB for desktop only. Planning formula: peak ~ 95 MB + 2.7 x site size. Also covers review M7 (the default `fsa-chunk-store` wipes other tabs' chunks and, on Safari 15.2-25.x, runs through a polyfill that spawns a module Worker per write, F-27, 01) and now has direct evidence: in WebKit 27.2's ephemeral session the default store throws `UnknownError` because OPFS is unavailable (F-32). Why: F-16, F-17, F-32.

**R-06 (P1, M). Bound the chain database by bytes on mobile, not only by block count.** `ARCHITECTURE.md` section 6.6 loads up to 50,000 blocks at startup; at the 16 KiB block limit that is 50,000 x 16,384 B = 781 MiB (inference: reachable by an attacker with several identities because `writers: 'open'` is the default and hashcash is 14 bits), well past an iPhone's ~1.5 GB soft limit once the site is also loaded; a jetsam kill followed by an automatic reload would then loop. Add `maxLoadedBytes` (mobile 32 MiB, desktop 128 MiB), load newest-first, and surface "chain truncated on this device". Why: F-16, F-17.

**R-07 (P1, M). Treat the identity and TOFU pin as losable on Safari; add backup/restore and test the key round-trip.** Export/import the P-256 identity (review M1 fix 1), show "first time on this device" whenever a pin is missing, and run an on-device test that a non-extractable P-256 `CryptoKey` survives an IndexedDB put/get on iOS 16.4, 17, 18.x, 26, 27 (it already does on WebKit 27.2 for macOS, for Ed25519 too; X25519 fails, WebKit bug 312279, F-32). Keep ECDSA P-256; Ed25519 is not universal until iOS 17 / Samsung 30 / Chrome 137 (F-24); do not introduce X25519 keys in IndexedDB without a wrapped-JWK fallback. Why: F-20, F-21, F-24, F-32.

**R-08 (P1, S). Persistence behaviour per browser.** Call `navigator.storage.persisted()` and `estimate()` for diagnostics at startup. Call `persist()` only after a user gesture and never at load (Firefox prompts, F-21); expect `false` in every Safari tab. On iOS (detect with UA `iPhone|iPad` or `navigator.maxTouchPoints > 1 && /Macintosh/.test(UA)`) when not standalone (`navigator.standalone !== true` and `!matchMedia('(display-mode: standalone)').matches`), after the first successful load show a dismissible "Add to Home Screen to keep this site and your identity on this device" hint (iOS 26+ makes any site installable, F-22). Why: F-20 to F-22.

**R-09 (P1, S). IndexedDB resilience wrapper.** All IDB access through one helper that: keeps transactions short and never awaits inside one (Safari/Firefox auto-commit, review m4), retries once on `UnknownError`/`InvalidStateError`, reopens the connection on `close`/`versionchange`, treats "connection permanently broken until reload" (Safari 26.5 fix) by offering a reload, and handles `QuotaExceededError` (already present in `persistSite`). Finish and commit any write transaction before the page becomes hidden (Safari <= 26 can stall other pages behind a suspended transaction, F-23). Why: F-23.

**R-10 (P1, M). Container detection and the degraded path.** `!('serviceWorker' in navigator)` selects degraded mode; add an "Open in Safari / Chrome" button (use `intent://` on Android, a plain link on iOS) and a one-line cause ("in-app browser", "Lockdown Mode", "private window"). Use UA hints (`FBAN|FBAV|Instagram|Line/|MicroMessenger|Snapchat|Twitter|LinkedInApp|GSA/|; wv\)`) only to word the message, never to decide capabilities (alternative engines exist in the EU and Japan, F-26). Why: F-25, F-26, F-28.

**R-11 (P2, S). Battery-aware sharing where a battery API exists.** On Chromium (`getBattery`: Chrome 38+, Samsung 3.0+) disable sharing when `!charging && level < 0.30` and enable the default-on case of R-02 only while `charging`. Everywhere else (iOS, Firefox) assume battery. This mirrors Delivery Optimization's "won't upload on battery" default. Why: F-13, F-15, F-31.

**R-12 (P2, S). Upload budgets.** Per page-visit 64 MiB and per origin per calendar month 256 MiB on mobile (Delivery Optimization defaults to 20 GB/month on PCs, F-31; these phone numbers are a proposal, not a measurement). Count bytes in `TorrentManager` (`uploaded` already exists on the torrent) and persist the monthly counter in IndexedDB. Why: F-13, F-31.

**R-13 (P2, S). Reduce WebRTC churn on mobile.** Pass `tracker: { getAnnounceOpts: () => ({ numwant: 3 }) }` (2 on `mobileMetered`), cap `maxConns` at 8/6/4 per class, use at most two tracker URLs (research 02 R2); every extra connection adds a 5 s ICE consent timer (F-13). Why: F-13.

**R-14 (P2, S). React to network changes where the platform allows.** On Chromium listen to `navigator.connection.addEventListener('change', ...)` to recompute the policy and re-announce; everywhere listen to `online`/`offline`; on iOS and Firefox no change event exists, so recompute on `visibilitychange` and before each large transfer. Why: F-15, F-14.

**R-15 (P2, M). Real-device matrix and runbook (nothing in this study touched a phone).** See "Open questions" Q-01 to Q-06 for the timestamped tests. Minimum devices: iPhone on iOS 16.x (an iPhone 8/X class device if available), 17.x, 18.1, 18.2+, 26.x; the same site in Safari, Chrome iOS and an in-app browser; an iPad; Android Chrome current on a 2-3 GB RAM phone and a recent phone; Samsung Internet 29 and 30; Firefox Android; Brave Android. Why: every "not device-tested" label in this file.

**R-16 (P3, S). Optional "Keep screen on while sharing".** Screen Wake Lock (Chrome 84, Firefox 126, Safari 16.4; iOS Home Screen web apps were partial until 18.4) is released when the page hides and must be re-requested on `visibilitychange`. Opt-in only, because it defeats the battery policy. Why: F-07.

**R-17 (P3, S). `freeze`/`resume` on Chromium.** Add `document.addEventListener('freeze', ...)` to close peers and `resume` to rebuild (Chrome 68+, Samsung 10+); `visibilitychange` already covers the main case, this only helps Chromium discard/freeze paths. Why: F-10.

**R-18 (P3, S). A telemetry-free diagnostics panel.** Show `persisted()`, `estimate()`, SW state, policy class and reason, last hidden duration, rebuild count, tracker state, and "Copy report". It replaces analytics for field debugging of everything in this file. Why: F-02, F-12, F-20.

**R-19 (P2, L). Prioritised partial download, so memory, data and time-to-first-render stop scaling with the whole site.** WebTorrent 3.0.21 already exposes what is needed (`Torrent.select/deselect/critical`, `File.select(priority)`, `File.deselect()`, `File.createReadStream/stream/blob/arrayBuffer({start,end})`; by default it "start[s] off selecting the entire torrent with low priority", `lib/torrent.js` ~622). Design: `deselect` everything, mark the entry HTML plus the assets it references `critical`, render as soon as that set verifies, then fetch the rest at low priority only while the policy allows (visible, class permits) or on demand when the Service Worker misses a file (page asks the torrent for that file's byte range; the Range plumbing in `sw/lib.js` already exists). Evidence for the need: peak tab memory is about 95 MB + 2.7 x site size with a whole-site Blob (F-17), and mobile caps of 24-48 MiB reject many existing sites. Precedent for fetch-on-demand through a Service Worker: the IPFS service-worker gateway (research 04). Cost: the renderer currently waits for `done` (`app.js` `persistSite` then `renderSite`), so this is a rework of the download state machine and of the cache schema (partial manifests). Why: F-16, F-17, goal 1 (existing sites migrate with their large media intact).

**R-20 (P2, S). A publish-time mobile budget lint for site owners.** `tools/publish.mjs` should print the total size, the five largest files and the class each fits (cellular 24 MiB, mobile 48 MiB, desktop 128 MiB), warn when the total exceeds 48 MiB or any single file exceeds 16 MiB, and suggest keeping large media on the HTTP web seed only (R-19 `deselect`) or splitting the site. This makes the mobile limits visible to the person migrating an existing website instead of surfacing as `E_TOO_LARGE` on a phone. Why: F-16, F-17.

**R-21 (P1, S). Survive Safari Private Browsing: probe for an ephemeral session and fall back to ArrayBuffer storage.** At startup try, in try/catch, a 1-byte Blob `put` into a scratch IndexedDB store and `navigator.storage.getDirectory()`; when the Blob put fails with `UnknownError` ("Error preparing Blob/File data to be stored in object store") or OPFS throws, set `S.ephemeral = true`, store file contents as `ArrayBuffer`/`Uint8Array` values instead of Blobs (reconstruct `new Blob([buf])` on read; the Service Worker can build a `Response` from the buffer), skip the OPFS store, show "Private window: nothing is kept after you close it" instead of the storage-full error that `persistSite` shows today, and suppress the Home Screen hint. Cost is one extra copy in memory while the page is open, which the 48 MiB cap absorbs. Add an e2e case with Playwright WebKit using a non-persistent context (`browser.newContext()`), which reproduces the failure. Why: F-32.

### Mobile policy v1 (concrete values)

Detection (all feature-based):
```js
isMobile = matchMedia('(pointer: coarse)').matches || /Mobi|Android/i.test(UA)     // iPadOS reports a coarse pointer
conn     = navigator.connection              // Chromium only (F-15); Firefox Android removed it in 99
type     = conn && typeof conn.type === 'string' ? conn.type : null
unmetered= type === 'wifi' || type === 'ethernet'                    // means "not known to be metered" (F-15)
metered  = (conn && conn.saveData === true) || ['cellular','bluetooth','other','mixed','none'].includes(type)
class    = !isMobile ? 'desktop' : metered ? 'mobileMetered' : unmetered ? 'mobileUnmetered' : 'mobileUnknown'
```

| Setting | desktop | mobileUnmetered (Chromium proves it) | mobileUnknown (iOS, Firefox Android, WebViews) | mobileMetered (cellular, Data Saver) |
|---|---|---|---|---|
| `maxConns` | 30 | 8 | 6 | 4 |
| tracker `numwant` | 5 (default) | 3 | 3 | 2 |
| upload default | on, 1 MiB/s | **off**, except on when `getBattery().charging` | **off** | **off** |
| upload after the visitor opts in | n/a | 128 KiB/s | 128 KiB/s | not offered (Settings > Advanced override) |
| per-visit / per-month upload budget | none / none | 64 MiB / 256 MiB | 64 MiB / 256 MiB | 0 |
| `maxSiteBytes` | 128 MiB | 48 MiB (64 MiB if `deviceMemory >= 4`) | 48 MiB | 24 MiB |
| ask before downloading more than | never (the cap applies) | never (the cap applies) | **16 MiB** | **8 MiB** |
| when hidden | unchanged (pause after 10 min; Chromium exempts data-channel pages from intensive throttling) | lock uploads at once, rebuild on return | same | same |
| chain gossip | on | on (frames <= 16 KiB) | on | on |
| site cache budget (LRU, never evict the open site) | 1 GiB | 256 MiB | 256 MiB | 128 MiB |
| chain load budget | 128 MiB | 32 MiB | 32 MiB | 32 MiB |

Why these numbers: 128 KiB/s is 0.47 GB per hour at the worst case (the original 256 KiB/s was 0.94 GB/h); nothing uploads on an unproven network, matching Delivery Optimization; 16 MiB is far above a typical page (page weights were not measured here), so the visitor is asked before a large P2P site is downloaded on a network the page cannot classify; cache and chain budgets keep the peak tab memory under about 25 % of an iPhone's 1.5 GB (F-16, F-17). If the product owner wants the swarm to benefit from phones by default, the least-bad alternative is on-by-default at 32 KiB/s with an 8 MiB per-visit budget on `mobileUnknown` and `mobileUnmetered` while visible, with the consent line naming "mobile data". None of the numbers is evidence-derived beyond the arithmetic above; they are defaults for the settings UI that already exists.

## Gotchas

- **G-01. One user, many storage containers.** Safari, Chrome iOS, Firefox iOS, an in-app WKWebView, a Home Screen web app and an Android in-app WebView each have their own IndexedDB/Service Worker/identity (the Home Screen app starts empty; only login cookies are copied at install, iOS 17.2+). The chain identity and the TOFU pin do not follow the person. Say "identity lives in this browser" in Settings (F-22, review m6).
- **G-02. The Safari-tab store can disappear without any signal.** ITP deletion is silent and covers IndexedDB, Cache API, Service Worker registrations, LocalStorage, SessionStorage, media keys and OPFS (F-20). Never assume a previous visit's data exists; every read path needs the "empty store" branch, and the identity needs a backup (R-07).
- **G-03. `navigator.storage.persist()`**: always `false` in a Safari tab; a permission prompt in Firefox; silent in Chromium. Do not call it on load and do not retry (F-21).
- **G-04. Timers stop while suspended.** A `setTimeout(pause, 30000)` set before backgrounding fires after the page returns, not at 30 s; Firefox Android stretches timers to 15 minutes. Compare timestamps on `visibilitychange` (F-07, F-09).
- **G-05. `pagehide`, `beforeunload` and `unload` are not delivered when the user swipes the app away or the OS kills it.** `visibilitychange` to `hidden` is the last reliable event; flush state there (F-10).
- **G-06. The tracker client's first reconnect is `10 s + random(0..5 min)` and `announce()` is ignored meanwhile (F-12).** Calling `tracker.update()` on resume looks like it works and does nothing.
- **G-07. A page restored from Safari's page cache has dead peer connections** whose sockets WebKit closed with error -1 and silently drops writes to; do not trust `connectionState` after `pageshow.persisted`; the current reload-on-restore is the safe path (F-11).
- **G-08. A WebSocket can report `open` and be dead after a screen lock** (developer reports collected in research 02/03, not reproduced here). Use an application-level ping, as the chain's 30 s HELLO already does.
- **G-09. `connection.type === 'wifi'` is not "free".** A phone hotspot looks like Wi-Fi to a tethered laptop or phone; Android's own docs say Wi-Fi is a poor proxy for meteredness; iOS exposes `isExpensive` to apps only (F-14, F-15).
- **G-10. Safari 26 masks some APIs for known fingerprinting scripts** (screen size, `hardwareConcurrency`, ...) and may refuse those scripts long-lived storage. Do not size worker pools from `hardwareConcurrency` on iOS; keep third-party scripts out of the loader (F-20).
- **G-11. iOS 26 lets users open any site as a web app without a manifest.** Expect standalone mode with no URL bar, `window.open` and `target=_blank` going to an in-app browser, and `matchMedia('(display-mode: standalone)')`/`navigator.standalone` being the only signals (F-22).
- **G-12. Samsung Internet's UA says `Chrome/143.0.0.0` (reduced) next to `SamsungBrowser/30.0`;** gate features on the Samsung version, not the Chrome token, because the Chromium base lags Chrome by about 5 months (F-29).
- **G-13. Android WebView hosts may have no DOM storage (default off) and no Service Worker;** Custom Tabs are Chrome (F-28).
- **G-14. Alternative engines may appear on iPhone in the EU and Japan;** an iPhone UA does not guarantee WebKit storage rules (F-26).
- **G-15. `estimate()` is fuzzed on Safari** and must not drive hard guarantees (F-19).
- **G-16. Chrome's "Clear cookies and site data when you close all windows" setting makes all storage session-only** and cuts the quota to about 300 MB; incognito quota is about 5 % of disk. A cache that survives normally can be empty next launch (F-19).
- **G-17. Private browsing**: Safari private tabs use an ephemeral session in which OPFS throws and IndexedDB rejects Blob values (measured on WebKit 27.2, F-32); Firefox private windows had no Service Workers before 140 (research 04); Chrome incognito deletes on close and gets about 5 % of disk as quota.
- **G-18. Lockdown Mode** disables Service Workers, Cache API, Web Locks and (per 03) `RTCPeerConnection`; the loader cannot work there without a per-site exclusion (research 03 F-21, 04 F15).
- **G-19. Screen Wake Lock is released whenever the page hides** and must be re-requested; iOS Home Screen web apps were only partially supported until 18.4 (BCD) (R-16).
- **G-20. Safari bug history means an IndexedDB connection can break until reload** (fixed in 26.5) and a hidden page's open transaction can stall others (fixed in 27.0); keep transactions tiny and auto-reopen (F-23).
- **G-21. The memory numbers here are desktop Chromium RSS, not phone numbers.** They measure a copy structure (pieces, then a Blob, then IndexedDB), which transfers; the absolute values do not (F-17).
- **G-22. `Uint8Array.prototype.toBase64` etc. exist in some engines with `setFrom*` too;** the polyfill deliberately omits `setFromHex/setFromBase64`, so never call those in `src/` (add them to the ban list in review M5).
- **G-23. The WebKit "title changes keep the page alive" trick is disabled on iPhone** and must not be used as a keep-alive anywhere (F-07).
- **G-24. WebTorrent's default store**: on Safari < 26 it silently takes a module-Worker polyfill path and, on every engine, `fsa-chunk-store` deletes the shared OPFS `chunks` directory at import time (research 01, 04). Always pass an explicit store (R-05).
- **G-25. WebKit ephemeral sessions (Safari Private Browsing) have no OPFS and reject every Blob/File IndexedDB value** (`UnknownError`), while ArrayBuffers work; probe at startup instead of assuming a Blob store (F-32, R-21). The same session type makes `fsa-chunk-store` log an unhandled rejection at import time.
- **G-26. A WebKit-for-macOS result is not an iPhone result.** Playwright's WebKit shares the engine and storage code with Safari but not the iOS process lifecycle, memory limits or Home Screen handling; use it for engine behaviour (API presence, storage errors, polyfill correctness), never for background or memory claims.

## Appendix C - The polyfills (also in `docs/research/labs/w1-08-mobile-lab/`)

`u8-polyfill.js` (classic script, ES2017 syntax; installs only what is missing; no `setFromHex/setFromBase64`; needs `btoa`/`atob`; 3,680 B, 2,448 B minified, 1,193 B gzip):

```js
/* Uint8Array base64/hex (ES2026) polyfill: toHex, toBase64, fromHex, fromBase64.
   Classic script, ES2017 syntax only. Installs only what is missing. setFromHex/setFromBase64 are NOT provided.
   Needs btoa/atob (every target browser; Node >= 16). Needed by uint8-util@2.3.x (webtorrent 3.0.21). */
(function (G) {
  'use strict';
  var U = G.Uint8Array, P = U.prototype, A = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/';
  var tag = Object.getOwnPropertyDescriptor(Object.getPrototypeOf(P), Symbol.toStringTag).get;
  function brand(a) { if (tag.call(a) !== 'Uint8Array') throw new TypeError('not a Uint8Array'); return a; }
  function live(a) { try { new U(a.buffer, 0, 0); } catch (e) { throw new TypeError('detached ArrayBuffer'); } return a; }
  function opts(o) {
    if (o === undefined) return {};
    if (o === null || (typeof o !== 'object' && typeof o !== 'function')) throw new TypeError('options must be an object');
    return o;
  }
  function alpha(o) {
    var a = o.alphabet;
    if (a === undefined) return 'base64';
    if (a !== 'base64' && a !== 'base64url') throw new TypeError('bad alphabet');
    return a;
  }
  var M = {
    toHex() {
      var a = brand(this), s = '', i;
      live(a);
      for (i = 0; i < a.length; i++) s += (a[i] < 16 ? '0' : '') + a[i].toString(16);
      return s;
    },
    toBase64() {
      var a = brand(this), o = opts(arguments[0]), al = alpha(o), pad = !o.omitPadding, s = '', i;
      live(a);
      for (i = 0; i < a.length; i += 8192) s += String.fromCharCode.apply(null, a.subarray(i, i + 8192));
      s = G.btoa(s);
      if (al === 'base64url') s = s.replace(/\+/g, '-').replace(/\//g, '_');
      return pad ? s : s.replace(/=+$/, '');
    },
    fromHex(s) {
      if (typeof s !== 'string') throw new TypeError('expected a string');
      if (s.length % 2) throw new SyntaxError('odd length');
      if (/[^0-9a-fA-F]/.test(s)) throw new SyntaxError('not hex');
      var r = new U(s.length / 2), i;
      for (i = 0; i < r.length; i++) r[i] = parseInt(s.substr(2 * i, 2), 16);
      return r;
    },
    fromBase64(s) {
      if (typeof s !== 'string') throw new TypeError('expected a string');
      var o = opts(arguments[1]), al = alpha(o), lc = o.lastChunkHandling, t, m, b, p, r, x, out, i;
      if (lc === undefined) lc = 'loose';
      else if (lc !== 'loose' && lc !== 'strict' && lc !== 'stop-before-partial') throw new TypeError('bad lastChunkHandling');
      t = s.replace(/[\t\n\f\r ]+/g, '');
      if (al === 'base64url') {
        if (/[+/]/.test(t)) throw new SyntaxError('bad character');
        t = t.replace(/-/g, '+').replace(/_/g, '/');
      }
      m = /^([A-Za-z0-9+/]*)(={0,2})$/.exec(t);
      if (!m) throw new SyntaxError('invalid base64');
      b = m[1]; p = m[2].length; r = b.length % 4;
      if (p ? r + p !== 4 : r) {                         // padding missing, misplaced or chunk incomplete
        if (lc === 'stop-before-partial' && (p ? r === 2 && p === 1 : true)) b = b.slice(0, b.length - r);
        else if (p || lc === 'strict' || r === 1) throw new SyntaxError('bad padding');
      } else if (lc === 'strict' && r && (A.indexOf(b.charAt(b.length - 1)) & (r === 2 ? 15 : 3))) {
        throw new SyntaxError('non-zero trailing bits');
      }
      x = G.atob(b); out = new U(x.length);
      for (i = 0; i < x.length; i++) out[i] = x.charCodeAt(i);
      return out;
    }
  };
  function def(o, k) { if (!(k in o)) Object.defineProperty(o, k, { value: M[k], writable: true, configurable: true }); }
  def(P, 'toHex'); def(P, 'toBase64'); def(U, 'fromHex'); def(U, 'fromBase64');
})(typeof globalThis === 'object' ? globalThis : self);
```

/* AbortSignal.timeout(ms) polyfill (Safari < 16, Chromium 103-123 partial, Samsung < 27). Classic script, ES2017. */
(function (G) {
  'use strict';
  if (typeof G.AbortSignal !== 'function' || typeof G.AbortController !== 'function' || typeof G.AbortSignal.timeout === 'function') return;
