# w1-07 VERIFY - second-pass fact-check of "Prior art: websites delivered by torrent or content hash, and why they stalled"

**Subject:** the eight design-critical claims lifted from `docs/research/w1-07-prior-art.md` (F1-F2, F5, F7-F14, F23 and its Summary).
**Checked:** 2026-10-17 (live probes carry UTC times). Every claim was re-opened at its primary source by a checker whose job was to refute or narrow it.
**Resume note:** on resume `docs/research/` contained `w1-07-prior-art.md` and no `w1-07-prior-art-VERIFY.md`, so nothing was lost or overwritten. `w1-07-prior-art.md` is untouched: corrections are proposed in section 9, not applied.

## 0. Method, limits, verdict key

- **How.** Raw primary files via `curl` (READMEs, CHANGELOG, DEVELOPMENT.md, BADBITS.md, NIP-5A, the Public Suffix List, RFC 1035, BEP 52, the Service Worker spec); official pages converted to text; GitHub Atom feeds (the unauthenticated GitHub REST API answered HTTP 403 "API rate limit exceeded" for this network, so commit/release dates come from `releases.atom` / `commits/<branch>.atom`); live HTTP and DNS probes; one browser experiment (section 8, lab files in `docs/research/labs/w1-07-verify-lab/sw-takedown/`).
- **Search budget.** `WebSearch` returned "budget used up (200 per turn, shared)" when I needed it for one question (how browsers treat a 404/410 on an installed worker's script). I did not search any other way. That question is answered instead from the spec text plus a browser experiment. Anything that needed an open-ended search is listed in section 11.
- **Not tested.** Firefox (Playwright's Firefox would not start in this sandbox, "Could not find profile folder"); Chrome/Safari stable (only Playwright builds of Chromium 156.0.8078.4 and WebKit 27.2); the 24-hour soft-update window itself (taken from the spec and from the IPFS team's own table).
- **Old sources are flagged** `[old]` (before 2024): Cofense 2022, CoinDesk 2022, Beaker 2022, ZeroNet changelog 2016-2019, WebKit ITP 2020, RFC 1035 (1987), the Brave blog body (2021, with a 2024 update).
- **Verdicts.** `confirmed` = every stated fact checks out against a primary source (caveats are about wording or interpretation only). `nuanced` = the facts are real but at least one statement is incomplete, mis-scoped or an inference presented as a finding, so the downstream document needs a change. `refuted` = a stated fact is contradicted. `unverifiable` = could not be checked. Where a claim has parts, the part that fails is named.

## 1. Claim 1 - Brave removal, "less than 0.1%", gateway traffic

**Claim.** Systems that required local software stayed niche: Brave removed native `ipfs://` and local-node support on 2024-08-22 (v1.69.153) because "less than 0.1% of users made use of this feature". Real traffic came through HTTPS gateways: "over 614 million requests and 45TB of data to 10 million users daily" (2025-07-23), yet a 2025-05-12..14 sample shows only 9.4% of requests were browsers loading pages and 67.4% automated clients.

**Verdict: confirmed (wording fixes).** Confidence: high for the facts, medium for the generalisation in the first clause.

| Sub-claim | Result | Evidence (primary) |
|---|---|---|
| Removed on 2024-08-22 in v1.69.153 | holds | Brave blog "IPFS Support in Brave" (published Jan 19, 2021; "Last updated Aug 22, 2024"): "Local node and protocol support for IPFS was deprecated in Brave as of August 22, 2024, with version 1.69.153." Brave desktop changelog, 1.69.153: "Removed support for IPFS local node and ipfs:// scheme. (#37735)". IPFS blog, 26 Aug 2024: "The removal was implemented in the latest stable release (v1.69.153) which shipped on Aug 22nd." |
| "Less than 0.1% of users made use of this feature" | verbatim | Same Brave paragraph. It continues: "...and the support and maintenance costs were too high for us to bear by ourselves. Basic ipfs:// redirecting to a gateway can be accomplished via build-time configuration." |
| "over 614 million requests and 45TB of data to 10 million users daily" | verbatim | Shipyard, "A Post Gateway World" (Cameron Wood, Adin Schmahmann, Jul 23, 2025), Summary |
| 9.4% browsers / 67.4% automated | verbatim | Same post, request share A 9.4% / B (hot-links, app embeds) 23.1% / C (automated clients) 67.4%; bandwidth 9.2% / 21.3% / 69.5% |

**Corrections and nuance.**
1. Say "deprecated (Brave's blog) / removed (Brave's changelog), v1.69.153, shipped 2024-08-22". The gateway redirect for `ipfs://` survives only as a build-time option. In 2026 Brave went further the same way: changelog 1.90.121 "[Security] Changed IPFS gateway usage from "ipfs.io" to "inbrowser.link" for IPFS domain resolution. (#53690)" (the changelog gives no date; Chromium 148 era, so roughly mid-2026, my inference).
2. "Because <0.1%" is one of three stated reasons: low use, support/maintenance cost (Brave), and, from the IPFS side, "we could not find a mutually agreeable set of terms to make this integration sustainable". Quote the whole sentence or none of it.
3. The traffic split is the vendor's own, short and heuristic: 3 days (2025-05-12..14), "filtering out known abuse via Cloudflare and Badbits", "Although imperfect"; "browser visitors" means "modern browser user agents without cross-origin headers". The same post says "Only about one-third is web browser-based" (9.4% + 23.1% = 32.5%) and "Browser UAs represent ~25% bandwidth but only ~15% of requests", so "only 9.4% were browsers loading pages" is accurate but is the narrowest of three browser-related readings.
4. 614M / 45TB / 10M is a headline with no method, dated mid-2025. The IPFS Foundation post of 2026-08-25 says IPFS "handles roughly 250 million requests per day" (scope not defined). Do not present 614M as current.
5. "Required local software -> niche" is the first pass's inference from four cases (Brave, ZeroNet, Maelstrom, Beaker); no source states it as a rule, and I could not search for counter-examples (section 0). Keep it as "in this niche, every case shows it", not as a law.

**For magnet-web.** No design change; the "no install, ordinary browser" principle is supported.

**Live state, measured 2026-10-17 21:33Z (this closes the first pass's "browser redirect not confirmed").**
- `HEAD https://ipfs.io/ipfs/<cid>` with a curl UA: HTTP 429, `retry-after: 900`, `sunset: Mon, 21 Sep 2026 00:00:00 GMT`, `link: <https://gatewaychanges.ipfs.io/>; rel="sunset"`.
- `GET` of the same URL with a Chrome UA but no navigation headers: 403 (Cloudflare). `HEAD` with a Chrome UA plus `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`, `Accept: text/html`: **302 to `https://<cid>.ipfs.inbrowser.link/`**.
- `ipfs.io/` and `dweb.link/` -> 301 `https://about.ipfs.io/`. `inbrowser.link/` 200.

**Why "strongest precedent" needs a limit.**
- The worker has no WebRTC and does not seed. `src/sw/lib/verified-fetch.ts` (main) builds libp2p with `transports = [webSockets()]` plus `webTransport()` only `if ('WebTransport' in globalThis)`, `addresses: {}` ("no need to listen on any addresses"), delegated HTTP routers, `recursiveGateways`, Bitswap and HTTP retrieval; `package.json` (v3.5.1) likewise has **no `@libp2p/webrtc`** (and a Service Worker has no `RTCPeerConnection` anyway). It is a consumer only: it never serves blocks to other visitors. The README says it fetches "directly from providers over HTTPS, Secure WebSockets, and other browser-compatible transports ... using a fallback trustless gateway". The IPFS Foundation's "direct peer-to-peer connections" therefore means libp2p connections to server-grade providers.
- Who the providers are: `delegated-ipfs.dev/routing/v1/providers/<sample cid>` on 2026-10-17 returned 50 records: 6 tagged `transport-ipfs-gateway-http` (HTTPS gateways), 4 tagged `transport-bitswap` (e.g. `bitswap.filebase.io` over WSS), 40 untagged peers. A forum user separately reported Pinata endpoints behind a phishing CID (user report, low weight).
- So it is precedent for "static bootstrap + SW + hash verification in the client + one origin per site" and, in practice, for a web-seed-like availability model run by commercial providers. It is **not** precedent for visitor-to-visitor replication over WebRTC (it never seeds), which is magnet-web's actual difference (the loader page, not the SW, owns WebTorrent).
- Trust root: Netcraft (2026-09-29) notes the model is "still reliant on inbrowser.link as the source of the service worker code", the same "static host is the trust root on every visit" that DESIGN-REVIEW 20 states for us.

**For magnet-web.** Cite it as validation of loader + SW + subdomain-per-site + client-side hashing; do not cite it as validation of the P2P data plane. Pair it with claim 4: the largest deployment of in-browser verification still depends on server-side providers.

**8.2 What an edge can and cannot do to an installed worker.**

*Spec (Service Workers Editor's Draft, fetched 2026-10-17).* When the script fetch fails in the Update algorithm: "If script is null ...: Invoke Reject Job Promise with job and TypeError. **If newestWorker is null, then remove registration map[...]**". So only a first-time registration is dropped; an existing worker survives a failed fetch. A registration "is said to be stale if ... greater than 86400" seconds; in-scope navigations and functional events then "run the Soft Update algorithm", and the request uses cache mode "no-cache" when "registration's update via cache mode is not 'all'" or "newestWorker is not null and registration is stale". Imported scripts are byte-compared too. The IPFS team's own table (issue #840) agrees: an update check needs the visitor to be online and to navigate ("No navigation = no update check"; "Offline = no update check possible").

*Experiment* (`docs/research/labs/w1-07-verify-lab/sw-takedown/`; local edge on 127.0.0.1; Playwright Chromium 156.0.8078.4 and WebKit 27.2 gave identical results; Firefox could not be launched here):

| Step | Observed |
|---|---|
| A. Worker installed and controlling; page fetches `/hello` | answered by the worker ("hello from SW v1"); **the edge saw 0 requests for `/hello`** |
| B. Plain reload inside the 24 h window | 0 new `/sw.js` requests (no update check) |
| C. Edge answers **404, then 410, then 500** for `/sw.js`; page calls `registration.update()` | `update()` rejects with TypeError; **registration still present; worker v1 still answers** |
| D. Edge serves a NEW 200 script (v2) with `Cache-Control: public, max-age=31536000, immutable` | `update()` resolves; v2 active; `/hello` now "hello from SW v2" (the main script bypassed the HTTP cache) |
| E. Edge serves a 200 script that calls `registration.unregister()` | **registration removed**; after reload the page is uncontrolled and `/hello` reaches the network ("hello from NETWORK") |
| F. Brand-new visitor while the edge answers 410 for `/sw.js` | registration fails ("A bad HTTP response code (410) was received when fetching the script") |

**Corrected statement.** Refusing requests (404, 410, 451, 5xx) stops *new* installs and is harmless to *installed* workers. A takedown reaches an installed worker only by serving a **new 2xx worker script** (a kill/self-unregister script, or code that checks a denylist), which the browser fetches at its next update check: the first in-scope navigation after the registration is more than 24 h stale, with the visitor online. Visitors who stay on one page, stay offline, or never return are not reached; the edge also never sees what the worker answers locally or fetches from peers.

**How the IPFS team actually handles it (repo and live site, 2026-10-17).**
- Each subdomain serves a 420-byte shim `/ipfs-sw-sw.js` (`cache-control: public, max-age=0, must-revalidate`) that `importScripts()` a content-hashed worker on the apex domain, so one deploy changes the worker for every installed subdomain at its next check.
- The worker TTL ("timebomb") that unregistered the worker after a period was **removed**: issue #840 (opened 2025-09-05) was closed on 2026-07-06 by PR #1147 "fix: remove service worker ttl". Maintainer reasoning there: the TTL only helped visitors who go offline and never return, "TTL degrades experience for legitimate users", and (lidel, 2025-09-08) "in my mind it was never a mechanism for protecting from badbits (if phishing loaded its already game over, expiring it does not matter, user already got tricked) -- it was mainly a way to avoid waiting 24h for users to update if we shipped broken JS".
- An in-worker denylist was costed and not built: #840 estimates an xor filter + MPHF + fingerprint of about 2.5 MiB (32-bit), 2.94 MiB (40-bit), 4.32 MiB (64-bit) for ~500k entries, with false-positive risk computed against 614M requests/day (18.4% per year at 32-bit); lidel: "this one is a cna [sic] of worms", the list changes "multiple times a day" and "we would have to check for new list every 5 minutes", and he preferred filtering at the delegated-routing endpoint. `BADBITS.md` still cites #840 as the place a future in-worker check would live, although #840 itself is closed.
- Enforcement is at the edge only: a gateway-edge Worker (merged 2026-10-05, inside the v3.5.0 tag of 2026-10-06; production deploy date not established) returns 410 for listed hosts "before the service worker installer is served". `BADBITS.md` explains why it was needed: until September 2026 Rainbow answered 410 at the origin; "Cloudflare Pages serves the installer for any hostname, so moving the origin to Pages removed that enforcement." That implies an enforcement gap of unknown length; forum users reported phishing pages still loading on `*.ipfs.inbrowser.link` on 2026-10-02 to 2026-10-13 (user reports, one says takedowns happened by 10-10 and the reporter says others remained; a forum moderator replied that inbrowser.link "is not hosting these contents" and that the forum is not a way of contacting the people who operate the gateway infrastructure).
- Kill switch: `?ipfs-sw-unregister=true` (README) works only if someone loads that URL on the affected origin.

**Corrections.**
1. Replace "cannot reach installed Service Workers" with the corrected statement above, and cite the experiment.
2. The planned kill switch must be a **200 script delivered through the update path**; a 404/410 "kill" does nothing to installed workers. Put the logic in code the hub controls and that every per-site registration re-fetches (the IPFS shim-plus-apex pattern does this).
3. "Needs an in-SW revocation check" is a design inference, not a finding: the IPFS team judged a full in-worker denylist heavy and chose edge plus routing-layer filtering. For magnet-web the list is the hub's own (small), so a signed revocation list polled by the worker is plausible, but it only protects visitors whose worker runs current code.

## 10. Added evidence the first pass did not have (design-relevant)

1. **Installed-worker semantics, tested.** 404/410/5xx on the worker script never evicts; a 2xx replacement does, even under `immutable` caching; first-time installs fail on 410 (section 8).
2. **IPFS removed its own worker TTL** (PR #1147, 2026-07-06) and has no in-worker denylist; its costed estimate for one is 2.5-4.3 MiB.
3. **Moving a gateway's origin dropped abuse enforcement** (Rainbow -> Cloudflare Pages, September 2026, per `BADBITS.md`) until an edge Worker was added; a kill/denylist path must be tested after every hosting change.
4. **The SW gateway has no WebRTC, listens on nothing, and sources data from HTTPS/WSS/WebTransport providers** (section 2; read from `src/sw/lib/verified-fetch.ts`).
5. **ar.io's 52-character base32 sandbox label** is production proof that a 32-byte id fits a DNS label; IPFS answers HTTP 400 for labels over 63 characters (section 7).
6. **Dependencies are quietly changing hands:** libp2p bootstrap `_dnsaddr` now maps to ipni.io hosts; the SW gateway's Cloudflare account moved to the IPFS Foundation; `dist.ipfs.tech` and `ipfscluster.io` time out from this network.
7. **Another vendor adopted the gateway:** Brave 1.90.121 uses inbrowser.link instead of ipfs.io for IPFS domain resolution, which is both validation and exposure to claim 3.
8. **Safari ITP** can delete worker registrations (2020 source).
