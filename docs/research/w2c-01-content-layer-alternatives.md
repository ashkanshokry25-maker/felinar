## Summary

**Bottom line.** The best "second content layer" for magnet-web is not a new protocol client. It is *more, better-behaved HTTP sources feeding the BitTorrent engine we already have*, because WebTorrent's web-seed path is already a multi-source fetcher with per-piece SHA-1 verification. IPFS gateways, Blossom servers and Arweave gateways are all just HTTP hosts that can serve Range requests, so they can be `ws=` URLs. Three defects stand between us and that, and I measured all three. After those are fixed, a signed per-file SHA-256 manifest is the right bridge to content-addressed stores (it is what Blossom, nsite and PeerTube already use).

1. **Fix the web seed first (P0).** Stock WebTorrent 3.0.21 (a) sends `Cache-Control` and `User-Agent` request headers that make every IPFS gateway fail the CORS preflight, (b) accepts any 2xx body, so a server that ignores `Range` silently stalls the download, and (c) never penalises a host that returns wrong bytes. Measured: one corrupt-but-206 host produced **58,421-66,926 requests in 10 s** (3.65-4.18 GB on loopback) with zero progress; one Range-ignoring host in a two-URL list left the torrent **stuck at 28 of 32 pieces forever** while the healthy URL sat idle. A replacement connection of about 90 lines of code (`torrent.addWebSeed(conn)`, prototype in the lab) fixes all of it, in Node and in headless Chromium 156 next to the unmodified `webtorrent.min.js`: bad hosts are capped at 5 requests and dropped, the loopback scenarios finish in 20-80 ms, and in the browser 12 of 15 live runs completed with SHA-256 verified (the other 3 are Range-ignoring hosts used alone, rejected and dropped instead of stalling).
2. **Stripping the two non-safelisted headers makes IPFS gateways, Blossom servers and ar.io gateways work as web seeds in a real browser** (Chromium 156, 13 hosts x 2 variants, SHA-256 of the result verified): with stock headers 4 of 4 IPFS gateways and `arweave.net` fail; with `Cache-Control`/`User-Agent` removed all 4 IPFS gateways pass. This confirms `w1-10` recommendation "strip the two headers" with end-to-end data, and shows a cheaper way to do it than patching the bundle (wrap `self.fetch` before the import).
3. **Do not build on the free public IPFS gateways, and do not add Helia/verified-fetch now.** `ipfs.io` and `dweb.link` retired on 2026-09-21 (HTTP 429 with `Sunset: Mon, 21 Sep 2026`, official page, and 3 blog posts); Shipyard's IPFS work ended 2026-09-30; Helia's last commit and npm release are 2026-09-29 and `@helia/verified-fetch`'s are 2026-09-22 (js-libp2p and the Service Worker gateway are still shipping; the Service Worker gateway's README names new Foundation maintainers). `@helia/verified-fetch@8.1.2` bundles to **1.27 MiB minified (384 KiB gzip) with 598 packages**, 6x the WebTorrent bundle. Paid, dedicated gateways (Pinata, Filebase) work fine as plain `ws=` URLs.
4. **Blossom is the best-fitting content-addressed layer.** A blob's address is the flat SHA-256 of the file (verified: the BUD-01 example blob hashes to its address), reading is an unauthenticated `GET /<sha256>`, BUD-01 *mandates* `Access-Control-Allow-Origin: *` and `Access-Control-Allow-Headers: Authorization, *` (wildcard is supported in Chrome 63+, Firefox 69+, Safari 13+), and the NIP-5A "nsite" draft already hosts static sites this way (path to sha256 manifest event, blobs on Blossom servers). Of 13 public servers probed, 4 held the test blob; 3 served it with working Range in a real WebTorrent download. One server (`blossom.primal.net`) ignores Range. Every BUD is still `draft` (only BUD-01 is `mandatory`), servers have no SLA and may expire blobs (BUD-01 defines a `Sunset` header).
5. **Arweave/ar.io is a good optional permanence anchor, a poor primary source.** Price today: the network quotes 13.81 AR per GiB (about $53 at CoinGecko's $3.85/AR) and 0.0135 AR per MiB; Turbo's list price is $81.87/GiB (floating; $81.68 an hour earlier); Turbo uploads up to 107,520 bytes per item are free within a 10 MiB lifetime cap. A 5 MiB site costs about $0.26-0.40 per release. Gateways redirect every transaction to a base32 sandbox subdomain; `arweave.net` (CDN-fronted) **ignores Range**, fails the preflight (a 302 on `OPTIONS`) and cannot be a web seed; `ardrive.net` and `vilenarios.com` honour Range and worked; `ar-io.net` and `g8way.io` have lame DNS delegation right now.
6. **BitTorrent v2 / hybrid: not now.** WebTorrent has no BEP 52 (issue #1117 open, last comment 2025-05-27, no PR; versions unchanged since 2026-07-27). A hand-built valid hybrid torrent works with WebTorrent as a v1 torrent (correct `btih`), but exposes `.pad/<n>` files in `torrent.files` and **stalls when the web seed cannot serve those paths** (152,456 of 185,224 bytes after 12 s); a connection that synthesizes pad zeros locally completes in 78 ms with no pad requests. The "file-level dedup" benefit of v2 is available today at application level with a per-file SHA-256 manifest. Native seeders that speak both WebRTC and v2 now exist on paper: **libtorrent 2.1.0 (2026-07-09) added WebTorrent support, enabled by default in its CMake build**, and `anacrolix/torrent` documents WebTorrent + BitTorrent v2; neither was interop-tested here.
7. **Precedent says HTTP-first with peers as an accelerator.** PeerTube removed WebTorrent from its player in v6.0.0 (issue #5465: "slow start time", "the P2P aspect of WebTorrent is not really used"), removed WebTorrent redundancy in v7.1.0, and validates P2P segments against a server-generated `segments-sha256.json`. P2P Media Loader downloads over HTTP first and falls back to HTTP when no peers exist. Peergos treats both IPFS and its S3-compatible block store as untrusted and relies on self-certifying data. All three support the plan: keep the web seed mandatory, verify by hash, treat every non-origin source as untrusted bytes.

**What to add first** (details in Recommendations): R1a/R1 hardened web seed + R2 seed doctor/probe (P0, about 1 week) -> R4 signed per-file manifest + R5 Blossom mirror/fallback (P1, about 2 weeks) -> R7 pointer hints (`bs=`, `ipfs=`, `ar=`, `btmh=`) and DNSLink as a discovery hint (P2, 2 days) -> optional Arweave anchor and nsite export (P2). Explicitly *not now*: Helia/verified-fetch, `publish --hybrid`, relying on any free IPFS gateway.

### A. Multi-source fetch with the engine we already have: WebTorrent web seeds

**F1 - Every `ws=` URL is an independent pseudo-peer; there is no preference order, no ban list and no backoff** (High; design-critical: yes; [C][S])
- `lib/webconn.js` (webtorrent 3.0.21): one `WebConn` (a `bittorrent-protocol` `Wire`) per URL, `connId = url`, duplicates dropped; each advertises *all* pieces; `maxWebConns` default 4 concurrent requests *per URL* (`torrent.js`); so 3 URLs mean up to 12 requests in flight.
- Request = `fetch(url, { cache:'no-store', headers:{ 'Cache-Control':'no-store', 'user-agent':..., range:'bytes=a-b' }, signal: AbortSignal.timeout(60000) })`; **success is `res.ok` only** (status, `Content-Range`, length and `Content-Encoding` are not checked); on error the piece is `donthave`'d and re-advertised after a **flat 10 s** `RETRY_DELAY`.
- When a piece fails SHA-1 verification the torrent resets the piece and emits `warning: Piece N failed verification`; **the wire that supplied the bytes is not penalised** (`torrent.js` `_request`), so the same host is asked again immediately.
- Single-file torrent: the URL is requested **verbatim**. BEP 19 says "If the url-list URL ends in a slash ... the client must add the name from the torrent"; WebTorrent does not (deviation). Multi-file: `url + '/' + file.path`, no percent-encoding (also in `w1-10` F8).
- `torrent.addWebSeed(urlOrConn)` accepts a custom connection object with a string `connId` (`Peer.createWebSeedPeer(conn, id, swarm, throttleGroups)`), but `WebConn` is not exported from the browser bundle, so a replacement must bundle its own `Wire` from `bittorrent-protocol` [I, prototype ran in Node: F6].
- Sources: `node_modules/webtorrent/lib/webconn.js`, `lib/torrent.js` (3.0.21, npm 2026-07-27); https://www.bittorrent.org/beps/bep_0019.html (Accepted; last modified 2017-01-12; created 2008-02-21); `01-webtorrent-browser.md` F10; `w1-10` F8.

**F4 - Why the IPFS gateways fail the stock preflight, and why Blossom does not** (High; design-critical: no; [X][S])
- Kubo/boxo-style gateways answer the preflight with `Access-Control-Allow-Headers: Content-Type, Range, User-Agent, X-Requested-With` (seen on `ipfs.filebase.io`, `ipfs.orbitor.dev` x3, `4everland.io`); `Cache-Control` is missing. The IPFS gateway specs do not mandate any CORS header set: the path-gateway spec only says gateways "SHOULD support single range requests" and "SHOULD include `Ipfs-Uri` in `Access-Control-Expose-Headers`" [S].
- BUD-01 mandates for every Blossom server: `Access-Control-Allow-Origin: *` on all responses and, for preflight, "at minimum, the `Access-Control-Allow-Headers: Authorization, *`" (wildcard) plus `Access-Control-Allow-Methods: GET, HEAD, PUT, DELETE`; 11 of 11 reachable servers (13 probed; one timed out, one has no DNS) sent `ACAO: *` (`cdn.satellite.earth` echoes the origin) and a preflight answer that admits `cache-control` (wildcard, explicit list, or echo). The wildcard does not cover `Authorization` (MDN) but reading needs no auth.
- ar.io sandbox hosts answer `ACAH: *` or echo the requested names; the apex of `arweave.net` answers `OPTIONS` with **302**, which browsers reject for preflights.
- Sources: curl matrices in `results/live-probes-run2.txt` (second pass 21:23 UTC, same as first pass 20:5x UTC); https://raw.githubusercontent.com/hzrd149/blossom/master/buds/01.md ("draft", "mandatory"); https://raw.githubusercontent.com/ipfs/specs/main/src/http-gateways/path-gateway.md (no date on page, read 2026-10-17).

**F5 - Cross-origin code cannot see `Content-Range` or `Content-Encoding` unless the host exposes them, so browser-side validation must lean on status, body length and the piece hash** (High; design-critical: no; [X][I])
- In the matrix the `Content-Range` header was readable for `cdn.hzrd149.com`, all four IPFS gateways, `ardrive.net` and `vilenarios.com`, and `null` for `nostr.download` and `cdn.satellite.earth` (not in `Access-Control-Expose-Headers`). `Content-Encoding` is not CORS-safelisted either, so a gzip-on-range failure (documented for GitHub Pages and jsDelivr in `w1-10` F12) shows up as a wrong body length or a decode error, not as a readable header.
- Implication: the Node-side "seed doctor" can check `Content-Range`/`Content-Encoding` (no CORS in Node); the in-browser probe and connection can only check status, length and hash. My prototype treats `Content-Range` as optional for this reason.
- Sources: lab `results/webseed-matrix-run1-2026-10-17T21Z.json` (per-host `cr` field, measured 2026-10-17); the Fetch Standard's CORS-safelisted response-header rule as summarised in `w1-10` F9 (read 2026-10-17).

**F6 - A hardened connection (about 90 lines) removes every failure in F2 and F3 and also makes BEP 47 padding web-seed-safe** (High: works in Node and in Chromium 156 with the real `webtorrent.min.js`; Medium for Firefox/Safari, untested; design-critical: yes; [X])
- `labs/w2c-01-lab/hardened-conn.mjs`: extends `bittorrent-protocol`'s `Wire` like `WebConn`, plugged in with `torrent.addWebSeed(new HardenedWebConn(url, torrent))` after `ready`. Behaviour: (1) send **only** the CORS-safelisted `Range` header; (2) require status 206 (or 200 when the range is the whole file), exact body length, `Content-Range` only if visible, no `Content-Encoding`; cancel the body on rejection; (3) when a request covers a whole piece, SHA-1 it and compare with the torrent hash so a corrupt host is *attributed*; (4) exponential backoff from 10 s up to 10 min and **drop the URL for the session after 5 consecutive integrity failures**, with an event callback for the UI; (5) synthesize zeros for `.pad/<n>` paths locally (no HTTP request).

Two copies of `bittorrent-protocol` (one inside `webtorrent.min.js`, one in our bundle) interoperated.

With a default client, a `.torrent` carrying a `url-list` made 9 requests to that host *in addition to* the hardened connection; with `new WebTorrent({ webSeeds: false })` the stock path made **0** requests and the hardened connection did all 16 (`addWebSeed` has no `webSeeds` check). So the loader must create the client with `webSeeds: false` and add every URL (pointer `ws=`, magnet `ws=`/`as=`, torrent `url-list`) itself (`labs/w2c-01-lab/webseeds-false.mjs`, `results/webseeds-false.txt`).

### B. BitTorrent v2 (BEP 52) and hybrid torrents

**F7 - What BEP 52 actually specifies (and why it is old news)** (High; design-critical: no; [S])
- Per-file SHA-256 merkle tree, binary, over **16 KiB blocks**; "the remaining leaf hashes beyond the end of the file ... are set to zero"; "identical files always result in the same root hash". The `info` dict gets `meta version: 2` and a `file tree` with a `pieces root` per file; the top level gets `piece layers` for files larger than the piece size. Each non-empty file is aligned to a piece boundary. Peers fetch proofs with messages 21/22/23 (hash request / hashes / hash reject).
- Hybrid torrents: the `pieces` and `files` of the v1 part "must be generated to describe the same data in the same order"; because v1 did not align files, "a multifile torrent must use BEP 47 padding files". Clients "can join both swarms by calculating the new and old infohashes". The v1 infohash of a hybrid torrent is the SHA-1 of the whole info dict (confirmed in F8). The v2 infohash is the SHA-256 of the info dict, written in magnets as `xt=urn:btmh:1220<64 hex>`.
- Status of the sources: BEP 52 is "Draft", last modified 2017-08-31 (created 2008-01-10); BEP 47 (padding files) "Draft", last modified 2016-08-07; BEP 19 "Accepted", 2017-01-12; BEP 17 (HTTP seeding) "Draft", 2016-07-21. **These are old sources**, but they are the live standards.
- Sources: https://www.bittorrent.org/beps/bep_0052.html , .../bep_0047.html , .../bep_0019.html , .../bep_0017.html (read 2026-10-17).

**F10 - The practical benefit people want from v2 ("same file, same hash, across versions and sites") is available today with a per-file SHA-256 manifest; real v2 would add little for browsers right now** (Medium-High; design-critical: no; [I] backed by F7, F8, F20-F23)
- With v1 and files concatenated in one byte stream, changing one file's length shifts every later piece, so old pieces cannot be reused across versions; v2 fixes that by aligning files. WebTorrent cannot use v2, so the alignment trick (BEP 47 padding) would only help if the HTTP/P2P layers also tolerate pads (F8) and files are few and large (a site of 200 small files at 256 KiB pieces would pad most of the torrent).
- A manifest `{path, size, sha256}` (the format Blossom, nsite and PeerTube's `segments-sha256.json` already use, F20-F23, F27) gives the loader file-level identity: skip unchanged files on update, verify cached files at rest, fetch single files from any content-addressed host (F21), and de-duplicate identical files across sites in hub mode. For files of 16 KiB or less the BEP 52 `pieces root` equals the plain SHA-256 of the file (one leaf; derived from F7, not executed against a reference implementation), so a later hybrid upgrade can reuse manifest hashes for small files.
- Sources: derived from F7, F8 and F20-F23; no separate external source.

**F18 - An IPFS CID can be a second source for the same files, but the CID is not derivable from the torrent; map by a per-file SHA-256 and verify with that, not with the CID** (High; design-critical: yes; [X][S])
- Demonstration with the 32-byte public file: the gateway-checker CID is `bafybei...` (CIDv1, dag-pb UnixFS wrapper); the **same 32 bytes added as a raw leaf would be CIDv1 raw + sha2-256 = `bafkreidvgaaqu7wgdwxpfybioihraktv2qfpsmssrz2c5mim3lsn5dlqaq`** (computed, `0x01 0x55 0x12 0x20 || sha256(file)`). Same bytes, different CIDs, depending on DAG layout, chunker, `raw-leaves` and CID version.
- Verification by CID without Helia works for single blocks: `GET /ipfs/<cid>?format=raw` (header `Accept: application/vnd.ipld.raw`) returns the block and "The Body hash MUST match the Multihash from the requested CID" (trustless gateway spec). Executed on `ipfs.filebase.io`, `ipfs.orbitor.dev` and `gateway.pinata.cloud`: all returned `application/vnd.ipld.raw`, 40 bytes, and `sha256(body)` equals the CID digest (`labs/w2c-01-lab/verify_cid.py`, 20 lines). Multi-block files need DAG-PB parsing and a walk (that is what Helia is for) or CAR responses; the spec's `entity-bytes=from:to` CAR parameter is the verifiable equivalent of a Range request.
- So the cheapest sound design is: the signed manifest carries `sha256` (and optionally the `cid` for locating); the loader fetches the file bytes from any gateway (`GET /ipfs/<cid>` or `/ipfs/<rootCID>/<path>`), hashes them with WebCrypto, and compares with the manifest. No DAG verification, no Helia.
- For multi-file torrents, a web-seed base of `https://<dedicated-gateway>/ipfs/<rootCID>` works only if the directory was created so that `<rootCID>/<torrent name>/<path>` exists (BEP 19 appends `name/path`); I did not test a multi-file directory CID [I]. Gateway path handling does not percent-encode names for you (F1).
- Sources: lab; https://raw.githubusercontent.com/ipfs/specs/main/src/http-gateways/trustless-gateway.md (no date on page); path-gateway spec ("Gateways SHOULD support single range requests").

**F19 - DNSLink and IPNS are specified, cheap to read from a browser, and overlap with our pointer; DNSLink is unsigned** (High; design-critical: no; [S])
- DNSLink: records "MUST be specified on the `_dnslink` subdomain", value `dnslink=/<namespace>/<identifier>` (examples `/ipfs/<cid>`); the bare-domain TXT is deprecated; several records may exist; resolvers "should never error on invalid record" and ignore them; sorting is lexicographic; CNAME chains are followed; suggested low TTL (about 60 s) vs a default of 3,600 s. Nothing about DNSSEC or string length. Our DoH code for `_magnet.<host>` could read `_dnslink.<host>` with the same two-resolver logic.
- IPNS: record = DAG-CBOR in `IpnsEntry.data` with `ValidityType` (EOL), `Sequence`, `TTL`, signed with `signatureV2`; "less than or equal to **10 KiB**". Delegated routing v1 exposes `GET /routing/v1/ipns/{name}` (`Accept: application/vnd.ipfs.ipns-record`) with browser-friendly CORS (`Access-Control-Allow-Origin: *`, preflight answers required). So an IPNS name is a signed, versioned pointer (our `seq`/`exp`/`sig` is the same idea), but its keys are libp2p keys (Ed25519/RSA/secp256k1) rather than WebCrypto P-256, and resolution depends on a router that may no longer be operated (F12).
- Sources: https://dnslink.dev/ (read 2026-10-17, no date); https://raw.githubusercontent.com/ipfs/specs/main/src/ipns/ipns-record.md ; https://raw.githubusercontent.com/ipfs/specs/main/src/routing/http-routing-v1.md .

### D. Blossom (Nostr blob servers) and nsite

**F20 - Blossom is a small, plain-HTTP spec for content-addressed blobs: read by hash with no auth, write with a Nostr-signed token, CORS and Range behaviour specified** (High; design-critical: yes; [S])
- Repo `hzrd149/blossom`, BUDs 00-12. **Every BUD I read (01, 02, 03, 04, 06, 07, 10, 11, 12) carries `draft`; only BUD-01 is also `mandatory`**, the rest `optional` (BUD-00, 05, 08, 09 not opened). No dates on the pages (read 2026-10-17).
- BUD-01 (retrieval): `GET /<sha256>[.ext]` "MUST return the contents of the blob"; `Content-Type` always present (`application/octet-stream` default); `206` for a valid `Range`, `416` otherwise; "servers should support range requests" (lower-case *should*, so not guaranteed: F21); redirects (307/308) are allowed only to a URL "containing the same sha256", and the destination "MUST set the `Access-Control-Allow-Origin: *`" header; `HEAD` mirrors `GET`; optional `Sunset` header for expected expiry ("Clients MUST NOT interpret `Sunset` as a permanent negative cache signal"); CORS: `Access-Control-Allow-Origin: *` on all responses and preflight `Access-Control-Allow-Headers: Authorization, *` plus `Access-Control-Allow-Methods: GET, HEAD, PUT, DELETE`, optional `Access-Control-Max-Age: 86400`.
- BUD-02 (upload): `PUT /upload`, server "MUST NOT modify the blob in any way and MUST compute the sha256 hash over the exact bytes received"; descriptor `{url, sha256, size, type, uploaded}`; "Servers MAY include additional fields in the descriptor like `magnet`, `infohash`, or `ipfs`" (the spec explicitly anticipates BitTorrent and IPFS bridges). BUD-04: `PUT /mirror {"url": ...}` server-to-server copy (hash must match the authorised `x` tag, else 409). BUD-06: `HEAD /upload` pre-check. BUD-07: HTTP 402 with `X-Cashu` / `X-Lightning` headers when payment is needed. BUD-12: `DELETE /<sha256>` and `GET /list/<pubkey>` ("unrecommended").
- BUD-03: replaceable event kind **10063** lists a user's servers, ordered "most reliable or trusted first"; clients extract "the last occurrence of a 64 char hex string" from any URL and, if the original host is gone, try the author's list in order, then well-known servers. BUD-10: `blossom:<sha256>.<ext>?xs=<server>&as=<author pubkey>&sz=<bytes>`, "similar to magnet links", with `xs`/`as` repeatable.
- BUD-11 auth: Nostr event kind **24242** (secp256k1 Schnorr), required `expiration` tag, `t` verb (`get|upload|list|delete|media`), optional `server` and `x` (blob hash) scoping, sent as `Authorization: Nostr <base64url(event)>`. Reading is normally unauthenticated. WebCrypto has no secp256k1, so signing belongs in the Node publish tool (a small library such as noble-curves/nostr-tools) [I].
- Sources: https://github.com/hzrd149/blossom (README: BUD table and endpoint table) and raw `buds/01,02,03,04,06,07,10,11,12.md` (read 2026-10-17).

**F22 - The address is the flat SHA-256 of the file, verified; BUD-03/BUD-10 are the pattern for "hash + hints" pointers** (High; design-critical: yes; [X][S])
- `curl https://cdn.hzrd149.com/b1674191...f553` -> 184,292 bytes whose `shasum -a 256` is exactly `b1674191a88ec5cdd733e4240a81803105dc412d6c6708d53ab94fc248f4f553`. So a manifest line `{path, size, sha256}` is already a complete Blossom address, and WebCrypto `crypto.subtle.digest('SHA-256')` is all the verification code needed.
- BUD-10 mirrors our pointer's `ws=`/`xs=` idea: hash first, then repeatable server hints, optional author, optional size. Our `bs=<server>` (repeatable) and `sz=` would be the same shape (R7).
- Sources: `curl` + `shasum -a 256` on 2026-10-17; https://raw.githubusercontent.com/hzrd149/blossom/master/buds/03.md and `10.md` (no dates on the pages).

**F23 - NIP-5A "nsite" is a draft, but it is a working precedent for a signed path-to-hash manifest plus dumb blob hosts, with tooling for diff uploads** (High for the facts; Medium for longevity; design-critical: no; [S])
- NIP-5A: status "Draft, optional", **created 2026-03-25, last updated 2026-06-16**. Kinds: **15128** root site (replaceable, no `d` tag), **35128** named site (`d` matches `^[a-z0-9-]{1,13}$`), **5128** snapshot. Tags: `["path", "/abs/path", "<sha256>"]` (required, one per file), `["x", "<sha256>", "aggregate"]`, `["server", "https://blossom..."]` hints, `title`/`description`/`source`. **Aggregate hash**: one line `<sha256hash> <absolute-path>\n` per `path` tag, sort lexicographically, concatenate as UTF-8, SHA-256, lower-case hex; "Two manifests are equivalent if and only if their aggregate hashes match".
- Gateway rules: resolve host label (`<npub>.host`, `v<snapshot>.host`, `<pubkey-base36><dtag>.host`), find the `path` tag, `index.html` fallback for directory-like paths, "verify that the served blob's SHA-256 matches the `path` tag" (mismatch = not found), fetch from `server` tags then the author's kind 10063 list, else 404; `/404.html` fallback.
- Implementations are **server-side**: `hzrd149/nsite-gateway` (Deno + Hono; env `LOOKUP_RELAYS`, `BLOSSOM_SERVERS`, verification worker pool, sha256 as strong ETag, no releases listed), Go gateways and a native `nsite://` browser (these two appear only in search-result titles, I did not open them). None that I could confirm runs in the visitor's browser the way magnet-web's loader does. `nsyte deploy ./dist` uploads to Blossom and relays with "smart diffing" (unchanged hashes are not re-uploaded) and can `run` a resolver. `nsite.run` itself returned only a title when fetched.
- Takeaways for magnet-web: (1) use the same manifest entry shape and aggregate-hash rule so a magnet-web site can also be published as an nsite for free; (2) diff-upload by hash is the production pattern for "file-level dedup across versions"; (3) because the NIP is a draft, make nsite export optional and generated, never required.
- Sources: https://nips.nostr.com/5a ; https://github.com/hzrd149/nsite-gateway ; https://raw.githubusercontent.com/sandwichfarm/nsyte/main/README.md ; https://nsite.run/ (read 2026-10-17); `w1-07` F22.

**F26 - Arweave path manifests and Wayfinder give a hosting layer and a client-side verification layer; verification is opt-in** (High; design-critical: no; [S])
- Path manifest: a data item tagged `Content-Type: application/x.arweave-manifest+json` with `{"manifest":"arweave/paths","version":"0.2.0","index":{"path":...},"fallback":{"id":...},"paths":{"css/style.css":{"id":"<txid>"}}}`; gateways resolve `https://<gw>/<manifestTxId>/<path>`. - Wayfinder (ar.io): `@ar.io/wayfinder-core`, `@ar.io/wayfinder-react`; routing strategies `PreferredWithFallbackRoutingStrategy`, `FastestPingRoutingStrategy`; "Automatic failover - If one gateway is down, requests route to another"; **verification is off by default** and, when enabled with no strategy, hashes against `turbo-gateway.com`; `strict: true` fails the request on mismatch. The docs page says nothing about Range requests or service workers; the browser extension handles `ar://`.
- Takeaway: Wayfinder is the same multi-source pattern as our web-seed list (ordered/raced providers, failover, hash check) but trusts a named gateway for the hash; our torrent piece hashes are strictly stronger (the publisher commits to them in a signed pointer).

### G. One table to design the mapping between layers

**F30 - What "the same file" means in each layer, and what can be derived from a flat SHA-256** (Medium-High; design-critical: yes; [X] where marked, otherwise [S]/[I]/[B])

| Layer | Names a file by | Derivable from the file's flat SHA-256? | Verifiable unit | Notes |
|---|---|---|---|---|
| BitTorrent v1 (WebTorrent today) | SHA-1 per piece over the *concatenation* of all files; btih = SHA-1 of the info dict | No | piece (pieces span files) | file identity is not stored |
| BitTorrent v2 / hybrid | SHA-256 merkle root per file (16 KiB leaves, zero-hash padding) | Only for files <= 16 KiB (single leaf) [I] | 16 KiB block with proof | needs piece-aligned files (BEP 47 pads in hybrids, F8) |
| Blossom | flat SHA-256 of the whole blob [X] | **Yes (identical)** | whole blob (Range allowed, verification after download) | author list + `xs` hints |
| IPFS, CIDv1 raw + sha2-256, single block | multihash of the block | **Yes** (`0x01 0x55 0x12 0x20` followed by the 32-byte SHA-256) [X: computed `bafkrei...`] | block (<= 1 MiB) | only when added with raw leaves and the file fits one chunk |
| IPFS default (dag-pb UnixFS, chunked) | multihash of the protobuf-wrapped root/leaves | **No** (same 32 bytes: `bafybei...` vs `bafkrei...`) [X] | block, DAG walk | CID depends on chunker, raw-leaves, CID version, layout |
| Arweave | transaction id (not the content hash); tx header has `data_root` (merkle over chunks) [B] | No | chunk with proof (gateway-side), or gateway-reported digest vs trusted gateways (Wayfinder) | txid is the address; verification trusts a gateway unless you fetch proofs |
| nsite NIP-5A | `path` tag `sha256` (flat) + aggregate hash | Yes | whole file | same shape as a magnet-web manifest |
| PeerTube HLS | `segments-sha256.json` (flat per segment) | Yes | segment | per-chunk manifest next to content |

Sources: F7-F29 above; items marked [B] are background not re-verified here.

Design consequence (drives R4): store `{path, size, sha256}` per file (plus optional `cid`) in a manifest that the signed pointer commits to by hash. Then Blossom, nsite and raw-leaf IPFS addresses are *derived*, dag-pb CIDs are *located* (you must record them), Arweave transaction ids are *located*, and nothing else needs to be verified with a foreign scheme.

### What I would not do

- Do not make any free public IPFS gateway part of a default `ws=` list or of documentation examples.
- Do not trust `Content-Range`, `Content-Encoding` or `Accept-Ranges` as seen from page JavaScript; they are often not exposed (F5).
- Do not put the Nostr signing key and the site owner key in the same file or reuse one for the other (secp256k1 Schnorr vs ECDSA P-256; different blast radius).
- Do not assume `arweave.net` or any CDN-fronted gateway honours Range; probe it (R2).

## Gotchas

1. **`Cache-Control` and `User-Agent` in WebTorrent's fetch cause a preflight that most gateways reject** (F3, F4). `Range` alone does not (`w1-10` F9). The stock S3 recipe `AllowedHeaders: ["Range"]` also fails (`w1-10`).
2. **A preflight must be answered 2xx without redirect.** `arweave.net` answers `OPTIONS` with 302 and Chromium reports "Redirect is not allowed for a preflight request" (F3).
3. **A server that ignores Range returns 200 and the whole body; WebTorrent treats that as success and stalls silently** (F2, F3). `blossom.primal.net` and `arweave.net` did exactly this on 2026-10-17.
4. **Stock WebTorrent never penalises a host that returns wrong bytes**: 58,421-66,926 requests in 10 s on loopback with 0 progress (F2). On a real network the rate is lower but unbounded; it can burn a mobile user's data and an S3 bill.
5. **`Content-Range` and `Content-Encoding` are not readable cross-origin unless exposed**; `cdn.satellite.earth` and `nostr.download` do not expose `Content-Range` (F5). Validate status, length and hash instead.
6. **Compression applied to ranges** (documented for GitHub Pages and jsDelivr in `w1-10` F12) was not exercised on these gateways because my test blobs are incompressible types; serve bundles as `application/octet-stream` and assume nothing.
7. **Hybrid torrents list pad files as normal files and need the HTTP host to serve zeros at `<name>/.pad/<n>`**, or a connection that synthesizes them (F8, F6).
8. **BEP 19 vs WebTorrent for single-file torrents**: BEP 19 appends the torrent name to a `url-list` entry that ends in `/`; WebTorrent requests the URL verbatim (F1). Give the full file URL.
9. **The same bytes have different IPFS CIDs** depending on layout (`bafybei...` dag-pb vs `bafkrei...` raw). Never derive a CID from a hash unless you control how it was added (F18).
10. **`ipfs.io` behaves differently for browsers and scripts** (`Vary: Sec-Fetch-Dest, Sec-Fetch-Mode, Origin`). My curl results (429) are the non-browser path; a sibling saw a Cloudflare challenge; neither tells you what a visitor's browser sees. Treat it as retired regardless.
11. **Gateway state is volatile.** Within this single session `storacha.link`, `nftstorage.link`, `cloudflare-ipfs.com`, `w3s.link` (locally), `trustless-gateway.link`, `ar-io.net`, `g8way.io` were already redirect-only or unreachable. Re-probe before every release (R11).
12. **Blossom servers can delete or never hold your blob.** 7 of 13 returned 404 for a famous blob; BUD-01 allows a `Sunset` header; BUD-07 allows 402. Always list at least two servers and verify after upload.
13. **All Blossom BUDs I read are `draft`** and NIP-5A is a draft updated 2026-06-16; wire formats may still change.
14. **Arweave uploads are immutable and public**, so a bad release or a leaked secret stays. USD prices float (Turbo moved from $81.68 to $81.87 per GiB in about 30 minutes).
15. **`maxWebConns` is per URL** (default 4), so adding mirrors multiplies concurrent requests; Pinata-style plans count every Range request (F1, F17).
16. **The prototype connection reads `torrent._hashes`** (private), so pin webtorrent and keep a canary test. It ran in Node and in Chromium 156 (two copies of `bittorrent-protocol` interoperated); never store `window.fetch` as an object property and call it as a method ("Illegal invocation" in browsers, invisible in Node).
17. **Environment note for reproducing this research on the author's Mac:** the local resolver sinkholes `w3s.link`, `turbo-gateway.com`, `g8way.io`, `latam.orbitor.dev` to 0.0.0.0, and brew Python cannot reach the network (firewall); use curl or Chromium as the lab scripts do.

## Open questions

1. Do Firefox and Safari send `user-agent` in the preflight and do they accept the same hosts after stripping? (Only Chromium 156 was run.)
2. Does a Service Worker re-issuing the request (spec-derived in `w1-10`, untested) give the same header stripping as the connection or the global `fetch` wrapper? Does the hardened connection behave the same in Firefox and Safari (only Chromium 156 was run)?
3. Multi-file directory CIDs as `ws=` bases on Pinata/Filebase dedicated gateways: does `<rootCID>/<name>/<path>` serve with Range, correct CORS and no compression surprises? Are dedicated-gateway CORS lists more permissive than the public ones I probed?
4. Compression plus Range on IPFS/Blossom/Arweave gateways for compressible types (HTML, JS, CSS, JSON).
5. Interop of libtorrent 2.1 / anacrolix/torrent seeders with browser WebRTC peers through a `wss://` tracker (R10); when will qBittorrent ship a release with libtorrent 2.1?
6. Who operates `delegated-ipfs.dev`, `inbrowser.link` and `trustless-gateway.link` after Protocol Labs decides, and does Helia's release cadence resume under named maintainers? Re-check at the next wave.
7. What happened to Storacha's IPFS pinning (pricing page now redirects to an S3 product)?
8. Real capacity, rate limits, retention and paid tiers of public Blossom servers (one request per server was all I measured); which servers will still hold a 5 MiB blob in a year?
9. Is the BEP 52 `pieces root` of a file of 16 KiB or less really equal to the plain SHA-256 (my reading of the spec; not compared with a reference implementation)?
10. Search-budget leftovers: other browser-capable BEP 52 implementations (SpawnDev.WebTorrent claim unverified), Satellite/nostr.build pricing, Arweave endowment assumptions, Iroh/BLAKE3 verified streaming as a further precedent for range-verifiable fetch.
11. Should the loader shell itself get a second host (nsite, an IPFS dedicated gateway with a Service Worker, Cloudflare Pages)? Out of scope here, but a content layer without a second shell host still has a single entry point.
