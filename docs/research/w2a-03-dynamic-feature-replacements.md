## 1. Summary

1. **Almost every "dynamic" feature of a typical brochure/blog/docs site has a workable replacement, but they fall into four different classes**, and the migration promise must say which class each feature is in: (N) works with the v0.2 ledger and SDK as specified (guestbook, comments, local personalization, search); (C+) needs a new chain/SDK piece (reactions with reducer-maintained counts, approval queue, sealed inbox, recoverable identity, lazy media); (E) is delegated to a hosted third-party service called from the browser (form relays, newsletter providers, Stripe Payment Links / Buy Button, cookieless analytics); (S) cannot be done without a server or edge function (sending email, payment webhooks and fulfilment, Stripe Checkout Sessions, secrets, scheduled jobs, private data). Section 2 is the table.
2. **STAR Origin preservation is the foundation of drop-in migration, and site code is never isolated from the engine.** In shell (per-domain) and drop-in mode the site runs at its own origin, so third-party embeds that validate the page origin keep working; at a hub origin they do not (inference, F2). In shell mode the same-origin iframe (`allow-scripts allow-same-origin`) is no sandbox - MDN says it "lets the embedded document remove the sandbox attribute" - and in drop-in mode there is no frame at all: `window.mw` is bound directly to the engine in the page (ARCH v0.2 section 3.4.9). Any feature that touches identity or money must assume hostile site code (doc 04 F11, doc 06 section 3.1.9, w1-11 F1).
3. **STAR Chain-backed comments/guestbook are the best-fitting feature; chain-backed counters, personal data and money are not.** Emulating the ARCH v0.2 block shape with the project's own `canonicalize`/`sha256`/`sign` code (`src/chain/block.js` did not exist yet): a 200-character comment is 798 B on the wire with one parent head and 1,267 B with eight; a "like" as a `put` is 570-1,039 B. The v0.2 default policy is `writers: 'owner'`, so visitor posts need `publish.mjs --policy open`; the default `maxChainBytes` of 8 MiB holds only about 8,000-14,700 likes (the 64 MiB ceiling about 65,000-118,000) before non-privileged blocks are refused (`E_CAP`). The full ingest check (canonicalize + SHA-256 + ECDSA verify) ran at 6,000-12,000 blocks/s in Node on an M3 (100,000 blocks = 8-17 s; phones not measured). Counts are Sybil-inflatable (doc 06 F40) and must be labelled "devices".
4. **STAR Do not put personal data on the chain, even encrypted.** The EDPB's final Guidelines 02/2025 (v2.0, adopted 2026-07-07), para 51: "encrypted personal data is still personal data and encryption does not remove the need for GDPR compliance"; para 50: "technical impossibility cannot be invoked"; para 48: "it is not advisable to store personal data on the blockchain". A replicated log that every visitor relays is exactly the case they worry about (by analogy: our log has no consensus, and legal applicability is unverified). So a "chain inbox encrypted to the owner key" is measurable (1,437 B maximum plaintext at the default 2,048 B `maxValueBytes`; a 300 B message becomes a 1,154 B block) and cryptographically easy (HPKE/age, both with maintained browser libraries), but it should ship **off by default, with a stated retention/erasure limit**, and default contact forms should use a form relay or `mailto:`.
5. **STAR Authentication: passkeys are now a safe optional layer, not a base layer.** WebAuthn Level 3 became a W3C Recommendation on 2026-08-25. PRF-derived keys work in my test inside the exact SW-served same-origin iframe design (Chromium 156 virtual authenticator: PRF enabled at create, 32-byte output, deterministic, per-site salt gives a different key, HKDF -> Ed25519 seed -> WebCrypto import -> sign/verify, same public key on re-derivation). Real-world support (Corbado, August 2026 snapshot) is good on Apple Passwords, Google Password Manager, Windows Hello (only after the February 2026 cumulative update), 1Password, Proton Pass, Keeper, Enpass, but **not** Dashlane or NordPass, and partial for Bitwarden; MDN's own compatibility data still lists Safari `get()` PRF as unsupported while Corbado reports it working (a conflict to resolve on devices). A WebAuthn assertion can also be used directly as a block signature: verified in my test, cost +178-180 raw bytes (about +240 base64url characters) per block, and it gives a hardware user-verification gate that a same-origin IndexedDB key cannot. Losing the passkey loses the key, and a WebAuthn co-editor warns against PRF for encryption keys for that reason, so identity must stay recoverable by export. ARCH v0.2 already keeps the owner key out of browsers (section 6.2) and has a passphrase-wrapped identity export; the keys a hostile script can still drive are the visitor's identity key and any imported moderator key, and the safer PRF design wraps the identity seed (an envelope) instead of deriving the only copy of the identity.
6. **Site search is a solved, measured drop-in.** Pagefind 1.5.2 (2026-04-12) ran unchanged inside the SW-served sandboxed iframe, including its Web Worker and WASM, with unknown file extensions served as `application/octet-stream`. Its index is **20.0% (pydoc corpus, 168 pages) to 43.3% (Postfix+CUPS docs, 194 pages) of the HTML bytes** (55-68% of the visible-text bytes), already compressed (gzip -9 saves about 0%), spread over 200+ files, and the output directory also carries about 0.42 MB of UI bundles a site rarely needs all of. Because magnet-web downloads the whole torrent first, the index's chunking saves no network; it only saves memory. In drop-in mode, requests made inside Pagefind's Worker are probably not mapped to the torrent and go to the host (inference from ARCH v0.2 section 3.4.2; untested).
7. **Analytics: the honest default is none.** Peer-served page views never reach the static host, so host logs undercount. Browser-native private measurement is being retired (on 2025-10-17 Google announced it will retire Private Aggregation, Attribution Reporting and Topics). The IETF DAP protocol is still an Internet-Draft (draft-ietf-ppm-dap-19, 2026-07-06) and needs two non-colluding aggregators, i.e. servers. Local differential privacy without any backend works only at scale: for a 10% feature rate and a 95% interval of +/-1 percentage point you need about 38,800 visitors at epsilon = 1 (about 10,400 at epsilon = 2) versus 3,457 without privacy (computed). The free signal is tracker `scrape` (current seeders + leechers; works on 3 of the 4 public trackers probed in doc 02).
8. **E-commerce: only the "hosted link" tier needs no backend of ours.** Stripe Payment Links and the Buy Button (`<script src="https://js.stripe.com/v3/buy-button.js">` + `<stripe-buy-button>`) need no backend; Checkout Sessions need a server endpoint and a secret key ("Always keep ... price and availability on your server"). Snipcart validates carts by crawling `data-item-url` with a plain unauthenticated GET from its servers, which works only if a **public static copy of the product pages (or a JSON endpoint) exists on the origin host**: in drop-in mode the HTML stays on the host by design (ARCH v0.2 sections 3.4.1 and 3.4.8), whereas shell mode answers every URL with the shell, so crawlers that do not run the loader see no content. Fulfilment and webhooks remain server work.
9. **Media: stream HLS segments, not WebTorrent pieces, and make large files lazy.** PeerTube removed WebTorrent from its player in v6.0.0 (issue #5465: "slow start time, hacky resolution change", P2P "not really used") and keeps P2P only through HLS (P2P Media Loader, now 4.0.0). In my SW test, a `<video>` served by the SW **could not seek in Chromium 156 unless the SW answered the `Range` request with 206** (seekable range [0,0] otherwise); WebKit 27.2 sent a `bytes=0-1` probe and tolerated a plain 200 for a 96 KB clip. iPhone Safari is untested. WebTorrent 3.0.21 already provides range reads (`file.stream({start,end})`) that mark the cursor pieces critical.
10. **Chat: use the swarm you already have.** Trystero 0.26.0 (MIT) provides rooms over the same WebSocket trackers, but its README says the BitTorrent, MQTT and IPFS strategies have "far less relay redundancy than Nostr" and that discovery still relies on third-party relays. A `mw_room` wire extension next to `mw_chain` would give ephemeral rooms with no new signalling dependency; iOS suspends WebRTC in the background (doc 06 F23), so chat is foreground-only on iPhones.
11. **Moderation has strong, convergent precedent and one clear gap.** Owner ops (doc 06 section 3.1.5) are the base. Matrix (spec v1.19) shares moderation as subscribable policy-list rooms (`m.policy.rule.*`, only recommendation `m.ban`), AT Protocol shares signed label objects chosen by the client (`atproto-accept-labelers`), Nostr has NIP-32/51/56. Nostr's proof of work (NIP-13) is optional and sits beside reports, labels and mute lists, and ZeroNet's own conservancy fork still lists "No reliable spam protection". What we lack: a **pre-moderation queue**, subscribable block lists and local mute lists. A browser-side toxicity classifier is not viable (smallest quantised toxic-bert ONNX 97.2 MB).
12. **Top actions** (details in section 4): (1) publish the migration classes and the "stays on a server" list together with the no-personal-data rule [P0, S]; (2) add the `react` op with a reducer index, an approval/report path, and a plan for the 8 MiB default ledger budget [P1, M]; (3) give `publish.mjs --dropin` an exclude list and a lazy/Range path so large media stays usable [P1, L]; (4) put Pagefind into `publish.mjs` and the e2e fixtures and test its Worker requests in drop-in mode [P1, S]; (5) treat imported moderator keys as hot keys (confirmation or WebAuthn-signed ops) and offer a PRF-wrapped identity seed [P1, M].

## 3. Findings

Format: **F# claim.** *Confidence; STAR if design-critical.* Evidence bullets, then sources with dates.

### 3.1 Cross-cutting: origin, sandbox, fallback, virtual endpoints

**F1 (STAR) Site code is not isolated from the engine in any mode, so every feature that touches identity, moderation or money must assume hostile site code.** *Confidence: high.*
- Shell mode. MDN (iframe `sandbox`): "When the embedded document has the same origin as the embedding page, it is strongly discouraged to use both `allow-scripts` and `allow-same-origin`, as that lets the embedded document remove the `sandbox` attribute - making it no more secure than not using the `sandbox` attribute at all." ARCH v0.2 section 7.2 sets exactly `allow-scripts allow-same-origin allow-forms allow-popups allow-downloads allow-top-navigation-by-user-activation`; my Chromium 156 runs logged "An iframe which has both allow-scripts and allow-same-origin for its sandbox attribute can escape its sandboxing."
- Drop-in mode. ARCH v0.2 section 3.4.9 says the engine runs in the site's own origin and `window.mw` is bound directly to it, with no Bridge. There is no frame; site scripts and the engine share one JavaScript realm.
- Doc 04 F11 (and w1-11 F2): a sandbox without `allow-same-origin` is not controlled by the SW at all (WPT 29/29 on Chrome 155, Firefox 158, Safari 27.0; doc 04 reproduced it in Chromium 156 with the iframe served by the network, and in this session the opaque-origin variant of my WebAuthn test never ran its SW-served page), so `allow-same-origin` is mandatory in shell mode. w2c-03 (identity UX) reports that in Chromium 156 a same-origin iframe opened the loader's IndexedDB and signed arbitrary bytes with the visitor's non-extractable key; I did not repeat that test.
- Doc 06 section 3.1.9 and F51: non-extractable CryptoKeys protect against theft, not against use.
- ARCH v0.2 section 6.2 already keeps the owner key out of browsers ("there is no 'owner login'"), which removes the worst case. What hostile script can still drive: the visitor's identity key and any moderator key imported in Settings (moderators may `tombstone` and `ban`).
- Consequence: payment scripts (Stripe), analytics beacons and form-relay widgets that a site includes run beside the identity key. Where a feature needs a hard guarantee (moderation, high-value identity) it needs a user-verification step that script cannot fake (WebAuthn, F29-F30) or must happen outside the browser (CLI signing).
- Sources: [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe) (undated, read 2026-10-17); ARCH v0.2 sections 3.4.9, 6.2, 7.2; doc 04 F11; doc 06 3.1.9, F51; w1-11 F1-F2; w2c-03 summary item 1; my runs in `labs/w2a-03-experiments/results-2026-10-17.txt`.

**F2 (STAR) Shell (per-domain) and drop-in modes preserve the origin that third-party services were registered against; the hub modes do not, and hub labels are stable only for signed pointers.** *Confidence: medium (the individual facts are read; the migration consequence is my inference).*
- Read: Stripe Buy Button docs - "Rendering the buy button requires a website domain"; Snipcart - "We accept a crawled URL when its host matches your default domain or one of your allowed domains"; ERC-4361 (SIWE) - the message `domain` "MUST correspond to the origin from where the signing request was made"; WebAuthn credentials are bound to an RP ID that must be "a registrable domain suffix of or is equal to the caller's origin's effective domain" (W3C WebAuthn L3, read), with Related Origin Requests limited to **5 labels** ("there are no known clients which support more than 5") and described as "designed to be used when federation is not possible".
- ARCH v0.2 section 3: shell and drop-in run at "the site's domain"; the subdomain hub at `<label>.<hub>`; the shared-origin hub at the hub origin ("never claims isolation"). The label is `base32(sha256(ledgerId)).slice(0,32)` for signed pointers (stable across releases) and `base32(btih)` for bare magnets (changes with every release); identity, ledger database and pins are keyed by ledger id on every origin. So the reset-per-release problem I first inferred from v0.1 is already avoided for signed pointers and remains only for unsigned bare magnets.
- Inference (not tested): reCAPTCHA/hCaptcha site keys, OAuth redirect URIs, Apple Pay domain verification and CORS allow-lists are all keyed to the page origin. They keep working unchanged after migration in shell and drop-in mode because `location.origin` stays `https://example.com`; at `<label>.<hub>` or the shared hub origin they do not.
- Sources: [Stripe Buy Button](https://docs.stripe.com/payment-links/buy-button) (undated); [Snipcart order validation](https://docs.snipcart.com/v3/setup/order-validation) (undated); [ERC-4361](https://github.com/ethereum/ercs/blob/master/ERCS/erc-4361.md) (Final, created 2021-10-11); [passkeys.dev related origins](https://passkeys.dev/docs/advanced/related-origins/) (undated); [W3C WebAuthn L3 Recommendation](https://www.w3.org/TR/webauthn-3/) (2026-08-25); ARCH v0.2 section 3.

**F3 Under the shell-mode iframe flags, `mailto:` links, top-level navigation to a payment page and popups behave as needed; two of the flags are load-bearing.** *Confidence: medium (Chromium 156 headless only; no mail client was available, so the launch itself was not verified).*
- Measured with `allow-scripts allow-same-origin allow-forms allow-popups allow-modals allow-downloads allow-top-navigation-by-user-activation` (the v0.1 set; v0.2 section 7.2 drops `allow-modals`, which only affects `alert`/`confirm`/`prompt`): plain `mailto:` link, `target=_blank` mailto, `location.href = 'mailto:...'` and `top.location.href = 'mailto:...'` produced no sandbox error; a `target=_top` https link navigated the top frame (the shape of a Stripe redirect).
- Without `allow-popups`: "Blocked opening 'mailto:...' in a new window because the request was made in a sandboxed frame whose 'allow-popups' permission is not set." Without `allow-top-navigation-by-user-activation`: "Unsafe attempt to initiate navigation for frame ... from frame ...". Both flags must stay in the shell-mode iframe attribute. In drop-in mode there is no frame and none of this applies.
- Sources: my `mailto-exp` run (2026-10-17); MDN iframe sandbox token table (above); ARCH v0.2 section 7.2.

**F4 The static host copy is itself a feature: in drop-in mode it is the crawl and validation target for services that insist on fetching your pages from their own servers; in shell mode it is not.** *Confidence: high for the behaviours, medium for the combined consequence.*
- ARCH v0.2 sections 3.4.1 and 3.4.8: in drop-in mode HTML "stays out of the torrent" and is served by the host, "so crawlers, link unfurlers, no-JS clients, Lockdown Mode, in-app WebViews and any engine failure see today's site. Drop-in fails open." Shell mode "answers every URL with the shell, so crawlers that do not run the loader see no content".
- Snipcart: "Every crawl is a plain GET from our servers, with no cookies and no authentication, so the URL has to be publicly reachable"; it parses the HTML for the buy button carrying the item id, or, if the response `Content-Type` is `application/json`, validates `id` and `price` from JSON; the docs do not say whether it executes JavaScript. A shell-mode product page is invisible to that crawler unless the host also serves a real page or JSON for the `data-item-url`.
- Google Search on A/B tests: do not cloak, use `rel="canonical"` on variants (not `noindex`), use 302 not 301, end experiments promptly. The host-served page must show the same content as the P2P-served one (the control).
- Sources: ARCH v0.2 sections 3.4.1, 3.4.8; [Snipcart order validation](https://docs.snipcart.com/v3/setup/order-validation) (undated); [Google Search: website testing](https://developers.google.com/search/docs/crawling-indexing/website-testing) (undated).

**F5 A site's own `fetch('/api/...')` calls can be answered in the browser; the precedent is mature, but the handler must not live in the Service Worker and drop-in mode limits what the SW may synthesize.** *Confidence: high for precedent, medium for the design.*
- Mock Service Worker (msw 3.0.3, 2026-10-10, about 23.0 million weekly downloads) "uses the Service Worker API to intercept actual production requests on the network level" instead of patching `fetch`. Hono ships a Service Worker adapter (`@hono/service-worker` 1.0.1, 2026-10-08, only about 202 weekly downloads, i.e. new): `fire(app)` registers the fetch listener; hono 4.13.13 itself has about 74 million weekly downloads.
- WebTorrent 3.0.21 already contains the pattern we need: `lib/worker-server.js` forwards a SW fetch to window clients over a `MessageChannel` and streams the reply back, with keep-alive and cancel endpoints (read in `node_modules`).
- Doc 04 test B: a SW had the same boot timestamp after 20 s idle but a new one after a further 65 s, so Service Worker globals die; handlers and state belong in the page, with the SW only forwarding (the page-fed stream test C in doc 04 worked across 40 s gaps).
- ARCH v0.2 constraints: in drop-in mode the SW "decides every request synchronously from in-memory state ... and passes the request through when unsure" and "never synthesizes redirects, 404s or headers for the host's URLs" (3.4.2), and the engine lives for one page view (3.4.6). So an API shim must be an explicit opt-in route list in the manifest, answerable from IndexedDB alone (reads) or by forwarding to the current page's engine (writes), and must never block a request the host can answer.
- Use: existing front-ends keep `fetch('/api/comments')`, `POST /contact` or `/api/search` and get answers from the chain, a form-relay adapter or a local index. The static host answers the same URLs with 404/405, which is the honest fallback.
- Sources: [MSW docs](https://mswjs.io/docs/) (undated); [Hono Service Worker](https://hono.dev/docs/getting-started/service-worker) (undated); npm registry data (2026-10-17); `node_modules/webtorrent/lib/worker-server.js`; doc 04 tests B and C; ARCH v0.2 sections 3.4.2, 3.4.6.

**F6 Redirects, custom headers and pretty URLs are already covered by the v0.2 routing manifest in shell mode; in drop-in mode the host keeps its own rules.** *Confidence: high (ARCH v0.2 and INTERFACES read; the manifest was not tested).* `publish.mjs` writes `/.mw/site.json` (`spa`, `cleanUrls`, `trailingSlash`, `redirects`, `headers`, `index`, `notFound`) from flags and from `_redirects`/`_headers` files if present (ARCH section 10), and the SW applies it in shell mode (section 7.1). In drop-in mode the host's redirects, clean URLs, 404s and headers are untouched by design (3.4.1). The remaining gap is API-style requests (F5), not redirects. I did not verify the `_redirects` file format semantics against Netlify/Cloudflare (section 6).

**F10 (STAR) Comments and guestbooks fit the v0.2 ledger without new op types; each comment is about 0.8-1.3 KB on the wire, but the default policy blocks visitor writes.** *Confidence: high for the sizes (emulated from the spec with the project's own `canonicalize`, `sha256`, `sign`; `src/chain/block.js` was not yet written, so real blocks may differ by a few bytes).*
- Default policy (ARCH v0.2 section 6.1): `writers: 'owner'`, `bits: 16`, `maxValueBytes: 2048`, `maxChainBytes: 8 MiB`; `maxBlockBytes` is 4,096 (canonical `e` plus canonical `v`). Visitor posts need `publish.mjs --policy open` (the example guestbook does this); `--policy allow --allow <pub>` for invited writers; up to 50 moderators may `tombstone` and `ban`.
- Shape: the op carries `vh = sha256(canonical(v))` and the value `v` sits beside `e`. Sizes: 200-character comment `append` to list `comments`: **798 B** wire JSON with one head in `prev`, **1,267 B** with eight (623 / 1,092 B counted toward `maxBlockBytes`); 1,000-character reply 1,660 / 2,129 B; `profile` rename 551 / 1,020 B. The author key (87 characters), signature (86), hash (64), `vh` (64) and each `prev` entry (64) dominate; the text is the minority. Under the 2,048 B value cap a comment object `{text, parent, name}` leaves roughly 1.9 KB for text.
- For comparison, the v0.1 block shape (value inside the hash) gave 701 / 1,170 B for the same comment (`results-2026-10-17.txt`).
- Sources: `labs/w2a-03-experiments/blocksize_v02.mjs` and `results-2026-10-17.txt`; ARCH v0.2 sections 6.1, 6.2, 10, 11.

**F11 (STAR) PoW is a speed bump, not the spam answer; the missing pieces are an approval queue and local filtering.** *Confidence: high.*
- Doc 06 F39-F41: at 16 bits a mid-range phone pays about 0.14-1.6 s but one RTX 4090 can still mint about 3.3x10^5 messages/s; Sybil resistance cannot come from PoW (Douceur 2002; Laurie & Clayton 2004, pre-2024). Nostr's NIP-13 commits the target difficulty in the nonce tag so that lucky low-difficulty spam is rejected (ARCH already inherits the idea).
- ZeroNet's conservancy fork still says "No reliable spam protection" (F9). Hosted comment systems solve this with accounts (Giscus: GitHub login) or with moderation queues (Staticman: "optionally through a moderation pull request").
- Gap in v0.2: `writers` is `owner|allow|open`, and the owner (and up to 50 moderators) can `ban` an author or `tombstone` a block after the fact, but nothing makes a post invisible until it is approved; the `allow` list is per author and is set offline (`allow` ops exist only in `tools/`). Add a per-post approval mode (R9). v0.2 already sets PoW at 16 bits with the target committed in `e.bits`, exempts owner and moderator blocks, and applies an ingress throttle of 30 per 10 minutes per author that is never part of validity.
- Sources: doc 06 F39-F41; [NIP-13](https://raw.githubusercontent.com/nostr-protocol/nips/master/13.md); F7/F9 above.

**F12 Migrating existing comments is an import problem, not a protocol problem: ship them as static data and render new chain comments after them.** *Confidence: medium (design reasoning; only the WordPress export format was checked, via w2a-02).* Existing systems export to files (Disqus XML, WordPress WXR, Staticman YAML/JSON files already in the repository, Giscus discussions via the GitHub API); I did not verify those formats. The owner should not re-sign historical comments as if their authors wrote them (that misattributes authorship); render a read-only `legacy-comments.json` in page order and mark chain comments as live. The static host copy can serve the legacy HTML for crawlers. w2a-02 F11 adds two verified points: the WordPress WXR export carries `comment_author_email` and `comment_author_IP` for every comment (an importer must drop both before anything enters a public torrent), and Staticman's last release is v1.7.1 (2020-12-23) while Remark42 is a server (1.18.0, 2026-10-11).

**F13 Posting and reading need at least one reachable peer or the owner's always-on node; otherwise comments exist only on the author's device.** *Confidence: high (restates doc 06 with this feature in mind).* Doc 06 section 3.1.5/3.1.10 and action 8: availability needs an owner "seedbox" (same protocol, Node) or overlapping visitors; iOS suspends WebRTC in the background (doc 06 F23, medium-low), so a phone can only exchange blocks while its tab is foreground. A guestbook on a low-traffic site is therefore eventually consistent with long gaps; the UI must show "pending, not yet shared" for local-only blocks.

**F14 Deleting a comment removes it from honest nodes' views, not from the network.** *Confidence: high.* ARCH v0.2 section 6.1/6.7: `tombstone` drops the value `v` and keeps `{e, h, s}` so the DAG stays connected, honest nodes purge it and do not re-serve it; doc 06 3.1.5: "Moderation hides; it cannot erase bytes from other peers' disks". A malicious or old node keeps the body, so promises such as "delete my comment" must be worded as "hide", and personal data in comments or profile names is handled under F25. The op also keeps `vh = sha256(canonical(v))`: EDPB para 52 says unsalted hashes are not sufficient and a hash of personal data is itself personal data, so for low-entropy values (a short name) `vh` is a dictionary-check target; w2c-02 recommends salting `vh`.

### 3.3 Reactions, likes and counters

**F15 A reaction is a last-writer-wins register per (author, target, kind); the count is the number of authors whose latest value is set - not a sum of increments.** *Confidence: high.* This is doc 06 section 3.1.4 (`react`) and what NIP-25 does. The CRDT alternative (G-Counter: one slot per replica, merge = element-wise max, value = sum; PN-Counter = two G-Counters) was formalised by Shapiro, Preguica, Baquero and Zawirski in 2011 (pre-2024). A per-author G-Counter lets one identity add unbounded increments and is unauditable; the set semantics bound one identity to one unit per target and make un-liking a simple overwrite. Sources: doc 06 3.1.4; [NIP-25](https://raw.githubusercontent.com/nostr-protocol/nips/master/25.md); [Wikipedia: CRDT](https://en.wikipedia.org/wiki/Conflict-free_replicated_data_type) (the HAL record was blocked by a bot challenge).

**F16 (STAR) Counts cost one signed block per vote; the cost is dominated by overhead, not payload, scales linearly, and meets the ledger budget first.** *Confidence: high for the arithmetic and desktop timings (emulated block shape, one M3); phones unmeasured.*
- Under the ARCH v0.2 block shape a like as `put k='like/ab12cd34/9f3e7a1c' v=1` is **570 B** on the wire with one head in `prev` and **1,039 B** with eight (395 / 864 B counted toward `maxBlockBytes`); an emoji reaction 584 / 1,053 B. So 1,000 likes = 0.57-1.04 MB and **10,000 likes = 5.7-10.4 MB**.
- Budget: the default `maxChainBytes` is **8 MiB**, which holds about **8,073 (eight heads) to 14,716 (one head) likes** or about 9,700 two-head 200-character comments if every block counts its wire size (the exact accounting is in the code, not the spec); the ceiling is 64 MiB, about 64,600-117,700 likes. Beyond the cap "only owner, moderator and allow-listed blocks are ingested" and writers get `E_CAP` (ARCH 6.3, 9). A like-heavy site therefore needs a raised cap, compaction of superseded last-writer-wins puts, or owner checkpoints/snapshots (`cs=`, see w2c-02) - or it should not count likes on the chain at all.
- Verification: `crypto.subtle.verify` ECDSA P-256 in Node 24: 6,500-10,800 verifies/s sequentially and 59,000-66,000/s with 3,000 in flight (two runs); full per-block ingest check (canonicalize + SHA-256 + `verify()` from `src/chain/crypto.js`) 5,951 and 11,974 blocks/s in the two runs, i.e. **100,000 blocks = 8.4-16.8 s** single-threaded on an M3. Doc 06 F47 already marks verification as the scaling limit; browsers and phones will be slower (not measured). ARCH 6.5 requires the reduce step to stay under 50 ms for 5,000 blocks.
- Implication: counts must come from a reducer-maintained index (not by scanning `kv` for a prefix), the UI must not recount on every block, and the budget must be visible to the owner.
- Sources: `labs/w2a-03-experiments/blocksize_v02.mjs`, `blocksize.mjs`, `results-2026-10-17.txt`; ARCH v0.2 sections 6.1, 6.3, 6.5, 9; doc 06 F47; w2c-02.

**F17 (STAR) Totals are Sybil-inflatable and should say "devices"; a trusted number needs the owner to sign it.** *Confidence: high.* Doc 06 F40 and 3.1.4/3.1.10: identities are free keypairs; unique-visitor counts and one-person-one-vote are out of scope. Add the owner `checkpoint{stats}` already proposed there, and show both "local verified count" and "owner-attested count". Do not use the chain for page-view counters (F36).

### 3.5 Sealed contact inbox and the data-protection limit

**F23 An inbox sealed to the owner's key is straightforward and small: about 1.2 KB per short message, and only 1,437 B of plaintext fit under the default 2,048 B value cap.** *Confidence: high for sizes (emulated block shape), medium for library suitability (READMEs only).*
- Emulated under ARCH v0.2 (`append` to list `inbox`, value `{"c": b64url(ephemeral P-256 point | IV | AES-GCM ciphertext+tag)}`, ephemeral ECDH P-256 + HKDF-SHA256 + AES-256-GCM, an HPKE-like base-mode shape): 300 B plaintext = **1,154 B** wire block; 1,000 B = 2,088 B; maximum plaintext **1,437 B** when `canonical(v)` must be <= 2,048 B and **2,151 B** if the owner raises the value cap to 3,000 B (`maxBlockBytes` is 4,096). w2a-02 F12 estimated 1,425 B independently. (The v0.1 shape allowed 6,045 B.) A longer message needs splitting across blocks or a higher per-ledger `maxValueBytes`.
- Maintained building blocks: `hpke-js` 1.8.0 (2026-03-08, MIT, about 284k weekly downloads): RFC 9180 on WebCrypto, DHKEM P-256/P-384/P-521 and X25519, AES-GCM in `@hpke/core` with zero dependencies; README: "has not been formally audited", tested against RFC 9180 and Wycheproof vectors. `age-encryption` (typage) 0.3.1 (2026-08-28, BSD-3, about 212k weekly): X25519 and passphrase recipients, **passkey recipients via WebAuthn PRF**, a `generateHybridIdentity` helper (the README does not name the algorithm), depends only on noble libraries; audit status not stated.
- Nostr's private DMs (NIP-17 over NIP-44 + NIP-59 gift wrap) show the metadata-hiding variant: unsigned inner "rumor", signed "seal", outer wrapper with an ephemeral key and randomised timestamps (up to 2 days back).
- Sources: `blocksize_v02.mjs`; [hpke-js](https://github.com/dajiaji/hpke-js); [typage](https://github.com/FiloSottile/typage); [NIP-17](https://raw.githubusercontent.com/nostr-protocol/nips/master/17.md), [NIP-59](https://raw.githubusercontent.com/nostr-protocol/nips/master/59.md); npm registry; ARCH v0.2 section 6.1; w2a-02 F12.

**F24 A static recipient key means no forward secrecy and a single point of failure, and the ciphertext is public and permanent.** *Confidence: high.* NIP-44's own limitations list: "No forward secrecy: when a key is compromised, it is possible to decrypt all previous conversations", "No deniability", and "For high-risk situations, users should chat in specialized E2EE messaging software". For us the sender's block `author` key is also visible on every message unless the sender uses a fresh throw-away key (then spam control rests on PoW only). A rotating, owner-signed "inbox key" record with an expiry reduces exposure but cannot rewind past messages. Source: [NIP-44](https://raw.githubusercontent.com/nostr-protocol/nips/master/44.md) (read 2026-10-17); doc 06 3.1.10 ("no confidentiality (public by default)").

**F25 (STAR) Treat anything personal on the log as permanent, even encrypted; the EDPB's final blockchain guidelines apply by analogy and say so in plain terms.** *Confidence: high for the quoted text; the legal applicability to a no-consensus browser log is unverified and this is not legal advice.*
- EDPB Guidelines 02/2025 on processing of personal data through blockchain technologies, **v2.0 adopted 7 July 2026** (v1.1 8 April 2025). Para 45: "Blockchain is only a technology, as cloud computing or peer-to-peer networks." Para 48: "In general, it is not advisable to store personal data on the blockchain, and it should not be stored in the content of transactions." Para 49: public blockchains "should only be employed if public access to the blockchain is necessary". Para 50: such data "will, in most cases, stay on the blockchain with no practical possibility of deletion or modification ... technical impossibility cannot be invoked to justify non-compliance". Para 51: "encrypted personal data is still personal data and encryption does not remove the need for GDPR compliance ... even state-of-the-art encryption perfectly implemented will be overtaken by time if the blockchain is retained indefinitely". Paras 52-54: prefer a salted/keyed hash, commitment or pointer with the data off-chain; unsalted hashes are insufficient. Paras 43-44: in public permissionless chains nodes "may" be controllers or joint controllers when they exercise decisive influence; the EDPB "strongly encourages" a legal entity among nodes. Para 63: erasure may require deleting "any copies held by nodes".
- What this means here: every visitor's browser relays and stores the log (a "node" in this sense); comment text with a real name, a `profile` display name, a sealed contact message and an IP-linked device key are all candidate personal data. We cannot offer erasure, and "encrypt it" is not a defence in the EDPB's reading.
- Therefore: contact and newsletter defaults go through relays (F18-F21), the sealed inbox is opt-in with a visible warning, `profile` names are documented as public and permanent, and a privacy notice template ships with the loader (R15).
- ARCH v0.2 already moves in this direction (value outside the hash, `tombstone` drops `v`, `ts` rounded to the minute, no analytics or third-party scripts in section 13), and w2c-02 concludes the same: keep personal data and free text out of permanent fields, salt `vh`, and treat key lifetime as the retention policy. w2b-06 covers the operator side (DSA notices, takedown).
- Sources: [EDPB Guidelines 02/2025 v2.0 PDF](https://www.edpb.europa.eu/system/files/2026-07/edpb_guidelines_202502_blockchain_v2_en.pdf) (text extracted with `pdftotext`, paragraph numbers as printed); [EDPB news 2026-07-08](https://www.edpb.europa.eu/news/edpb-sheds-light-on-anonymisation-and-web-scraping-for-generative-ai-and-adopts-final-version_en); [Erbguth comparison v1.1 to v2.0](https://blockchain-gdpr.org/edpb-guidelines-v2-changes.html) (secondary).


### 3.6 Authentication and identity

**F26 (STAR) Passkeys are a stable standard and a usable optional layer in 2026, but PRF support is uneven enough that it must be an enhancement, never a requirement.** *Confidence: medium (spec and MDN data are primary; the support matrix is a vendor blog built on small community samples and conflicts with MDN on one point).*
- Standard: **WebAuthn Level 3 is a W3C Recommendation dated 2026-08-25** (the 2026-05-26 Candidate Recommendation Snapshot had "no substantive changes"). The `prf` extension is section 10.1.4; the client hashes each salt as `SHA-256("WebAuthn PRF" || 0x00 || input)` before it reaches CTAP2 `hmac-secret`.
- MDN browser-compat-data (`main`, fetched 2026-10-17) for `extensions.prf`: on `create()` Chrome 116, Edge 116 (mirror), Firefox 139, Firefox Android 149, Safari 18, WebView no; on `get()` Chrome 116, Firefox 139, **Safari and Firefox Android listed as not supported**. MDN's prose notes that fewer authenticators can generate PRF outputs during credential creation than during assertion, so evaluate on `get()` if `create()` returns no result.
- Corbado (published 2025-04-16, modified 2026-09-29, August 2026 snapshot): Windows Hello returns PRF values only after the **February 2026 cumulative update (KB5077181; Windows 11 24H2 build 26100.7840+ / 25H2 build 26200.7840+)** (Microsoft has not documented the change), Windows 10 never; Chrome 147 added PRF-on-create on Windows (146 and below return PRF on `get()` only); Firefox 148+ with Windows Hello (147 backport for create); Apple Passwords/iCloud Keychain on macOS 15+ works in Safari 18+, Chrome 132+ and Firefox 139; Google Password Manager includes PRF on Android; the Chrome profile authenticator has none. Credential managers (create/get): **works** Apple Passwords, Google Password Manager, 1Password, Proton Pass, Keeper, Enpass; **partial** Bitwarden (platform split), Samsung Pass (get only), KeePassXC (no released version); **fails** Microsoft Password Manager (every `get()` with PRF throws `NotAllowedError`), Dashlane, NordPass (`prf.enabled: false`). Security-key PRF in Safari arrived in 26.4 (March 2026) with two open WebKit bugs (311099, 314934). Corbado also says capability flags are unreliable and recommends "PRF as an enhancement, not a hard dependency".
- Conflict to resolve: BCD says Safari `get()` has no PRF; Corbado reports Apple Passwords PRF on create and get "100%" in its demo data. Treat as unresolved until tested on real devices (R17).
- caniuse (data of about 2026-10-13): WebAuthn 94.45% global support, passkeys 95.08%; Firefox is "partial" (no TouchID); there is no caniuse feature for PRF.
- Sources: [W3C WebAuthn L3](https://www.w3.org/TR/webauthn-3/) (2026-08-25); [MDN WebAuthn extensions](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API/WebAuthn_extensions); [MDN BCD CredentialsContainer.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/CredentialsContainer.json); [Corbado PRF](https://www.corbado.com/blog/passkeys-prf-webauthn) (2025-04-16, upd. 2026-09-29); [Corbado L3 credential managers](https://www.corbado.com/blog/webauthn-l3-credential-manager-support) (2026-09-08, upd. 2026-10-03); [Yubico PRF guide](https://developers.yubico.com/WebAuthn/Concepts/PRF_Extension/Developers_Guide_to_PRF.html) (table "as of mid-2025", partly outdated: it says Windows Hello lacks hmac-secret).

**F27 (STAR) A passkey-derived signing identity works inside the exact iframe architecture and has a direct precedent in an append-only-log database.** *Confidence: medium-high for feasibility (measured, virtual authenticator); low for "same key on every real device" (not tested).*
- Measured (Chromium 156.0.8078.4, CDP virtual CTAP2.1 authenticator with `hasPrf: true`, page on `http://localhost`): in **both** a top-level page and the SW-served `sandbox="allow-scripts allow-same-origin ..."` iframe: `create()` with `extensions.prf = {}` gave `prf.enabled = true`; `get()` with `prf.eval.first = SHA-256("mw/site/"+id)` gave a **32-byte** result, **identical on repeated calls**, and **different for a different site id**; HKDF-SHA256 (info `mw/identity/v1/ed25519`) -> 32-byte seed -> PKCS#8 import as `Ed25519` -> sign/verify OK, and re-derivation gave the **same public key**. `getClientCapabilities()` reported `extension:prf: true`, `relatedOrigins: true`, `hybridTransport: true`.
- Precedent: Le-Space/orbitdb-identity-provider-webauthn-did PR #51 (merged 2026-09-10): "derive an Ed25519 signing key from the passkey", HKDF-SHA256 over the PRF output with the key type in the info string, claim "one passkey still yields one identity document on every device" - tested with a PRF-capable **mock** authenticator only. typage (age) offers passkey recipients through the same extension.
- Derivation notes: per-site salt gives unlinkable per-site identities in hub mode (one credential, many keys); Ed25519 is importable from a PKCS#8 wrapper in WebCrypto (Chromium 156 here; doc 06 F45 gives the browser floors and F46 notes Safari's randomised signatures), whereas the v0.1 P-256 identity cannot be rebuilt from a raw 32-byte seed with WebCrypto alone because the public point is not derivable (inference; `@noble/curves` 2.4.0 would be needed). Doc 06 already recommends algorithm-tagged author keys, which is the clean way to add this. w2c-03's lab adds that importing a PKCS#8 key without its public key works in Chromium but throws in WebKit, whereas seed -> HKDF -> P-256 scalar -> JWK import (public point supplied) worked in both, so a PKCS#8-only derivation path needs a WebKit fallback.
- Not covered: Firefox/WebKit WebAuthn (no virtual authenticators in the Playwright builds), real authenticators, hybrid (QR) PRF, cross-device PRF stability for synced passkeys.
- Sources: `labs/w2a-03-experiments/prf-exp/*`, `results-2026-10-17.txt`; [OrbitDB PR #51](https://github.com/Le-Space/orbitdb-identity-provider-webauthn-did/pull/51); [typage](https://github.com/FiloSottile/typage); W3C spec text (salt hashing).

**F28 (STAR) PRF-derived keys are only as durable as the passkey; the standards community's warning applies, and the mitigation is a layered identity.** *Confidence: high for the warning's existence, medium for the mitigation design.*
- WebAuthn co-editor Tim Cappalli (as reported in a secondary article, 2026-02-28, updated 2026-08-05; the original statement was not found): using the same credential for sign-in and encryption makes "the 'blast radius' for losing that credential ... immeasurably larger"; "Encryption keys are not replaceable; once they are lost, the data is gone forever." Yubico: a recovery strategy is "non-negotiable"; use envelope encryption with several registered credentials. Corbado: if the passkey is lost the derived key and the data it encrypted are lost.
- For a **signing** identity the loss is smaller (you lose the ability to author as that identity, not the content), but it is still an identity reset on a log with no password reset.
- Contrast with the device key: it is lost on browser data clearing and, on Safari, after 7 days of Safari use without interaction (doc 06 F25: storage persistence is "all-or-nothing"); ARCH v0.2 section 6.1 mitigates with a passphrase-wrapped identity export/import. A PRF-derived key survives both without a backup file. The safe design is layered and matches w2c-03's recommendation: the identity is a random seed; a passkey optionally **wraps the seed** (PRF -> HKDF -> AES-GCM key-encryption key, one wrapped copy per registered credential, as the Yubico guide and Cappalli advise); the recovery phrase/export stays the master backup; a signed `link` op from the old device key carries continuity. Deriving the identity directly from one PRF output (as the OrbitDB provider does) is acceptable only for throw-away per-site identities.
- Sources: [lilting.ch summary](https://lilting.ch/en/articles/passkeys-prf-extension-encryption-risk) (secondary); Yubico guide; Corbado; doc 06 F25, F53.

**F29 A WebAuthn assertion can be the block signature itself; it adds about 180 bytes and gives a prompt the page cannot fake, but it does not show the user what is being signed.** *Confidence: high for feasibility and sizes (measured), medium for design value.*
- WebAuthn L3 section 7.2: the relying party verifies "that sig is a valid signature over the binary concatenation of authData and hash" where hash is SHA-256 of `clientDataJSON`; the challenge sits inside `clientDataJSON`, so setting the challenge to the block hash binds the assertion to the block. Measured: with the challenge = SHA-256 of a block entry, verification in plain WebCrypto (SPKI from `getPublicKey()`, DER signature converted to 64-byte r||s) returned `true`, `clientData.challenge` matched, `authenticatorData` was 37 B, `clientDataJSON` 135 B (origin `http://localhost:<port>`; about 132 B for `https://example.com`), DER signature 70-72 B: **+178 to +180 raw bytes (about +240 base64url characters) per block** versus a 64-byte raw signature. A 473-942 B like becomes about 710-1,180 B.
- Precedent for treating a WebAuthn P-256 assertion as a signature scheme: Ethereum's **EIP-7951** (secp256r1 precompile, status **Final**, created 2025-05-27) says the precompile "enables native support for signatures generated by modern secure hardware including Apple Secure Enclave, Android Keystore, and FIDO2/WebAuthn devices"; passkey smart wallets verify exactly `authenticatorData || SHA-256(clientDataJSON)` (search summaries; not read in depth).
- Limits: the prompt shows the site, not the content (WebAuthn has no what-you-see-is-what-you-sign), so malicious site script can ask for a signature on a hash while the user thinks they are logging in; `signCount` is only "a signal, but not proof, that the authenticator may be cloned" (spec) and must not feed ordering; a prompt per action is poor UX for comments but reasonable for **owner moderation ops and pointer signing**.
- Sources: [W3C WebAuthn L3 section 7.2](https://www.w3.org/TR/webauthn-3/); [EIP-7951](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-7951.md) (read 2026-10-17); `prf-exp` results.

**F30 (STAR) Because site code is same-origin with the loader, only a per-use user-verification gate gives real protection; a key held in the loader's memory does not.** *Confidence: high for the web-platform reasoning (same-origin frames can reach each other's DOM and globals); the table is my synthesis.*
- Same-origin frames can use `window.parent` directly, patch shared built-ins in the parent realm and intercept the bridge; MDN states a same-origin parent "can still access the iframe's DOM", and the reverse is the platform default. So the SDK bridge (ARCH section 9) is a convention, not a barrier, for hostile site code.

| Key / signer | Silently usable by site script? | Survives storage clearing / Safari 7-day eviction? | Same identity on another device? | User verification per use? |
|---|---|---|---|---|
| Visitor identity (ARCH v0.2): non-extractable P-256 CryptoKey in the `keys` store (JWK fallback after an iOS `DataCloneError`) | **Yes** (read the store, call `sign`; in drop-in the engine is in the same realm) | No (export/import exists) | Only by export/import | No |
| Imported moderator key (Settings; powers `tombstone`, `ban`, `_` keys) | **Yes** | No | Only by import | No |
| Owner key (ARCH v0.2: never in a browser; `tools/` only) | No (not present) | n/a | n/a | n/a |
| PRF-derived identity held in page memory | **Yes in practice** after one approval (script can read memory or ask for PRF itself; the prompt is not content-aware) | **Yes** (re-derive) | Yes if the passkey syncs (untested) | Once per derivation |
| PRF-wrapped seed (envelope) | Yes in practice once unwrapped for the session | **Yes** (wrapped copy plus recovery phrase) | Yes if the passkey syncs | Once per unwrap |
| WebAuthn assertion per block | **No** (prompt per signature; but see F29) | Yes | Yes if the passkey syncs | **Every signature** |

- Consequence: ARCH v0.2 already puts the highest-value key (owner) outside the browser. The next-highest is the moderator key: it can ban any author and hide any block. Treat it as a hot key - keep it out of the shared origin (separate origin or tool), or require a WebAuthn assertion for moderator ops (R2, R13). The real fix for everything else remains a separate origin per site or trust level (doc 04 R1, doc 06 3.1.9) rather than trying to harden the shared one.

**F31 "Sign in with Nostr" is cheap to offer as a linked identity; making a Nostr key the chain identity needs a second signature scheme.** *Confidence: medium.*
- NIP-07 (`draft optional`): `window.nostr.getPublicKey()` and `signEvent(event)` are mandatory, NIP-44 `encrypt`/`decrypt` optional; NIP-46 adds remote signers ("bunkers"); **NIP-26 (delegated event signing) is marked `unrecommended`: "adds unnecessary burden for little gain"**. Nostr signs with secp256k1/Schnorr, which WebCrypto lacks, so a verifier needs `@noble/curves` (2.4.0, 2026-08-27, 33.4M weekly downloads) or `nostr-tools` 2.25.2 (2026-09-04, Unlicense, 636k weekly).
- Unknown: whether extensions inject `window.nostr` into a SW-served, sandbox-attributed same-origin iframe (it depends on each extension's frame matching); in shell mode the loader's top frame is the safer place to call NIP-07, with a bridge method exposing only the resulting public key and a proof; in drop-in mode the page is shared with site code, so there is no safer place.
- A natural proof format is NIP-98's `kind 27235` event with `u` (absolute URL) and `method` tags, reused as "I control this npub for this site" (my proposal; not an existing convention for this use).
- Sources: [NIP-07](https://raw.githubusercontent.com/nostr-protocol/nips/master/07.md), [NIP-26](https://raw.githubusercontent.com/nostr-protocol/nips/master/26.md), [NIP-46](https://raw.githubusercontent.com/nostr-protocol/nips/master/46.md), [NIP-98](https://raw.githubusercontent.com/nostr-protocol/nips/master/98.md) (master, read 2026-10-17); npm registry.

**F32 Sign-In with Ethereum is a Final standard whose message and signature can be verified offline for ordinary accounts, but its session and nonce security assumes a relying party that we do not have.** *Confidence: medium.*
- ERC-4361: status **Final**; message fields `domain`, `address`, `statement`, `URI`, `Version`, `Chain ID`, `Nonce`, `Issued At`, optional `Expiration Time`, `Resources`; `nonce` is "typically chosen by the relying party" (at least 8 alphanumerics) and "MAY" be derived from a recent block hash or timestamp; the spec prefers generating the message wholly client-side when privacy matters. Contract wallets are verified through ERC-1271, whose results "can return different results for the same inputs depending on blockchain state" (not a pure function, needs an RPC). ERC-5573 (ReCaps, capability delegation over SIWE) is still **Draft**.
- Search result summaries found server-side verification guidance everywhere (Coinbase, better-auth, kavachos) and none for client-only verification; `siwe` 3.0.0 last published 2025-01-21 (about 205k weekly downloads), `viem` 2.57.7 (2026-10-14, 6.7M weekly).
- Use here: treat a SIWE signature as a **link statement** whose `URI` or `Resources` entry carries the device public key and whose `domain` is the site; verify only externally owned accounts offline in v1; do not grant moderator rights from a linked wallet; no contract-wallet support until an RPC policy exists.
- Sources: [ERC-4361](https://github.com/ethereum/ercs/blob/master/ERCS/erc-4361.md), [ERC-5573](https://github.com/ethereum/ercs/blob/master/ERCS/erc-5573.md), [ERC-1271](https://github.com/ethereum/ercs/blob/master/ERCS/erc-1271.md) (read 2026-10-17); npm registry; search summaries (low).

**F33 Delegation certificates have weak adoption evidence; start with a minimal, display-only `link` op.** *Confidence: medium.* NIP-26 is unrecommended (F31), ERC-5573 is Draft (F32), and WebAuthn Related Origin Requests are capped at five labels and meant for cases where federation is not possible (passkeys.dev). I did not verify other delegation designs (for example Matrix cross-signing) in this session. A minimal `link` op `{scheme, subject, proof}` verified at ingest, shown in the UI as a badge, carries no authority and is easy to remove; anything that grants rights should wait for evidence.

**F35 Pagefind runs unchanged under the `/_mw/s/<btih>/` prefix inside the SW-served iframe; because the whole torrent is already local, its chunking saves memory, not network.** *Confidence: high for this build (measured), medium for other browsers (not tested).*

### 3.8 Analytics

**F36 Peer-served visits never reach the host, so host logs undercount; the only free signal is tracker scrape (current seeders and leechers, not visitors), and the loader already receives it.** *Confidence: high for the mechanism, medium for the public-tracker coverage.*
- ARCH v0.2: after the first view, subresources (and in shell mode even the pages) come from IndexedDB and peers, so the host sees only part of the traffic. `bittorrent-tracker` 11.2.3 (read in `node_modules`) answers a WebSocket `scrape` with `{complete, incomplete, downloaded}` per infohash, and the code sets `downloaded` equal to `complete` with the comment "this only provides a lower-bound": you get current seeders and leechers, never a cumulative count. ARCH v0.2 section 8 already sends a `scrape` every 90 s to keep tracker sockets alive, so the loader receives these numbers anyway and could surface them (for example `mw.net.swarm()` and a `tools/stats.mjs`) at no extra cost.
- Coverage: doc 02 probed scrape OK on `tracker.webtorrent.dev`, `open.ftorrent.com` and `tracker.novage.com.ua`, and a closed socket with no reply on `tracker.openwebtorrent.com`; w2b-04 reports the same.

**F37 (STAR) There is no browser-native private-measurement API to build on, and the standard aggregation protocol needs servers and is still a draft.** *Confidence: high.*
- Google announced on **2025-10-17** that it will retire Attribution Reporting, IP Protection, On-Device Personalization, **Private Aggregation (including Shared Storage)**, Protected Audience, Protected App Signals, Related Website Sets, SelectURL, SDK Runtime and **Topics**; CHIPS, FedCM and Private State Tokens stay.
- IETF **draft-ietf-ppm-dap-19** ("Distributed Aggregation Protocol for Privacy Preserving Measurement", updated 2026-07-06, expires 2027-01-07; working-group state "WG Consensus: Waiting for Write-Up"; **no RFC number**; authors from ISRG and Cloudflare plus Rescorla). RAPPOR (Erlingsson, Pihur, Korolova, ACM CCS 2014, pre-2024): randomized response for client-side statistics. So "owner + one helper aggregator" is a server product, not an option for a no-backend site.
- Sources: [Privacy Sandbox update](https://privacysandbox.google.com/blog/update-on-plans-for-privacy-sandbox-technologies) (2025-10-17); [IETF datatracker draft-ietf-ppm-dap](https://datatracker.ietf.org/doc/draft-ietf-ppm-dap/); [Prio, USENIX NSDI '17](https://www.usenix.org/conference/nsdi17/technical-sessions/presentation/corrigan-gibbs); [RAPPOR arXiv:1407.6981](https://arxiv.org/abs/1407.6981).

**F38 Local differential privacy through the chain needs no backend but needs tens of thousands of visitors for useful accuracy, and the log leaks more than the noise hides.** *Confidence: high for the arithmetic (my computation, standard estimator), medium for applicability.*
- Binary randomized response: each visitor tells the truth with probability p = e^eps / (e^eps + 1); estimator = (r - (1 - p)) / (2p - 1) with variance r(1 - r) / (n (2p - 1)^2). For a true rate of 10%, the 95% interval half-width in percentage points is:

| epsilon | p(truth) | n = 100 | 1,000 | 10,000 | 100,000 | 1,000,000 |
|---|---|---|---|---|---|---|
| 0.5 | 0.622 | 39.2 | 12.4 | 3.9 | 1.2 | 0.39 |
| 1.0 | 0.731 | 19.7 | 6.2 | 2.0 | 0.62 | 0.20 |
| 1.1 (ln 3) | 0.750 | 18.0 | 5.7 | 1.8 | 0.57 | 0.18 |
| 2.0 | 0.881 | 10.2 | 3.2 | 1.0 | 0.32 | 0.10 |
| 4.0 | 0.982 | 6.5 | 2.1 | 0.65 | 0.20 | 0.06 |

- Visitors needed for +/-1 percentage point at 95% (rate 10%): **38,826 at eps 1.0, 32,269 at ln 3, 10,411 at eps 2, 4,188 at eps 4, versus 3,457 with no privacy** (about 11x penalty at eps 1).
- Chain-specific problems: each report is a signed block, so the author key is a persistent pseudonym unless an ephemeral key is used per report (then PoW is the only anti-stuffing control, doc 06 F39-F40); every report costs 0.5-1 KB for everyone; Sybils can poison the aggregate. Verdict: do not build; document why.
- Sources: `rr_table.py`, `results-2026-10-17.txt` (formulas in the script); doc 06 F39-F40.

**F39 Cookieless hosted analytics is the practical opt-in; their privacy claims are vendor statements, and consent law was not researched.** *Confidence: medium.*
- GoatCounter: no cookies, no localStorage; session mapping of site+IP+User-Agent to a random id "only stored in memory (for up to eight hours)"; no IP stored. Plausible: no cookies, `hash(daily_salt + domain + IP + UA)`, "The salt is rotated and deleted every 24 hours", stores individual event and session records, EU hosting. Cloudflare Web Analytics: "Privacy-first analytics ... without changing DNS or using Cloudflare proxy", available on all plans.
- magnet-web specifics: a beacon in the loader's top frame sees one page load per visit; in shell mode navigations inside the iframe only update the URL with `history.replaceState` (ARCH v0.2 section 7.2), so the loader must report them explicitly; in drop-in mode every page view is a real navigation and an ordinary beacon counts it. A beacon needs `connect-src` to the vendor in any CSP and breaks the ARCH promise "no third-party scripts", so keep it opt-in and off by default.
- Sources: [GoatCounter privacy](https://www.goatcounter.com/help/privacy); [Plausible data policy](https://plausible.io/data-policy); [Cloudflare Web Analytics](https://developers.cloudflare.com/web-analytics/) (all undated, read 2026-10-17).

**F42 The tier that needs no backend of ours is "hosted link": Stripe Payment Links and the Buy Button need no backend, and a Payment Link is a plain `<a href>` that works without JavaScript.** *Confidence: high (documentation read 2026-10-17).*

- Buy Button: `<script async src="https://js.stripe.com/v3/buy-button.js">` plus `<stripe-buy-button buy-button-id="..." publishable-key="...">`; optional `client-reference-id` (up to 200 characters, returned in the `checkout.session.completed` webhook), `customer-email`; CSP needs `frame-src` and `script-src` for `https://js.stripe.com`; "Rendering the buy button requires a website domain" (local testing via a local HTTP server on localhost). Passing an existing customer needs a server to mint a `CustomerSession`.
- Under the ARCH iframe flags a redirect to the hosted page works as a top-level navigation by user activation (F3). Success URLs must be "publicly accessible", which the shell's SPA-fallback deep links satisfy.
- Sources: [Stripe Payment Links](https://docs.stripe.com/payment-links); [Stripe Buy Button](https://docs.stripe.com/payment-links/buy-button) (both undated, read 2026-10-17).

**F43 (STAR) Anything that needs a secret key, an inventory check or a fulfilment trigger needs a server; do not promise it.** *Confidence: high.* Stripe's Checkout quickstart: "Add an endpoint on your server that creates a Checkout Session"; "Always keep sensitive information about your product inventory, such as price and availability, on your server to prevent customer manipulation from the client"; fulfilment is driven by an "event destination" (webhook) after payment succeeds. So dynamic pricing, discount logic, shipping calculation, stock counts, licence-key or download delivery and order emails are class S. A bring-your-own edge function can be wired in through the virtual-endpoint table (F5), but it is then "a backend of ours" in the user's account and must be described honestly. Source: [Stripe Checkout quickstart](https://docs.stripe.com/checkout/quickstart) (read 2026-10-17).

**F44 Snipcart works on a static front end only if its servers can crawl a public copy of each product page (or a JSON product endpoint) on the registered domain.** *Confidence: high for the mechanism, low for current pricing.* See F4. Pricing page: 2% per transaction, or a flat $20/month for merchants with under $1,000 monthly sales, forever-free test mode - but the page footer reads (c) 2023, so treat the figures as unverified for 2026. In drop-in mode the host copy satisfies the crawler; in a pure magnet-web deployment with no host copy it does not. Sources: [Snipcart order validation](https://docs.snipcart.com/v3/setup/order-validation); [Snipcart pricing](https://snipcart.com/pricing) (stale).

**F45 Crypto payments split into "hosted processor" (works) and "dynamic endpoint" (needs a service); none solves fulfilment.** *Confidence: medium.*
- BTCPay Server: free, open-source payment processor; self-hosted or a shared third-party instance; an embeddable tipping button plus an API for custom integrations. Lightning Address (LUD-16): wallets resolve `user@domain` with `GET https://domain/.well-known/lnurlp/<user>` and then follow LUD-06; a service must answer that request (a static JSON file pointing at a provider's callback is plausible but is my inference). x402: HTTP-402 payments with server-side middleware, "75.41M transactions and $24.24M in volume over the last 30 days" (page last updated 2026-08-25).
- Sources: [BTCPay Server](https://btcpayserver.org/); [LUD-16](https://github.com/lnurl/luds/blob/luds/16.md); [x402](https://www.x402.org/).

**F46 Payment flows put third-party scripts into the identity origin; compliance scope was not researched.** *Confidence: medium (F1) / low (compliance).* A Buy Button loads `js.stripe.com` into the page and frames; with `allow-same-origin` that script shares the origin with the visitor's chain identity and any owner key (F1, F30). Payment-page script-integrity rules (for example PCI DSS 4.0.1 requirements for scripts on payment pages) were not researched; Payment Links avoid the issue by leaving the site entirely.

### 3.11 Media streaming

**F47 (STAR) Media breaks the "download everything first" model, so large files need a lazy tier; the current spec lists streaming before completion as a non-goal.** *Confidence: high (project documents).* ARCH v0.2 section 2 non-goals: "streaming media before completion; sites above the size caps". ARCH section 8 caps: 128 MiB desktop, 48 MiB mobile Wi-Fi, 24 MiB cellular. A site with a handful of videos exceeds that, and migration of such a site is exactly the common case. Either media stays on the HTTP web seed/CDN, or the manifest marks files as lazy (not selected at start, fetched on first read). In drop-in mode `publish.mjs --dropin` builds a torrent of every non-HTML file (ARCH 3.4.1), so a site with large media would exceed `maxSiteBytes` (`E_TOO_LARGE`, section 5.4) and lose peer delivery altogether; it needs an exclude list so media stays host-served over HTTP (inference from 3.4.1 and 5.4).

**F48 WebTorrent 3.0.21 already provides what a lazy tier needs: range reads that re-prioritise pieces, and a Service Worker streaming pattern.** *Confidence: high (source read in `node_modules`).* `file.select(priority)` / `deselect()`; `file.stream({start,end})` returns a `ReadableStream`; `file[Symbol.asyncIterator]` selects the file's pieces at priority 1 and, for a missing piece, calls `torrent.critical(index, index + n)` with `n = min((1 MiB / pieceLength) | 0, 2)` (so one or two pieces at the cursor); `lib/server.js` honours `Range` (first range only; 206 with `Content-Range`, `Accept-Ranges: bytes`); `lib/worker-server.js` is the browser SW variant (message-channel pull). With ARCH's 256 KiB pieces a seek makes up to two pieces critical.

**F49 (STAR) The SW must answer `Range` requests with 206 slices; otherwise Chromium cannot seek, and WebKit's behaviour differs.** *Confidence: high for these builds (measured), medium for phones (untested).*
- Setup: 6 s 320x240 clips (H.264/AAC MP4 with faststart, 96,629 B; VP9/Opus WebM, 153,610 B), served by the SW inside the ARCH-flagged iframe, `<video>` seeked to 4 s.
- Chromium 156: SW honouring Range -> MP4 and WebM load and seek (`currentTime` 4, seekable [0,6]); SW returning 200 with the whole body and no `Accept-Ranges` -> plays from the start but **seek fails** (`currentTime` stays 0, seekable [0,0]); the first request carried `Range: bytes=0-`.
- WebKit 27.2 (Playwright build): MP4 with 206 -> the SW saw a `bytes=0-1` probe then `bytes=0-96628`, seek worked; MP4 with a plain 200 -> still loaded and seeked for this small file. WebM only reached HAVE_METADATA (codec limits of the build; inconclusive). **iPhone Safari was not tested**, so do not read the WebKit result as "206 is optional on iOS".
- Media element requests were seen by the SW in both engines. Workbox (Chrome developers) says media "must be told to respect Range request headers", that a runtime-cached 206 response will not populate the cache, and that media elements need `crossorigin` "even for same-origin URLs"; it does not mention Safari.
- Sources: `media-exp/*`, `results-2026-10-17.txt`; [Workbox: serving cached audio and video](https://developer.chrome.com/docs/workbox/serving-cached-audio-and-video) (undated); doc 04 R9 (video Range seeking was listed there as untested).

**F50 HLS is the practical streaming format, and 2026 browsers split three ways: native HLS, MSE via hls.js, or ManagedMediaSource.** *Confidence: high (caniuse data, hls.js README).*
- caniuse (data of about 2026-10-13): native HLS in Safari (macOS 6+, iOS 3.2+), Samsung Internet 4+, **Chrome 142+** (141 no, 142 yes), Chrome Android and Firefox Android in current versions, **not** Firefox desktop; Media Source Extensions: desktop Chrome 23+, Firefox 42+, Safari 8+, but **Safari on iOS is "partial" in every version through 27.2** ("Fully supported only in iPadOS"). hls.js 1.7.3 (2026-09-11, Apache-2.0, about 10.3M weekly downloads, 17.0k stars) "only compatible with browsers supporting MSE", uses Managed Media Source on Safari 17.1+ (since 1.5.0), and Safari plays HLS natively through a plain source URL. P2P Media Loader 4.0.0 (2026-08-19, Apache-2.0, about 2.2k weekly downloads) runs on hls.js or Shaka, needs "a compatible WebTorrent tracker", and lists iOS 17.1+.
- I could not read hls.js's custom-loader documentation (the README points to `docs/API.md`), so the exact hook for fetching segments from the torrent (loader configuration) is unverified.
- Sources: caniuse `data.json` (Fyrd/caniuse, read 2026-10-17); [hls.js](https://github.com/video-dev/hls.js); [P2P Media Loader](https://github.com/Novage/p2p-media-loader); npm registry.

**F51 (STAR) The largest P2P-video deployment that used WebTorrent in the browser abandoned it for HLS segments; build on that lesson.** *Confidence: high (changelog and issue read).* PeerTube v6.0.0: "Remove WebTorrent support in player ... We still use P2P with the HLS player"; its maintenance note says the player "doesn't use WebTorrent anymore (which was doing a large amount of small HTTP requests)"; v8.0.0: "Remove WebTorrent redundancy support ... Upgrade p2p-media-loader to v2". Issue #5465 (opened 2022-12-15, closed 2023-07-10): "many limitations of the library", WebTorrent "leads to a bigger bundle size for a bad user experience (slow start time, hacky resolution change etc.)", and "the P2P aspect of WebTorrent is not really used since most of new and popular videos are using HLS now". Sources: [PeerTube CHANGELOG](https://raw.githubusercontent.com/Chocobozzz/PeerTube/develop/CHANGELOG.md) (latest entry v8.3.1); [issue #5465](https://github.com/Chocobozzz/PeerTube/issues/5465).

**F52 Recommended media recipe for migrated sites.** *Confidence: medium (synthesis).* (1) Default: leave large media on the HTTP web seed or CDN (a `<video src>` over HTTP needs nothing from us) and let the torrent carry the "core" site. (2) Opt-in lazy tier: files flagged `lazy` in the manifest are excluded from the initial selection; the SW forwards Range requests to the loader page, which answers with `file.stream({start,end})` (F48), and the SW returns 206 (F49). (3) HLS: one playlist plus 2-6 s segments as separate lazy files, played with hls.js (native HLS where available), never by teaching the player to read raw torrent pieces. (4) Test on real iPhones before promising anything (R17).

### 3.12 Chat and live rooms

**F53 Trystero is the maintained library for rooms without a signalling server of your own and its BitTorrent strategy uses the same kind of trackers we already depend on - with caveats it states itself.** *Confidence: high.* Trystero 0.26.0 (npm 2026-10-04, MIT, about 21.4k weekly downloads, 44 KB unpacked, about 2.8k stars): strategies Nostr (default `trystero`), BitTorrent (`@trystero-p2p/torrent`), MQTT, Supabase, Firebase, IPFS, self-hosted WebSocket relay; `joinRoom({appId, password}, roomId)`; session descriptions are encrypted with a key derived from app and room id (a relay operator can reverse it; a `password` strengthens it); README: discovery "still relies on third-party relays", "MQTT, BitTorrent, and IPFS have far less relay redundancy than Nostr", TURN may be required, browsers support a limited number of WebRTC connections, default 256 MiB incoming budget per room. Doc 02 read the torrent strategy: it takes the first 3 of five default trackers (`open.ftorrent.com`, `tracker.webtorrent.dev`, `tracker.openwebtorrent.com`, ...). Sources: [Trystero](https://github.com/dmotz/trystero); npm registry; doc 02.

**F54 For chat inside a magnet-web site, a small wire extension next to `mw_chain` avoids a second signalling system; history, if wanted, is a chain list with a short retention.** *Confidence: medium (design synthesis).* Ephemeral room messages ride the existing swarm wires as `mw_room` frames (<= 15 KiB like the gossip frames of ARCH v0.2 section 6.6), signed with the device key but not stored, with presence/typing as unsigned hints; a room key kept in the URL fragment (which is not sent in HTTP requests) provides a capability-URL private room, with the tool-side limits of NIP-44-style encryption (F24). ARCH section 8 `maxConns` (30 / 10 / 6) bounds the mesh, so use gossip fan-out rather than full mesh; doc 06 F23: iOS suspends WebRTC when the tab is not foreground, so rooms are foreground-only on iPhones and must catch up on `visibilitychange`.

**F55 Do not add a general WebRTC library for chat.** *Confidence: medium.* `y-webrtc` 10.3.0 was last published 2023-12-28 (about 198k weekly downloads) and `simple-peer` 9.11.1 on 2022-02-17 (the maintained fork `@thaunknown/simple-peer` 10.1.2, 2026-07-25, is what WebTorrent 3.0.21 already depends on, per doc 02); `peerjs` 1.5.5 was published 2025-06-07 (its broker requirement was not verified here); `yjs` 13.6.33 (2026-09-23, about 10.3M weekly) is a document CRDT for the sites that want collaborative editing and could ride the same wires later. Source: npm registry (2026-10-17); doc 02.

### 3.13 Moderation tooling

**F56 The base moderation model exists (doc 06 section 3.1.5); three user-visible tools are missing.** *Confidence: high.* Doc 06 defines owner-signed `ban`, `hide`, `policy`, `fence` and `checkpoint` ops with precedence by the owner's sequence number, and local mute lists as a complement. ARCH v0.2 (sections 6.1-6.2) adds `moderators` (up to 50; `tombstone`, `ban`, `_`-prefixed keys), per-author `allow` lists and `ban`, with the errors `E_NOT_MODERATOR` and `E_BANNED` and `mw.mod.ban()` in the SDK. Missing: (a) **pre-moderation** - posts invisible until an owner `approve` op (a `moderated` writers mode), (b) **report** ops from visitors to the owner, (c) a **moderation console** page in owner mode (queue, approve/hide/ban, policy), plus (d) **local mute** lists per visitor.

**F57 Three independent ecosystems converged on "moderation data as signed, subscribable objects, enforced by the client" - the right shape for a no-server system.** *Confidence: high for the facts, medium for the fit.*
- Matrix (client-server spec v1.19): moderation policy lists are room state events `m.policy.rule.user|room|server`, rules carry a recommendation (only `m.ban`) and a reason, "the enforcement of this is deliberately left as an implementation detail", and subscribing means following the list room.
- AT Protocol (label spec v1, (c) 2026): labels are self-authenticating objects `{ver, src, uri, cid, val, neg, cts, exp, sig}` signed by the labeler's key; the client chooses which labelers to apply via the `atproto-accept-labelers` header; the spec does not define hide/warn behaviour ("generally communicated elsewhere"); negation retracts a label; `cts` timestamps "are not trustworthy or verified by default". Ozone is the MIT/Apache-2.0 labeling service and moderator UI (not archived; self-hostable with Docker).
- Nostr: NIP-32 labels (`kind:1985`, "distributed moderation"), NIP-56 reports (`kind 1984`, types nudity, malware, profanity, illegal, spam, impersonation, other), NIP-51 mute lists (`kind 10000`: pubkeys, hashtags, words, threads).
- Fit: a magnet-web owner (or a trusted third party) can publish signed label/mute lists as chain objects that other sites subscribe to by chain id; each visitor's loader decides how to act (hide, collapse, warn). Keep timestamps out of precedence (doc 06 principle).
- Sources: [Matrix spec v1.19 client-server API](https://spec.matrix.org/latest/client-server-api/) (section "Moderation policy lists", downloaded and read); [AT Protocol label spec](https://atproto.com/specs/label); [Ozone](https://github.com/bluesky-social/ozone); [NIP-32](https://raw.githubusercontent.com/nostr-protocol/nips/master/32.md), [NIP-56](https://raw.githubusercontent.com/nostr-protocol/nips/master/56.md), [NIP-51](https://raw.githubusercontent.com/nostr-protocol/nips/master/51.md).

**F58 Automatic toxicity classification cannot run in every visitor's browser; if used, it runs on the owner's node.** *Confidence: high for the sizes.* The smallest quantised ONNX export of `Xenova/toxic-bert` is `model_q4f16.onnx` at 97.2 MB (`model_int8.onnx` 110 MB, `model.onnx` 438 MB) against ARCH's 24-128 MiB whole-site caps. The status of Google's Perspective API could not be established (its documentation page failed to load for me), so I do not recommend depending on it. Source: [Hugging Face Xenova/toxic-bert onnx folder](https://huggingface.co/Xenova/toxic-bert/tree/main/onnx) (read 2026-10-17).

**F59 Moderation cannot remove bytes from other peers, and every visitor relays what others post; legal exposure of that is unresearched.** *Confidence: high for the technical half, low for the legal half.* Doc 06 3.1.5 and action 12 already say so; EDPB paras 43-44 (F25) show regulators asking who the controller is when many nodes hold data. Ship a report path, a documented hide/drop behaviour in honest nodes, an abuse contact in the pointer metadata, and take legal advice before inviting open posting on a public site.

### 3.14 What stays on a server

**F60 These server features have no honest client-only replacement; the migration guide should list them up front.** *Confidence: medium (reasoned from the architecture; each item is not individually sourced).*
- Sending email of any kind (transactional, notifications, newsletters, double opt-in confirmation).
- Payment secrets, webhooks, inventory, order fulfilment, licence/download delivery (F43).
- Secrets in general (API keys, OAuth client secrets): anything in the torrent or on the host is public.
- Private or per-user content, paywalls, authenticated downloads: the torrent is public to anyone with the infohash, and so is the host copy.
- Server-side rendering with personalization, IP-based rate limiting or geo-blocking, bot scoring by IP.
- Scheduled jobs and cron: only at build time or on the owner's machine (`tools/*.mjs`, CI); a client cannot publish at 09:00.
- Image/video transforms on demand: precompute at build time.
- Log-based analytics (F36).

## 5. Gotchas

1. **Bare-magnet hub labels reset identity on every release** (`base32(btih)` = new origin = new IndexedDB, RP ID and SW scope); labels from signed pointers derive from the ledger id and do not (F2, R1). Shared-origin hubs share one origin by design.
2. **Two sandbox tokens are load-bearing in shell mode**: `allow-popups` (for `target=_blank` links including mailto) and `allow-top-navigation-by-user-activation` (for payment redirects). The v0.2 set has no `allow-modals`; the shared-origin hub additionally drops `allow-downloads`. Drop-in mode has no frame (F3).
3. **`allow-scripts` + `allow-same-origin` is no sandbox**, and in drop-in mode there is no frame at all (`window.mw` is bound to the engine in the page); the SDK bridge is a convention, not a barrier, for hostile site code (F1, F30).
4. **PRF support claims conflict**: MDN BCD says Safari `get()` has no PRF; Corbado says Apple Passwords works. Capability flags are unreliable (Chrome reported `extension:prf` while some managers returned nothing); detect by trying `create()` then `get()` and fall back (F26).
5. **Windows Hello PRF exists only after the February 2026 cumulative update** (undocumented by Microsoft per Corbado) and Chrome 147+/Firefox 148+ for creation; Windows 10 never (F26).
6. **PRF salt is part of the identity.** Changing `mw/site/<id>` changes the derived key; fix the salt policy in the pointer and never derive it from the infohash (F27, R12).
7. **Ed25519 via PKCS#8 works only where WebCrypto has Ed25519** (doc 06 F45; Safari randomises signatures, F46). A P-256 identity cannot be re-derived from a seed with WebCrypto alone (inference); that is another reason to tag algorithms.
8. **Virtual-authenticator success is not real-world success**: one device, no sync, no hybrid transport, Chromium only (F27).
9. **Pagefind quirks**: the output includes every UI bundle (about 0.42 MB); chunk and fragment files are already compressed (HTTP compression adds nothing); file names embed hashes (for example `pagefind.<lang>_<hash>.pf_meta`) so they change every build; 200+ files for a 200-page site; cold first query was 90 ms (F34-F35). In drop-in mode, requests made inside Pagefind's Worker are probably served by the host rather than the torrent (inference, F35).
10. **Service Worker video**: answer `Range` with real 206 slices (Chromium cannot seek otherwise); WebKit sends a `bytes=0-1` probe first; runtime-caching 206 responses does not populate caches; set `crossorigin` on media elements if a cache layer is involved (F49).
11. **SW globals die after about 65-85 s idle** (doc 04 test B): never keep chat rooms, counters or route handlers in the SW (F5).
12. **Counts scan cost**: do not recount by scanning `kv`; keep a reducer index. Ingest speed was 6-12k blocks/s on a desktop M3 across two runs (a 2x spread from machine load); phones will be slower and are unmeasured (F16). The default ledger budget is 8 MiB (about 8,000-14,700 likes) and visitor writes need `--policy open`; past the cap writers get `E_CAP` (F10, F16).
13. **Encrypted is not anonymous and not erasable**: the sender's key is on the block unless throw-away keys are used; WebRTC peers see IP addresses; EDPB says encrypted personal data is personal data (F24-F25).
14. **Form relays**: Formspree free is 50 submissions/month with 30-day retention; FormSubmit puts the recipient address in page source; Web3Forms figures are from a snippet (pricing page returned 403); Mailchimp's browser path is an undocumented JSONP endpoint (F18, F21).
15. **Snipcart**: crawler = plain GET without cookies from their servers; it needs a public host copy; their pricing page is dated 2023 (F44).
16. **Stripe Buy Button** needs a real website domain (localhost is fine for tests) and `js.stripe.com` in `frame-src`/`script-src` if the site sets a CSP; the existing-customer flow needs a server (F42).
17. **Third-party scripts share the identity origin** (Stripe, CAPTCHAs, beacons); each one is a trust decision (F1, F46).
18. **Tracker scrape is not unique visitors**: it returns current seeders/leechers only, and `tracker.openwebtorrent.com` closed the socket on scrape in doc 02's probe (F36).
19. **Web Push on iPhone** requires a Home Screen web app and a user gesture; sending needs a sender holding subscriptions (F22).
20. **Playwright WebKit is not iPhone Safari**; the media result there (200 tolerated) must not be relied on (F49).
21. **Benchmarks varied by up to 2x between two runs** on the same machine because other work was running; quote ranges, not single numbers (F16).
22. **Search budget**: part of the research ran after the shared search budget was exhausted; unverified items are in section 6.
