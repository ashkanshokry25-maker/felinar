## 1. Summary

The current plan (ARCHITECTURE section 12) is a sound base: unit tests under `node --test`, a Chromium-only E2E with a local tracker, injected `now`, `storage` and `miner` seams. Production grade needs six additions, each backed by a measured result below.

1. **Web seed failure modes are the biggest untested risk.** With webtorrent 3.0.21, a host that ignores `Range` (200 with the whole file), answers 403, or truncates a 206 body leaves the download at 0 percent with **no warning at all**; a host that returns corrupted bytes triggers a **hot retry loop** (27,474 and 38,057 requests, 6.9 and 9.5 GiB served in 15 s on loopback in two runs, one "failed verification" warning per request, no ban). The "web seed is the availability floor" promise needs a hardened web-seed manager and a fault-injecting test server (F-D1, R-01).
2. **Hostile peers need a wire-level harness, and the wave-1 "4 GiB" description is imprecise.** `bittorrent-protocol` 5.0.9 reads the length prefix as a signed 32-bit integer, so `0xFFFFFFFF` is treated as a keep-alive and the real worst case is `0x7FFFFFFF` (2 GiB - 1). A peer that declares it and drips 16 KiB chunks costs about 11 s wall and 15-16 s CPU for 64 MiB (two runs) because every chunk re-concatenates the whole buffer. A test written with `0xFFFFFFFF` would pass vacuously (F-D3, R-02).
3. **Chromium 156 can impair WebRTC data channels from CI without root**, via CDP `Network.emulateNetworkConditionsByRule` with an empty `urlPattern`: latency, bandwidth, loss, reordering and queue length all measurably apply. But only to connections created while a rule is armed, not to WebSockets, and `offline` never cuts an established channel. Playwright's `context.setOffline(true)` does not drop peers either, so ARCHITECTURE section 12 E2E case (5) tests HTTP-offline rendering only and a separate peer-loss case is needed (F-C1 to F-C3, F-B9, R-03).
4. **Cross-engine P2P coverage cannot be assumed from Playwright.** WebKit 27.2 passes Service Worker, IndexedDB, WebCrypto and modern-API probes, but on this Mac it never established a data channel (zero ICE candidates by default); Firefox 157.0 would not start at all. An independent report (dallen4/deadrop#97) shows the same class of WebKit problem. No cloud vendor documents data channels between two remote sessions. Plan: engine-level coverage on Linux CI, P2P E2E on Chromium, hybrid local-plus-device smoke for iOS/Android, and a one-day spike to find out what the farms really allow (F-A1, F-B4, F-B5, R-04, R-10).
5. **Compatibility promises should be frozen as vectors now.** The project's `verify()` agrees with all 262 Wycheproof ECDSA P-256 P1363 vectors in Node, Chromium and WebKit, and its `canonicalize()` matches all six RFC 8785 reference files byte for byte; 11 fast-check properties over the existing parsers pass 30,000 runs each. Pin these (plus golden block, frame and pointer vectors) so a future refactor cannot silently break old data (F-E2, F-E5, R-06).

6. **The baseline suite is not yet a reliable gate on the pinned Node.** On Node v24.22.0 the planned command `node --test test/unit` fails ("Cannot find module .../test/unit"); run per file, four files pass (50 passed, 1 skipped, 0 failed in 0.2 s) but `test/unit/sw-sdk.test.mjs` has one test that never completes ("the SDK follows the port the host actually adopted": 30.5 s, then the runner does not exit, so a plain `node --test` run hangs). A green, hermetic, fast baseline on Node 22 and 24 comes before any new layer (F-J7, R-25).

Other headline numbers: 50,000 blocks (33.3 MB JSON) store in 0.84-1.0 s (Chromium) and 1.6-1.8 s (WebKit) and read back in 0.24 s and 0.17-0.20 s; WebCrypto SHA-256 runs about 494,000-529,000 per second in Chromium and 53,000-66,000 per second in WebKit on the same M3 (8-9x), so the default 14-bit hashcash averages 0.03 s versus 0.25-0.31 s (F-I1). `axe-core` 4.14.0 has 105 rules but only one WCAG 2.2 rule and none for status-message announcements, so the loader's live status line needs a manual screen-reader script (F-F1). `@lhci/cli` 0.15.1 still bundles Lighthouse 12.6.1 while Lighthouse is at 13.5.0, so run Lighthouse's Node API directly (F-G1). `performance.measureUserAgentSpecificMemory` needs COOP+COEP and a full (not headless-shell) Chromium, so soak tests should use CDP heap counters (F-H1).

What to build first (details in section 4): R-25 a green baseline, R-01 web-seed hardening plus fault server, R-02 wire adversary harness, R-03 impairment helpers and corrected E2E, R-06 golden vectors, R-05 model/simulation tests for the DAG and gossip, then R-04 the Linux cross-engine pipeline.

Compatibility promises to freeze with golden files and "old data still opens" tests (a mistake here silently orphans visitors' data): pointer record signing input (ARCH section 4), block canonical bytes, hash and signature (section 6.1), gossip frame layouts (6.5), IndexedDB schemas `mw-sites` and `mw-chain-<id>` (6.6, INTERFACES `cache.js`), the SDK message protocol (section 9), and the reserved `/_mw/` paths (section 3). Proposed production-readiness gates (to be calibrated, not measured values): every web-seed fault class surfaces a visible, specific error within 20 s and never exceeds a bounded request rate; an oversized wire frame destroys the peer within 1 s and RSS grows by less than 20 MiB; zero failures in the nightly 10^6-run property job and the 1,000-seed simulation; unit and component layers green on Chromium, Firefox and WebKit; P2P E2E green on Chromium and either green or explicitly exempted (with a manual checklist entry) on Firefox and WebKit; a 2 h soak shows heap after forced GC within 5 percent between minute 10 and minute 120, flat DOM node and listener counts, and bounded IndexedDB size; zero axe violations on every UI state plus a passed manual screen-reader script; shell JavaScript within the agreed gzip budget.

### C. Network impairment (Chrome DevTools Protocol)

**F-C1. In Chromium 156, `Network.emulateNetworkConditionsByRule` with an empty `urlPattern` shapes RTCDataChannel traffic.** Confidence: high (single machine, repeated). [SRC] Typings: `Network.emulateNetworkConditions` is "deprecated in favor of the emulateNetworkConditionsByRule and overrideNetworkState commands"; `NetworkConditions` = `{urlPattern, latency, downloadThroughput, uploadThroughput, connectionType?, packetLoss? (0-100, WebRTC), packetQueueLength? (WebRTC), packetReordering? (WebRTC), offline?}`; "If the pattern is empty, all requests are matched (including p2p connections)"; "Global conditions ... are also applied for throttling of p2p connections"; the call returns `ruleIds`. [DOC] Chrome 124 added packet loss, packet queue length and packet reordering to DevTools custom throttling profiles (crbug 41175925). ### D. Chaos and hostile peers

**F-D1. webtorrent 3.0.21's web-seed path fails silently on three fault classes and loops hot on a fourth.** `DESIGN-CRITICAL` (the architecture promises the web seed as the availability floor, ARCH section 0 and section 13). Confidence: high for the observed behaviour (Node build, same `lib/webconn.js` as the browser build, 3 MiB file = 12 pieces of 256 KiB, no peers or trackers, 15 s window); the explanation for the silent stalls is a hypothesis. [SRC] `lib/webconn.js` accepts any `res.ok` (every 2xx), never checks for 206 or `Content-Range`, uses `SOCKET_TIMEOUT = 60000` and `RETRY_DELAY = 10000`; on error it sends `lt_donthave` for the piece and re-announces it after 10 s. [FH] Results: host honours Range, finishes in 54 ms with 12 requests. Host ignores Range (200 with the whole 3 MiB): progress 0 after 15 s, one request, 3 MiB served, **no warning or error event**. Host answers 403: progress 0, 24 requests in 15 s (each piece retried about every 10 s), **no warning**. Host returns a 206 with the first byte of each piece flipped: progress 0, **27,474 and 38,057 requests (6,869 and 9,514 MiB) served in 15 s in two runs, with one "Piece N failed verification" warning per request (27,474 and 38,056), and the web seed is never dropped** (loopback speed; on a real link it drains the visitor's bandwidth until the tab closes, which on a metered connection is a cost attack by a compromised or misconfigured host). Host returns a truncated 206 body: progress 0, one request, **no warning**. [SRC] Seams for a fix: `torrent.addWebSeed(urlOrConn)` also accepts a connection object with a string `connId` (so the loader can supply its own hardened web-seed connection) and `torrent.removePeer(id)` can drop a web seed. Sources: `node_modules/webtorrent/lib/webconn.js`, `lib/torrent.js` (lines 1123-1160, 2011); lab `webseed-chaos.mjs`. Date: measured 2026-10-17.

**F-D2. Wire-level hostile input: the length prefix is signed, there is no maximum, and every chunk is re-concatenated.** `DESIGN-CRITICAL` (needs a patch or wrapper before any public deployment; wave-1 review item B4 is real but mis-described). Confidence: high. [SRC] `bittorrent-protocol@5.0.9`: `getUint32` is `(b0 << 24) | (b1 << 16) | (b2 << 8) | b3`, a signed result; `_onMessageLength` treats `length > 0` as a message and everything else as keep-alive. [FH] `0xFFFFFFFF` leaves `_parserSize` at 4 (read as -1, a keep-alive); `0x7FFFFFFF` (2,147,483,647) makes the wire wait for 2 GiB. `_write` appends each chunk and re-concatenates the whole buffer, so cost is quadratic: fed in 16 KiB chunks after the prefix, 4 MiB costs 0.04 s, 16 MiB 0.66 s wall (1.05 s CPU, about +830 MiB RSS churn), 32 MiB 2.9 s (4.3 s CPU, +1.1 GiB), 64 MiB 11.7 s wall (16.3 s CPU, +2.1 GiB); a second run gave 10.9 s wall, 15.2 s CPU, +2.2 GiB; in 64 KiB chunks 64 MiB costs 2.7-2.9 s wall and 3.7-3.9 s CPU. The wire is never destroyed and no error is emitted. The harness is about 20 lines of Node and needs no WebRTC because `Wire` is a Duplex stream. Sources: `node_modules/bittorrent-protocol/index.js` (lines 36-38, 849-860, 945-961); lab `wire-oversize.mjs`, `wire-debug.mjs`. Related [W1]: `docs/review/security.md` B4 proposes a 256 KiB cap by wrapping the wire.

**F-D3. Node synthetic peers are practical for adversarial and load tests.** Confidence: high for local loopback. [FH] `node-datachannel` 0.32.3 (installed; 0.33.4 current, published 2026-09-12): 20 of 20 in-process loopback data-channel pairs (40 PeerConnections) connected in 1,064-1,075 ms with RSS 84-85 MiB (two runs); a Node peer and a Chromium 156 page opened a data channel in 184-186 ms (host/udp pair) and echoed in 1.1-1.2 ms. Sources: lab `ndc-loopback.mjs`, `chromium-node-peer.mjs`; npm registry.

**F-D4. A usable web-seed fault server and tracker fault server are small, and the tools exist.** Confidence: medium. [DOC] Toxiproxy is "A TCP proxy written in Go", HTTP API on port 8474, toxics latency, bandwidth, slow_close, timeout, reset_peer, slicer, limit_data (the README also lists packet_loss), a Node client `toxiproxy-node-client` 4.1.0 (2026-04-26); UDP support is not stated, so it cannot impair data channels. **R-25 (P0, S) Green, hermetic baseline first.** Add the `scripts` block with `"test": "node --test --test-timeout=60000 test/unit/*.test.mjs"` (explicit glob; the directory form fails on Node 24.22), keep browser layers behind explicit scripts (`MW_BROWSER=1` pattern), investigate the `sw-sdk` adopted-port test (it exercises `MessageChannel` ports with `unref()` and a held first `hello`; whether this is a Node 24 behaviour change or a real SDK retry bug is not established) and either fix it or mark it `skip` with a linked issue, make sure no test leaves open handles, and run the same command on Node 22 and 24 in CI as WebTorrent does (F-A4). **R-01 (P0, M) Web-seed hardening and its tests.** What: (1) `probeWebSeed(url)` before use: `fetch(url, {headers:{Range:'bytes=0-0'}})` must return 206 with `Content-Range: bytes 0-0/<n>`, CORS must expose `Content-Range`, `Content-Length`, `Accept-Ranges`; otherwise show a specific message ("host ignores Range", "403", "CORS") and do not add the seed. (2) Supply the seed as a custom connection through `torrent.addWebSeed(connObject)` (subclass of `WebConn`) that rejects non-206 responses, wrong `Content-Range`, wrong length and, after K bad pieces or M wasted MiB, opens a circuit breaker (call `torrent.removePeer(id)` and retry only after a long backoff with jitter); count and surface every failure. (3) Progress watchdog: no byte for 20 s with zero wires shows an error with a next action (webtorrent itself emitted nothing in three of four fault classes). (4) `test/chaos/webseed-server.mjs` with modes honours-range, ignores-range, 403, 404, 5xx-flapping, redirect, wrong-Content-Range, truncated-206, corrupt-bytes, slow-stall, no-CORS; Node tests assert request-rate and bytes-wasted ceilings (for example under 3 requests per piece per minute and under 2x the site size), and Playwright tests assert the visible error text and the time to show it. Why: F-D1 (silent stalls; up to 38,057 requests in 15 s). Acceptance: all fault classes yield a specific visible error within 20 s and bounded traffic.

**R-02 (P0, S for the harness, M for the fix) Hostile-wire harness.** Build pairs of `Wire` objects connected through `PassThrough` streams (no WebRTC), attach the real `wire-ext` adapter to the victim, and drive an adversary that writes raw bytes: length prefix `0x7FFFFFFF` followed by a drip of 16 KiB and 64 KiB chunks; the values `0x80000000` to `0xFFFFFFFF` (currently read as keep-alives, a parser-desync risk worth a decision, not a crash); truncated and duplicated handshakes; zero-length keep-alive floods; `extended` frames larger than 16 KiB for `mw_chain`; invalid bencoded extended handshake; `bitfield` of wrong length; `have`/`request` with out-of-range indices; request floods. Assert the victim destroys or ignores the peer within 1 s, RSS grows less than 20 MiB, CPU time stays under 200 ms, and counters increment. Fix: enforce the 256 KiB cap from `docs/review/security.md` B4 in a wrapper or patched `_write`/`_onMessageLength`, record it in `docs/DEVIATIONS.md`, and open an upstream PR for a `maxMessageLength` option; also fix the quadratic concatenation (do not re-concatenate until the declared length has arrived). ## 5. Gotchas

Test-authoring traps found or confirmed while producing this document:

1. **`0xFFFFFFFF` is not an oversized message to `bittorrent-protocol` 5.0.9.** The prefix is read as a signed integer, so it becomes -1 and is handled as a keep-alive; a test that sends it and expects a destroyed wire fails, and a test that expects "nothing bad happens" passes vacuously. Use `0x7FFFFFFF`. The wave-1 review's "4 GiB" wording should be corrected to "up to 2 GiB - 1" (F-D2).
2. **The obvious JCS oracle is wrong.** `JSON.stringify(Object.fromEntries(sortedKeys))` reorders integer-like keys first (`{"0":null,"":""}` instead of `{"":"","0":null}`). Write the oracle as a manual recursive serialiser (F-E2).
3. **`context.setOffline(true)` and CDP `offline` do not cut an established data channel.** Fetches fail, peers keep talking (F-B9, F-C2).
4. **CDP impairment only attaches to peer connections created while a rule is armed.** Arm a neutral rule before `goto`; flip it later. Pages, popups and iframes need their own session. The deprecated `Network.emulateNetworkConditions` ignored `packetLoss`. WebSockets are not shaped at all (F-C2).
5. **A vanished peer does not announce itself quickly or cleanly.** In Chromium: `disconnected` after about 5 s, `connectionState: failed` after about 15 s, ICE state may stay `disconnected` and never reach `failed`, the data channel stays `open`, no `close` event (F-C3). Watchdogs must be the loader's own.
6. **`page.clock` and `routeWebSocket` stop at the main thread.** Workers and the Service Worker keep real time and real sockets (F-B6, F-B7).
7. **Playwright's service-worker API is Chromium-only.** Test SW behaviour in other engines through page behaviour (F-B2).
8. **Playwright's browsers are separate binaries to a per-process firewall.** LuLu has rules for `chrome-headless-shell` in `chromium_headless_shell-1248` but none for the WebKit build, and the path changes with every Playwright upgrade, so each upgrade brings new unanswerable prompts in headless runs; Chromium's loopback HTTP keeps working, so runs look "half working" while UDP silently fails (F-B4; inference, not proven for WebKit).
9. **Firefox 157.0 (Playwright 1.64.1) does not start on this macOS 27.0** ("Could not find profile folder"); cross-engine runs belong on Linux (F-B5).
10. **Docker's default NAT is not a chosen NAT type**; classify what you built before trusting a matrix cell (F-A7).
11. **mDNS candidates need a resolvable `.local`.** Headless Chromium and containers need `--disable-features=WebRtcHideLocalIpsWithMdns` (already in ARCH section 12) and WebKit offers no candidates at all without an active capture; keep one realistic mDNS-on run on a real LAN. [W1]
12. **Read the selected ICE pair through `RTCTransportStats.selectedCandidatePairId`**; the `selected` property on pair stats is Firefox-only (F-C4).
13. **`measureUserAgentSpecificMemory` needs COOP+COEP, exists only in full Chromium (not `chrome-headless-shell`), waits for a GC (14-15 s measured, 20 s documented) and is incomparable across browsers.** `performance.memory` is quantised unless `--enable-precise-memory-info`; `gc()` needs `--js-flags=--expose-gc` (F-H1).
14. **`Memory.prepareForLeakDetection` terminates workers**, including the PoW worker and any synthetic-peer helper workers; call it last (F-B8).
15. **Lighthouse CI is a major version behind Lighthouse**, and Lighthouse user flows are Puppeteer-based and keep Service Worker and Cache Storage state across callback navigations; cold-start numbers need explicit clearing (F-G1, F-G2).
16. **Screenshot baselines are per OS and per engine**; never generate them on macOS for a Linux job. The Docker image tag must equal the Playwright package version (F-G4).
17. **Scheduled GitHub workflows can be delayed and stop after 60 days of repository inactivity**; Checkly's free plan is capped at 1,000 browser runs per month (F-J2, F-A3).
18. **A datacenter probe proves availability, not NAT traversal.** Runners have public or datacenter addresses; the NAT matrix (R-08) is the only traversal evidence.
19. **A seed alone may not pin a generated dataset** (ssb-fixtures bumps its version when the dataset changes). Store generator version and file sha256 with each fixture (F-I2).
20. **`fc.scheduler().waitAll` is deprecated since fast-check 4.2.0 and `waitIdle` cannot await uncontrolled sources such as `fetch`**; model time and network inside the simulator (F-E1).
21. **BrowserStack's Playwright table lags** (1.63, WebKit 26.6 versus 1.64.1, WebKit 27.2) and WebKit on macOS Ventura and Sonoma was removed (F-A2).
22. **iOS suspends WebRTC when the screen locks or the app backgrounds**; real-device P2P tests must keep the page foregrounded and the screen on [W1].
23. **Web-seed bad-bytes loop speed in F-D1 is a loopback figure.** On a real link the request count per second drops but the unbounded retry behaviour is the defect.
24. **Do not put E2E in `npm test`.** The existing opt-in `MW_BROWSER=1` pattern is right; keep browser layers behind explicit scripts so a clean clone still runs `npm test` with no downloads.
25. **Use a dedicated test device for USB-debugging experiments**, not a daily-driver phone.
